## 决策树关键分支详解

### 分支 1: 多个候选同时高分（E007 vs E064 同时命中）

```
日志特征:
  "cannot guess build type"          → E007 评分高
  "conftest: inaccessible or not found" → E064 评分也高

                    ┌─── E007 (14分) ──┐
                    │                   │
                    │  caused_by: [E064]│ ◄── 关系图!
                    │                   │
                    └─── E064 (11分) ──┘

引擎行为:
  1. 取最高分 E007 作为主诊断
  2. 发现 E007.caused_by = [E064]
  3. 检查 E064 是否也在候选列表中
  4. 如果是 → 输出提示:
     "⚠️ E007 可能由 E064(conftest失败)导致,
      建议: 先确认安全弹窗已触发, 再重试"
```

### 分支 2: 推荐方案被原则拒绝（降级到 fallback）

```
假设某条目的推荐方案不幸包含了禁止模式:

  rec_approach: set-env-var
  rec_command:  CC=clang --build=aarch64-linux-gnu   ← 错误!

Phase D 检测:
  P-AUTOTOOLS-001 forbid: "--build=.*linux-"
  → 命中! auto_reject=true
  → ❌ 推荐方案被拒绝

  降级尝试 fallback:
  fallback_approach: add-cflags
  fallback_command: CFLAGS="-D__OHOS__ $CFLAGS"
  → 不含 --build= ✓ 通过
  → 输出 fallback 方案
```

### 分支 3: 无任何候选通过（纯手动模式）

```
所有候选要么评分太低, 要么方案被原则拒绝:

  → 输出 Top-3 的诊断信息供参考
  → log_warn "未找到安全的自动修复方案"
  → 显示最佳匹配的 doc/*.md 内容
  → _EP_AUTO_RETRY=false
  → 返回后调用方 exit 1 (需人工介入)
```

### 分支 4: graph/ 不存在时的降级（向后兼容）

```
  if [ ! -d "${_EP_DIR}/graph" ]; then
      # 降级到 v2 逻辑: 扫描旧 error-patterns*.md
      _match_error_pattern_v2 "$@"   # 旧引擎
      return $?
  fi
```

### ohc-run.py build 集成

`match_error_pattern()` 函数已升级为双路径架构：

```
match_error_pattern() 调用流程:
  │
  ├─ v3 路径（优先）:
  │   graph/index.tsv 存在? → Phase A(粗筛) → Phase B(.kv精排) → Phase C(方案生成+输出)
  │   → 命中 → return 0
  │   → 未命中 → 降级到 v2
  │
  └─ v2 路径（fallback）:
      扫描 error-patterns.md（原有逻辑不变）
```

### update-entry.sh 功能矩阵

| 操作 | 选项 | 效果 |
|------|------|------|
| 修改字段 | `--field K=V` | 直接替换 .kv 字段值 |
| 追加关系 | `--add-relation TYPE=IDS` | 去重追加到关系字段 |
| 追加原则 | `--add-principle P-XXX` | 验证存在性后追加 |
| 添加禁止 | `--add-forbid PAT REASON CONSEQ` | 自动编号 forbid_N |
| 重建索引 | `--regenerate-index` | 从 .kv 重新生成 index.tsv 行 |

所有修改操作完成后自动：同步 index.tsv、更新 last_updated、运行 graph validate。
