# E543: OHOS ELF signing requires a verified signer closure and owner-execute proof

## Symptom

An OpenHarmony PC package can compile and transfer as an AArch64 ELF, yet its
first target consumer exits with `Permission denied` / RC126. A superficial
section or mode check can also pass when the target signer is unavailable or
the owner execute bit is missing.

## Root cause

Target execution depends on two independent properties: the ELF must carry a
signature accepted by the target, and the installed file must be executable by
the owner running the consumer. The signer is therefore part of the frozen
input closure. A host JAR can produce a locally verifiable `.codesign` block,
but that does not prove the target accepts the certificate. The official
OpenHarmony native signer must run on the target with `-selfSign 1`; a
successful local build does not exercise either target property.

## Fix

1. Freeze the official native `ohossigntool` archive and extracted
   `binary-sign-tool` by source URL, byte count, and SHA-256 in the task-owned
   evidence directory. Host JAR/certificate material may be retained only as
   structural diagnostics.
2. Transfer the native signer and unsigned task-private ELF copies to the
   target, then sign with `binary-sign-tool sign -selfSign 1`. Leave the Conan
   cache and failed-run payloads unchanged.
3. Run the signer display/section check on every output and require an
   AArch64 ELF identity and changed output bytes before execution.
4. In the target prepare phase, set owner/group/other execute bits and record
   the resulting mode. Prove the installed consumer executes as the same
   owner; a local mock or upstream-only test is insufficient.
5. If a consumed launch fails, clean only its task-owned remote root and create
   a new run with a new payload and runner identity. Never launch the same run
   a second time.

## Evidence and validation

For pkgconf 3.0.6, run-002 transferred seven files exactly but the unsigned
`test_pkgconf` launch returned RC126 while the device signer was unavailable.
The official host and native signer closures were then downloaded into
`F:\\HarmonyPC\\contrib-claim-af-20260903-pkgconf-3.0.6\\signer-closure` and
verified. Five host-signed task-private copies were structurally verified, but
the target run-003 returned EPERM, so that result is not target PASS. The
The native-signed successor `run-004` completed the installed consumer and
CLI checks on `10.62.195.15:8022` with `W3_RESULT=PASS`; its task-owned root
was released and independently returned `POSTRELEASE_PASS`. The full host
upstream suite then ran as `33/33` (`32 OK + 1 EXPECTEDFAIL`, `Fail=0`).

## Applicability and safety boundaries

Apply this to any OHOS task that executes transferred ELF files, including
command-line tools and private shared-library copies. A `.codesign` section
count is structural evidence only; it does not replace target verification.
Do not modify shared package caches, reuse stale signer material, or combine
results across run IDs, payload hashes, boot IDs, or launches. If the signer
closure or target owner-execute proof cannot be established, fail closed.
