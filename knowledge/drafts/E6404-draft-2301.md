# E6404 - Header-layout fallback must preserve upstream include contracts

## Symptom

Meson reports a required dependency as found and links its library metadata,
yet a production translation unit fails with `fatal error: 'SDL_net.h' file not
found`. The generated compiler command contains the dependency's package
`include` root but not the nested directory in which the published package
installed the header. The same basename was present in four production
include sites, so fixing only the first failing translation unit was
insufficient.

## Root Cause

Dependency discovery and header reachability are separate contracts. A valid
pkg-config record can identify the library and version while its `Cflags` expose
only the package root. Some SDL2-family packages install public headers below
`include/SDL2`, whereas upstream consumers historically include them by the
basename `<SDL_net.h>`. The mismatch is therefore a package-layout boundary,
not evidence that the dependency is unavailable or that the feature should be
disabled.

## Fix

1. Keep the dependency enabled and bind the exact published package revision
   and generated include roots.
2. At every production include site, try the canonical basename first, then
   the known API-family subdirectory with `__has_include`.
3. Emit a hard compile error when neither location exists; do not copy headers
   into the consumer or silently disable the feature.
4. If metadata itself is proven incorrect, use a task-local normalizer with
   exact package/header readback instead of modifying the dependency artifact.

## Validation

Buildbot `49497` completed checkout, quality checks, dependency resolution, and
Meson configuration; `sdl2_net/2.2.0.1` was found, but `program_serial.cpp`
failed on `<SDL_net.h>`. A follow-up compile reached three additional
production include sites with the same error, confirming that the package
include root was insufficient globally. The successor patch adds the ordered
fallback to all four sites and the complete patch chain applies with
`patch_ng` against the frozen source.

## Applicability and Safety Boundary

This pattern applies when a dependency is demonstrably present but its public
headers are nested under a stable API-family directory. It does not authorize
arbitrary include guesses, copying dependency files, changing versions, or
turning off a production backend. Every accepted path must be tied to the
published package layout and still be compiled and tested through the normal
dependency closure.
