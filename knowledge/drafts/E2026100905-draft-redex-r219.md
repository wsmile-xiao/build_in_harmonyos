# E2026100905 — 预生成二进制测试输入的内部完整性与构建消费者绑定

## 错误特征

目标机或目标架构执行 APK 转换时，Python zipfile 报
BadZipFile: Bad CRC-32 for file 'classes.dex'，但传输阶段的字节数和
SHA-256 均一致。对输入 APK 调用 ZipFile.testzip() 返回 classes.dex，说明
损坏已经存在于源包内，而不是传输链路丢字节。

## 触发条件

- 构建系统：任意构建系统，只要测试输入包含官方预置 ZIP/APK/DEX
- 阶段：目标测试或运行时解包、APK 转换
- 典型场景：发布包携带预生成的二进制 fixture，ZIP 中央目录 CRC 与实际
  member bytes 不一致，或 DEX 的 SHA-1/Adler-32 字段与 payload 不一致

## 根因分析

精确传输只验证了“本机发送的文件”和“设备收到的文件”相同，不能证明
文件内部的完整性元数据正确。Redex r218 使用官方
v2026.04.30 源包中的 test/instr/redex-test.apk；源文件 SHA-256 为
62de75fd32b94dd80553337a19bc6b0af195edea98b111bce279b29fc3ce9941，
testzip() 唯一返回 classes.dex。该成员的 ZIP CRC、DEX SHA-1 与
Adler-32 均失配，r218 在 apk-flow 真实失败；r218 的设备传输和清理证据
保持不变。

## 解决方案

### 推荐方案

1. 在 runner 中固定并校验官方源 APK 的 SHA-256。
2. 只在当前事务的私有工作目录读取成员字节；对已知损坏 CRC 的读取可在
   诊断代码中关闭 _expected_crc，但必须要求损坏集合精确、可解释。
3. 对每个 DEX 重算 SHA-1(data[32:]) 写入 [12:32]，再重算
   Adler-32(data[12:]) 写入 [8:12]；按原 ZIP 成员元数据重建到
   create-new 副本。
4. 重新打开副本，要求 testzip() is None，并绑定源/副本字节数与
   SHA-256。目标转换只接受副本，官方源仍保持只读。
5. 把修复输出纳入当前事务日志或既有 APK-flow 日志，保留 RC、源哈希、
   副本哈希和唯一修复成员，便于后续验证。

本次 r219 修复副本为 230,973 bytes，SHA-256
078af83d6aac79b85cfb3d39230c72f90112e653c80f8a4fb547f39ef062783e，
testzip() 通过；该逻辑已绑定到新的 runner 输入归档。

### 禁止做法

- 只看到 transfer SHA-256 PASS 就宣称 APK 可用，跳过成员级 CRC/DEX 校验。
- 覆盖官方源包、修改已消费 r218 结果，或为同一 launch 重试。
- 使用不受哈希约束的外部 APK 替换，导致目标测试输入不可复现。
- 在损坏成员无法唯一定位或修复后仍有 CRC 错误时强行继续；此时应保留
  真实终态并创建新的 successor。

## 验证

~~~bash
python3 -c "import zipfile; print(zipfile.ZipFile('redex-test.apk').testzip())"
python3 repair-apk-fixture.py SOURCE_APK TASK_LOCAL_APK
python3 -c "import zipfile; assert zipfile.ZipFile('TASK_LOCAL_APK').testzip() is None"
~~~

必须同时记录源/副本 bytes、SHA-256、损坏成员集合、修复成员集合和命令
RC。该过程只能证明 fixture 完整性；仍需在目标机执行真实 APK 转换，不能
用本地 testzip() 替代 W3。

## 适用范围与安全边界

此模式适用于预置 ZIP/APK/DEX fixture 的完整性修复，尤其是目标架构无法
运行生成 fixture 的宿主工具时。不适用于未知损坏、签名校验或生产用户
APK；后者必须使用其正式签名/发布流程。任何已消费 W3 的失败结果都保持
不可变，修复只进入 create-new successor。

## 新增验证：内部完整性不等于构建系统实际使用

目标架构不能执行宿主生成器时，即使补丁已经提供 prebuilt 模式、源目录也
存在有效 fixture，默认关闭的 configure 选项仍可能运行原生成器。out-of-tree
构建还可能在 build 目录用相对路径读取输入，源目录副本不能满足该消费者。
通用决策必须同时绑定三个条件：

1. **模式**：显式启用已有 prebuilt 模式，不能把补丁存在视为已经启用。
2. **身份**：将冻结 SHA-256 传入预期哈希变量，在消费前核验每项输入；不能
   只对未经约束的新文件现场计算哈希再自我认定可信。
3. **位置**：按实际 Make/测试进程工作目录部署；源和 build 目录有不同消费者
   时保留独立精确副本，并校验两者。不能用成功 stub 替代宿主生成器。

有效输入与损坏输入拒绝的定向检查后，还必须在目标构建日志确认规则真的执行。
保留原测试清单和断言；成功不证明目标系统支持原宿主生成器。
