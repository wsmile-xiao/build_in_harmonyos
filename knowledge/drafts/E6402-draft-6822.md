# E6402 — OHOS musl：program_invocation_* 头文件无声明、libc.so 不导出、libc.a 有弱别名（静态验证假阳性）

> Contributor: 6822 / Status: **DRAFT** / Updated: 2026-09-23 / Severity: 2 (medium)
> Source: sleepenh 1.8 适配（HarmonyOS PC aarch64）

## 错误特征

编译期（直接引用）：

```console
sleepenh.c:97:3: error: use of undeclared identifier 'program_invocation_short_name'
```

只补 `extern char *program_invocation_short_name;` 之后，默认（动态）链接：

```console
ld.lld: error: undefined symbol: program_invocation_short_name
>>> referenced by sleepenh.c
```

同一份源码加 `-static` 则链接成功、运行正常——这正是 x86 runner 上"同源 .o 静态重链 + qemu-aarch64"验证走的路径。

## 触发条件

- 源码引用 glibc 扩展变量 `program_invocation_short_name` / `program_invocation_name`（常见于 usage 文本、报错前缀）
- 构建系统不限（本例为裸 Makefile）；阶段：编译（未声明）→ 链接（只补声明时）
- 本地用静态重链副本做功能验证，或配方本身以 `-static` 构建时，问题被掩盖

## 根因分析

musl 在 libc 内部把 `program_invocation_short_name`、`program_invocation_name` 定义为 `__progname`、`__progname_full` 的弱别名。OHOS SDK 三处不一致（sleepenh 适配时用 SDK 自带 llvm-nm 实测）：

| 位置 | 实测 |
|---|---|
| sysroot 头文件 | 无任何 `program_invocation_*` / `__progname` 声明（grep usr/include 为空）→ 编译期未声明 |
| `libc.so` 动态符号表 | 只有 `B __progname` → 动态链接找不到 `program_invocation_short_name` |
| `libc.a` | `B __progname`、`B __progname_full`、`V program_invocation_name`、`V program_invocation_short_name` → 静态链接能解析 |

因此"补声明"只解决了编译期的一半：静态链接从 libc.a 取到弱别名，动态链接失败。x86 runner 跑不了动态 OHOS 产物（缺 `/lib/ld-musl-aarch64.so.1`），惯例用静态重链副本经 qemu 验证——恰好落在能工作的那一半，验证给出假阳性。

## 解决方案

### 推荐方案 — 从 argv[0] 取程序名（progname-from-argv0）

glibc 的 `program_invocation_short_name` 就是 `argv[0]` 的 basename。补丁里用程序自己的变量替代，无平台宏：

```c
static const char *progname = "sleepenh";          /* argv[0] 为空时的默认名 */
...
int main(int argc, char *argv[]) {
  if (argc > 0 && argv[0] && *argv[0]) {
    const char *slash = strrchr(argv[0], '/');
    progname = slash ? slash + 1 : argv[0];
  }
  ...
}
/* 原 program_invocation_short_name 引用处改为 progname */
```

sleepenh 1.8 的补丁即此形态（+7/-1，`refresh-patch --auto` 生成）。

### 回退方案 — compat 定义单元

引用点分散在大量文件时，按 `DRAFT-ohos-musl-glibc-specific-symbols` 由配方编译一个 compat 翻译单元**定义**（不只是声明）这两个变量：强定义在静态链接时覆盖 libc.a 的弱别名，动态链接时补上 libc.so 缺的符号，两种链接方式都成立。

### 禁止做法

- ❌ 只加 `extern char *program_invocation_short_name;`：静态验证通过、交付的动态链接失败。
- ❌ `#ifdef __OHOS__` 改用 `__progname`（E493 旧方案）：违反 R8（PF5 拦截），且 `__progname` 同样需要自补声明、依赖 libc 内部符号。

## 验证

```bash
NDK=/opt/command-line-tools/sdk/default/openharmony/native
L=$NDK/sysroot/usr/lib/aarch64-linux-ohos
$NDK/llvm/bin/llvm-nm -D $L/libc.so | grep -E 'progname|program_invocation'          # 只有 __progname
$NDK/llvm/bin/llvm-nm $L/libc.a | grep -E ' [BV] (__progname|program_invocation)'   # 含两个 V 弱别名
printf '#include <stdio.h>\nextern char *program_invocation_short_name;\nint main(void){puts(program_invocation_short_name);return 0;}\n' > p.c
CC=$NDK/llvm/bin/aarch64-unknown-linux-ohos-clang
$CC p.c -o p_dyn                          # ld.lld: error: undefined symbol: program_invocation_short_name
$CC -static p.c -o p_sta && qemu-aarch64 ./p_sta   # 链接成功，打印 p_sta
```

sleepenh 1.8 实测：只加 extern 的未打补丁源码，动态链接失败；`-static` 副本经 qemu 跑 test_package 的 F2（usage 程序名）通过。采用推荐方案后，conan create 动态产物链接通过，静态重链副本 F1-F8 全部通过。
