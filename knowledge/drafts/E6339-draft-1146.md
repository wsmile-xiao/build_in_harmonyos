# E6339 - Conan override requirement 不会成为 PkgConfigDeps 的直接生成器依赖

## 问题现象

一个 Conan 2 recipe 的依赖图里已经能看到目标版本，例如 `zlib/1.3.1.1`，
但 Meson 配置仍报：

```text
Dependency "zlib" not found, tried pkgconfig
```

对应 generators 目录中没有 `zlib.pc`。只看 `conan graph info` 容易把“版本已经
被覆盖”误判为“当前 recipe 已经声明并获得直接依赖元数据”。

## 根因

`self.requires("name/version", override=True)` 的职责是改写图中已有的同名传递
requirement；它不表示当前 recipe 自身直接消费该包。`PkgConfigDeps` 根据生成器
可见的依赖关系产生元数据，因此 override-only 节点可以出现在最终图中，却没有
为当前构建生成对应 `.pc`。

当 recipe 本身确实通过 pkg-config、头文件或链接使用该包，并且还需要统一传递
版本时，应使用 `force=True`。它同时承担直接 requirement 和版本强制统一的语义。
若多个提供者精确要求同名包的不同 recipe 版本，根 recipe 还必须选择一个 ABI
兼容版本；Windows 路径不能直接作为 `re.sub` replacement，否则反斜杠会被解释为
正则转义并触发 `PatternError: bad escape`。

## 修复步骤

1. 先确认报错包确实被当前 recipe 直接探测或链接，而不是只由下游传递使用。
2. 将该包声明为直接 requirement，优先使用 `force=True`；只有平台图必须改写
   同名传递版本时才同时使用 `override=True`，并显式保留 `headers=True`、
   `libs=True`、`run=True` 及 transitive traits，避免在 component requires 中直接
   引用该 override 节点。若其 `.pc` 还引用了未生成的传递 `.pc`，将真实且已发布
   的包（本次为 `pcre2/10.45`）声明为直接生成器依赖；同时按 resolved recipe
   name 选择生成器来源，避免 `dependencies["glib"]` 被 override 别名劫持。不要在
   消费方手写伪 `.pc`。
3. 使用 fresh Conan home 重跑完整 graph，并确认同名包只剩一个 ABI 兼容版本。
4. 执行 `conan install --build=never`，证明新的 package ID/PREV 二进制闭包已发布。
5. 重跑 `conan create`，检查 generators 中出现所需 `.pc`，且主包与 test_package
   都成功。
6. 依赖 recipe identity/PREV 改变后创建新的目标 W3 successor；旧 run 不可拼接。
7. 在 Windows 主机上对 `.pc` 等文本做路径替换时使用 callable replacement，避免
   `C:\\...` 中的反斜杠被正则 replacement 语义消费。

## 验证

本次平台 CI 的依赖构建使用 `libsoup3/3.6.5-r2` 时缺少 `zlib.pc`。已发布的
`libsoup3/3.6.5-r3` 把 `zlib/1.3.1.1` 改为 `force=True`。下游精确引用 r3 后：

- `conan install --build=never` 成功解析并取得完整二进制闭包；
- `librest/0.10.2` r037 完成 80/80 编译、打包和 test_package 交叉编译；
- HarmonyOS PC W3 `run-021` 在新冻结闭包上 consumer `1/1 PASS`；
- transfer、prepare、唯一 launch、release/postrelease 和冻结 validator 全链 PASS。

随后平台 CI `#50040` 的建图日志显示 `libsoup3/3.6.5-r3` 要求
`glib/2.84.0.1.1`，而 `json-glib/1.10.6` 要求 `glib/2.84.0.1`。根 recipe 增加
`self.requires("glib/2.84.0.1.1", options={"shared": True}, headers=True, libs=True,
run=True, transitive_headers=True, transitive_libs=True, override=True, force=True)`
后，旧 r049 在 `package_info()` 的 direct 校验处暴露了 `glib::` component require
非法；r051 又显示默认 traits 会让 `libpcre2-8.pc` 不进入闭包。移除该 component
require 并显式恢复 traits 后仍缺少 `pcre2.pc`，因此再声明已发布的 `pcre2/10.45`
direct requirement；r053 又证明按键名读取 `dependencies["glib"]` 会选中 glib override，
因此必须按 resolved recipe name 选择真正的 glib2/2.88.0 来源；还需重新证明本地 graph、package_info、`conan install
--build=never` 和 `conan create` 均 RC0，最终只保留 `glib/2.84.0.1.1`，并生成
glib/json-glib/pcre2/libsoup3 的 `.pc` 文件。

本轮补充的 direct/component 边界：`glib/2.84.0.1.1` 是用于统一传递版本的
override 节点，不能直接出现在 `cpp_info.components[*].requires` 中；但 librest
仍然实际消费 GLib/GObject 符号，因此不能把合法的 `glib2::glib2` 传递闭包一并删掉。
r055 在 package_info 通过前的修复中移除该 component 后，r056 的 test_package
最终链接缺少 `g_type_check_instance_is_a` 与 `g_object_unref`。最终做法是声明
已发布的 `glib2/2.88.0` 为独立 direct requirement（保留 headers/libs/run 与
transitive traits），同时保留 `glib2::glib2` component；r060 证明 package_info、
OHOS 交叉编译、打包、CMake consumer 和 test_package 均 RC0。该 direct requirement
不替代 glib override 的版本统一职责，且 W0 仍必须证明该 glib2 二进制闭包可用。

## 适用与安全边界

- 仅当当前 recipe 确实直接消费该包时使用 `force=True`；纯顶层版本覆盖仍可保留
  `override=True`。
- `force=True, override=True` 不能证明 ABI 兼容，也不能替代 W0、`--build=never` 和消费者测试；
  `override=True` 节点在 Conan 2.29.1 中不应被 component requires 当作 direct requirement。
- graph 可解析不等于 `.pc` 已生成，更不等于目标二进制闭包可用。
- 组件链接符号缺失时，不能通过引用 override 节点绕过 Conan direct 校验；必须补齐
  实际消费的合法 direct provider，并重建 package revision 与目标验证 successor。
- 不得通过手写 `zlib.pc`、复用旧 package revision 或复用旧 W3 证据绕过修复。
- Windows 路径替换必须避免把反斜杠直接放入正则 replacement；callable replacement
  只解决转义边界，仍需保留路径来源和生成器内容的哈希验证。

## 查重增量

- E468 处理 generators 路径没有进入 `PKG_CONFIG_PATH`，本条处理 requirement 身份
  导致 `.pc` 根本不生成。
- `DRAFT-pc-chain-invisible-transitive-deps` 和
  `DRAFT-conan-shared-pkgconfig-requires-drop` 处理传递/Skipped 节点，本条处理
  override-only 与 direct/force requirement 的差异。

## 当前候选修正与目标验证

本轮当前候选已移除 `glib2/2.88.0` direct requirement 和 `glib2::glib2`
component 引用，保留 `glib/2.84.0.1.1` 的 `force=True` 版本统一，并显式声明
已发布的 `libffi/3.4.4` 与 `pcre2/10.45`。Windows OHOS 交叉构建只把真实包内的
`libpcre2-8.pc`、`libpcre2-posix.pc` 和 `libffi.pc` 复制到任务私有生成器目录，
用绝对 `prefix` 解析原包元数据；这不是伪造 `.pc` 或替换依赖身份。

本轮针对平台 CI `#50135` 的根因又补齐了 zlib 的直接 requirement。旧候选虽然
能解析 `zlib/1.3.1.1`，但 worker 的 `PKG_CONFIG_PATH` 没有 `zlib.pc`；当前
`conan-create-r083-zlib-pc-fix.log`/`.rc` 证明精确图、任务私有 zlib 元数据、
Meson 配置、84/84 编译、打包和 test_package 配置/编译均 RC0，并生成
`ZLIB::ZLIB`。该证据只覆盖主机交叉构建和消费者编译；`can_run=False` 的目标 ELF
仍必须由新 successor W3 独立验证，不能复用 run-029。

### Worker 子进程环境边界

CI #50135 的后续复现表明，只有 `MesonToolchain.pkg_config_path` 仍不足以覆盖
平台 worker：Meson 之外启动的 `pkg-config` 子进程不会读取该 native-file 字段，
因此 `gio-2.0.pc` 解析仍可能报 `Dependency "zlib" not found`。修复必须把同一
任务私有 `.pc` 目录同时通过 `buildenv_info.prepend_path("PKG_CONFIG_PATH", ...)`
注入 Conan build environment，并在日志中打印目录闭包。r084 的
`conan-create-r084-pkgconfig-env.rc=0`、`Task-local pkg-config dirs` 输出、真实
`zlib.pc` 路径以及 package/consumer/test_package 阶段证明该双绑定生效；这只是
worker/交叉构建证据，不能替代新 W3 successor 的目标运行验证。

旧候选平台 CI `#50072` 的真实失败是 `glib2/2.88.0` 的 312 项依赖测试中
2 个 timeout、1 个 abort，而不是 librest 上游测试失败。该结果是移除 direct
`glib2` 的回归依据。当前 r074 本地包由
`F:\\HarmonyPC\\librest-0.10.2-20260913\\conan-create-r074-cross.log`
生成；该日志单独的 `test_package` 终态由同目录 `evidence/conan-create-ohos-r060.rc`
记录为 `conan_create_rc=0`，不得把日志末尾的 `Running test()` 单独解释为 PASS。
当前 W3 `run-028` 绑定 HEAD
`6329953d5c8f6b3d5a040bd5526e7ddeee1f0a23`、tree
`c2d5ccff1577567cee90474df3225874aaa0c986`，唯一 launch 后 target consumer
`1/1 PASS`，并完成 `RESULT_FROZEN=PASS`、`RELEASED=PASS`、
`POSTRELEASE_PASS` 和 `FULL_CHAIN_VALIDATION=PASS`。这使本知识结论同时覆盖
依赖图身份、真实 pkg-config 元数据、平台 timeout 回归和单次 W3 事务边界。
