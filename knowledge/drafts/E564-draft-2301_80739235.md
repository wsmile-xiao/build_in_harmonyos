# HMDFS 模式归一化后必须用运行用户有效访问检查

## 问题现象

OHOS/arm64 ELF 在 Windows 主机上构建后，首轮通过 `scp` 看似传输成功，
但目标消费者返回 `Permission denied`/RC126。目标 `stat` 显示 owner 为
服务账号，`chmod 755` 后数值 mode 又被 HMDFS 归一化为 `710`；单看数字
mode 无法解释当前 SSH 用户能否加载文件。另一次首轮传输日志出现
`scp: stat local "2222"`，说明参数错位时不能把日志当成远端状态。

## 根因

HMDFS 共享目录的 owner、group 和 ACL 由文件服务层管理，chmod 请求可能被
归一化。`stat` 的数字字段是诊断信息，不是运行用户的有效访问证明；必须在
同一个 SSH 身份下直接执行 `test -r` 和 `test -x`。此外，Windows PowerShell
将复杂 scp 参数组合成字符串时，端口或路径可能落入本地参数位置，导致
“传输命令已执行”但目标文件根本不存在。

## 修复步骤

1. 在首个远端副作用前冻结 run、endpoint、运行 UID、远端根和每个本地
   payload 的 bytes/SHA-256。
2. 通过 `ProcessStartInfo` 的 `StandardInput.BaseStream` 将原始字节流送给
   目标 `cat`，为每个文件保存 SSH RC；不要用可能产生参数歧义的字符串化
   scp 作为唯一证据。
3. 独立回读 `wc -c`/`sha256sum`，再记录 `stat`、`file`、`test -r`、
   `test -x`。chmod 后数值 mode 改变只作诊断，不得替代有效检查。
4. 将未签名 ELF 交给任务自有目标 `binary-sign-tool sign -selfSign 1`，
   回读 `display-sign`、字节哈希和有效访问结果后才允许唯一 launch。
5. 已消费的失败 run 不重传、不重签、不二次启动；修复必须创建新 successor。

## 本次验证

`libxml2-utils/2.15.3` 的 `run-001` 在同一设备上因 HMDFS 文件服务账号
owner 和 RC126 终止；其 `scp` 首次日志还暴露了端口参数错位。新建
`run-002` 后，四个文件用字节流传输并独立回读精确哈希；官方
`ohossigntool-1.0.0-ohos-aarch64.tar.gz`（2,076,594 bytes，SHA-256
`efb7d04e8dd326aef40d8c3788e5932a1f5b9ef4b4c1405ec049d872414306ce`）在目标
执行 self-sign。HMDFS 将签名 ELF 的 `chmod 755` 回读为 `710`，但当前
运行用户的 `test -r`/`test -x` 均 PASS，`display-sign` 返回 `self-sign`，
唯一消费者运行得到 `W3_RESULT=PASS`、RC=0；清理和 postrelease 也 PASS。

## 适用范围与安全边界

该模式适用于 OHOS HMDFS/共享用户目录中的 ELF、插件和命令行工具闭包，
不适用于 owner 与运行用户一致且没有服务账号访问层的普通 Linux 目录。
传输 RC、marker、数字 mode 或 host signer 结果都不能单独升级为目标 PASS；
必须保留同一 run 的 exact-byte、native signer、有效访问、唯一 launch 和
release 证据。任何 run 身份、payload、signer、endpoint 或分母漂移都要求
重新冻结 successor，禁止跨 run 拼接结果。
