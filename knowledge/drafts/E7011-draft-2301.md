# E7011 — OHOS 静态归档器的 llvm-ar 回退

## 问题现象

平台 CI #37603 已通过 L0 门禁并成功下载源码，但 `conan create` 在生产
recipe 的静态库分支失败：

```text
FileNotFoundError: [Errno 2] No such file or directory: 'ar'
```

目标 Worker 的 PATH 既没有名为 `ar` 的 GNU 命令，也没有裸 `llvm-ar`。

## 根因

OHOS Worker 可能只暴露 LLVM 工具链，归档器不在 PATH。custom/Makefile recipe
从 `tools.build:compiler_executables` 读取编译器，但在未配置 `ar` 时只调用裸
`ar` 或裸 `llvm-ar`，因此静态归档阶段失败。该错误是工具命名/环境差异，不
是源代码或链接逻辑问题。

## 修复步骤

优先使用 Conan conf 显式配置的归档器；缺省让配置的 clang 报告其内部
`llvm-ar` 路径，再检查编译器同目录和 HNP 工具目录，最后才保留裸命令回退：

```python
executables = self.conf.get("tools.build:compiler_executables", default={}) or {}
ar = executables.get("ar")
if not ar:
    probe = subprocess.run(
        [str(cxx), "-print-prog-name=llvm-ar"],
        capture_output=True, text=True, check=True,
    )
    ar = probe.stdout.strip()
```

已配置的绝对路径保持原样；如果 clang 探测、同目录和 HNP 路径都没有工具，
应在任务自有的环境补齐阶段提供并验证该工具，不能静默把静态库改成可重定位
对象。

## 验证方式

先执行 recipe 与 test-package 的 `python -m py_compile`，再以绑定当前 HEAD 的
平台 CI 验证静态归档、消费者链接和测试。CI #37603 的 `ar` 缺失日志是本条
经验的失败证据，替换构建必须产生新的、绑定新 HEAD 的 CI 终态。

## 适用范围与边界

适用于 OHOS/aarch64 Conan 配方通过 custom/Makefile 生成静态库的场景。不要用
主机 GNU `ar` 处理目标归档，也不要覆盖工具链显式配置；动态库构建和目标运行
验证仍需各自的真实证据。
