# A fuzzy patch dry-run is weaker than Conan's exact patch application

In the libdvbcsa target run, the first fix added the missing `linux-ohos` branch to an old `config.sub`. Local `patch --dry-run -p1` returned success, but explicitly reported `fuzz 2`. The next frozen target `conan create` failed in `apply_conandata_patches`: patch-ng expected a context line beginning with one space while the real file had two. The two whitespace bytes were not part of the semantic change; they were still decisive to the delivery engine.

The repair was to copy the upstream context indentation exactly and test the same unified diff with `patch_ng.fromfile(...).apply(strip=1, root=<fresh copy>, fuzz=False)`. Then `sh config.sub aarch64-unknown-linux-ohos` returned the exact tuple, and a new target transaction completed all four upstream `make check` tests plus one installed-library consumer. The successful Conan log SHA-256 is `2eb4f950681296c6106d91d8082893e8fa8df1a817ba4d503856dbdb5d8eee36`.

The reusable boundary: use GNU patch's dry-run only as a supplemental check when Conan will apply the patch with patch-ng. Any reported fuzz means it is not evidence of exact acceptance. Verify on a fresh source copy with the delivery engine and `fuzz=False`, then verify the patched script's behavior. E279 covers zero-context placement; this case is different because the patch had context but one indentation byte was wrong. Existing Autotools tuple knowledge explains the necessary `config.sub` branches, not the cross-engine acceptance gap.

## CI validation increment: generated-script directory creation

Worker #80106 applied the exact patch but then failed in `config.status` writing `subs*.awk/sed/out`. Exact patch delivery and tuple detection do not prove filesystem creation semantics. On identity-mapped HMDFS, `mktemp -d` creates owner-only 0700 regardless of a relaxed outer umask; changing chmod afterwards is not a dependable repair.

Match the release's primary and fallback creation branches strictly. Use exclusive `mkdir` under umask 007 inside a recipe-private TMPDIR, retain the failure path and upstream cleanup, and restore the caller umask after making the parent scratch. Do not globally change permissions, share scratch, overwrite an existing directory, or skip configure. This supplements existing HMDFS advice with the distinction between the shell's umask and the creation tool's fixed mode. It applies only to the diagnosed temporary-directory branch, not arbitrary permission-denied errors.
