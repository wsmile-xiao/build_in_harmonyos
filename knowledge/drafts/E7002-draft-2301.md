# E7002: Validate HMDFS execution modes by required safety semantics

## Symptom

An OpenHarmony target preparation step signs a task-private ELF and runs
`chmod 0750` successfully. A following `stat -c %a` reports `0710`, so a
controller that requires exact equality with `0750` fails before launch even
though the owner execute bit is present and group/other write bits are clear.

## Root cause

HMDFS can project a requested POSIX mode to a different visible mode. Exact
mode equality makes optional permission bits, such as group read, part of the
transaction contract even when the executable only requires these properties:

- the owning user can execute it;
- group and other users cannot write it;
- the exact observed mode is recorded for attribution.

This differs from accepting `chmod` return code alone. A successful `chmod`
does not prove the readback mode, and a superficial "some execute bit exists"
check does not prove that the owner can execute the file.

## Fix

1. Run `chmod` on the frozen task-private artifact and read the resulting mode
   with `stat` in the same target shell and identity context.
2. Parse the three octal permission digits. Require the owner digit to contain
   execute and reject group or other digits that contain write.
3. Record the exact readback mode in the PREPARED receipt. Do not rewrite it to
   the requested mode.
4. Keep exact equality only when every requested bit has a proven functional or
   security requirement and the target filesystem can represent that mode.
5. If the frozen policy rejects the mode, preserve the failed transaction. Use
   a new run ID and root after correcting the policy; never relabel the old run.

For the common owner-executable and non-world-writable contract, the shell
predicate is:

```sh
case "$mode" in
    [1357][0145][0145]) : ;;
    *) exit 1 ;;
esac
```

## Validation

GLEW 2.3.1 W3 `r003` on an HMDFS-backed target requested mode `0750` for the
self-signed consumer. The signer remained `0750`, while the signed consumer
read back as `0710` with 948672 bytes and SHA-256
`2838bb288c8de599225429ebacd0fb2db3418829e485a54555e2f32c93c334bd`.
The frozen exact-mode policy failed preparation, and readback proved
`launch_count=0`, no launch lock, and no PREPARED receipt. This establishes the
false-negative mode check; a create-new successor must still prove the positive
target execution path. The create-new `r004` successor then accepted the same
`0710` safety semantics, wrote its PREPARED receipt, and executed the exact
self-signed ELF. That run failed later in an unrelated consumer version oracle,
so it validates the permission fix without being reported as an overall W3
PASS.

## Applicability and safety boundaries

Apply this pattern to task-private executables, signers, runners, scripts, and
shared libraries on HMDFS when the real requirement is owner execution plus
protection from group/other writes. It does not permit skipping mode readback,
accepting a group/other-writable artifact, accepting execution by a non-owner,
or treating preparation as W3 PASS. Target execution, terminal receipts,
release, and postrelease verification remain mandatory.
