# E2026100907：未知系统的编译器白名单不等于缺少语言能力

## 场景与通用触发特征

CMake 项目已经设置所需的 C++ 标准，但其 `compiler ID + CMAKE_SYSTEM_NAME` 白名单在未列出的系统直接报告 `Your C++ compiler does not support C++17.`。此时先检查报错控制流是否真正执行过编译／链接探测，不要把未知系统警告或未命中分支当作能力缺失。

## 精确根因

原 ANTLR 4.12.0 顶层源码已设置 C++17、required 和 extensions OFF；Clang 分支却只接受 Android、Apple、Linux 或 FreeBSD，HarmonyOS 未命中任何分支便进入最终 FATAL_ERROR。这与缺少标准库、老版本编译器和 `try_compile` 本身失败是不同机制。

## 可复用修复步骤

1. 保留原来已支持平台的版本检查和特殊编译参数。
2. 只给原白名单未命中的真实 Clang 系统加入 `CheckCXXSourceCompiles`；实际编译链接包含 `<optional>`、`<string_view>`、`<variant>` 和 `static_assert(__cplusplus >= 201703L)` 的程序。
3. 探测不成功仍立即 FATAL_ERROR；不得预置探测成功、伪装其他 OS、降低标准或排除上游测试。
4. 随后构建并实际运行完整原测试。配置接受性只是一个门禁，不是全部产品能力。

## 查重与实质增量

现行知识树 `E096` 处理 CMake 的自动标准检测与显式 CMAKE_CXX_STANDARD，`E130` 处理 SDK 标准库需要更高标准。本次的反例是“标准已经正确、编译器能力真实存在，但上游在探测之前按 OS 白名单拒绝”。修复必须改变对应的源码控制流并执行真实能力检测，单独添加 `-std=c++17` 不能修复这个分支，也不能把 `System is unknown to cmake` 当作唯一根因。此机制独立于库名称、版本及路径，可用于其他依赖同类白名单的 CMake 工程。

当前四范围实际查重另命中E267/E140平台名和feature-macro路由、E375的Windows/POSIX实现选择及enchantum的format头假阳性。这些都不覆盖语言标准已启用但名称白名单未执行能力测试即拒绝的反例。本次不是复述“探测比名字可靠”，而是保留已有平台版本分支、只补未知真实Clang的标准库编译链接集合，并以完整目标原用例验证这一控制流修复。查重原始记录SHA `d647fe0cea9bc622110fc0bffe30667909f2280914b6ac260de9e805d3be0eb9`，逐条语义差异结论SHA `7afc9f3da9cde21024123abbba7f37722a40c624155c01c8ed7f64526fbeab44`。

## 适用与安全边界

### 新增反例：能力结论不能跨执行进程迁移

平台 build96229 的原测试与消费者已通过，但 Python 进程中的 `ctypes.CDLL` 对私有已签名 DSO 返回 Permission denied。这不是 C++17 能力检测失败，也不能仅凭签名 section、权限位或其他消费者加载成功便宣布 Python 的装载能力成立；具体系统策略根因尚未证明。

当验收对象是库的原生动态装载/API 能力而不是 Python ctypes 绑定时，可保留原 ELF/签名/SONAME/NEEDED 检查，以单独签名、未预链接被测库的原生 ELF 执行真实 dlopen/dlsym。探针先用绝对路径装载同包依赖，再装载主库，调用真实 RGBA 编解码并用 dladdr 和进程 maps 核对私有包归属；执行失败仍失败，禁止加载系统替代库或伪造 JSON。若产品承诺 ctypes，则该替代路径不能消除其失败。

新独立 r005 同一事务完成原76/76、消费者4/4与上述鸿蒙1/1，零失败/跳过；观察SHA `34bf8d447dc79944adce78e45bf86d0004e4ec5950e65fc723a46bebd99b36c0`，源码匹配SHA `27c6c6de9d0e4d6cf910074a41181a4d07aa341cbcc05a0d98f4c7bf29be0d5d`。原 ctypes 失败保留，并不宣称其已恢复。这个反例补充本条的通用边界：能力检测必须对应真实执行域，语言探测通过、原生装载通过和 Python 进程装载通过不是同一个结论。平台当前新 HEAD 的 CI/Review 仍需另行验收。

### 可复用补充：捕获子进程输出不能丢失失败证据

真实检视发现独立装载探针使用 capture_output=True 和 check=True，但 CalledProcessError 被抛出时子进程 stderr 未流回 CI，因此只有“入口 RC1”，不能定位真实失败阶段。保留原超时、原 argv、原非零退出语义：捕获该异常后输出实际 stdout、stderr 和真实 returncode，再抛出同一个异常；不要补造成功 JSON、吞掉错误或把 Permission denied 统一归因于缺签名。

本机真实子进程分别产生成功输出和 exit7 失败输出，2/2 定向验证确认原 stdout/stderr/返回码完整传播（webp-loader-output-directed-oct11-r732/result.json）。新独立正式 r006 同事务重新构建并执行原76/76、消费者4/4、鸿蒙1/1，零失败/跳过；独立观察 SHA256 3e480e02ac65adbc42fb933508be13ccfc33e5dc2651d66b6702454c744434d1，逐源码匹配 SHA256 7eb67685a4a2c95a6fe0e8862f423c15dc1ae5a2b45ac45d030359745c97bcec。该增量适用于捕获日志的任意真实 runner；保留诊断不是修复未知平台权限根因，也不是当前新 HEAD 平台 CI 成功。

仅适用于未列出的系统和经真实编译链接可证明的编译器／标准库组合。原平台版本约束、实际缺少的头文件／符号／ABI、交叉编译不可运行条件、系统调用或认证能力不足不在此结论的覆盖范围；不能清除它们的失败或跳过状态。正式补丁必须由官方生成器生成并真实回放，不将源文件编辑本身称作配方自包含。
