# 补充至 PR #5678：源码解包修复后断言宏参数倒置的假阳性验证边界

## 原知识与实质增量

E483（来源 PR #5678）已解释 Conan 无后缀归档 URL 的 `BadZipFile`
与显式 `filename` 修复。本草稿不把该修复重复申报为新知识，而补充
早期解包失败解除后才到达的消费者假阳性：无类型断言宏参数倒置
仍会报告正确断言数并返回成功。可复用增量是以精确宏定义和一个
故意为假的谓词控制，区分“执行了断言”和“断言检查了正确条件”。

## 现象、根因与触发特征

从 `assert(message, condition)` 风格迁移到 `assert(condition, message)`
风格时，C 宏不提供函数式类型检查。非空诊断字符串处于条件位置会
恒真。消费者即使包含 API 调用、断言总数正确、RC0，也可能完全
检测不到应失败的条件。这不是 `NDEBUG` 的断言删除问题。

## 可复用修复步骤

1. 保持原源码 URL、已核对 SHA，不用换源掩盖格式识别问题；沿用 E483。
2. 阅读被测包实际头文件的宏定义，纠正条件/诊断参数顺序。
3. 用同一头文件哈希运行最小假条件和真条件对照；要求假条件 RC 非零、
   对应失败数为 1，真条件 RC0、失败数为 0。
4. 负例只作定向诊断，不修改上游用例，不计入产品测试失败或新增用例分母。
5. 完成修复后的实际消费者与独立目标专项；宿主对照不能替代 OHOS 执行。

## 适用范围和安全边界

适用于无类型约束的 C/C++ 断言/测试宏及同名 API 迁移；类型检查能在
编译期拒绝倒置参数的函数式 API 需另行验证。宿主负例不证明平台
计时器、签名或运行时兼容；目标专项必须真实依赖库的执行路径。
此诊断是当前错误的最小检查，不新增通用审计或 W3 前置矩阵。
当前草稿不宣称修复提交的最新平台 CI/AI Review 或提审已经通过。
