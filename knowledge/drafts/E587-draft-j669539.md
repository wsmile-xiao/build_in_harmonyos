**类别**：Conan / 链接 / 依赖图 / 打包 / OHOS
**来源**：kcalcore 5.116.0 适配，PR !14698（任务卡 #7770），2026-10-04，八轮构建依赖链攻坚
**编号说明**：主 agent 派工口径 E554；实测 E554 已被 tinyxml PR（E554-draft-A7F3）占用且 E555-E586 均有占用，按"被占顺延"取首个空闲编号 E587，最终编号由主编确认。

## 错误特征

三类特征互相咬合出现（同一适配的连环爆发）：

```text
# 1. 图冲突（conan 解析期）
ERROR: Version conflict in graph:
    zlib/1.3.2 ... required by glib/2.88.3
    zlib/1.3.1 ... required by qt5-qtbase/5.15.2.2

# 2. force 错方向后的链接期重定位失败（glib 源码重建，共享 libgio）
ld.lld: error: relocation R_AARCH64_ADR_PREL_PG_HI21 cannot be used against
symbol z_errmsg; recompile with -fPIC (zutil.o of static non-PIC libz.a)

# 3. 世代更名 404（源获取期）
https://download.kde.org/stable/frameworks/5.116/kcalcore-5.116.0.tar.xz
→ 404（官方 tarball 实名 kcalendarcore-5.116.0.tar.xz）
```

## 触发条件

- 制品仓图内同一传递依赖（zlib）被两条消费者边钉死在不同版本线，且两边均为静态嵌入边（依赖版本全量进消费者 package_id）；
- 某一 force 方向把"共享库消费者"（glib 的 libgio）推入源码重建，而它链接的制品仓静态库是 non-PIC 构建；
- KDE Frameworks 世代更名包（kcalcore→kcalendarcore 于 KF 5.68），按任务卡登记名构造官方下载 URL。

## 根因分析

1. **版本线冲突与翻转面**：qt5-qtbase/5.15.2.2 钉 zlib/1.3.1，libical3→glib/2.88.3 钉 zlib/1.3.2，conan 拒绝混图。两边都是嵌入边，force 任一侧都触发消费者重编译——决策必须比较各方向翻转面，而不是见冲突就 force。
2. **non-PIC 静态库在共享库图内的系统性约束**：zutil.o 的 z_errmsg 是编译期已知地址的 const 表，用 ADR_PREL 直接寻址；共享库要求全部代码地址无关。zlib 官方把 PIC 修复版**另发为 zlib/1.3.1.1**（manifest 明文"适配修复递增打包版本号 1.3.1 → 1.3.1.1……不改已发布的 1.3.1"），1.3.1 本体永不修复；zlib/1.3.2 本身是 PIC 供给。凡图内有共享库链接静态 zlib 的 KF5/glib 链消费者都会踩此雷。
3. **连环翻转**：force glib/2.88.0 会让 libical3 的 glib 边从非嵌入（shared，minor 掩码）翻转为嵌入（static，全版本），libical3 重建死于其已发布配方 pc-fix 不适配静态 glib 布局（`Package 'pcre2', required by 'glib-2.0', not found`）——依赖链冲突逐层暴露逐层归一（glib→zlib→libical3 八轮迭代）。
4. **世代更名**：kcalcore 在 KF 5.68 更名 kcalendarcore，官方 5.116.0 tarball 实名 kcalendarcore-5.116.0.tar.xz（download.kde.org 对 KF5 终版线 302 跳转 Attic 存档区）；任务卡给的 kcalcore-*.tar.xz 官方 404。

## 修复方案

**A. zlib 图归一（四方向实测，选最小翻转面）**

| force 方向 | 结果 |
|---|---|
| zlib/1.3.1 | glib 源码重建，libgio 链 non-PIC libz.a 死于 ADR_PREL z_errmsg ✗ |
| glib/2.88.0 | libical3 的 glib 边翻转为嵌入 → libical3 重建死于 pc-fix（pcre2 not found）✗ |
| zlib/1.3.1.1 | glib+qtbase 双翻转，双小时级重建 ✗ |
| **zlib/1.3.2** | **仅 qt5-qtbase 单包翻转重建（约 27 分钟），glib/libical3 全保二进制命中 ✓** |

```python
# archives/k/kcalcore/5.116.0/conanfile.py（313-347 行有完整决策注释）
self.requires("zlib/1.3.2", force=True)
```

zlib 1.x ABI 稳定（无版本 soname，静态链入 libQt5Core.so，消费者不可见）；CI 侧 `ci/config/build_timeouts.txt` 加 `kcalcore/5.116.0 10800s` 覆盖 conan create 内依赖重建（gobject-introspection 先例，属官方"构建超时配置"例外条款）。

**B. kcalcore→kcalendarcore 世代甄别**

开工先查 `download.kde.org/stable/frameworks/<版本>/` 目录实名；conandata.yml 写实名 URL + 实测 sha256（`2f57ea99…a53c`）；conan 包名保留任务卡登记名 kcalcore 维持平台绑定；名称映射写进 notes.md/manifest.yaml/PR 正文。

## 降级方案

- force zlib/1.3.2 的 qtbase 重建在 CI 超时不可扩 → 退回 force zlib/1.3.1.1（双翻转但两侧链接都过）；
- 世代更名兜底：invent.kde.org 仓库页确认 tarball 实名再写 conandata；**禁止**把任务卡登记名直接拼官方 URL 当下载源；
- 连环冲突无法配方层归一 → 回告平台侧协调制品仓版本线收敛。

## 验证

kcalcore/5.116.0 本地 conan create 八轮迭代：round6（qtbase 999fc4db 重建后）`100% tests passed, 0 tests failed out of 492`；round8 全链 RC=0 + test_package 15/15 断言全过。PR !14698。

## 红线

- 见版本冲突不比较翻转面就 force——会引爆连环重建甚至 non-PIC 重定位死局；
- 假设"1.3.1 以后会修 PIC"——官方明确 1.3.1 永不改，PIC 版是独立的 1.3.1.1；
- 拿任务卡登记名直接拼 KDE 官方 URL——更名世代的包必踩 404。
