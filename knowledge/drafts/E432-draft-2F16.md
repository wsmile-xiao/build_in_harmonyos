# E432 — 复用输出缓冲区未 NUL 结尾，导致测试断言读到上一次调用的残留

> 草稿条目，来源：`rtl-wmbus/1.1.0` 适配 HarmonyOS PC（OHOS aarch64）。
> 状态：draft，待主编审核后 promote 为正式知识条目。

## 错误特征

```text
测试断言行数/字段随调用顺序漂移（实际抓到 272 字节却报 8 行）
```

实际遇到的报错：

```text
trace: run1 used=58, run2 used=518, run3 used=272 但 strlen(out)=518（残留 run2 尾部）
```

## 触发条件

- 分类：`testing`
- 阶段：`testing`
- 工具：`test`
- 适用范围：自研 C 测试 harness 复用同一输出缓冲区、多次调用被测程序并按行/字段做断言的场景

## 根因分析

harness 只在函数入口做 out[0]=0，读完子进程输出后按 used 写入短输出，却没在结尾写 out[used]=0。strlen()/逐行遍历会越过真实数据继续读到上一轮更长的残留，表现为“行数/字段断言被污染且随调用顺序变化”，且污染内容来自另一条命令的输出（例如 usage 文本），极具迷惑性。

## 解决方案

### 推荐方案

捕获子进程输出到复用缓冲区时，入口置空之外必须在读循环结束后显式 out[used]='\0'（并保证 used < outcap）。

**方案说明**：复用缓冲区每次调用都必须写终止符，不能只在入口清首字节。

```bash
/* 读循环结束后 */
if (outcap && used < outcap) out[used] = '\0';   /* 必须 */
```

### 禁止做法

- ❌ 不要只在函数入口清空缓冲区——短输出会留下上一轮更长输出的尾巴。
  - 原因：清首字节不能保证后续 strlen/遍历在新数据之后终止。
  - 后果：断言结果随调用顺序漂移，误报为被测程序行为异常，浪费大量定位时间。

### 回退方案

若不便维护终止符，可为每次调用使用独立的堆分配缓冲，或先 stat/记录长度再按长度解析。

