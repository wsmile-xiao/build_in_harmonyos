# 补充 PR #13428：源码型语言库的资产完整性不能代替原生功能回归

## 场景、根因与通用触发特征

库只安装语言源码且无 native 构建系统，并不代表没有功能或上游测试。遇到源码哈希清单被计入测试数、examples 文件含断言却宣称测试为零，先区分资产完整性与执行语义。宏展开、作用域处理、求值行为必须由真实语言实现执行，不能由 Python 重写解析器或只检查文件存在代替。

## 修复与决策步骤

1. 先用发布的运行时做全新 OHOS `--build=never` 闭包解析，分别记录 runtime 的 RREV/PID/PREV；只下载配方不算运行时可用。
2. 从固定官方源码盘点核心回归入口、第三方互操作示例和可选系统。入口文件数是本轮明确的分母，不猜测内部断言数，第三方 fixture 缺失也不能冒充已执行。
3. 解释型源码分发可使用 ASDF 官方 `load-source-op`。设置其正常加载操作，不替换 `load-system`、不删断言、不吞 unmatched throw。每个官方回归文件在独立 ECL 进程完整执行。
4. 从 provider 复制运行时到自己的独占目录，对需要执行/加载的 ELF/FAS 本地签名，显式绑定 ECLDIR 和运行库路径；不改 provider 缓存或系统工具，不复制别的任务目录。
5. 安装消费者实际调用包内宏展开并求值；鸿蒙测试独立读取中文空格 HMDFS 文件，经同一库处理再写回精确结果，验证数据不变、文件对父目录的投影属主及精确清理。

ASDF 操作语义见 [官方 ASDF 手册](https://asdf.common-lisp.dev/asdf.html)。解释执行证明不等于编译模式、native FFI 或可选 debugger 通过。

## 查重增量与安全边界

这是对 PR #13428 自身旧完整性豁免草稿的实质修正：可执行语言库不能套用纯数据豁免。已有 cl-unicode 草稿解决 ECL 编译期前缀/模块及语言预检，本条新增无需 C 编译的标准 ASDF 解释加载边界、未修改核心回归入口分母和独立 HMDFS 真实 I/O。当前解释模式无需那些草稿所述模块/头文件软链，不把此反例泛化为所有编译模式都无需它们。font/firmware 数据资源没有同类库的可执行语义，不使用本条强迫其调用不存在的语言 API。
