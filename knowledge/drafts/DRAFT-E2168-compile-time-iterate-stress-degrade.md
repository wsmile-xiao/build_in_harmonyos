# E2168: 编译期常量压测在共享设备不可全量执行——迭代数编译期覆盖与如实申报策略

## 问题描述

ck 0.7.2 的上游回归套件（`regressions/`）包含大量压测型 validate 程序：迭代数是编译期常量（`#ifndef ITERATE / #define ITERATE 5000000`），barrier 系列 5 个程序以 20 线程（configure 从 /proc/cpuinfo 探测 CORES=20）跑 5M 次迭代。在多人共用的 OHOS 开发设备（容器实际 8 核、长期多任务并发）上：单个 barrier 程序 8 小时以上 CPU 无法完成，并曾因设备内存耗尽被 OOM 杀死（`make: *** [check] Killed`，日志 regressions_check.dead1.log），整个 `make check` 因此无法收尾。

## 根因

- 压测强度是编译期常量，不是测试正确性的必要条件（每轮迭代的 barrier 正确性断言都会执行）；
- `/proc/cpuinfo` 探测核数（20）> cgroup 实际可用核数（8），20 线程超订阅造成惊群放大；
- 共享设备多租户并发使情况恶化，且测试无法在 CI worker 上等价复跑（小时级）。

## 解决方案（先评估窗口，再降级执行）

1. **排期前先读测试源码**：`grep -n "define ITERATE\|CORES" regressions/*/validate/*.c`，同时识别进度输出（如 ck 的 `[W] j/ITERATE_S` 刻度）用于估算时长；
2. **编译期覆盖，不改源码**：`make clean` 后用"原始 CFLAGS + 一个额外 `-DITERATE=500000`"重编目标程序，线程数与 argv 保持上游原样（`./barrier_centralized 20 1 1`）；
3. **低优先级跑**：`nice -n 19`（设备无 renice 时，新起进程直接带 nice；已运行进程组可按 50% 占空比 SIGSTOP/CONT 节流）；
4. **如实申报**：PR"上游测试用例修改说明"逐文件列出（原文件/原因/修改内容/结果），附原版 8h+ 与 OOM 的日志证据；通过率分母口径不变（仍是 check 注册的静态全量）。

## 验证

- 降迭代后每个程序仍执行全部每轮正确性断言、退出码 0；
- 模块 RC 与逐程序日志与申报数字一致；
- PR 中记录：原始常量、覆盖值、原因、证据路径。

## 适用范围与边界

- 适用于 ck、liburcu、xthread 等一切"编译期常量压测"型上游测试；
- **反例**：迭代数没有编译期 guard 的程序只能改源码（等同修改上游测试，需逐项申报）；正确性断言本身依赖迭代次数语义的（如收敛测试）不可降级；
- **解除条件**：独占 8 核以上设备可去掉 `-DITERATE` 覆盖按原版执行；
- **底线**：若 1/10 迭代仍跑不完，按 PARTIAL/部分执行口径如实申报（`N_executed/N_static` + 原因 + 日志），绝不静默缩分母、删测试或伪造通过。
