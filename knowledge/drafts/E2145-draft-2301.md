# E2145 — Meson allocator fault-injection build contract

## 错误特征

完整上游测试库存中可能出现三类连续但不同的失败：

1. Meson 输出 `Checking for function "reallocarray" : NO`，OOM 和 corpus
   replay 测试根本没有注册。
2. 补齐能力后，链接器报 `undefined reference to strndup`，或 MinGW 最终
   符号表仍含 `__imp_malloc` / `__imp_strdup`，说明 `--wrap` 没有覆盖调用。
3. 错误地强制静态被测库后，`api-oom-spdxtool` 报
   `TEST_ASSERT_NULL(...) was ...`，GDB 显示注入发生在被测库内部而非测试
   注释声明的 consumer 源码边界。

## 触发条件

- 构建系统: Meson
- 阶段: configuration, linking, testing
- 测试使用 GNU ld `--wrap=malloc/calloc/realloc/...` 做确定性故障注入。
- 测试注册受 `reallocarray`、临时文件 API 或链接器语义探测控制。

## 根因分析

测试能否注册、包装器能否拦截、包装边界是否正确是三个独立门禁。缺少
API 会让测试静默消失；MinGW 的 `dllimport` 间接符号会绕过 GNU ld
包装；强制 `default_library=static` 又会把原本只覆盖 consumer 源码的
注入扩大到被测库内部，使库内可恢复分配失败被误判为 consumer 构造失败。
仅看 `meson test` 返回码无法区分这些情况。

## 解决方案

### 推荐方案

1. 从 `meson introspect --tests` 绑定应注册的完整测试清单。
2. 仅在隔离验证环境补齐缺少的 POSIX API，不能改交付源码来伪造能力。
3. MinGW 使用 `-mnop-fun-dllimport`，并检查最终对象确实引用
   `__wrap_*`，而不是 `__imp_*`。
4. 保持上游测试声明的共享/静态链接边界；不要为了打包策略改写测试构建
   变体。
5. 对 corpus runner 同时核对顶层状态和 `REPLAYED_INPUTS=N`，负测必须是
   明确的预期非零退出。

### 禁止做法

- 禁止把未注册的 capability 测试计为通过。
- 禁止用静态被测库扩大 `--wrap` 范围后解释 OOM 失败为源码缺陷。
- 禁止只看顶层 Meson 测试数而重复或遗漏 corpus 输入。

## 验证

```bash
meson introspect --tests build
meson test -C build --num-processes 1 --print-errorlogs
nm build/test-api-oom-* | grep -E '__wrap_|__imp_'
```

pkgconf 3.0.5 的最终验证注册 33 个顶层测试，32 个 `OK`、1 个要求的
`EXPECTEDFAIL`、0 个失败；parser 和 solver runner 分别报告
`REPLAYED_INPUTS=141` 与 `REPLAYED_INPUTS=3`。

## 关联条目

- 原则: 能力探测优先、失败闭合、测试库存唯一计数
