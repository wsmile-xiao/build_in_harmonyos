# E6340 — Meson build 阶段的 OHOS 上游测试必须绑定间接共享库 RPATH

## 问题现象

平台 CI 能完成 librest 的 OHOS/armv8 编译和链接，但 `Meson.test()` 的 10 个上游
测试全部以 RC 127 退出。日志同时出现：

```text
Error loading shared library libjson-glib-1.0.so.0
json_parser_new: symbol not found
```

## 根因

`conan graph`、`PkgConfigDeps` 和链接成功只证明编译闭包；它们不会为 build() 阶段
测试 ELF 自动建立 loader 搜索路径。librest 直接依赖 json-glib，但测试二进制的
运行时环境没有包含该包的 `lib` 目录，因此目标 loader 先找不到 SONAME，再报告
由此产生的 `json_*` 符号缺失。`LD_LIBRARY_PATH` 或 `VirtualRunEnv` 不能替代
ELF 自身的 loader-bound 搜索路径。

## 修复步骤

1. 在 recipe 的 `generate()` 中枚举当前 host dependency graph 的
   `package_folder` 与 `cpp_info.libdirs`，转换为绝对路径并去重。
2. 为 C 和 C++ Meson 链接参数追加
   `-Wl,--disable-new-dtags,-rpath,<absolute-libdir>`。使用
   `--disable-new-dtags`，使链接器生成 `DT_RPATH` 而不是 `DT_RUNPATH`。
3. 保留显式运行环境作为辅助，但不把它作为测试通过证据；build() 阶段的上游
   测试必须在同一 recipe 闭包内运行。
4. 对当前候选执行 fresh `conan create`；不得使用会禁止根 recipe
   重建的 `--build=never`。对完整上游测试 ELF 清单执行
   `llvm-readelf -d`，要求每个仅有一个 `DT_RPATH`、无 `DT_RUNPATH`，
   且 RPATH 覆盖间接 SONAME 所在目录。实际上游 N/N 执行仍由同
   HEAD 平台 CI 证明。

## 验证与边界

CI #50226 的失败是 10/10 测试 RC 127，修复目标是消除 `libjson-glib-1.0.so.0`
找不到及其连带符号错误。fresh Conan r087 返回 RC 0，84/84 编译和
test_package 编译完成；独立审计确认 10/10 上游测试 ELF 各有一个
`DT_RPATH`、无 `DT_RUNPATH`，且 RPATH 包含 json-glib 实际包目录；
`librest-1.0.so.0.0.0` 的 `DT_NEEDED` 中存在 `libjson-glib-1.0.so.0`。
本地交叉主机未执行目标 ELF，因而实际 10/10 通过仍必须由同 HEAD 平台
CI 回读，不得用动态段审计代替。

本次证据为 `conan-create-r087-runtime-rpath.log` 与
`runtime-rpath-audit-r087.log`，两者都位于任务自有的
`F:\HarmonyPC\librest-0.10.2-20260913`。
该条目适用于交叉构建阶段直接执行上游测试的共享库 recipe；它不替代目标机签名、
W3 唯一 launch、W3 consumer、平台 CI 或当前 HEAD 的 Review/Pre-PR 门禁，旧 W3
事务也不得因 recipe 变化而复用。

## 与已有条目的区别

`conan-consumer-runtime-rpath` 关注独立 `test_package` consumer 的运行时闭包；
本条专门约束 recipe `build()` 内的 Meson 上游测试，避免“consumer 有 RPATH、
但上游测试仍在 CI 中 RC 127”的遗漏。
