# Conan 消费者完整依赖闭包的 fail-closed 校验

## 问题现象

在 OHOS/aarch64 Conan 消费者中，配方只检查少数关键依赖的版本，或只判断
`self.dependencies[name]` 存在。其余依赖节点可能没有可消费的 binary、include
根或 lib 根，手工编译的消费者探针却仍可能通过，形成假绿。另一类误报发生在
`conan graph info --build=never`：根包尚未构建时 `binary`/`prev` 为空是正常状态，
旧验证器若要求根节点已有 binary，会把正常图错误报告为 `root_count=0`。

## 根因

Conan 图阶段描述的是“待构建的根包 + 已解析的依赖闭包”，而 test_package
阶段描述的是“已物化的消费者输入”。两者的身份边界不同。仅校验版本不能证明
package folder 已下载；仅校验目录存在也不能证明消费者有头文件和库目录。必须把
精确版本、真实 package folder、`cpp_info.includedirs` 和 `cpp_info.libdirs` 绑定在
同一个消费者契约里，并让根包在 graph 阶段保持可构建状态。

## 修复步骤

1. 在 `test_package` 中列出所有直接或运行时必需依赖的精确版本，逐项读取
   `self.dependencies`，缺节点或版本漂移立即抛出 `ConanInvalidConfiguration`。
2. 对每个依赖检查 `package_folder` 是真实目录，并检查 include/lib 元数据非空，
   再生成编译器参数；不要静默跳过缺失依赖。
3. 用隔离 Conan Home 执行 `conan download --only-recipe` 和 OHOS profile 的
   `conan graph info --build=never`，记录依赖 RREV/PID/PREV 与 `info_invalid=0`。
4. 把根包的空 `binary`/`prev` 解释为“等待当前 conan create”，只有消费者阶段
   才要求根包 package folder 已物化；验证器不得跨 run 复用旧根节点字段。

## 本次验证

本任务的 `libspatialite/5.1.0.2` 图解析得到 7 个节点，sqlite3、zlib、proj、
geos、librttopo、libxml2 均从 `ohpcd` 解析到可用 package；根包仅保留待构建的
package ID。消费者契约因此扩展为六个精确依赖，并在每个节点缺目录、缺 include
或缺 lib 元数据时 fail-closed。后续目标平台验证必须使用当前候选的全新 W3 证据。

在同一候选的目标 W3 中，配置阶段先暴露了目标工具目录缺少 `ld` 别名，随后
Libtool 归档阶段将缺失的 `AR` 降级为 `false` 并以 `false cru` 失败；工具修复后，
libxml2/zlib 的 `books.xml`、`opera.xml`、`movies.xml` 压缩长度分别观测到
433、427、557，而上游固定值为 432、425、577。根因是交叉工具闭包只提供
`ld.lld`、`llvm-ar`、`llvm-ranlib` 等 LLVM 名称，而 Autoconf/Libtool 仍按传统
`LD`、`AR`、`RANLIB` 环境变量探测；同时目标 XML 压缩实现与上游主机的固定尺寸
不同。修复时应从当前编译器的绝对路径目录和受控工具目录按优先级解析这些工具，
缺失即停止；测试对所有目标统一允许已观测的精确尺寸集合，并在错误信息中列出
完整集合（books 为 432 或 433，opera 为 425/426/427，movies 为 577 或 557），
不要在共享系统目录创建别名。验证需在目标机真实 `conan create` 中
确认配置完成、归档命令不再
出现 `false cru`，三个 fixture 均通过后再进入完整上游和消费者测试。目标共享
库的测试图还可能把 zlib 这类仅由被测 ELF 的 NEEDED 使用、而消费者源码不直接
调用的传递运行时依赖标为 `Skipped binaries`；消费者应保留精确版本检查，但只
要求实际参与编译/链接的依赖物化，并对签名工具按当前 PATH 解析。

## 注册表版本碰撞

PR 创建后的平台 CI 可能在源码和真机均通过后，才由 L0j 发现同一 `name/version`
已经以不同 recipe 发布。该结果是 Conan 制品身份冲突，不是构建或测试失败；继续在原
版本目录上改写会让 CI 的 recipe revision 语义不明确。处置时应从当前已修复候选创建
新的版本 identity（例如 `5.1.0.2.1`），同步迁移 archive 路径、配方版本、manifest、
分支、Issue/PR 合同和测试清单，再对新候选重新完成 W3、Pre-PR、CI 与 Review。旧 PR、
旧 HEAD/tree 和失败日志必须作为不可变历史保留，不能把新版本的结果拼接回旧候选。

## 适用范围与安全边界

该模式适用于手工消费者编译、传递依赖较多或要求 `--build=never` 的 Conan C/C++
配方，也适用于 OHOS 交叉工具只提供 LLVM 命名的 Autotools/Libtool 构建，以及
共享库测试图中存在被跳过的运行时传递依赖。纯
header-only 包不能机械要求 libdirs，应按其 package_type 定义等价契约。依赖与
工具检查是只读/任务自有环境门禁，不代替当前候选的 Conan create、真实目标执行、
精确 CI 或 Review；任何版本、RREV、package ID、HEAD 或 W3 身份漂移都必须重新验证。
版本碰撞 successor 也必须遵守同一边界：版本号递增只解决 registry identity，不能免除
目标真机、精确当前 HEAD CI 或平台 Review；旧候选证据不得跨版本复用。
