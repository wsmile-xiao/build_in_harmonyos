# E1002 - Windows-hosted OHOS builds need separate tool identities

## Problem and root cause

Windows-hosted Conan builds of legacy Autotools projects can cross several
different command boundaries. w64devkit may run a compiler path through a
POSIX `sh`, so a Bash-only wrapper (`args=()`, `${drive^^}`) fails with
`syntax error: unexpected (` and the compiler appears unusable. A host profile
that leaves `LD` as `C:/Program Files/...` can then be split at `C:/Program`,
producing `no acceptable ld found in $PATH`. Even after tool identity is
correct, invoking configure from an absolute `F:/...` source path makes old
Autoconf write `db_cxx.h:F:/...` template pairs; `config.status` interprets
the drive colon as a separator and reports `cannot find input file: F`.

The Windows CMake consumer has a different boundary: a `.sh` compiler wrapper
can be called by make for compilation, but CMake's direct link command uses
CreateProcess and returns `inappropriate file type or format` for that wrapper.
OHOS workers add a runtime boundary: a shared cache `TMPDIR` can be readable
but not writable by the package process. Legacy `config.guess` creates a
`dummy.c` probe there, so configure fails with `Permission denied` before the
compiler is tested. A worker may restore or inject a process-level TMPDIR
after Conan writes its generated toolchain file, so the generated file alone
does not prove the value seen by configure.
Even a task-local TMPDIR can remain ACL-restricted for the legacy
\`umask 077 && mktemp -d\` path; in that case an explicit build triplet avoids
the unnecessary compiler probe while retaining the real target host triplet.
The same ACL boundary can affect Autoconf's later \`config.status\` private
directory (for example \`subs1.awk\`), so the task shell and recipe process
must use \`umask 022\` during configure and package generation.

## Repair and verification

1. Bind CC, CXX, LD, AR, RANLIB, NM, and STRIP to task-local POSIX-compatible
   wrappers. Keep shell utilities and a real `make.exe` under the task root so
   PATH lookup does not expose space-bearing w64devkit paths.
2. Run legacy Autoconf from the recipe build directory and pass a relative
   `../src/dist/configure` path. Keep generated environment files normalized
   before sourcing them.
3. Treat Windows CMake direct execution of `.sh` wrappers as a separate host
   contract. Resolve the wrapper's native `clang.exe`, then carry `--target`,
   the quoted `--sysroot`, `-fuse-ld=lld`, and platform flags into one custom
   `CMakeToolchain` instance. Keep WSL/Linux as an independent cross-check, not
   as proof of the Windows execution boundary.
4. For a non-Windows OHOS build context, define `TMPDIR` to the task-owned
   Conan build directory before Autoconf runs. This keeps config.guess probes
   writable without modifying a shared worker cache. Verify the generated
   environment file and the first configure output both use that directory.
   Also set the value in the recipe process before configure/package and export
   it again from any task shell wrapper; all three observations must point to
   the same task-owned build directory.
   If the worker still rejects \`config.guess\`'s private dummy file, pass
   \`--build=x86_64-linux-gnu\` (or the actual worker triplet) alongside the
   target \`--host\`; do not disable target cross compilation.
   Set \`umask 022\` around Autotools configure/package calls and export the
   same policy from task wrappers; restore the caller's umask afterward.
5. On db-c/5.3.28, r019/r020/r023/r024/r025 recorded the respective wrapper,
   linker, drive-colon, shell-utility, and CMake direct-link failures. The
   current recipe passed WSL r011 with `CONAN_CREATE_OHOS_R011_RC=0`. Windows
   r027 reproduced direct `.sh` execution failure and r029 reproduced missing
   target linker flags; r031 then completed Conan create with RC=0 and built
   both AArch64 `test_package` targets through native OHOS clang; platform CI
   #47677 then exposed the shared-TMPDIR permission boundary; CI #47771 showed
   that a worker-level environment override can bypass the generated file, so
   the successor adds process-level and wrapper-level bindings. CI #47803 then
   reproduced an ACL denial inside the task-local mktemp subdirectory; the
explicit build triplet was the first follow-up; CI #47831 then reproduced
   \`config.status\` \`subs1.awk\` denial, motivating the umask 022 guard.
The worker can still reject the private directory created by \`mktemp -d\`
itself. A task-owned shim that creates 0755 directories and delegates all
other mktemp modes to the system utility keeps the workaround scoped to this
package and avoids changing shared worker state.
CI #47917 then reached the recipe and exposed a separate shell identity fault:
config.status emitted repeated \`print: command not found\` diagnostics and
libtool failed at \`archive_expsym_cmds\` with an unexpected \`}\`. The
generated scripts had selected a shell builtin set that did not match the
worker shell used for the subsequent phase. Bind the PATH-resolved bash path
to both \`SHELL\` and \`CONFIG_SHELL\` before AutotoolsToolchain generation and
keep that value for the whole configure/build transaction. Environment
assignment alone is not sufficient when the configure script shebang still
selects the worker shell; invoke configure explicitly as
\`CONFIG_SHELL=<bash> SHELL=<bash> <bash> configure ...\`, then run make and
install with the same shell identity.

## Reuse and safety boundary

This applies to Conan recipes that invoke POSIX shells around an OHOS SDK and
to their CMake test consumers. Tool wrappers, SDK paths, make binaries, and
temporary directories must remain task-private and be hash-bound to the
candidate.
WSL success does not prove Windows CMake direct execution, and Windows consumer
build success does not prove target execution, signing, upstream test
completion, CI, review, or submission. Never rewrite a missing RC, make an
absolute-drive Autoconf path look relative after the fact, or claim a Windows
consumer PASS from a WSL log.
