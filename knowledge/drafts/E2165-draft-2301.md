# E2165 - Validate materialized shared-library modes by security baseline

## Symptom

A Conan package completes compilation and installation on HMDFS, then fails
while converting a versioned shared-library symlink into a regular SONAME
alias. The source and alias are regular, byte-identical, and owner-executable,
but the source mode is 0750 while the materialized alias is 0770.
shutil.copy2() and a later copymode() do not make the exact modes equal.

## Root Cause

Shared HMDFS paths can project an added group-write bit so adjacent sessions
whose numeric UIDs differ can still update task-owned state through the shared
group. Exact mode equality treats that filesystem policy as content or
executable drift. Removing all mode checks would be unsafe because world-write,
lost execute/read bits, or setuid/setgid/sticky bits are materially different.

The reusable boundary is therefore a security baseline:

- owner rwx must remain exact;
- group and other read/execute bits must remain exact;
- an added group-write bit is allowed;
- world-write and setuid/setgid/sticky are rejected;
- regular-file, non-symlink, and exact-byte checks remain mandatory.

## Fix

After copying each logical shared-library alias, calculate source and
materialized modes with stat.S_IMODE. Compare owner rwx and group/other
read-execute bits under a fixed mask. Permit the destination to add group-write
only, and fail if it adds world-write or any special bit. Apply the same helper
to package aliases and task-private runtime copies so producer and consumer use
one representation contract.

Do not use this rule to accept arbitrary regular files. Resolve each declared
alias to the intended versioned library first, then require identical size and
SHA-256 or an equivalent streaming byte comparison.

## Validation

The failing target package contained:

- libXft.so.2.3.9: regular, mode 0750, SHA-256
  a293d086d66612efed88732b3295d85e7cf494af0e7097d3f7cfd5970d5d26a9;
- libXft.so.2: regular, mode 0770, the same size and SHA-256;
- libXft.so: still a symlink to libXft.so.2.

Both the production recipe helper and test-package helper passed the same seven
directed cases, for 14/14 total checks:

- exact 0750 to 0750: pass;
- HMDFS group-write 0750 to 0770: pass;
- owner execute loss 0750 to 0660: fail;
- group read/execute loss 0750 to 0700: fail;
- world-write gain 0750 to 0777: fail;
- setuid gain 0750 to 04750: fail;
- other read/execute loss 0755 to 0750: fail.

The fresh r26 target transaction then passed shared/static package creation,
consumers `2/2`, variant executions `4/4`, and 95 assertions with one launch.
This establishes the repaired policy on the target; the directed matrix alone
would not have replaced W3.

## Safety Boundaries

- Do not weaken byte equality, logical-link identity, or regular-file checks.
- Do not allow world-write or special permission bits.
- Do not assume copy2() or copymode() can override shared-filesystem mode
  projection.
- Native filesystems that preserve exact modes may keep using the same helper;
  exact mode remains one accepted case.
- A host mode matrix proves policy logic only. Re-run a fresh target package
  transaction after changing recipe or consumer materialization.
