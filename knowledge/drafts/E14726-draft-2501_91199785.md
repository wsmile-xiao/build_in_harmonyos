# E14726 草稿 — INTERFACE 组件也需要已编译提供者闭包

## 现象、根因与适用范围

多组件包经选择性安装后，下游 CMake 能找到包，编译命令也有正确 include 根，却在包含某个组件的公开头时失败。第一层诊断是包内容：检查目标头及对应组件 config 是否实际存在，而不是继续改下游 include 路径。第二层诊断不能因目标是 `INTERFACE` 就省略依赖：上游的 INTERFACE target 可能公开链接同包的已编译组件。

本次 `libosl/0.8.0` 真机编译遇到 `boost/accumulators/accumulators.hpp` 缺失；旧 Boost 包的 include 根已在命令行，但其选择列表未含 Accumulators。Boost 1.91.0 [官方 Accumulators CMakeLists.txt](https://github.com/boostorg/accumulators/blob/boost-1.91.0/CMakeLists.txt) 声明 `Boost::accumulators` 为 INTERFACE，同时公开链接 `Boost::serialization`。因此修复不仅要将 Accumulators 加入生产和上游测试选择，还要让 Conan 的 `Boost::accumulators` 组件传播 Serialization 的真实编译目标。

## 可复用修复顺序

1. 从失败编译命令和解析出的 package folder 同时核对 include 根、目标头、对应 CMake config；include 根存在不等于头已打包。
2. 按精确上游 tag 追踪组件归属及 `INTERFACE` / `PUBLIC` 目标链接闭包，不能仅按库名推测“纯头文件”。
3. 把组件加入选择性构建与测试入口；在 Conan `package_info()` 暴露官方目标名，同时用 Conan 组件键声明已编译提供者依赖。
4. 消费者只 `find_package` 新组件，包含原本失败的头，并实例化真实 API；再检查最终链接闭包及运行结果。
5. 对上游测试与消费者分别清点 N/N；最后从已发布的精确包回读头、target 和二进制，才允许下游升级引用。

禁止把单个头拷到下游、造一个无依赖的空 target、或仅在下游加 `target_link_libraries`。本规则仅适用于已证实包内容与组件闭包缺失的情况；若头已存在，应转查 CMakeDeps include 传播、包版本选择和编译器参数。

## 与现有知识的增量

`boost-selective-component-package-missing-header` 已覆盖“include 根正确但组件头未入包”的第一层问题；本草稿新增第二层：被补入的组件虽是 INTERFACE，其官方目标仍公开要求已编译提供者，Conan 元数据必须精确导出该闭包。`conan-component-key-and-cmake-target-contract` 解释 Conan 键与 CMake target 名不同；本草稿进一步给出选择性组件包的内容闭包与链接闭包必须一起交付的判断顺序。

## 当前证据与待验证边界

- 负向证据：`D:\Projects\harmonyPC\workspace\four-base-20261004\w3-libosl-20261004T082319Z` 的原始真机编译在目标头缺失处失败；此证据只定位旧依赖包问题，不证明新 Boost 已可用。
- 官方目标契约：上述 Boost.Accumulators 精确 tag 的 CMakeLists 声明 INTERFACE 与 Serialization 依赖。
- 正向证据：`boost/1.91.0.1.4` 已选 Accumulators、导出 `Boost::accumulators` 与 `serialization` 依赖，并增加真实 count/mean 消费者。真机事务 `boost-w3-20261004T141208Z` 的 `conan create` 返回 0、适用上游清单 66/66、消费者 9/9，完整回执链的独立校验返回 `W3_PASS`；回读日志 SHA-256 为 `92a4b9b668abc08e23dc4dbf72fdf291fbc521dd9552375687db9465d9ae9010`。66 项包含 Accumulators 48 项：官方 Jamfile 的 `valarray` 在 libc++ 下明确跳过，而 `tail` 因 CMake Jamfile 导入器不解析同行要求，需另行注册未改动的上游测试。此证据尚不代表比赛 worker CI 或制品仓发布成功，`libosl` 仍应等待正式包可用后重新验证。

源码下载失败另有独立证据：第一次 Boost W3 在 `source()` 连接 GitHub 超时，尚未进入编译。后继事务可以使用由官方 URL 取得并与 `conandata.yml` SHA-256 完全一致的归档；该途径只解决传输，不替代组件与测试验证。

另一个可复用测试边界是 Boost.Test 链接模型：Jamfile 指定静态 framework 的旧式 `init_unit_test_suite` 测试，若误随生产共享库选项而使用动态 framework，会出现 `undefined symbol: main`。应只将测试工程改为静态链接，并保持生产共享库与上游测试源码不变。OHOS Clang 下还须核对 Boost.UUID 默认的 `-latomic` 传递链接；目标 sysroot 无独立 libatomic 时关闭该选项，再用完整链接和运行结果证明原子实现足够。
