# E2184: Bind Conan metadata to versioned CMake library outputs

## Symptom

A CMake-based Conan recipe compiles and packages a shared library, but the
OHOS consumer fails during CMakeDeps configuration with `Library 'tbb12' not
found in package`. The package tree contains a versioned shared object such as
`libtbb.so.12.3`, while the upstream CMake target is still named `TBB::tbb`.

## Root cause

The logical target name and the linker lookup name are different contracts,
and the lookup name can vary by platform. CMakeDeps uses `cpp_info.libs` to
locate files in the package; it does not infer that the Windows import-library
name `tbb12` should mean the OHOS `libtbb.so` namelink for
`libtbb.so.12.3`. The producer build therefore does not exercise the
generated consumer metadata.

## Fix

1. Inspect the installed package tree on each supported platform and record
   the actual linker basename.
2. Set `cpp_info.libs` to that platform linker lookup name, such as `tbb12` on
   Windows or `tbb` for an OHOS shared package, while retaining
   `cmake_file_name` and `cmake_target_name` for the upstream logical target
   (`TBB` and `TBB::tbb`).
3. Run a real `conan create` with the recipe's `test_package`; require CMakeDeps
   configure, linking, and the consumer executable to pass.
4. Repeat the readback for OHOS/Linux, where the versioned shared-object name
   may differ from the Windows import-library name.

## Validation

oneTBB 2023.1.0 first built all producer targets and passed the Windows
consumer after binding `cpp_info.libs` to `tbb12`, but Buildbot #40659 then
showed that the same name is wrong for OHOS: CMakeDeps could not find a
`tbb12` library. The source install macro proves that Unix shared installs
provide the `libtbb.so` namelink beside `libtbb.so.12.3`; the repair therefore
uses `tbb` for shared non-Windows builds and keeps `tbb12` for Windows and
static builds. A fresh OHOS consumer and platform CI remain required.

## Applicability and safety boundaries

This applies to CMake libraries whose install rules version shared libraries
or import libraries while exposing an unversioned logical target. It does not
permit fabricating aliases, skipping the consumer test, or treating a
producer-only build as package validation. Platform-specific names must be
rechecked after any CMake, compiler, or packaging change.
