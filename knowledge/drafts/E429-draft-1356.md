# E429 — mkc（BSD make / mk-configure）构建体系与 GNU make 不兼容：配方内等价手工编译 + 检测宏注入

## 错误特征
```
Makefile: .for 循环语法错误（GNU make 4.4.1 不解析 BSD make 的 `.for d in ${tests}`）
.include <mkc.subprj.mk> 找不到
SIZEOF_LONG 未定义
struct rusage 字段不完整（timer.c）
```

## 触发条件
- 构建系统: BSD make / mk-configure (mkc) 体系，顶层 Makefile 使用 `.for` 与 `.include <mkc.*.mk>`
- 阶段: configuration / compilation
- 平台: HarmonyOS PC (aarch64, OHOS/armv8)，仅有 GNU make 4.4.1

## 根因分析
libmaa 1.4.7 使用 BSD make 的 mk-configure (mkc) 体系构建：顶层 Makefile 用
`.for d in ${tests}` 循环与 `.include <mkc.subprj.mk>` / `.include <mkc.lib.mk>` 框架 include，
GNU make 无法解析这两种语法。更关键的是，mkc 在 configure 阶段自动完成的平台检测被整体跳过：

- `MKC_CHECK_SIZEOF long` → 本应生成 SIZEOF_LONG 宏（aarch64 上为 8）
- `MKC_CHECK_HEADERS sys/resource.h alloca.h` → 本应生成 HAVE_HEADER_SYS_RESOURCE_H 等宏

缺少 HAVE_HEADER_SYS_RESOURCE_H 时 maaP.h 第 54 行 `#if HAVE_HEADER_SYS_RESOURCE_H` 为假，
`#include <sys/resource.h>` 被跳过，timer.c 中 `struct rusage` 变为不完整类型而编译失败。
此外 arg.c 依赖 awk 生成的 arggram.c，也需在构建中手动生成（`awk -f arggram2c arggram.txt > arggram.c`）。

> 误判警示：旧适配笔记曾记录"musl 缺 sys/resource.h，排除 timer.c"。实测 OHOS 实际提供
> sys/resource.h 与 getrusage（探针 `#include <sys/resource.h>` + 调用 getrusage 编译链接运行均成功），
> 真实根因是检测宏未注入，不是头文件缺失。平台头文件可用性必须实测，不能沿用旧结论。

## 解决方案

### 推荐方案
conanfile.py 的 build() 中直接等价手工构建，不依赖 mkc：

```python
def build(self):
    apply_conandata_patches(self)
    cc = self.conf.get("tools.build:compiler_executables", default={}, check_type=dict).get("c") or "clang"
    # 1) 生成 arg.c 依赖的 arggram.c
    self.run('awk -f arggram2c arggram.txt > arggram.c', cwd=src + "/maa")
    # 2) 全量源文件（含 bit.c/timer.c）编译，注入 mkc 检测宏
    cflags = "-O2 -fPIC -I. -DMAA_MAJOR=4 -DMAA_MINOR=0 -DMAA_TEENY=0 " \
             "-DSIZEOF_LONG=8 -DHAVE_HEADER_SYS_RESOURCE_H=1"
    # 3) 静态：llvm-ar rc + llvm-ranlib；动态：cc -shared
```

关键点：
- 检测宏必须显式注入：`-DSIZEOF_LONG=8`（aarch64 long=8）、`-DHAVE_HEADER_SYS_RESOURCE_H=1`、
  `-DHAVE_HEADER_ALLOCA_H=1`
- 编译器从 `self.conf.get("tools.build:compiler_executables")` 获取（R33），不用裸 shell 环境变量
- 测试程序编译需 `-Imaa -Imaa/build -Lmaa/build -lmaa`（hashtest/settest 上游 SRCS 还附带 maa/rnd.c）

### 禁止做法
- ❌ 尝试让 GNU make 解析 BSD make 的 `.for` / `.include <mkc.*.mk>` 语法（不可行）
- ❌ 记录为"musl 缺 sys/resource.h 排除 timer.c"（误判；必须实测头文件与 getrusage 可用性）
- ❌ 使用裸 `${CC}`/`${CFLAGS}` 环境变量编译（R33，CI 上为空）

## 验证
```bash
# 库构建 + 18 个上游测试（输出与 expect.out 一致）
awk -f arggram2c arggram.txt > arggram.c
clang -c -O2 -fPIC -I. -DMAA_MAJOR=4 -DMAA_MINOR=0 -DMAA_TEENY=0 -DSIZEOF_LONG=8 -DHAVE_HEADER_SYS_RESOURCE_H=1 <src>.c
llvm-ar rc libmaa.a <objs> && llvm-ranlib libmaa.a
clang -shared -fPIC -o libmaa.so.4.0 <objs> -lm
# 鸿蒙专项：自旋 ≥1.1s 后 tim_get_real ≥1.0 且 user+sys ≥1.0（getrusage 真实可用）
# bit_cnt=3（第 0/31/63 位置位，64 位 popcount 分支正确）
conan-verify libmaa 1.4.7   # 8 门禁全通过
```

## 适用边界
- 适用: mkc/mk-configure 体系的单目录 C 库（libmaa、dictd、dico 等 dict 项目生态），
  或任何顶层 Makefile 使用 `.for`/`.include <mkc.*.mk>` 的项目
- 不适用: 纯 GNU make、autotools、CMake、Meson 库（走各自标准流程）
- 上游固有行为（测试断言须避开，非平台缺陷）:
  - bit_tst 返回 int，第 63 位掩码 0x8000000000000000 截断为 0
  - timer.c DIFFTIME 宏对 tv_usec 整数除法，亚秒精度截断为 0；专项测试须跨整数秒边界

## 查重差异（相对既有条目）
- E097 custom-config-mk（BearSSL 自定义 Makefile conf/*.mk 手动安装）: 同为"自定义 Makefile 体系手动等价构建"，
  但不含 `.for` 循环、`<mkc.*.mk>` include、SIZEOF/头文件检测宏注入与 awk 生成源（arggram.c）的组合
- E151 manually-add-have-defines（CMake 检测失败手动补 HAVE_*）: 同为"手动补检测宏"，
  但仅覆盖 CMake 检测失败，不覆盖 mkc/BSD-make 与 GNU make 不兼容场景
- 新增差异: combination（.for+include mkc+检测宏注入+awk 生成源 组合）、
  boundary（mkc 特定语法、MKC_CHECK_SIZEOF/HEADERS 宏、arggram.c 生成）、
  test_migration（18 个上游测试程序在 OHOS 的编译/运行/expect.out 比对迁移）
