## 错误特征

按名字找不到 0.1 版本的 libusb 时，构建在三个阶段各报一种错（字面子串，engine 只做包含匹配）：

```text
# 配置期（configure/CMake 检查 usb.h）
checking for usb.h... no
configure: error: libusb-0.1 headers not found

# 编译期
cycfx2dev.h:18:10: fatal error: 'usb.h' file not found

# 链接期
/usr/bin/ld: cannot find -lusb
undefined reference to `usb_init'
undefined reference to `usb_open'
```

**关键判据**：报错只说明「没有按 `libusb` 这个名字找到 0.1 版本」，**不等于 OHOS 上不存在
可用的 0.1 API 实现**。OHOS 制品仓里该能力由另外两个包名提供，必须按 API 形态（`usb.h` +
`-lusb`）而不是包名字符串去核查。

## 触发条件

- 构建系统: 任意（autotools / cmake / 手写 Makefile 均可，只要链接 `-lusb`）
- 阶段: configuration / compilation / linking
- 源码特征: `#include <usb.h>`，或调用 `usb_init` / `usb_find_busses` /
  `usb_find_devices` / `usb_open` / `usb_bulk_*` / `usb_interrupt_*` 等 libusb-0.1 符号

## 根因分析

`ohpcd` 上发布的是：

| 包 | 版本 | 提供的文件（实测） | 角色 |
|----|------|--------------------|------|
| `libusb-compat` | 0.1.7 | `include/usb.h`、`lib/libusb.a`（静态，`fPIC=True`）、`lib/pkgconfig/libusb.pc` | 0.1 API 兼容层，定义的库名就是 `usb`（`self.cpp_info.libs = ["usb"]`） |
| `libusb` | 1.0.27 | `include/libusb-1.0/libusb.h`、`lib/libusb-1.0.so.0.4.0`（+ `.so`/`.so.0` 符号链接） | 真正的 USB 访问实现，linux_usbfs/netlink 后端 |

`libusb.pc` 自述即证明这种分层关系：

```text
$ grep -E 'emulated|Version|Requires.private|Libs:' $COMPAT/lib/pkgconfig/libusb.pc
emulated=1
emulated_by=libusb-1.0
Version: 0.1.7
Requires.private: libusb-1.0
Libs: -L${libdir} -lusb
```

`libusb-compat` 的 `package_info()` 声明 `libs = ["usb"]`，所以消费方链接参数就是
`-lusb`（静态 `libusb.a`）+ `-lusb-1.0`（传递依赖 `libusb/1.0.27` 的动态库），与上游
Makefile 里原有的 `LDFLAGS = -lusb` 语义一致。

## 与既有条目的差异（对 E485「stub 绕过」口径的前提变更说明）

仓库内已有 `knowledge/graph/E485.kv`（头部写明 `Status: UNMATCHED`，标题为
「OHOS 无硬件环境的外设库依赖 stub 绕过」，来源 avarice 2.14，时间戳 2026-08-22），其
推荐方案是：适配依赖 libusb-0.1 的软件时用 **stub 头 + stub 实现**（返回 -1/0）让编译
链接通过。

**要点在于 E485 正文自己写明了它的前提**，而不是它论证有错：

读该条目的命令：

```sh
$ grep -n '无法直接依赖' knowledge/graph/E485.kv
34:  无法满足（libusb-compat 无配方/不在制品仓——无法直接依赖）
```

即 E485 判断 stub 绕过的理由是「libusb-compat 无配方/不在制品仓——无法直接依赖」。该前提
在 2026-08-22 成立，**在 2026-09-11 已不成立**：`libusb-compat/0.1.7` 已经发布到 ohpcd
（本任务 W0 实测可安装 binary，且其包内 `libusb.pc` 自述 `emulated=1`）。因此本条的增量不是
「E485 错了」，而是**前提变更后应改用真实依赖**，并且要回头复核那些在前提成立期靠 stub
落地的包（如 avarice 2.14）——stub 形态下 USB 功能 100% 不可用。

以下三条实测反证用于确认「前提确已变更」：

反证 1 — **依赖真能装**（不是"能搜到"，而是按 OHOS profile 实际取 binary）：

```sh
$ conan install --requires="libusb-compat/0.1.7" \
    --profile:host="$HOST_PROFILE" --build=never -of <tmpdir>
Graph root
    libusb/1.0.27#0e6a7c47e7b3b5c19d0bdb3887145a1e - Cache
    libusb-compat/0.1.7#149f825ecfbaf5b475b12e115307cc06 - Downloaded (ohpcd)
libusb/1.0.27: Already installed! (1 of 2)
libusb-compat/0.1.7: Package installed eb099f95f7fe600de671f5b18336d91ea4efcb3a
Install finished successfully
```

反证 2 — **0.1 API 符号齐备**（不是"只有头文件没有实现"）：

```sh
$ nm -g --defined-only $COMPAT/lib/libusb.a | grep -cE ' T usb_'
27
$ for s in usb_init usb_find_busses usb_find_devices usb_open usb_close usb_control_msg \
           usb_bulk_read usb_bulk_write usb_interrupt_read usb_interrupt_write \
           usb_claim_interface usb_release_interface usb_set_altinterface usb_strerror; do
    nm -g --defined-only $COMPAT/lib/libusb.a | grep -qE " T $s\$" && echo "OK $s"; done | wc -l

```

反证 3 — **stub 要替换的功能在设备上真跑得起来**（无 USB 设备环境里 libusb 初始化成功）：

```sh
$ LD_LIBRARY_PATH=$LIBUSB1/lib ./cycfx2prog --list ; echo rc=$?
rc=0
# --list 内部依次调用 usb_init() → usb_find_busses() → usb_find_devices()，
# 三者都必须返回 >= 0 才会走到打印分支并 exit(0)；任何一步失败都会打印
# "usb_find_busses failed (rv=..)" 并以 1 退出（cycfx2prog.cc:212-222）。
```

`libusb-1.0.so.0` 里 linux 后端字符串命中 47 处（netlink/usbfs），`readelf -dW` 只有
`NEEDED libc.so` + `SONAME libusb-1.0.so.0`，说明这是完整的 musl 动态库而非占位库。

**差异结论**：E485 的 stub 方案在其自身声明的前提（「libusb-compat 无配方/不在制品仓」）
下是可理解的权宜之计，但该前提已随 `libusb-compat/0.1.7` 的发布而失效。前提失效后继续
沿用 stub 会让产物保住"能编译链接"却丢掉全部真实功能；本条主张的是**按 API 形态而不是
包名字符串去核查依赖能力**，并在确认能力已发布后直接使用真实依赖。两条口径在今天是互斥
判断，本条优先级更高。

本条的**唯一来源事件是 cycfx2prog 0.47**（2026-09-11）；起草时未在其他软件上实测过本条
口径。因此这里给出的是**建议**而非既成事实：E485 来源的 avarice 2.14，以及其他靠 stub
绕过 libusb-0.1 的历史适配，建议按本条重新核查依赖并评估是否切换为真实依赖（切换后需
重跑各自的设备验证）。E485 条目本身是否随之收窄适用范围，由知识库主编裁决。

## 解决方案

### 推荐方案

```python
def requirements(self):
    # libusb-0.1 API（<usb.h>、-lusb）由 compat 层提供，底层是 libusb/1.0.27
    self.requires("libusb-compat/0.1.7")     # R27：精确 name/version
```

链接参数从 `cpp_info` 取（直接依赖在前，静态库顺序不能反）：

```python
includedirs, libdirs, libs = [], [], []
for dep in self.dependencies.values():
    cppinfo = dep.cpp_info.aggregated_components()
    includedirs += cppinfo.includedirs
    libdirs += cppinfo.libdirs
    libs += cppinfo.libs          # ["usb"] → ["usb-1.0"]
```

最终产物（cycfx2prog 实测）：

```text
$ readelf -dW cycfx2prog | grep NEEDED
 0x0000000000000001 (NEEDED)  Shared library: [libusb-1.0.so.0]
 0x0000000000000001 (NEEDED)  Shared library: [libc.so]
```

`libc.so` 里已含 dl/pthread（musl），因此**不需要**额外补 libusb/libusb-compat 声明的
`system_libs`（`dl`/`pthread`）；实测 `clang t.c -ldl -lpthread` 也能通过，两者都不构成
设备上的阻断点。

### 回退方案

仅当制品仓确实取不到 `libusb-compat` binary 时，才在任务私有 prefix 从源码构建
libusb-compat 0.1.7（上游 autotools，需注意 HMDFS 下 `mktemp`/权限限制），**仍不使用 stub**；
拿到可用发布版 binary 后回到推荐方案。

## 注意事项（容易踩的三个坑）

1. **不要用包内 `.pc` 定位依赖**：`libusb-compat` 包内 `libusb.pc` 的
   `prefix=/storage/Users/currentUser/.cache/conan2/p/b/libus8c4e8f03c5cab/p` 是打包机路径，
   在本机不存在。`PKG_CONFIG_PATH` 指向包内 `lib/pkgconfig` 会让 pkg-config 报 Found 而
   给出死路径（workflow 第 5.1 节同型陷阱）。
2. **不要给依赖加平台条件编译**：`#include <usb.h>` 在 OHOS 上原样可用，实测零补丁通过
   编译（cycfx2prog 0.47 用 OHOS clang 15 原样构建，只有 2 条上游自带的
   `-Wunused-but-set-variable` 告警）。加 `__OHOS__` 分支属 R8 违规。
3. **静态 compat 层需要 fPIC**：`libusb-compat/0.1.7` 默认 `shared=False, fPIC=True`，
   链接 PIE 可执行文件正常；若下游改成 `shared=True` 需重新确认 `libusb.so` 是否与
   `libusb-1.0.so` 同名冲突（当前默认形态无此问题）。
