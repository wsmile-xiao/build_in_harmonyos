# E6339 — 旧版 FUSE 低层 API 迁移到 libfuse 3 的完整方法

> 状态：draft，仅作为路径 B / B 类知识库扩展候选材料提交评审。是否
> 认定为 B 类由知识库维护者和赛事评审决定。

## 错误特征

老项目从 FUSE 2 切到 libfuse 3 时，常见表现不是单一的“缺少头文件”，而是
多个接口在不同阶段连续暴露：

- `fuse_mount`、`fuse_kern_chan_new` 或旧 channel 类型不可用；
- `op_rename` 函数指针参数数量不匹配；
- `op_init` 的回调签名与 `struct fuse_lowlevel_ops` 不兼容；
- `fuse_dirent_size`、`fuse_add_dirent` 等旧目录项接口无法继续使用；
- 即使勉强链接成功，挂载、session loop 或目录读取仍可能在运行期失败。

## 触发条件

- 构建系统：Autotools 或手写 Makefile。
- 源码类型：低层 FUSE 文件系统、用户态块设备浏览器、文件系统守护进程。
- 阶段：编译、链接和首次挂载。
- 典型源代码信号：`FUSE_USE_VERSION 25`、`fuse_mount`、
  `fuse_kern_chan_new`、旧版 `op_rename` 和 `fuse_add_dirent`。

## 根因分析

FUSE 3 迁移不是简单的库名替换。旧代码把“创建 channel、挂载、进入事件循环、
卸载”拆成 FUSE 2 的 channel API；FUSE 3 推荐以 `fuse_session` 作为生命周期
对象。与此同时，低层回调会新增参数或改变数据编码契约，例如 `rename` 增加
flags，`init` 增加连接信息，目录项应由 `fuse_add_direntry` 根据请求上下文
计算长度和写入。

因此必须把三层契约一起核对：

1. 构建层：用 `fuse3.pc` 提供 include 和 link 参数，不再硬编码
   `/usr/include/fuse`。
2. API 层：统一 `FUSE_USE_VERSION=31`，更新回调签名和不支持 flags 的错误返回。
3. 生命周期层：按 `session_new -> set_signal_handlers -> session_mount ->
   session_loop -> session_unmount -> session_destroy` 管理对象。

## 推荐解决方案

### 1. 先迁移构建发现

使用 `PKG_CHECK_MODULES([FUSE], [fuse3 >= 3.0])`，由 Conan 的 `libfuse/3.18.2`
提供依赖。配方消费依赖元数据，不把 include 路径写死到 Linux 主机目录。

### 2. 再迁移 session 生命周期

将旧的 `fuse_mount`、channel 创建和 `fuse_session_add_chan` 路径替换为
session API。要保留清理路径，特别是 signal handler、mount 成功标志和
`fuse_opt_free_args`，避免失败路径泄漏。

### 3. 最后迁移回调和目录项

- `op_rename` 增加 `flags`，对未实现的 `RENAME_NOREPLACE` 或
  `RENAME_EXCHANGE` 返回 `EOPNOTSUPP`；
- `op_init` 接受 `struct fuse_conn_info *`，不用的参数显式 `(void)conn`；
- `readdir` 用 `fuse_add_direntry` 先查询 entry size，再写入缓冲区，并把
  `fuse_req_t` 保存到目录遍历上下文。

本库最终使用了上述三层方案，最终 Shadow CI 的 `conan create` 和消费者测试均
通过。

## 禁止做法

- ❌ 只把 `-lfuse` 改成 `-lfuse3`，却保留旧 channel 和目录项 API。
- ❌ 只修改头文件中的版本宏，不核对每一个低层回调签名。
- ❌ 只用 `--version` 或 `--help` 证明 FUSE 挂载功能已经通过。
- ❌ 用 Linux 主机的绝对 include 路径替代 Conan 依赖元数据。

这些做法可能让配置阶段变绿，却不能证明真实 session 和请求处理路径可用。

## 验证

```bash
git apply --check archives/e/ext2fuse/0.8.1/patches/0001-configure-fuse3.patch \
  archives/e/ext2fuse/0.8.1/patches/0002-src-fuse3-api.patch \
  archives/e/ext2fuse/0.8.1/patches/0006-fuse3-session-direntry.patch
rg -n "fuse_session_mount|fuse_session_loop|fuse_session_unmount|fuse_add_direntry" src
conan create archives/e/ext2fuse/0.8.1 --build=missing
```

在 OHOS 目标环境中，最终证据为 Shadow CI run
`codex-0.8.1-ext2fuse-0.8.1-shadow-20260911-101228-conan-20260911-233854-47932`
返回码 `0`，且 `test_package` 输出
`PASS: ext2fuse executable and argument parsing`。

## 适用范围和边界

本条适用于使用 libfuse 低层 API 的旧 C/C++ 项目。高层 FUSE API、内核 FUSE
模块和需要特权 mount namespace 的测试仍需单独分析。真实挂载还需要目标设备
提供可访问的 `/dev/fuse` 和可用文件系统镜像。
