# E329: Prune a bundled database client graph for OHOS CMake cross builds

> **Contributor**: 2301_79503900 | **Status**: DRAFT | **Created**: 2026-08-18
> **Severity**: blocking | **Category**: Conan / CMake / OHOS cross compilation
> **Knowledge draft path**: `knowledge/drafts/E329-draft-7950.md`

## Usage

Use this pattern when a large MySQL-compatible CMake source tree must provide a
client library or client tools package for an OHOS AArch64 target. The source
tree may bundle dependencies and helper projects, while the package only needs
the client surface.

This entry is Percona-specific at the workflow level. It combines several
package-graph decisions that are easy to miss when the upstream project treats
all Linux builds as full server builds. It does not replace generic HMDFS,
cross-compilation, or static C++ runtime entries.

## Inputs

- An exact upstream source archive and digest.
- An OHOS Conan host profile and a build-machine profile for helper tools.
- The intended package surface, such as a static client library and client CLI.
- The upstream CMake options controlling server, router, NDB, RPC, editline,
  bundled libraries, and unit tests.
- The dependency package paths needed by bundled `FindCurses` or TLS probes.

## Outputs

- A target-architecture client package with no unneeded server artifacts.
- Generated sources produced by build-machine CMake targets rather than target
  executables found through `PATH`.
- A reproducible CMake configure result with cross `try_run` values explicit.
- A C consumer test proving the installed target, static link closure, and
  target-side basic API execution.

## Symptoms

Typical failures include:

```text
Could NOT find Curses
MYSQL_CHECK_RPC pulls bundled tirpc into a client-only build
Permission denied while creating a convenience symlink on HMDFS
cannot execute binary file while running a generated target tool
try_run cannot execute the target program during cross compilation
```

## Root Cause

The upstream project uses one broad Linux build graph. A client-only OHOS
package can therefore enter server-oriented RPC and coredumper checks, create
shared helper targets that only exist to support the server build, or invoke a
target executable during source generation. CMake may also create `bin`, `lib`,
and plugin convenience symlinks that are rejected by HMDFS.

Bundled editline still uses CMake `FindCurses`, so selecting bundled editline
does not eliminate the need to provide the published ncurses include and
library paths. Finally, OHOS resolver and libc feature probes do not always
match the Linux APIs assumed by the upstream source.

## Implementation

1. Keep the upstream Linux OS module selected while using the OHOS compiler
   profile:

   ```text
   -DCMAKE_SYSTEM_NAME=Linux
   -DCMAKE_SYSTEM_PROCESSOR=aarch64
   -DOHOS=ON
   ```

2. Define the smallest supported package surface before configure:

   ```text
   -DWITHOUT_SERVER=ON
   -DWITH_ROUTER=OFF
   -DWITH_NDB=OFF
   -DWITH_UNIT_TESTS=OFF
   -DWITH_COREDUMPER=OFF
   ```

   For a client-only OHOS graph, skip unused RPC checks instead of patching
   bundled generated `tirpc` configure scripts.

3. Pass the actual published dependency paths to the CMake cache when bundled
   components use `FindCurses` or system TLS:

   ```text
   -DWITH_EDITLINE=bundled
   -DCURSES_INCLUDE_PATH=<ncurses-package>/include
   -DCURSES_NCURSES_LIBRARY=<ncurses-package>/lib/libncursesw.a
   -DCURSES_FORM_LIBRARY=<ncurses-package>/lib/libformw.a
   -DWITH_SSL=system
   ```

4. For every custom command, resolve a CMake target with `$<TARGET_FILE:...>`
   instead of relying on a bare executable name or the current directory.
   Never execute an AArch64 target helper on the build machine.

5. On OHOS/HMDFS, skip convenience symlink creation when the real runtime,
   library, and plugin output directories are already valid. Set the expected
   cross `try_run` result variables for checks such as `setns` and
   `clock_gettime` instead of running target binaries during configure.

6. Keep OHOS libc compatibility changes narrow. For example, select the
   resolver API path that exists on OHOS for DNS SRV support, and avoid broad
   Linux-header assumptions when the OHOS SDK provides an equivalent
   `netinet` interface.

7. Expose the real static link closure in Conan metadata. If a C API archive
   contains C++ objects, propagate the required C++ runtime libraries and
   verify the closure with a plain C consumer.

8. Make each helper target own the dependencies needed to compile its sources.
   A static unit-test helper that compiles bundled cURL sources must link the
   bundled cURL CMake target itself; linking cURL only from final test
   executables does not propagate include directories backward to the helper.
   System-wide headers can otherwise hide an incomplete target graph.

9. Keep platform conditions consistent between production and unit-test build
   graphs. If generated RPC headers require bundled SunRPC includes on OHOS,
   the test directory must enable those paths under the same condition as the
   production target; a Windows-only test condition can be hidden on systems
   that install RPC headers globally.

## Forbidden Approaches

- Do not set `CMAKE_SYSTEM_NAME=OHOS` when the upstream source only provides a
  Linux OS module and has no corresponding OHOS module.
- Do not execute target-architecture generators or use an unversioned system
  generator discovered through `PATH`.
- Do not patch bundled generated RPC scripts when the client-only graph does
  not consume RPC.
- Do not force HMDFS to create convenience symlinks or silently ignore a
  failed symlink operation.
- Do not claim full `mysqld` runtime or upstream server-test coverage when the
  package only contains the client surface.

## Verification

1. Apply the portability patch to a clean upstream source tree and run
   `git apply --check --unidiff-zero`.
2. Inspect the generated CMake commands to confirm host tools use
   `TARGET_FILE` and target libraries use the OHOS package paths.
3. Run the Conan create/package flow and verify the installed client headers,
   archive, and client tools.
4. Compile a plain C `test_package` against the installed Conan target and
   confirm the C++ runtime closure is complete.
5. Execute that consumer on an OHOS PC target, keeping build, link, target
   execution, CI, merge, and publication as separate claims.
6. For a full-server validation build, configure unit tests and compile every
   registered CTest target so missing direct dependency usage requirements are
   detected before test execution.

## Validated Example

Percona Server `8.4.10_10` uses this pattern for its `WITHOUT_SERVER=ON`
client package. The adaptation handles bundled editline/Curses discovery,
OHOS DNS SRV APIs, cross `try_run` checks, CMake helper-tool paths, HMDFS
symlink avoidance, and the static C++ client link closure. The Conan package
and C consumer were built successfully and the consumer executed on the OHOS
target with output `percona-client:8.4.10-10:80410:1`. Full server runtime
validation remains outside this package scope.
