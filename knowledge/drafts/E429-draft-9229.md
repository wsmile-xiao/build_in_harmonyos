# E429 — OHOS 上 Go ELF 必须自签名才能 execve；签名判定必须读 `.codesign` section 头

> 状态：**DRAFT**（待主编复核后提升为正式 E 条目）
> 来源：codex-probe 1.0.3 适配（2026-09-18，archives/c/codex-probe/1.0.3）
> 严重度：2（medium）—— 现象误导性极强，会把人推向错误排查方向

## 错误特征

典型症状只有一行，且**看起来像权限/挂载问题**：

```
/data/storage/el2/base/haps/entry/files/<pkg>-go/go-sdk/go1.26.5-arm64/go/bin/go: Permission denied
# shell 返回码 126
```

配套的误导性线索（都会让人误判）：

- `ls -l` 显示 `-rwxr-xr-x`（x 位齐全）
- `file` 显示正常的 `ELF executable, 64-bit LSB arm64, static`
- 二进制字节里 **确实能搜到** `codesign` 字样
- 同一路径下 clang 直接编译出的 C 程序**未签名也能正常执行**（对照实验结果相反，进一步误导）

另一条相关症状（签名后的配方阶段）：

```
PermissionError: [Errno 13] Permission denied: '.../go/bin/go'
    at os.chmod(path, 0o755)
```

## 触发条件

- 平台：OpenHarmony / HarmonyOS PC，aarch64
- 场景：任何需要 **execve** 的 ELF，且该 ELF 不是由本机 clang 现场编译的
  - **Go SDK 自举**（对照：worker 上预装的 go 位于受信任挂载，不触发）
  - **Go `go build` 产出的二进制**（在 OHOS 上执行/自测时）
- 发生阶段：`build`（工具链引导）→ `package` → `test_package`（冒烟测试执行产物）

## 根因分析

### 1. OHOS 拒绝执行未携带有效 `.codesign` section 的 ELF

实测对照（同机同路径，仅签名状态不同）：

| 二进制状态 | `go version` 结果 |
|---|---|
| 从 go1.26.5 官方 tarball 解压，**未签名** | `Permission denied`（rc 126） |
| `binary-sign-tool sign -selfSign 1` 之后 | `go version go1.26.5 linux/arm64`（rc 0） |
| `llvm-strip --strip-all` 之后再签名 | 同样 rc 0（strip 非必需） |

结论：**自签名是充分且必要的**；`strip` 不是前提条件（与 `archives/g/go/1.21.13/notes.md`
的“必须先 strip 再签名”表述不同——该表述把 strip 当作必要步骤，实测并非必要）。
本机 clang 产出的 C 程序未签名却可执行，说明该限制并非对所有 ELF 一视同仁，
按 Go 产物（含 Go 工具链自身）需要签名的经验操作即可。

### 2. ★ 真正隐蔽的坑：签名「判定」方式错误导致静默漏签

配方里常见的写法是**字节/字符串搜索**：

```python
def _has_ohos_signature(path):
    with open(path, "rb") as f:
        data = f.read()
    return b".codesign" in data or b".note.ohos" in data   # ← 假阳性
```

**Go 二进制内嵌了 macOS 工具链用的 `codesign` 字样**（Go 的 `os/exec`、
`crypto`/`debug/macho` 等标准库会把该名字作为字符串常量编进产物），
于是上面的判定对**从未签名的 Go ELF 也返回 True** → 配方认为“已签名” →
**静默跳过签名步骤** → 最终只剩一句 `Permission denied`（rc 126）。

此时所有的表面证据都自洽：文件有 x 位、字节里有 `codesign`、`file` 说是正常 ELF，
**唯一的出路是检查 ELF section 表**：

```bash
# 错误做法（假阳性）
grep -c .codesign <elf>          # 可能 >0，但那是字符串不是 section

# 正确做法
llvm-readelf -S <elf> | grep '\.codesign'
# 未签名：无输出
# 已签名： [16] .codesign   PROGBITS   0000000000000000 60e000 001000 00   0   0 4096
```

### 3. 次要坑：`os.chmod` 在这些路径上可能被拒

`/data/storage/el2` 上，进程 uid（worker 的匿名 uid）未映射进 passwd 库时，
对自己属主的文件 `chmod` 仍返回 `Permission denied`。由于 tar 解压/签名已保留 x 位，
**chmod 应当非致命**：包装成 `try/except OSError: pass`。

```python
try:
    os.chmod(path, 0o755)
except OSError:
    pass   # 权限位本就存在；HMDFS/el2 上 chmod 不可靠
```

## 解决方案

### 推荐方案（priority 1）

签名判定**只看真实 ELF section**，其余流程不变：

```python
def _has_codesign_section(self, path):
    out = subprocess.run(["llvm-readelf", "-S", path],
                         capture_output=True, text=True, timeout=30).stdout or ""
    return ".codesign" in out

def _sign_elf_if_ohos(self, path):
    if self._has_codesign_section(path):
        return True
    subprocess.run(["llvm-objcopy", "--remove-section", ".codesign", path],
                   capture_output=True, timeout=30)
    subprocess.run(["binary-sign-tool", "sign", "-selfSign", "1",
                    "-inFile", path, "-outFile", path + ".signed"],
                   capture_output=True, check=True, timeout=120)
    shutil.move(path + ".signed", path)
    try:
        os.chmod(path, 0o755)
    except OSError:
        pass
    return True
```

Go SDK 自举时对 **`bin/{go,gofmt}` 与 `pkg/tool/<os>_<arch>/*`** 全部执行；
产物二进制在 `package()` 前执行（本机 1.26.5 SDK 共 10 个 ELF）。

## 验证

```bash
# 1) 先确认 ELF 真的有 section（而不是只有字符串）
llvm-readelf -S <elf> | grep '\.codesign'

# 2) 执行验证（最关键）
<elf> version        # 期望 rc 0；未签名/漏签时 rc 126
```

## 禁止做法

- ❌ 用 `b".codesign" in data` / `grep -a` 判定是否已签名 —— Go 二进制假阳性，会静默漏签
- ❌ 见到 `Permission denied`（rc 126）先归因到挂载 noexec / 目录权限 / 属主问题
  —— 先跑 `llvm-readelf -S` 排除漏签
- ❌ 因 `os.chmod` 抛 `PermissionError` 就判失败 —— chmod 在此平台不可靠，应容忍
