# E6340 — 旧式 extern inline 在 OHOS Clang 下产生重复符号

> 状态：draft，仅作为路径 B / B 类知识库扩展候选材料提交评审。

## 错误特征

链接阶段出现类似日志：

```text
ld.lld: error: duplicate symbol: ext2fs_get_inode_bitmap_start
>>> defined at ext2fs.c ... ext2fuse-ext2fs.o
>>> defined at valid_blk.c ... libext2fs_a-valid_blk.o
```

同一类问题还可能表现为 `ext2fs_get_block_bitmap_start`、
`ext2fs_fast_test_block_bitmap` 等来自老式 bitmap 头文件的多个函数重复定义。
它通常只在最终链接阶段出现，单个 `.c` 文件编译可能完全正常。

## 触发条件

- 构建系统：Autotools、Makefile 或把内嵌静态库直接加入链接的工程。
- 编译器：OHOS Clang/LLVM 或其他采用 C99 及以后 inline 语义的现代编译器。
- 源码特征：头文件使用 `extern __inline__` 或 `extern inline`，同时工程还编译
  一个 `inline.c` 作为外部实现。

## 根因分析

这不是普通的“静态库链接顺序”问题。旧版 ext2fs 代码假定 GNU89 风格的
inline 语义：头文件中的 inline 函数用于调用点优化，库内 `inline.c` 提供
唯一的可链接实现。现代 Clang 按 C99 规则处理部分 `extern inline` 定义时，
多个翻译单元可能各自产生外部符号；当这些对象再与 `inline.c` 静态对象合并，
`ld.lld` 就报告 duplicate symbol。

排查时应先看符号来源，而不是盲目调整 `-l` 顺序：

```bash
nm libext2fs.a | grep ext2fs_get_inode_bitmap_start
```

如果同名函数同时出现在业务对象和库对象中，优先检查头文件的 inline 宏和
库是否提供 `inline.c`。

## 推荐解决方案

ext2fs 自己提供了 `NO_INLINE_FUNCS` 兼容开关。对 OHOS 目标编译时在
`CPPFLAGS` 中定义它，使头文件只暴露声明，使用 `inline.c` 生成的外部实现：

```text
CPPFLAGS += -DNO_INLINE_FUNCS
```

在 Conan 配方中应通过目标环境追加该宏，确保顶层源码、内嵌 `lib/ext2fs` 和
静态库对象看到一致的定义。不要只给某一个源文件加宏，否则仍可能出现一半
翻译单元生成 inline 定义、另一半使用外部实现的混合状态。

本库第一次 Shadow CI 的编译和补丁阶段已经通过，但链接阶段复现了该问题；
加入 `-DNO_INLINE_FUNCS` 后，最终 Shadow CI run 返回码为 `0`。

## 回退方案

如果项目没有 `NO_INLINE_FUNCS`，可以对明确依赖 GNU89 语义的代码验证
`-fgnu89-inline`。这应当是有符号证据支持的回退方案，不能凭经验全局添加。
对于同时包含 `inline.c` 的项目，优先寻找项目自己的“关闭头文件 inline 实现”
开关。

## 禁止做法

- ❌ 先加 `-fcommon`。它主要处理 C 暂定对象定义，不能等价替代函数 inline
  语义修复。
- ❌ 删除 `inline.c` 或随意删掉静态库对象。这样可能把 duplicate symbol 变成
  undefined reference。
- ❌ 只修改一个翻译单元的宏定义。宏必须覆盖所有包含相关头文件的对象。
- ❌ 把错误归因于 `--start-group/--end-group` 或库链接顺序而不查看 `nm`。

## 验证

```bash
nm libext2fs.a | grep ext2fs_get_inode_bitmap_start
make clean
CPPFLAGS="$CPPFLAGS -DNO_INLINE_FUNCS" make -j1
```

验证标准是最终程序链接成功，且链接命令不再出现同一 ext2fs inline 函数的
多重定义。ext2fuse 的消费者测试随后验证安装后的 `bin/ext2fuse` 可执行并能
正确处理版本、帮助和缺少参数路径。

## 适用范围和边界

本条适用于旧式 C inline 代码与静态库组合导致的 OHOS/Clang 链接失败。普通
全局变量的 tentative definition 应参考 `-fcommon` 类知识；C++ ODR 或头文件
模板实例化问题也应分别诊断。

## 与相似条目的区别

E163 处理的是 OHOS 内核头文件把 `__packed` 暴露为全局定义导致的重复符号；
本条处理的是项目自身旧式 inline 语义与 `inline.c` 外部实现的冲突。两者都
表现为 `ld.lld duplicate symbol`，但符号来源、诊断命令和修复开关完全不同，
不能用 E163 的内核头文件宏守卫替代本条的 `NO_INLINE_FUNCS`。
