# E2181: Bound OHOS Autotools triplets and filesystem-sensitive tests

## Symptom

A GNU Autotools release archive can reject `aarch64-linux-ohos` during
configure because its checked-in `config.sub` predates the OHOS triplet. The
same source can then build successfully, while mode-sensitive upstream tests
fail when the build is placed on a Windows-mounted filesystem: every chmod
result is observed as `0777` instead of the requested Unix mode.

## Root cause

The portability helpers, generated configure script, and test filesystem each
have separate platform contracts. `config.guess/config.sub` decide whether the
cross host is recognized; configure's temporary-directory umask affects target
HMDFS; and a Windows mount may not preserve chmod bits. A failure in one layer
does not establish failure in the others.

## Fix

1. Before configure, add the minimal `HarmonyOS`/`linux-ohos` recognition rules
   needed by the archive's helper scripts and apply the target-specific umask
   adjustment to the generated configure script.
2. Cross-compile with the OHOS SDK and explicit `--host=aarch64-linux-ohos`,
   then inspect the resulting ELF header and dynamic NEEDED entries.
3. Run permission-sensitive upstream tests from a native POSIX scratch tree,
   keeping their logs and hashes in the task's F-drive evidence directory.
4. Stage the exact target ELFs in a task-private root, use the native OHOS
   self-sign tool before the only launch, and execute a real archive
   create/extract consumer test.

## Validation

For cpio 2.15, the official archive hash was
`EFA50EF983137EEFC0A02FDB51509D624B5E3295C980AA127CEEE4183455499E`. The
OHOS cross build produced AArch64 PIE `cpio` and `rmt` binaries with only
`libc.so` in their NEEDED closure. Running `make -C tests check` from `/tmp`
completed all 17 tests; the same test on `/mnt/f` produced six mode-only
failures with observed `0777`, demonstrating the mount boundary. The consumer
round-trip then passed 6/6 assertions on the POSIX build.

## Applicability and safety boundaries

Use this pattern for Autotools C tools with generated GNU portability helpers
and tests that assert Unix permissions. A POSIX scratch run is only a valid
host-side test location; it cannot replace target transfer, native signing,
runtime execution, or release/postrelease evidence. Keep the source archive and
completed transaction immutable, and create a new run ID if the payload or
signer changes.
