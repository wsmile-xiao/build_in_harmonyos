# E350 — OHOS autoconf works-check 执行 conftest 被沙箱拦截：必须以 build≠host 交叉模式规避

## 错误特征

OHOS 交叉编译 autotools 库时，configure 以**原生模式**（`--build == --host`）运行时，
autoconf 的 C 编译器 works-check（`checking whether the C compiler works...`）会尝试
**执行** conftest 二进制，被 OHOS worker 沙箱拦截（无法 exec 自定义 ELF），报
`C compiler cannot create executables`。

该失败是 worker/运行模式相关的、非确定性：libXdamage 1.1.6 曾 7 次 CI **全部在
configure 期失败**；同批 CI 中 libxrender/0.9.12 交叉模式通过、libxcursor/1.2.3
原生模式失败，即为对照实证。

## 触发条件

- 构建系统: Autotools（带 configure 脚本），需要 OHOS 交叉三元组。
- configure 阶段: works-check 编译并运行最小 conftest。
- OHOS worker: 沙箱/运行环境拒绝执行自定义 ELF（与真机 SELinux 限制同性质，见 device 限制）。

## 根因分析

- autoconf 在 `checking whether the C compiler works...` 时编译并**运行**一个最小
  conftest。原生模式（`cross_compiling=no`，即 `--build == --host`）会真实执行；
  OHOS worker 拒绝执行，返回失败 → `C compiler cannot create executables`。
- `--build != --host`（如 `--build=aarch64-unknown-linux-ohos
  --host=aarch64-linux-ohos`）进入 `cross_compiling=yes` 分支，works-check **只链接
  不运行**即通过。
- 失败发生在 configure 早期，极易被误判为"clang 坏了 / worker 环境问题"，实际上与
  编译器本身无关，是运行模式问题。

## 解决方案

### 1) 强制交叉模式

conanfile 的 generate() 传入 `--build=aarch64-unknown-linux-ohos
--host=aarch64-linux-ohos`（或等价三元组），保证 build≠host。config.guess 对
HarmonyOS 返回 `aarch64-unknown-linux-ohos`（config.guess 补丁见 E344）。

### 2) 判定是否进入交叉分支

configure 日志出现 `checking whether the C compiler works... yes` 即通过；若报
`C compiler cannot create executables` 且 configure 极早期（几秒内）即 FAIL，优先
检查是否原生模式（`--build==--host`），而不是盲目重发 /rebuild。

### 3) 与 worker 抽签区分

worker 环境问题（clang 链接管线损坏、/tmp 不可写）也报同一串错误，但发生在 configure
早期、**跨配方稳定复现**；本陷阱只影响 autotools 且只在原生模式。判定方法：同一配方
改为 build≠host 后即稳定通过 → 是本陷阱，不是 worker。

## 禁止策略

- 不因 `C compiler cannot create executables` 盲目重发 /rebuild（原生模式下重复多少次都失败）。
- 不让 configure 以 `--build==--host` 原生模式运行（必触发 works-check 执行 conftest）。
- 不改上游 configure.ac 来跳过 works-check。
