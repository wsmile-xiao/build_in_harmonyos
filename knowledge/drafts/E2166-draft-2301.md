# E2166 - Expose a transitive public-header provider through pkg-config

## Symptom

The target build finds `opusfile` and then fails while compiling a consumer of
its public header:

```text
opusfile.h:109:11: fatal error: 'ogg/ogg.h' file not found
```

The Conan graph already contains `libogg/1.3.5`, but the generated
`opusfile.pc` contains only:

```text
Requires: opus
```

## Root Cause

Graph presence is not the same as consumer visibility. `opusfile.h` publicly
includes `ogg/ogg.h`, while the selected provider metadata does not expose the
Ogg module through the generated component contract. Setting transitive header
or library traits on the existing edge did not change the generated `.pc`
files.

After making `libogg` a direct consumer requirement, Conan exposes the edge but
uses the package name `libogg` by default. The upstream pkg-config module name
needed by the component is `ogg`.

## Fix

1. Add the exact published `libogg/1.3.5` as a direct requirement.
2. Before `PkgConfigDeps.generate()`, set:

   ```python
   pkgconfig.set_property("libogg", "pkg_config_name", "ogg")
   ```

3. Require a regular generated `ogg.pc` and reject `libogg.pc` as the expected
   module projection.
4. Require `opusfile.pc` to contain the exact unique sequence
   `Requires: ogg opus`; do not silently invent a missing edge during rewrite.
5. Keep the existing narrow `include/opus` and `-lopusfile` repair scoped to the
   affected provider.

## Safety Boundaries

- Do not patch the upstream `#include <ogg/ogg.h>` line.
- Do not use global compiler or linker flags for one provider edge.
- Do not add an OHOS-named source conditional.
- Do not treat graph success, generated `.pc` files, or local W0 as target
  build/runtime evidence.
- Any recipe or dependency change requires a fresh current-snapshot W3 before
  its result is reported as passing.
