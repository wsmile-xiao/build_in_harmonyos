# E2166: Windows-to-OHOS Qt5 cross builds must separate target Qt from native host moc/rcc/uic

> Status: DRAFT | Contributor: 2301 | Date: 2026-08-28

## Symptom

During a Windows-to-HarmonyOS PC AArch64 CMake cross-build, Qt AUTOGEN tries
to execute the `moc` supplied by the target Qt package. The failure is an
execution-format or host-tool mismatch, represented by:

```text
Automatic MOC ... moc
Exec format error
```

The same package can configure successfully and still fail when CMake starts
the generator. This is not evidence that the target C++ compiler or Attica
source is incompatible.

## Scope

This rule applies when a Windows build host cross-compiles a Qt5-based CMake
project to OHOS AArch64 and the Conan Qt package is the target dependency. It
covers CMake AUTOGEN, resource compilation, and UI generation, so it applies
to `moc`, `rcc`, and `uic`. A native Qt installation matching the target Qt
release must be available on the Windows host. Native same-architecture builds
and projects that do not execute Qt generators are outside this rule.

## Root Cause

CMake executes Qt generators during the build on the host, while the Qt
package in the target dependency graph is built for OHOS AArch64. Its `moc`,
`rcc`, and `uic` are target executables and cannot run as Windows processes.
Using one Qt prefix for both roles confuses target runtime files with host
build tools. The roles must be represented separately even though both come
from a compatible Qt release.

## Fix

1. Keep the OHOS Qt package as the target `find_package` and link dependency.
2. Obtain a native Windows Qt host-tools directory from the matching Qt5
   release, containing `moc.exe`, `rcc.exe`, and `uic.exe`.
3. Pass that directory through the recipe configuration, for example
   `user.attica-kf5:qt_host_tools_dir="$QT_HOST_TOOLS_DIR"`.
4. Map the three native tools to
   `CMAKE_AUTOMOC_EXECUTABLE`, `CMAKE_AUTORCC_EXECUTABLE`, and
   `CMAKE_AUTOUIC_EXECUTABLE` in `CMakeToolchain` before configure.
5. Add the native tools directory to the build-time `PATH` only while CMake
   and the upstream build run. Keep target Qt libraries in the target runtime
   and link paths.
6. Fail closed when any of the three native tools is missing, and verify that
   the tool versions match the target Qt release.

## Forbidden Shortcuts

- Do not point `CMAKE_AUTOMOC_EXECUTABLE` or `QT_HOST_PATH` at the target
  AArch64 Qt package.
- Do not run the target `moc` through an emulator or silently fall back to a
  host tool from a different Qt release.
- Do not remove AUTOGEN, disable all tests, or modify generated sources just
  to avoid executing the generator.
- Do not treat a successful configure as proof that the host generators are
  executable; the build must reach the AUTOGEN steps.

## Validation

Use a clean Conan build with the OHOS host profile and a native Qt host-tools
directory:

```text
conan create archives/a/attica-kf5/5.116.0 -pr:h=ci/conan/profiles/ohos-aarch64 -c user.attica-kf5:qt_host_tools_dir="$QT_HOST_TOOLS_DIR"
```

Before configure, inspect the target and host tool identities separately with
the platform's ELF/PE inspection tools. After configure, inspect the generated
CMake cache and build commands to confirm the three AUTOGEN variables point to
native host tools. The Attica adaptation that produced this draft completed
86/86 target objects and generated 94 package files; its target consumer and
the `configtest` and `persontest` target runs also returned successfully.

The negative check is equally important: if the target AArch64 `moc` is
selected on Windows, the build must fail at the generator boundary rather than
silently skipping generated files. This draft does not count the separate
network-dependent `providertest` result as a host-tool validation pass.

## Safety Boundary

This knowledge only describes build-time host-tool selection. It does not
authorize emulation, arbitrary executable downloads, global environment
mutation, target-device access, signing, publication, or a full upstream test
claim. Target Qt libraries remain target artifacts and must be validated by a
matching OHOS runtime separately. Any missing or version-mismatched host tool
must remain a failed configuration rather than being hidden by a skip.
