# E573 — conan test_package 链接消费者程序时 lld 载入 libxml2.so.16 失败

- **条目类型**：平台/工具链环境（L1 平台真理）
- **严重级**：3（阻塞，CI 红但本地绿）
- **发现版本**：cpu 1.4.3（PR #9639，CI run #44867）
- **关联条目**：E002（/tmp 不可写）、E046（HMDFS chmod 不生效）、E490（可执行位）
- **状态**：草稿（待主编审核转正）

## 1. 现象

CI `conan-build-test` 红在 **test_package 阶段**，包本身的 `conan create`（构建+安装+打包）全部通过：

```
Error loading shared library libxml2.so.16: (needed by
  /data/service/hnp/ohos-sdk.org/ohos-sdk_26.0.0.18/ohos/native/llvm/bin/lld)
Error relocating /data/service/hnp/ohos-sdk.org/ohos-sdk_26.0.0.18/ohos/native/llvm/bin/lld:
  xmlFreeDoc: symbol not found
```

同一提交**重复触发 CI 结果不同**（#44867 ❌ / #44873 ✅），典型的"本地绿、CI 红、重跑又绿"。

## 2. 根因

1. `test_package/test()` 用 `${CC:-clang}` 现场编译消费者程序；clang 驱动会调用 **lld** 完成链接。
2. lld 自身是动态链接程序，**运行时依赖 SDK `llvm/lib` 下的 `libxml2.so.16`**。
3. conan test 阶段的 runenv（`conanrun.sh`）只导出**包目录**（cpu/openldap 的 lib），不含工具链 lib 目录；lld 是否能启动，取决于调用它的 shell 恰好带没带这个目录 → **环境依赖 → 间歇性失败**。
4. musl 的搜索语义放大了这一点：`LD_LIBRARY_PATH` 中一旦命中**同名但不可加载**的条目（文件损坏、架不匹配），musl **硬失败**，不再回退 RPATH/默认路径；而空条目等于"当前目录"、相对条目按 cwd 解析，都会让搜索结果随环境漂移。

## 3. 本地复现（与 CI 报错逐字一致）

```bash
# 造一个"同名但不可加载"的 libxml2.so.16，放在搜索路径最前
mkdir -p "$HOME/tmp/fakexml" && : > "$HOME/tmp/fakexml/libxml2.so.16"

# 复现
LD_LIBRARY_PATH="$HOME/tmp/fakexml" clang -o consumer consumer.c -L"$PREFIX/lib" -lcputil
# → Error loading shared library libxml2.so.16: (needed by .../llvm/bin/lld)
#   Error relocating .../lld: xmlFreeDoc: symbol not found

# 把工具链 lib 目录前置后同样命令立即成功
LD_LIBRARY_PATH="$SDK/ohos/native/llvm/lib:$HOME/tmp/fakexml" clang -o consumer consumer.c ...
# → 退出码 0
```

这条复现是关键：**它不是"网络/权限"抖动，而是 loader 搜索路径的确定性行为**，因此必须用环境无关的写法修掉，不能靠重跑 CI。

## 4. 修复

`test_package/test.sh`（链接前）：

```sh
CC="${CC:-clang}"
cc_bin="$(command -v "${CC}" 2>/dev/null || true)"   # 兼容裸命令名
[ -n "${cc_bin}" ] || cc_bin="${CC}"
cc_real="$(readlink -f "${cc_bin}" 2>/dev/null || echo "${cc_bin}")"
cc_lib="$(cd "$(dirname "${cc_real}")/../lib" 2>/dev/null && pwd || true)"
if [ -n "${cc_lib}" ] && [ -e "${cc_lib}/libxml2.so.16" ]; then
    LD_LIBRARY_PATH="${cc_lib}${LD_LIBRARY_PATH:+:${LD_LIBRARY_PATH}}"
    export LD_LIBRARY_PATH
fi
```

三重加固：

1. **前置工具链 lib 目录**——让 lld 的依赖由脚本自己保证，不再依赖调用方 shell。
2. **GNU ld 兜底**——若仍报 libxml2（lld 完全起不来），用 `clang -fuse-ld=bfd` 重链一次；该链接器不依赖 libxml2，产出二进制语义等价，测试仍然是"真实编译 + 真实执行"。
3. **`chmod +x` 新二进制**——HMDFS 上链接器不保证留可执行位（E046/E490），GNU ld 路径实测无 x 位，会表现为 `Permission denied`。

`test_package/conanfile.py` 同步修正：`cpp_info.libdirs/bindirs` 是**相对名字**，拼进 `LD_LIBRARY_PATH/PATH` 前必须 `os.path.join(package_folder, d)`，并过滤空条目（空条目 = 当前目录）。

## 5. 验证

| 场景 | 结果 |
|---|---|
| 干净环境（`env -i` + 无 CC，仅包目录在搜索路径） | 11 passed, 0 failed |
| 敌对环境（坏 `libxml2.so.16` 置于搜索路径首位，复刻 CI 失败条件） | 11 passed, 0 failed |
| 真实 conan test 阶段（`conan test test_package cpu/1.4.3 -pr:a=…`） | 11 passed, 0 failed |
| 修复前同条件对照（仅坏 libxml2，无工具链 lib 目录） | 链接失败，报错与 CI 逐字一致 |

## 6. 防范清单（同类配方通用）

- 测试脚本里**不要**把 `LD_LIBRARY_PATH` 写成 `lib:lib`、`.:lib` 这类相对/空条目；一律用绝对包目录。
- 测试脚本若现场调用 `${CC}`/`clang` 编译并链接，**必须**自行保证工具链依赖（`$(dirname $(readlink -f $(command -v clang)))/../lib`）在 loader 路径上。
- "本地绿 CI 红且重跑可变"时，先怀疑**链接/加载期环境**，用上面的"坏同名库"复现法把问题钉死，再改脚本；不要靠反复重推 CI 撞运气。
