# E6402 — autotools 配方用 LIBS 注入外部依赖补齐静态闭包时缺 -L 路径 → configure 首轮编译器试探失败（C compiler cannot create executables）

## 错误特征

configure 在探测编译器可用性时即失败（尚未进入任何功能检测）：

```
configure:3985: /data/service/hnp/bin/clang -fPIC -O2 ... -L<profile 用户级目录> conftest.c -lcrypto
ld.lld: error: unable to find library -lcrypto
clang-15: error: linker command failed with exit code 1
configure:4027: result: no
configure: error: in `/…/build':
configure: error: C compiler cannot create executables
```

同一 `config.log` 的缓存值暴露关键信号：

```
ac_cv_env_LIBS_value=-lcrypto
ac_cv_env_LDFLAGS_value=-L<profile 用户级目录>      # ← 缺 <dep>/lib
```

## 触发条件

- 构建系统：Autotools 三方库，配方**在 configure 期**通过 `LIBS="-l<dep>"` 注入外部依赖
  （用于补齐静态链接闭包；上游只把该库写进共享插件链接变量时常见）
- 依赖库位于 Conan 缓存路径（不在系统默认搜索路径）
- 工具链：OHOS clang 15 / 任意 clang + lld（ld.lld 报错措辞）
- 阶段：configuration，且**早于**任何功能探测

## 根因分析

Autoconf 的「whether the C compiler works」试探（configure 约 3985 行）执行的命令是
`<CC> $CFLAGS $CPPFLAGS $LDFLAGS conftest.c $LIBS`。`LIBS` 从 configure 第一条编译命令起
就生效，而 `LDFLAGS` 此时**不含**该依赖的 libdir —— `AutotoolsToolchain` 不会把依赖的
`cpp_info` libdir 自动并入首轮试探（实测 LDFLAGS 只有 profile 的用户级 `-L`）。

于是 linker 找不到 `-l<dep>` → 试探失败 → Autoconf 以「C compiler cannot create
executables」收场。该措辞把**链接搜索路径缺失**伪装成**编译器不可用**，是主要误判来源。

判别口径：`config.log` 里失败命令行含你注入的 `-l<dep>`，且 `-L` 列表中没有该依赖路径；
而用同一源码树手工编译（显式带 `-L<dep>/lib`）可正常通过。

## 修复方案

Conan 配方 `generate()` 中，把该依赖的 include/lib 显式并入工具链旗标（保留 LIBS 注入，
它同时服务 make 阶段的静态链接闭包）：

```python
def generate(self):
    tc = AutotoolsToolchain(self)
    dep_root = str(self.dependencies["<dep>"].package_folder)
    tc.extra_cflags.append("-I%s/include" % dep_root)   # 注意：没有 extra_cppflags
    tc.extra_ldflags.append("-L%s/lib" % dep_root)
    tc.configure_args.extend([...])
    tc.generate()
```

无 Conan 时等价写法：configure 阶段不设 LIBS，改在 make 阶段传
`make -j1 LIBS="-l<dep>"`。

## 验证

```
grep -n "conftest.c" <build>/config.log | grep -o "\-l[a-z0-9_-]*"   # 修复后同时出现 -L<dep>/lib 与 -l<dep>
configure 退出码 0；make 通过；下游静态链接无 undefined reference
```

实测（cyrus-sasl-scram 2.1.28，OHOS aarch64）：修复前 `conan create` rc=1 且 build() line 194
抛异常；`generate()` 补 `extra_ldflags/-L`+`extra_cflags/-I` 后 `conan create` rc=0（102s），
test_package 9/9、conan-verify G0-G3 PASS、W3 本地 CI PASS。

## 适用边界与反例

- 适用：任何 autotools 配方在 **configure 期**用 `LIBS="-l<dep>"` 主动注入外部依赖的场景
  （尤其是依赖位于 Conan 缓存、不在系统搜索路径）。
- 不适用/反例：配方不在 configure 期注入 LIBS（只在 make 阶段传）时不触发；依赖在系统
  默认路径（`-L/usr/local/lib` 恰好有）时不会复现 —— 这正是「本地手工 build 脚本能过、
  conan create 失败」差异的来源（手工脚本额外显式传了 `-L<dep>/lib`）。
- 与 `DRAFT-iverilog-13.0-autotools-host-libs-forbuild-static-readline` 场景①的区别：那条是
  **宿主编译器（*_FOR_BUILD）被目标库的 -l 污染**，解法是清空 configure 期 LIBS/隔离 host
  flags；本条是**目标编译器的 -l 生效但缺 -L 搜索路径**，解法是补齐 -L/-I。二者错误签名
  相同、处置相反，必须按「失败命令行里 -l 是给谁用的」区分。
- 与 `E524`（共享 SYS_PREFIX 注入污染）的区别：E524 是注入目录本身含坏库（共享
  `/usr/local`），本条是依赖库路径根本没进 LDFLAGS。

## 查重差异

- `knowledge/graph/`：`engine "unable to find library -lcrypto / C compiler cannot create
  executables"` 命中 E001（PATH 无 cc，编译器选择问题）、E524（共享 prefix 污染 + REQUIRE
  依赖缺失）—— 根因、方案均不同。
- `knowledge/drafts/`：`DRAFT-iverilog-13.0-autotools-host-libs-forbuild-static-readline`
  命中相同错误签名（场景①），但其根因是宿主/目标 flags 混用、解法为清空 LIBS；本条为
  「注入生效但缺 -L」，解法为补齐 -L/-I，且额外记录 `AutotoolsToolchain` 无
  `extra_cppflags` 属性这一实现细节（避免二次踩坑）。
- 结论：`new_draft`（路径 B 知识库扩展），与既有条目互补而非重复。
