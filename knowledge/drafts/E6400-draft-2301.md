# E6400 - Bind capability probes to production backend boundaries

## Symptom

A cross-platform application reports its version successfully and a provider
package exposes generic SDL, EGL, or audio headers. The adaptation is then
described as having native graphics, audio, or architecture-specific execution
even though the application-level paths were never exercised. A second false
positive occurs when an audio callback writes a waveform into its destination
buffer: the callback becomes non-zero regardless of whether the application's
mixer produced PCM. A dynamic-core log line can be equally misleading when a
guest workload was not executed or the runtime selected a normal-core fallback.
Numeric environment fields have a separate failure mode: relying only on
`strtoull` accepts a leading minus sign and can turn it into an unsigned
maximum. A surface identifier or dimension therefore needs a lexical
all-digits check before numeric range validation.

## Root Cause

Version reporting proves only that an executable can start far enough to print
metadata. Header presence proves neither that a backend was compiled nor that
the packaged application selected it. Runtime capability claims therefore need
an observable boundary in the production path. For graphics, the relevant
boundary is a successful frame presentation after NativeWindow and renderer
creation. For audio, it is a real provider callback receiving samples that
originated in the application's mixer. For dynamic recompilation, it is the
combination of entry into the selected production core and an output produced
by a guest instruction stream.

## Fix

1. Gate all probes with explicit test-only variables and keep the normal user
   execution path unchanged.
2. Validate the NativeWindow surface identifier and dimensions before SDL
   initialization. Require `SDL_VIDEODRIVER=nativewindow` and an OpenGLES2
   renderer, then emit a marker only after `SDL_RenderPresent` or the OpenGL
   swap returns. Reject dummy, offscreen, software-only, and missing markers.
3. Select `SDL_AUDIODRIVER=ohaudio` and add a bounded deterministic signal at
   the application mixer output before final conversion. In the callback,
   inspect finite samples with byte-preserving reads and emit a marker only
   when non-zero PCM is observed. Never write a synthetic waveform in the
   callback.
4. Select `core=dynamic`, mark entry into the production dynamic run function,
   and execute an autoexec guest command that prints a sentinel. Require both
   markers from the same invocation.
5. Keep the four consumer checks in one installed-package flow with a strict
   `4/4` terminal. A provider fixture remains diagnostic and cannot replace
   the packaged application run.
6. Enforce the same positive-decimal contract in the production entry point,
   not only in the shell wrapper: reject empty, signed, non-decimal, zero, and
   overflow values before passing backend hints to SDL.

## Validation

The DOSBox Staging successor implements the above contract in the production
SDL main loop, mixer, and dynamic-core sources. The NativeWindow entry point
performs an all-digits and positive-range check before `strtoull`; a standalone
C++20 probe test rejects empty, signed, non-decimal, zero, and overflow values.
The patch applies cleanly to the pinned v0.82.2 archive. A host fixture with all four markers returns
`DOSBOX_CONSUMER_FLOW|4/4|PASS`; removing the audio marker returns non-zero.
The target W3 remains a required independent gate: only a fresh signed package
run can establish NativeWindow presentation, OHAudio callback delivery, and
dynamic guest execution on OpenHarmony.

## Applicability and Safety Boundary

This pattern applies to callback- and presentation-based runtimes where the
application owns a mixer or render loop. It does not prove speaker acoustics,
display calibration, input latency, a particular game's media content, or
every instruction generated by a dynamic compiler. It also does not authorize
dummy/offscreen providers, callback-buffer synthesis, static markers, or
cross-run evidence splicing. Target identity, package hash, test denominator,
and one-shot W3 transaction boundaries remain mandatory.
