# E7010 — 有静态全局初始化保护的 C++ 库必须让目标 probe 运行在独立进程

## 错误特征

真机上的共享插件已经通过签名、`$ORIGIN` RUNPATH 和动态符号解析，但 runner
串行调用 upstream 与 consumer 时出现：

```text
upstream_rc=0 consumer_rc=101
consumer_exception_stage=1 what=Curl already globally initialized
```

## 触发条件

- C/C++ 库用 RAII `global` 对 `curl_global_init` 等进程级初始化做静态状态保护。
- 一个 Python/ctypes runner 在同一解释器内先后加载并调用多个独立 probe。
- 首个 probe 的析构执行清理，但库的静态“已初始化”标志仍保持为真。

## 根因分析

插件装载和第一个 upstream probe 都成功，说明 ELF 签名、依赖闭包、RUNPATH 和
目标代码入口均已通过。失败发生在第二个 probe 的构造阶段：库把 global 初始化
视为每进程一次，而测试 harness 却把两个应独立的测试组放在同一进程中。此时
`consumer_rc=101` 是进程生命周期污染的确定性结果，不是消费者 API 的独立结论。

## 解决方案

让父 runner 为每个 probe 启动独立的 `python3 -c` 子进程，子进程各自加载同一
哈希绑定插件并返回真实终态；父进程只汇总 stdout/stderr 和返回码。这样每个
probe 获得新的 C++ 静态状态，同时不需要修改库内部初始化语义。

```python
result = subprocess.run(
    [sys.executable, "-c", code, plugin_path, *args],
    cwd=str(root), env=env, check=False,
)
```

运行契约仍必须绑定插件、依赖库、runner、输入文件的 SHA-256，并在同一目标端点
执行一次唯一 launch；若原 runner 已 launch，必须冻结并释放原 run，再创建 successor。

## 本次验证

`w3-successor-015` 在 `10.62.150.125:8022` 上使用独立子进程 runner，真实输出为
`upstream_rc=0 consumer_rc=0`，consumer 阶段 `global/callback/handle/tag` 全部执行；
runner 退出后 PID 缺失，随后远端根释放并独立回读为 `ABSENT`。此前 `w3-successor-014`
已唯一 launch 且冻结为 harness 生命周期污染失败，未重放。

## 适用范围与安全边界

适用于带进程级单例、静态初始化保护或不可重入全局状态的 C/C++ 目标 probe。它不
授权修改生产库的初始化/析构语义，也不允许在同一进程中拼接不同测试分母；如果
子进程创建失败，应报告真实环境失败并按 W3 successor 规则处理，不能把异常改成
PASS。
