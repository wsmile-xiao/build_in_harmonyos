## 使用说明

本条目适用于：在多核调度环境中使用每核硬件周期计数器（ARM PMCCNTR_EL0、
x86 RDTSC/RDTSCP、RDPMC/perf counter）做高精度计时，并发现"后一次读数
小于前一次读数"（计数器回退 / 巨大负差值）的场景。

当你的测试失败日志中出现：

- 周期差值为巨大负数（如 `dc` 约为 -7e13 量级，即睡后计数仅为睡前的 ~51%）；
- 后一次 cycle 读数小于前一次（跨 sleep/nanosleep 后读数下降）；
- `counter went backwards` / `decreased` / `non-monotonic` 类断言失败；
- `persecond-consistency` 或 `tracesetup` 类跨调度点断言失败；

先按本条目的"通用处理算法"走一遍，再决定是修测试契约还是修库实现。
核心判断标准：**这是测试断言超出了 API 承诺的范围，还是计数器在单核
紧循环内真的回退了？** 前者修测试，后者修库（或换 backend），两者
绝不能混淆。

## 适用范围

满足以下全部条件的场景适用本条目：

- 使用每核硬件周期计数器：ARM PMCCNTR_EL0（MRS 读取）、x86
  RDTSC/RDTSCP、RDPMC/perf counter 后端；
- 涉及 CPU cycle counter 库（libcpucycles 及同类）、profiler、
  benchmark timer；
- 两次读取之间存在 sleep、I/O、锁等待或其他调度点；
- 运行环境允许线程在 CPU 核心间迁移（未固定 affinity）；
- 多核调度环境中做高精度计时的消费者测试。

## 不适用范围

以下场景**不适用**本条目，应另寻原因：

- **API 明确承诺跨核全局单调**：若库文档承诺全局单调（如某些 TSC
  封装库声明 invariant TSC），回退就是库缺陷，直接报 bug；
- **系统级 CLOCK_MONOTONIC**：clock_gettime(CLOCK_MONOTONIC) 是
  内核维护的系统级单调时钟，天然跨核单调，回退属内核 bug 或时钟
  源问题，与本条目无关（编译期未定义问题见 E138/E152）；
- **已固定 CPU affinity 且确认未迁核**：若 sched_getcpu() 前后一致
  且 affinity 绑核已回读验证成功，紧循环外的回退才可能与本条目
  机制无关，需单独排查；
- **真正的紧循环相邻读取仍发生回退**：这是计数器/库的真实故障，
  走 fail-closed，不得引用本条目开脱；
- **计数器溢出、权限错误或后端初始化失败**：溢出是位宽问题
  （wrapper.c 注释也把 overflow 与 core swap 并列为两类 !ok 原因），
  权限错误如 PMU 访问被禁，属 E270 类运行时不可用问题；
- **CLOCK_SGI_CYCLE 返回 EINVAL**：这是 SGI 周期时钟在运行时
  不被支持的问题，属于 E270，与本条目机制无关。

## 错误表现

libcpucycles 20260625 首测的真实失败形态：

- `persecond-consistency` 断言失败：50ms nanosleep 前后周期差 dc 与
  `persecond*0.05` 交叉验证，实测睡后计数（~7.4e13）**小于**睡前计数
  （~1.4e14），即 dc 为巨大负数，约为睡前值的 51%；
- 旧式 `after >= maxv`（tracesetup 检查的旧形式）：跨 sleep 断言
  同样出现后一次读数小于前一次；
- 注意：这些是**本仓库初版 test.c 的断言名与行为**，其他库的日志
  文本可能不同，但"跨调度点负差值 + 每核计数器"的组合特征一致。

通用签名（error_signature）覆盖：

- 周期差值为巨大负数；
- 后一次 cycle 读数小于前一次；
- `counter went backwards` / `decreased` / `non-monotonic`；
- `persecond-consistency` / `tracesetup` 对应失败。

## 根因分析

1. **硬件周期计数器可能按 CPU 核心独立维护**。ARM PMCCNTR_EL0 是
   per-core 寄存器，各核心独立维护自己的计数起点/偏移；x86 TSC 的
   跨核同步也只是厂商实现保证（constant_tsc/nonstop_tsc 需单独探测），
   不是体系结构保证。
2. **sleep、I/O、锁等待或调度点可能导致线程迁核**。线程让出 CPU 后，
   调度器可自由把它放回任意核心。
3. **新旧核心计数起点不同**。迁核后读到的绝对值与旧核不可比较——
   本案例实测睡后值约为睡前值的 51%，说明新核计数起点远低于旧核。
4. **跨调度点直接比较绝对周期值可能回退**。上述三个条件叠加：
   每核计数器 + 调度点 + 起点不同 ⇒ 负差值。
5. **API 只声明 unspecified epoch 时不保证跨核全局单调**。
   libcpucycles man page 的契约是 "an estimate ... since an
   unspecified time in the past"——没有承诺跨核心、跨调度点的
   绝对值全局单调。上游 wrapper.c 的选择循环注释也明确承认
   "!ok can be caused by overflow or by core swap"。
6. **因此这类失败是测试契约错误，不应直接判定为库实现错误**。
   断言把 API 未承诺的行为当作契约检查，产生无法通过修库解决的
   伪失败。

## 通用处理算法

1. **确认当前 backend 是每核计数器还是系统级单调时钟。** 读库的
   backend 文档或实现（如 libcpucycles 的 options.inc 列出各后端；
   arm64-pmc 读 per-core PMCCNTR_EL0）。
2. **核对 API 是否承诺跨核全局单调。** 找到手册/头文件的契约表述。
   只承诺 "unspecified epoch" 则不承诺跨核全局单调。
3. **识别两次读取之间是否存在 sleep、I/O、锁等待或其他调度点。**
   sleep/nanosleep、read/write、锁等待都给调度器迁核机会。
4. **对每核计数器使用无阻塞紧循环的相邻读取验证局部非递减。**
   紧循环内线程极大概率不迁核，是每核计数器唯一可依赖的硬保证。
5. **紧循环判据应与上游 backend selection/acceptance 标准一致。**
   libcpucycles 上游选择循环用"CALLS 次连续读取非递减"作为接受
   backend 的判据，测试断言用同一判据（1000 次连续读取非递减）
   才是对齐契约而非另立标准。
6. **如果必须跨调度点比较，优先固定 CPU affinity。**
   sched_setaffinity/pthread_setaffinity_np 绑核后须回读验证
   （musl 缺这些 API 的编译期问题见 E094/E147/E211）。
7. **无 affinity API 时，读取 CPU ID 并只比较同核样本。**
   sched_getcpu() 前后一致时比较才有意义。
8. **无法确认核心身份时，改用 CLOCK_MONOTONIC 等系统级时间源。**
   跨调度点计时需求应交给系统级单调时钟，而非每核计数器。
9. **对真正同核、紧邻读取中的回退保持 fail-closed。** 紧循环内
   1000 次相邻读取出现递减，是计数器或库实现的真实故障，测试
   描述必须失败，不得放宽。
10. **输出 backend、前后读数、差值、CPU ID、调度点和测试范围。**
    诊断信息完整才能区分"迁核回退"与"真实故障"。

## fail-closed 安全边界

| 禁止行为 | 原因 | 后果 |
|----------|------|------|
| 通过扩大数值容差掩盖巨大负跳变 | 巨大负跳变（dc 约 -7e13）是迁核后新核计数器起点不同所致的系统性偏移，不是测量噪声 | 扩大容差只会把负值吞进 PASS 区间，断言失去检出能力，未来真正的计数器故障（溢出、后端错乱、寄存器配置错误）也不会被发现 |
| 删除全部单调性测试 | 紧循环内相邻读取非递减是每核计数器真实提供、且上游选择循环自检的保证；正确做法是把断言收窄到紧循环，不是整体删除 | 测试失去对计数器基本正确性的防线，default-zero 等退化后端也可能通过 |
| 假设所有硬件周期计数器跨核同步 | PMCCNTR_EL0 按 core 独立维护；x86 TSC 的跨核同步也只是厂商实现保证而非体系结构保证 | 测试在允许迁核的系统上随机失败（flaky），或迫使维护者用放宽断言来"稳定"它 |
| 跨 sleep、I/O、锁等待直接比较每核绝对计数 | sleep/I/O/锁等待期间线程可能迁核，前后绝对读数来自不同核心的计数器，不可直接比较 | 断言把 API 未承诺的行为当契约检查，产生无法通过修库解决的伪失败 |
| 在未证明迁核时把所有回退都归因于调度 | 回退也可能来自计数器溢出、PMU 权限错误、后端初始化失败或库 bug；必须先输出 CPU ID/前后读数证明发生了迁核 | 真实的计数器/后端缺陷被误标为"调度噪声"而不修，fail-closed 边界失效 |
| 将同核紧循环中的真实回退改为 PASS | 紧循环相邻读取非递减是唯一可依赖的硬保证（上游选择循环自用它接受后端）；同核紧循环内的真实回退说明计数器或库实现有问题 | 把真实缺陷标记为预期失败，库的计数正确性再无测试防线 |
| 以 CPU affinity API 不可用为由伪造绑核成功 | 宏替换或空 stub 不会真正固定线程（musl 缺 affinity API 见 E094/E147/E211），绑核是否成功必须用 sched_getcpu/sched_getaffinity 回读验证 | 未生效的"绑核"给出虚假的同核保证，迁核回退依旧发生且更难定位 |
| 把 CLOCK_MONOTONIC 和每核 cycle counter 混为一类 | CLOCK_MONOTONIC 是系统级单调时钟（跨核全局单调、纳秒量纲），每核 cycle counter 是硬件周期计数（核心局部、周期量纲）；量纲、单调域、精度都不同 | 断言语义错位：要么把系统级保证错误安到每核计数器上（伪失败），要么把周期数当时间比较（数量级错误） |

## fallback 顺序

按实际环境能力降级：

1. **CPU affinity 固定线程**：sched_setaffinity/
   pthread_setaffinity_np 绑核后回读验证，再跨调度点比较
   （API 可用性边界见 E094/E147/E211）；
2. **记录 CPU ID，只比较同核数据**：无 affinity API 时用
   sched_getcpu() 标注每个样本，只比较同核样本对；
3. **使用系统级 monotonic clock**：跨调度点计时需求整体交给
   CLOCK_MONOTONIC 等系统级时间源；
4. **无法满足契约时显式 Skip**：对明确不适用的 backend 显式
   Skip 并说明能力边界。Skip 只能用于明确不适用的 backend，
   不能用于掩盖真实失败。

## 实际示例：libcpucycles 20260625

本案例是本条目通用规则的**首个成功案例**，不是规则本身。

**环境与后端**：OHOS aarch64，交叉构建 libcpucycles 20260625，
运行时 backend 选择为 `arm64-pmc`（读 per-core PMCCNTR_EL0）。

**初版断言（提交 40fb5f4711）**：test_package/test.c 的
`persecond-consistency` 断言在 50ms nanosleep 前后取周期差 dc，
与 `cpucycles_persecond() * 0.05` 交叉验证；tracesetup 旧式检查
`after >= maxv` 同样跨 sleep。

**真实失败**：CI 首测中，睡后周期计数（~7.4e13）**小于**睡前计数
（~1.4e14），dc 为巨大负数（约 -51% 的差值），`persecond-consistency`
失败；tracesetup 前后读数同样下降。失败原因不是库缺陷——
arm64-pmc 读的是 per-core PMCCNTR_EL0，50ms sleep 期间线程迁核，
新核计数器起点远低于旧核。上游 wrapper.c 选择循环注释明确承认
"!ok can be caused by overflow or by core swap"；libcpucycles
man page 契约为 "an estimate ... since an unspecified time in
the past"，不承诺跨核全局单调。

**修正（提交 44c7711bbf）**：删除两个跨 nanosleep 断言
（`persecond-consistency` 与 `after >= maxv`），全部读数间断言
收窄到无阻塞紧循环相邻读取——与上游选择循环接受 backend 的
判据一致（CALLS 次连续读取非递减）。

**修正后结果**：1000 次连续读取非递减通过；10/10 断言通过，
Scoped CI 全绿。10 个断言为：version、implementation-nonnull、
implementation-stable、implementation-known、persecond-positive、
counter-increases、counter-monotonic、persecond-stable、
persecond-plausible、tracesetup-noop-after-init。

## 修正前后的测试对比

| 维度 | 修正前（40fb5f4711） | 修正后（44c7711bbf） |
|------|---------------------|---------------------|
| 断言对象 | 跨 50ms nanosleep 的绝对周期差 | 无阻塞紧循环相邻读取 |
| 单调域假设 | 隐含假设跨核全局单调（API 未承诺） | 仅假设紧循环内局部非递减（上游自检判据） |
| persecond-consistency | dc 与 persecond*0.05 交叉验证，负差值失败 | 删除（超出契约），保留 persecond-positive/stable/plausible |
