# E2175 — glibc/libstdc++ 宽松、musl/libc++ 严格的 OHOS C++ 移植差异清单（bobcat 6.14.00 实证）

## 错误特征

同一库在同一 OHOS 工具链（clang 15 / musl / libc++）下出现多类编译/链接错误，典型日志：

```
exception/errnodescr.cc:12:19: error: cannot initialize a variable of type 'char *' with an rvalue of type 'int'        # GNU strerror_r
tmp/bobcat/clocktypes:62:25: error: no member named 'clock_cast' in namespace 'std::chrono'                             # C++23 缺失
tmp/bobcat/clockbase:22:23: error: missing 'typename' prior to dependent type name                                      # clang 严格 typename
tmp/bobcat/mmapbuf:48:17: error: unknown type name 'mode_t'                                                             # 传递包含缺失
childredirections.cc:12:40: error: use of undeclared identifier 'STDIN_FILENO'                                          # 传递包含缺失
serversocket1.cc:16:47: error: invalid operands to binary expression ('__bind<int, sockaddr *, unsigned long>' and 'int')  # 裸 bind 被抢占
reverse_iterator<It> requires It to be a bidirectional iterator                                                          # category 断言
Error loading shared library libxml2.so.16: (needed by .../llvm/bin/lld)                                                # CI worker 链接子进程无法启动
```

## 触发条件

- 构建系统: 任意（bobcat 为 icmake，conanfile 复刻其编译语义；与构建系统无关）
- 阶段: compilation（前六类）/ linking（lld 动态依赖）

## 根因分析

上游库按 glibc/libstdc++ 开发，OHOS 是 musl/libc++ 且 clang 对标准更严格，六类差异：

1. **strerror_r 语义分叉**：glibc 默认 GNU 版（返回 `char*`），musl 按 POSIX（返回 `int` 错误码）。
2. **typename 严格性**：gcc 接受缺 typename 的依赖类型名（别名声明/类外成员定义等场景），clang 报错；C++20 P0634 未覆盖全部场景。
3. **C++23 缺口**：libc++15 未实现 `std::chrono::clock_cast`、`std::string::contains`；上游若用 C++26 编译则被掩盖。
4. **传递包含缺失**：glibc 环境下其他系统头恰好带入 `<sys/types.h>`/`<unistd.h>`，musl 头不带入，裸 `mode_t`/`STDxx_FILENO` 报未声明。
5. **`using namespace std` + 裸 POSIX 函数名**：libc++ 的 `std::bind` 是完美转发模板，参数经整型转换即精确匹配，抢占 `::bind`；产物 `__bind` 对象无 `operator<` 随即报错。
6. **迭代器 category 声明与实现不符**：libstdc++ `reverse_iterator` 不检查 concept，libc++ 有 `static_assert`（要求 bidirectional）。

独立基础设施位：**CI worker 上 SDK 的 `lld` 依赖 `libxml2.so.16`**（`ohos/native/llvm/lib/` 自带），worker 的 loader 搜索路径未覆盖该目录 → 链接子进程 `unable to execute command: No such file or directory`。本地设备 loader 可自行解析，造成"本地过、CI 挂"。

## 解决方案

### 推荐方案

按错误类别逐个补丁（全部对 gcc/C++26 无损，bobcat 已以 8 个补丁在 1050 TU 全量实证）：

1. `strerror_r` 改 POSIX 语义：`if (strerror_r(errno, buf, n) == 0) out << buf;`
2. 缺 typename 处补显式 `typename`。
3. `clock_cast<FileClock>(sys_time)` 改 `std::chrono::file_clock::from_sys(sys_time)`（C++20 规定的 sys 链转换）；跨时钟时长类型差异（OHOS libc++ `system_clock::duration`=微秒、`file_clock::rep`=__int128 纳秒）处补显式 `std::chrono::time_point_cast`。
4. 裸 `mode_t` 头补 `#include <sys/types.h>`；裸 `STDxx_FILENO` 的 .ih 补 `#include <unistd.h>`。
5. 裸 `bind(...)` 改 `::bind(...)`。
6. 迭代器实现确有 `operator--` 时把 `iterator_category` 改 `bidirectional_iterator_tag`（真实缺陷修复）。

基础设施位（CI 专属）：conanfile 里对编译/链接子进程注入
`LD_LIBRARY_PATH=<os.path.realpath(cxx)>/../lib`（SDK llvm/lib 自带 libxml2.so.16）。
**必须 realpath**：profile 的编译器路径常是符号链接（`/data/service/hnp/bin/clang++` → SDK llvm/bin），
不 realpath 会推导出 `/data/service/hnp/lib`（不存在）→ 注入恒 no-op → CI 仍挂。

### 禁止做法

- ❌ 用 `LD_LIBRARY_PATH` 指向编译器 bin 目录（`/data/service/hnp/bin`）——那是二进制目录不是库目录；未 realpath 时真实库目录根本不会被注入。
- ❌ 为绕开 `std::bind` 抢占而删除内部头的 `using namespace std;`——影响面不可控，属大范围无依据重构。
- ❌ 以"平台原因"跳过对应类（bobcat 的做法是按类别补丁，全部可上游化）。
