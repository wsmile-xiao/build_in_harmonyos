# E2180: 生成型纯数据包必须绑定输入与验证输出语义

## 问题现象

架构无关的数据包能够完成构建，测试命令也可能返回成功，但测试实际匹配了
零个输入。安装目录中的生成文件虽然存在，却可能是非法 XML、零字节文件，
或因分组生成器未冲刷最后一组而静默缺少记录。

## 根因

测试脚本把数据域解释为当前工作目录的相对路径，而 Meson 从 build 目录启动
测试；空 glob 没有 fail-closed。生成器又直接把源字符串拼进 XML 属性，并以
“遇到下一组时写出上一组”的方式输出，因而分别产生未转义字符、缺失域分支
和 EOF 尾组丢失。文件存在与构建 RC 0 都没有覆盖这些语义错误。

## 修复步骤

1. 以测试脚本位置或显式 source root 解析输入目录，零输入立即失败。
2. 对生成格式统一做属性转义，逐项覆盖构建系统声明的全部数据域。
3. 分组输出在 EOF 显式冲刷最后一组，不能依赖下一个键触发。
4. 消费者解析所有生成文件，并把每个域的输出记录数与权威源记录数比较。
5. 同时验证兼容符号链接、发现元数据和所有已声明 catalog，而非只查路径存在。

## 验证方式

`iso-codes/4.20.1` 的修复后 Meson 清单为 8 项且通过 8/8。八个 XML 域分别
与 JSON 对齐，包括 5,046 条 ISO 3166-2、31 条 ISO 3166-3 和 7,923 条
ISO 639-3。OHOS/armv8 Conan r6 的消费者进一步通过 1513 项断言，并检查
708 个 canonical `.mo` catalog、5 个 XML 兼容链接及 `iso-codes.pc`。

## 适用范围与安全边界

适用于由 JSON、YAML、CSV、PO 等源数据生成 XML、schema、catalog 或数据库的
跨平台构建。若某兼容格式确实不需要，必须在构建选项和包合同中显式移除；
不能保留空文件，也不能降低消费者检查来接受非法或不完整输出。记录数相等
只证明结构闭包，仍应结合格式解析、关键字段和目标平台文件语义验证。
