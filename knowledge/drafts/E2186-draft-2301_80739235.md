# E2186（草稿）: 架构驱动的密码学后端替换属于兼容性契约，而非编译开关

> 主张收窄：本条只宣称一件事——当库的默认密码学后端因目标架构不可用而被迫替换时，
> 替换本身是**包级兼容性契约**（公开类型名、ABI 布局、序列化格式、消费者 defines、
> package ID 全部随之改变），不能当作只改一个 CMake 选项的编译开关处理。
> 子模块缺失/按固定提交恢复（gitlink mode 160000）属 E150，本条仅作为案例前置条件引用，
> 不再作为本条的新贡献宣称。

## 案例背景（libff 0.2.1 → OHOS aarch64）

- 官方 tag 归档缺功能性 git 子模块（gitlink，mode 160000，不随 tar.gz 导出）：
  `depends/ate-pairing` @ `e6989012…`、`depends/xbyak` @ `f0a8f7fa…`。
  归档取证与按固定提交恢复的方法 → **E150**（manual-download 模式）。
- 按固定提交组装后，默认 CURVE=BN128 仍在编译期失败（非补齐即可用）：
  `zm2.cpp:3644: use of undeclared identifier 'Xbyak'` ×3 —— `zm.h:68` 在非
  `__x86_64__`/`_WIN64` 平台 `#undef MIE_USE_X64ASM`，而 `zm2.cpp:3644` 位于
  3574 行守卫 `#endif` 之外，无条件引用 Xbyak 类型。Xbyak 是 x86-64 运行时
  JIT 代码生成器，在 aarch64 上既不能编译也无法运行其生成的 x86 机器码。
- 上游提供的自包含替代路径 `CURVE=ALT_BN128` 不依赖 ate-pairing/xbyak，
  构建并通过真实域/群/配对运算测试。

## 根因：为什么"换后端"不是编译开关

BN128 与 ALT_BN128 密码学等价（同一条 BN254 曲线，q/r 常数逐位一致），
但工程上非等价，四层断裂：

1. **公开类型名不同**：`bn128_G1` vs `alt_bn128_G1`，`bn::Fp` vs
   `Fp_model<4, mod>`——消费者源码不可互换；
2. **ABI 对象布局不同**：BN128 走 `mie::Vuint` + 静态函数指针初始化，
   ALT_BN128 是固定 `mp_limb_t mont_repr[4]` 数组——链接符号集完全不同；
3. **流序列化格式不互通**：`operator<</>>` 的实现与实例化随宏集不同而不同
   （见第 4 点），跨实现交换数据不能默认互操作；
4. **序列化宏影响已安装公共模板的实例化**：`BINARY_OUTPUT`/
   `MONTGOMERY_OUTPUT` 改变 `bigint.tcc:189`/`fp.tcc` 中 `operator<<` 的
   输出格式（二进制 limbs vs 十进制文本）——这些模板在**消费者侧**实例化，
   宏集不同即实例化出不同的序列化函数，符号不匹配。

结论：即使密码学常数逐位一致，两条后端路径也是"密码学等价但工程非等价"的
两套实现。消费者契约必须整体重构，不能只改一个 CMake 选项了事。

## 推荐方案：五项联动

1. **后端选择进入 package ID 或公开声明单后端契约**：本例配方固定
   `CURVE=ALT_BN128`，docstring 公开声明"只提供 ALT_BN128，与默认 BN128
   非等价"；影响公共头/模板实例化的选项（序列化宏、后端选择）保留在
   package ID 中，仅删除真正无关的选项（`with_openssl`）。
2. **defines 全集下发**：所选后端的全部编译定义——`CURVE_ALT_BN128` 及
   影响已安装公共头的 `BINARY_OUTPUT`/`MONTGOMERY_OUTPUT`、
   `LOWMEM`/`MULTICORE`——必须经 `package_info().cpp_info.defines` 下发，
   确保消费者与库本体按同一宏集实例化同一模板。
3. **test_package 不硬编码后端类型**：必须经 `default_ec_pp`（由
   `CURVE_*` 宏选择）+ `static_assert` 编译期门禁验证消费者真实拿到的
   配置，并覆盖真实域/群/配对运算与序列化往返。
4. **差异显式记录**：在 notes/README/manifest 记录两后端的密码学等价性
   （q/r 常数逐位一致）与工程非等价性（类型/ABI/序列化三方面实测差异
   对照表），既有 BN128 消费者迁移必须显式改写源码，不能默认直接迁移。
5. **证据链三层落档**：默认后端不可用（编译失败日志）→ 替代后端真实可用
   （上游 ctest + 消费者测试全绿）→ 消费者契约验证（data.cmake defines
   全集 + static_assert 门禁编译通过）。

## 与相邻条目的分界（查重结论）

- **E150**（已转正）：覆盖"tag 归档缺子模块 + 按固定提交 manual-download
  恢复"。本条 A 部分（gitlink 恢复）引用 E150，不重复宣称。
- **E412**（已转正，最近邻）：覆盖"可选加速后端显式化"，但其适用边界是
  "后端只影响性能不影响公共 API"——不覆盖"后端替换改变公开类型名/ABI/
  序列化"的兼容性契约场景。本条与其互补，不重复。
- **E543 草稿**（另一编号体系/主 worktree）：覆盖"布局宏必须经
  cpp_info.defines 下发"的通用规则。本条是该规则在密码学后端替换场景的
  具体化，并扩展到序列化模板实例化。
- **kangaru 草稿**：子模块是测试框架（catch2），用 test_requires+CMakeDeps
  替代——非功能性默认路径，与本条不同问题面。

## 适用边界

适用于默认密码学后端（或公开类型面由后端决定的功能路径）在目标架构不可用、
需切换到替代后端的 C/C++ 库（密码学、编解码、压缩等），尤其是后端间
"密码学等价但 API/ABI/序列化不互通"的场景。不适用于：后端替换不影响公开
API 的场景（→ E412）；子模块仅用于测试的场景（→ kangaru 草稿）。

## 安全边界

- 不得把后端替换当作只改 CMake 选项的编译开关：必须同步 package ID/契约
  声明、defines 下发、test_package 门禁、差异记录四处；
- 不得假设密码学常数一致（q/r 逐位相同）即可默认源码/数据可迁移——类型名、
  ABI 布局、流序列化均需显式验证；
- 不得用密码学等价掩盖工程非等价；
- 不得在 test_package 硬编码后端类型绕过包配置链（必须走 default_ec_pp
  宏选择路径）；
- 取证用子模块组装树不得进入交付源。
