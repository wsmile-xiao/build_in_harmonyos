# E6401 — OHOS musl BUFSIZ=1024：fgets(buf, BUFSIZ) 静默切段长行

## 错误特征

没有任何编译/链接错误或告警；短行测试全部通过。只有当输入里出现 **1024 字节及以上**的行时，
OHOS 上的程序才输出错误结果——行被截断、与下一行粘连、被重复计数或解析失败，而同一源码在
glibc（Linux x86_64/aarch64）上对 8191 字节以内的行都正常。

multisort 1.1 实测（两份日志合并）：

```
输入:   long.log 1 行 1313 字节（含 UA "[FBAN/FBIOS;FBAV/1.0]"） + short.log 1 行 67 字节
glibc:  2 行，与输入逐字节一致
OHOS:   1 行 1359 字节（长行被切段，续段中的 '[' 被当作日期解析，写入 \0 后 fputs 截断）
```

## 触发条件

- 平台：OHOS SDK sysroot（musl）`usr/include/stdio.h:50` → `#define BUFSIZ 1024`；glibc 为 8192
- 代码形态：`char buf[BUFSIZ]` / `char buf[BUFSIZ + 1]` + `fgets(buf, BUFSIZ, fp)`（或 `sizeof buf`），
  并假定一次 `fgets` 返回完整一行
- 阶段：运行时（test_package 若只用短行会漏检）

## 根因分析

C 标准只要求 `BUFSIZ >= 256`，具体值由 libc 决定。把它当"足够长的行长度"是 glibc 时代的隐含假设：
glibc 8192 时绝大多数文本行都装得下，musl 1024 时 Combined Log 的长 URL/UA、长配置行、长 CSV 记录
都会被 `fgets` 分多次返回。续段没有行首结构，按行处理的逻辑（解析、排序、计数、加前缀）随之出错；
multisort 还叠加了上游 `conv_time()` "先写 `\0` 再校验、失败不还原"的写法，表现为输出截断。

## 解决方案

### 推荐方案（explicit-line-buffer-size）

在补丁中为程序自己的行缓冲引入显式常量，缓冲声明与所有对应的 `fgets` 长度参数统一改用它：

```c
#define LINEBUF_SIZE 8192          /* 与 glibc BUFSIZ 行为一致，不依赖 libc 常量 */
char buf[LINEBUF_SIZE + 1];
fgets(buf, LINEBUF_SIZE, fp);
```

无平台宏，glibc/musl 走同一代码路径。修改源码后经 `refresh-patch --auto` 生成补丁，
并用 >1024 字节的输入行回归（x86 runner 没有 OHOS 的 `/lib/ld-musl-aarch64.so.1`，动态产物起不来，
改用同源 `.o` 静态重链副本经 `qemu-aarch64` 实跑）。

### 回退方案（posix-getline）

需要支持任意长度行时改用 POSIX.1-2008 `getline()`（OHOS musl 已提供），由 libc 动态扩容缓冲。

### 禁止做法

- ❌ `-DBUFSIZ=8192`、`#undef BUFSIZ` / `#define BUFSIZ ...` 改写 libc 常量：与 stdio.h 定义冲突，并改变 `setbuf()` 等用法的含义
- ❌ 用 `__OHOS__` / `__MUSL__` 平台宏只在 OHOS 上放大缓冲：违反 R8，且行缓冲大小与平台无关
- ❌ 只用短行做 test_package：无法暴露该问题

## 验证

```bash
grep -n 'define BUFSIZ' "$OHOS_SDK/native/sysroot/usr/include/stdio.h"   # -> 1024
grep -rnE 'fgets\s*\([^;]*\bBUFSIZ\b' <src>                              # 定位风险点
# 构造 >1024 字节的输入行，目标机（或静态重链副本 + qemu-aarch64）运行，与输入 / glibc 版输出逐字节比对
```
