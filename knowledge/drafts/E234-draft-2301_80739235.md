# E234: Exact dependency overrides require a new package identity

## Symptom

A downstream Conan recipe explicitly selects a newer provider version to
remove an exact-version conflict. The dependency graph resolves, but the
binary for the downstream package is missing or the CMake configure step
fails while looking up the provider's exported target. A Windows-hosted
configure can additionally invoke the host linker and report missing
host-only libraries even though the OpenHarmony compiler is present.

## Root cause

Conan computes a package ID from settings, options, and the resolved graph.
Changing a provider from one exact version to another therefore changes the
consumer binary closure. A recipe revision under the old version is not a
substitute for a new package built against the new provider. Conan's
--build=missing can compile a local fallback, but it does not publish that
binary to the configured remote and must not be described as release
availability.

There is a second, independent boundary at CMake generation. The provider's
native exported configuration is a case-sensitive file and target contract.
CMakeDeps output and a guessed lowercase filename do not prove that the
published provider exposes the expected target. Finally, target compiler
flags do not by themselves change CMake's platform model: without the SDK
toolchain's system name, target triple, sysroot, lld, and archiver settings,
host link rules can leak into the target compiler probe.

## Fix

1. Create the next adaptation version (for example, 2.2.0.1) so the new
   dependency closure has a distinct recipe and binary identity.
2. Declare one exact provider version and retain the provider's transitive
   headers and libraries. Recompute the full graph and assert that the old
   provider node is absent.
3. Inspect the provider package itself and bind the real native CMake config
   directory. Accept only explicitly documented filenames such as
   SDL2Config.cmake; do not create a substitute config in the dependency.
4. In the host profile, load the official target SDK toolchain before the
   first configure. The toolchain must set CMAKE_SYSTEM_NAME, the target
   triple, sysroot, lld linker, and llvm-ar; keep jobs bounded.
5. Build the new package from a hash-verified source archive and compile the
   complete independent consumer set against that package. Keep target
   execution and remote publication as separate gates.
6. After formal release, verify the new recipe revision, package ID and PREV
   from a fresh Conan home with conan install --build=never.

## Validation

For SDL2_net 2.2.0.1, the exact official 2.2.0 archive was 8,707,169 bytes
with SHA-256
4e4a891988316271974ff4e9585ed1ef729a123d22c08bd473129179dc857feb.
The local recipe selected sdl2/2.32.10, found the published package's
SDL2Config.cmake, and used the DevEco OHOS toolchain. Conan created the
static package with recipe revision
ff7ca722767e5c938fdc22724a2f947b, package ID
7b8a00ecd1dcc9231ac0df36c334f8d078a74783, and local PREV
8d0c2c006a3cf03f4828e4c0c14f1e87. The test package compiled and linked all
seven independent network consumers. Because this was an OHOS cross build,
the seven target executables were not run locally; target runtime remains a
separate NOT_RUN result until a real device transaction.

The initial provider check failed on the guessed lowercase
sdl2-config.cmake; accepting the actual standard-case name fixed generation.
An initial profile without the official toolchain reached the compiler probe
but selected the Windows w64devkit linker and failed on -lgcc_eh.
Loading the SDK toolchain corrected the target model and allowed the package
and consumer compile/link stages to complete. An unsupported
--non-interactive flag and an invalid core.* command-line configuration
were rejected by Conan 2.29.1 before any build; omitting those flags is the
portable invocation for this version.

## Reusable decision rule

When an exact provider is replaced, treat the downstream package as a new
binary closure even if source code is unchanged. First prove graph identity,
then prove the provider's native configuration and target platform model,
then compile consumers. A local package proves only local compilation and
consumer linkage; it does not prove remote parsing, target execution, or
release publication.

## Safety boundary

This pattern applies to cross-built Conan packages whose dependency graph or
CMake target contract changes. It does not authorize replacing an already
published binary in place, copying local artifacts into a remote repository,
or inferring target runtime from a successful compiler probe. Preserve the
failed input and build roots, and use a create-new package identity for every
changed closure.
