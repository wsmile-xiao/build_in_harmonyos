# E6412 - Bind transfer archive layout to the production wrapper namespace

## Symptom

A frozen archive is transferred with SSH return code zero, and two independent
remote byte-count and SHA-256 reads match the host archive. Target extraction
also returns zero, yet the production wrapper fails before preparation with a
missing entrypoint under the expected namespace, for example:

```text
/system/bin/sh: <task-root>/bundle/w3-transaction.sh: No such file or directory
```

The target root instead contains `archives/`, `candidate-manifest.tsv`, and
other payload members directly beneath `<task-root>`.

## Root Cause

Archive integrity and extraction success establish the bytes of a payload, not
the semantic namespace in which the production controller will resolve those
bytes. A command such as `tar -cf output.tar -C bundle .` stores the contents
of `bundle` without the `bundle/` component. Extraction therefore succeeds
while violating the wrapper's frozen path contract. Treating the transfer hash
as a complete identity would convert a deterministic prelaunch rejection into
an opaque runtime failure.

## Fix

1. Include the expected top-level directory name in the transfer contract,
   independently of the archive digest.
2. Archive the unique directory with an explicit root name, such as
   `tarfile.add(bundle, arcname="bundle")`; do not archive its contents as the
   archive root.
3. Before transfer, inspect the member table and require every member to be the
   named root or a path below it. Reject absolute paths, parent traversal, and
   unrelated top-level entries.
4. After two exact-byte readbacks and extraction, read back the exact wrapper,
   runner, manifest, and cache paths below the named root. Run the production
   wrapper preflight, including target shell/Python syntax and manifest checks,
   before prepare or launch.
5. If a wrong-layout archive has already been extracted, preserve the original
   transfer, extraction, and preflight receipts. Prove that no result,
   execution root, or foreign process exists, clean only the task-owned root,
   and create a new successor. Do not re-transfer or patch the consumed run.

## Validation

DOSBox Staging Issue #1093 r171 transferred a 667,667,456-byte archive with
matching readbacks and extraction RC 0. Its members were rooted directly at the
task base, so the wrapper could not find `bundle/w3-transaction-r171.sh` and
returned RC 127 before prepare; launch_count remained zero. A read-only layout
inspection proved that the result and execution roots were absent and that no
target task process existed. The task-owned root was then removed and read back
absent.

Successor r172 created a 667,668,480-byte archive whose 104 archive members
were all prefixed by `bundle`. Both readbacks, extraction, target shell/Python
syntax, dependency-cache validation, and the production wrapper preflight
passed. The same transaction then completed one launch with upstream `24/24`
and consumer `4/4` PASS, followed by owner-only release and two clean scans.

## Applicability and Safety Boundary

This pattern applies to any target controller that resolves frozen inputs below
an archive root such as `bundle`, `input`, or `payload`. It does not make a
transfer, extraction, or wrapper-preflight PASS a W3 result; production build,
upstream tests, consumer checks, terminal validation, and release evidence
remain mandatory. It does not authorize deletion of foreign roots,
overwriting an in-flight run, cross-run evidence splicing, or artifact upload.
