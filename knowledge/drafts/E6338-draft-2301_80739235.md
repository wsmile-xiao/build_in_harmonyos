# Windows 主机 OHOS Conan/Meson 依赖元数据必须任务内本地化

## 问题现象

Windows 主机向 OHOS/aarch64 交叉构建时，Conan 生成的 Meson/pkg-config 元数据会
携带宿主 package_folder 和 Windows 路径。安装阶段可能出现 `New rpath must not be
longer than the old one`；即使安装成功，目标 ELF 也可能把
`/storage/.../.conan2` 等构建缓存路径写进 RUNPATH。主机或本地消费者测试可通过，
但目标机无法按发布布局加载依赖。

## 根因

Meson 的 prefix、pkg-config 的 `prefix/libdir/includedir` 和链接器 RPATH 是三个
不同边界。只修正 Windows 到 POSIX 的 prefix，不能消除 .pc 中依赖的宿主绝对路径；
同时动态 `libarchive.so` 的 RUNPATH 可能引用 Conan 缓存，交叉目标没有该目录。把
主机编译通过误当成目标闭包通过，会掩盖部署时的加载失败。

## 修复步骤

1. 在 recipe 与 `test_package` 的 OHOS/Windows 交叉分支中固定 Meson prefix 为 `/`。
2. 把 glib、libarchive、zlib 等实际使用依赖的 include/lib 复制到当前构建目录的
   任务私有 `conan-deps`，并将生成 `.pc` 中的 package_folder 前缀替换为相对构建
   目录的 POSIX 路径；缺少依赖节点时 fail closed。
3. 对会泄漏 Conan RUNPATH 的依赖，在任务私有闭包只保留经过验证的静态归档；
   `test_package` 显式声明 `$ORIGIN/../lib`，使安装副本和消费者使用同一部署布局。
4. 在进入目标机前检查主包和消费者 ELF 的架构、NEEDED、RUNPATH；目标机上再完成
   exact-byte transfer、官方 signer 自签和签名后独立回读。

## 本次验证

gnome-autoar/0.5.2 的本地 `conan create` r16 通过，日志
`local-build-r16/conan-create.combined.log` SHA-256 为
`624aafdbb4203e04feae7cff3a6839ed408f4a76e2f2df3e9f8de53f7e8c9643`。主包和消费者
安装 ELF 均为 AArch64，RUNPATH 为 `$ORIGIN/../lib`，NEEDED 闭包不再依赖带 Conan
缓存 RUNPATH 的 `libarchive.so`。同一 `w3-r001` 在设备 `10.62.150.125:8022`
单次 launch 完成上游 `1..22`（22/22，2 个明确 crypto backend SKIP）和消费者
10/10，随后 release/postrelease 均 PASS；完整结果
`w3-r001-result.json` SHA-256 为
`f52f1b7d46b5f0bb0aea75d7d701e880ac62467b390b1905f56d08efb174916a`。

## 适用范围与安全边界

该模式适用于 Windows 主机的 OHOS Conan/Meson 交叉构建，尤其是同时提供静态和
动态产物、或通过 pkg-config 暴露绝对路径的 C/C++ 库。任务私有副本只能写入
`F:\\HarmonyPC` 当前任务目录，不得修改共享 Conan 缓存或系统库目录。`$ORIGIN`
RPATH 是部署布局契约，不是目标验证替代品；主机构建、静态 ELF 检查或签名回读
都不能单独升级为 W3、CI、Review 或提审 PASS。路径、RPATH、签名、HEAD 或 run
身份任一漂移都必须停止并重建证据。
