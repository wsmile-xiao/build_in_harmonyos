# DRAFT-ncmpc-meson-install-elf-remirror

Meson install copies an OHOS executable into a Conan package directory, after
which the build-tree binary still runs but the package copy fails with
`Operation not permitted`.

- Source event: ncmpc 0.53 HarmonyOS PC adaptation
- Trigger command: single-package shadow CI for `archives/n/ncmpc/0.53`
- Affected phase: `package()` / `test_package`

## Failure

The package builds and the upstream smoke test runs from the Meson build tree:

```text
[115/115] Linking target ncmpc
ncmpc/0.53: RUN: ".../build-release/test/run_hscroll" "hello" "|" "5" "3"
hello
ello|
llo|h
```

The following consumer test then fails when `VirtualRunEnv` resolves `ncmpc`
from the packaged `bin/` directory:

```text
test_ncmpc.sh: line 5: .../p/bin/ncmpc: Operation not permitted
ConanException: Error 126 while executing
```

The same source-built executable in `build-release/ncmpc` is runnable and prints
`ncmpc version: 0.53`. After replacing the package copy with that build-tree ELF,
the packaged command runs and the full shadow CI passes.

## Root Cause

On this OHOS runner, the linker-produced build-tree ELF has a valid executable
state for the current device policy. `meson install` performs a file copy into
the Conan package directory; that copy preserves visible mode bits but is no
longer accepted by the kernel execution policy. Repeating `chmod` alone does not
repair this class of failure.

This is adjacent to general OHOS ELF signing failures, but the distinguishing
signal is that no post-link tool modified the binary. The build-tree target runs,
the package copy does not, and the two files have different content hashes after
install. The fix is to mirror the already runnable build-tree ELF into
`package/bin` after `meson install`.

## Reusable Diagnostic

```sh
BUILD_ELF="$CONAN_BUILD_FOLDER/build-release/<program>"
PKG_ELF="$CONAN_PACKAGE_FOLDER/bin/<program>"

"$BUILD_ELF" --version
"$PKG_ELF" --version
sha256sum "$BUILD_ELF" "$PKG_ELF"
/data/service/hnp/bin/llvm-readelf -S "$PKG_ELF" | grep -E 'codesign|ohos.ident'
```

If the build ELF succeeds, the package ELF returns exit 126 with
`Operation not permitted`, and both are generated by the same Meson target, test
whether replacing the package ELF with the build ELF restores execution:

```sh
cp -p "$BUILD_ELF" "$PKG_ELF"
chmod 755 "$PKG_ELF"
"$PKG_ELF" --version
```

## Recipe Pattern

```python
def package(self):
    self._run_meson(
        "install",
        ["-C", self.build_folder, "--destdir", self.package_folder],
    )
    if str(self.settings.os) == "OHOS":
        self._remirror_ohos_executable()

def _remirror_ohos_executable(self):
    built = os.path.join(self.build_folder, "program")
    packaged = os.path.join(self.package_folder, "bin", "program")
    if not os.path.isfile(built) or not os.path.isfile(packaged):
        raise ConanException("expected OHOS executable path is missing")
    self.run(f'cp -p "{built}" "{packaged}"', env="conanbuild")
    self.run(f'chmod 755 "{packaged}"', env="conanbuild")
```

Use this after install, not before it. Keep it OHOS-only, and keep the operation
inside the package directory so no dependency package is mutated.

## Verification Evidence

- First ncmpc shadow run: build and `run_hscroll` passed; `test_package` failed
  at `ncmpc --version` with exit 126.
- Manual probe: replacing `p/bin/ncmpc` with the build-tree `ncmpc` made
  `ncmpc --version` print `0.53`, including `wide` support.
- Second ncmpc shadow run: `L0=pass`, `L1=pass`, `L2=pass`, `L4=pass`,
  `L5=pass`.

## B-Class Difficulty Evidence

This issue required separating four superficially similar OHOS failure modes:
script noexec, HMDFS file permissions, missing dynamic libraries, and invalid
executable state after install. The decisive proof came from comparing
build-tree and package-tree ELFs and rerunning the full consumer test.

## Do Not

- Do not mark this as an external device block before comparing the build ELF
  and package ELF.
- Do not rely on `chmod` alone; exit 126 with existing execute bits can still be
  an OHOS executable-state problem.
- Do not re-sign or patch dependency packages as part of the consumer recipe.
  This pattern only remirrors the current package's own executable.
