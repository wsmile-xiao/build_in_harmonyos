## 为什么模板里的单元测试和集成测试是 0

这两个数字是**测试类型分类结果**，不是上游测试总数：

- `pex` 是纯 shell 应用，没有 C/C++ 单元测试框架；
- 上游没有单独组织的 integration/integration-test 目录；
- 官方测试全部放在 `t/*.t`，由 shell TAP 文件执行；
- 因此“单元测试 0、集成测试 0”只能表示这两个分类不适用；
- 官方上游测试应归入“其他测试/上游 TAP”，共 17 个文件、98 个计划
  断言，入口是 Linux 的 `make check` 或 OHOS 的
  `prove --exec /system/bin/sh t/*.t`。

如果只把模板的两个分类项相加，就会错误地得到“上游测试为 0”。
本条目把分类数量和实际测试入口拆开记录，避免出现 0/0 假通过。

## 本轮 CI 的真实口径

OHOS shadow CI 使用上游命令：

```text
prove --exec /system/bin/sh t/*.t
```

CI 结果为：

| 项目 | 结果 |
|---|---:|
| 上游测试文件计划数 | 17 |
| 上游断言计划数 | 98 |
| `audit.t` | skipped，缺少 Perl YAML 模块 |
| 实际运行文件 | 16 |
| 实际运行断言 | 88 |
| 通过断言 | 87 |
| 条件 skipped 断言 | 1，OHOS `chmod a-r` 未移除读模式位 |
| 失败断言 | 0 |
| 消费测试 | 15/15，本地 shell 级验证通过 |

历史 #43866 的唯一失败来自 `t/pg_config.t` 的第 7 项：对不可读
`postmaster.opts` 使用 `-d` 时，测试期望命令干净失败；OHOS CI 的权限
语义没有呈现上游 POSIX 环境中的同样结果。当前分支 #43900 在确认
`chmod a-r` 未移除读模式位后，只对该权限前提断言做带原因的条件 skip，
并以 0 失败通过。这个处理没有用 `|| true`、删除测试或改写期望值来掩盖
实际边界。

## 推荐报告方式

1. 在 PR 模板中把 unit/integration 写为 `0`，并在说明中注明“不适用”。
2. 在“其他测试”中填写“上游 shell TAP：17 文件、98 计划断言”。
3. 单独记录 `audit.t` 的 `skipped` 原因，不把缺失 Perl YAML 混入
   `pex` 的 Conan 依赖，也不把 skipped 计为通过。
4. 把 16/88、87 passed、1 条条件 skipped、0 failed 作为当前 OHOS
   实际证据，并把 #43866 的 1 failed 标为旧快照历史记录。
5. 将 `test_package` 的 15 项消费断言单列，不能冒充上游测试结果。

这种记录方式既解释了为什么模板中两个类别是 0，也保留了可复核的官方
测试入口、文件数、断言数、跳过原因和失败原因。

## 与已有知识的差异

本条目不是泛化的 TAP 教程，也不是“缺少测试工具”的普通环境提示。
它直接针对 `pex` 的测试组织方式和本轮 CI 的实际结果，解决“分类为 0”
与“上游套件未运行”之间的证据歧义，并要求消费测试与上游测试分开计数。

## 不能宣称的结论

- 不能写成“上游测试 0 个”或“0/0 通过率 100%”。
- 不能把 `audit.t` skipped 写成 PASS。
- 不能把 87/88 加工成“上游全量无条件通过”；必须同时说明 10 个
  `audit.t` 断言和 1 个权限前提断言的 skipped 原因。
- 不能因为失败来自权限语义，就直接删除 `pg_config.t` 断言；应在目标
  环境复现并形成有边界的修复或豁免说明。
- 本草稿是路径 B 申请材料，不代表已经获得 B 类认定。
