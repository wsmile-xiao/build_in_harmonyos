# E429 — Conan CMakeToolchain SharedLibBock 强制注入 BUILD_SHARED_LIBS=ON（CACHE 变量，tc.variables 无法覆盖）导致 vendored 子库变共享

## 错误特征

conan create 构建主包成功后，test_package 运行时出现：

```
Error loading shared library ../library/lib/libwavpack.so: (needed by .../p/lib/libsfizz.so)
Error relocating .../libsfizz.so: WavpackOpenRawDecoder: symbol not found
```

或 conan-verify 报告：
```
Library 'sfizz' not found in package.  If 'sfizz' is a system library, declare it with 'cpp_info.system_libs' property
```

构建日志中 CMake 配置阶段输出：
```
-- Conan toolchain: Setting BUILD_SHARED_LIBS = ON
```

## 触发条件

- 构建系统: CMake（Conan 2.x CMakeToolchain 驱动）
- 阶段: configuration（生成 conan_toolchain.cmake）/ linking（test_package 运行期）
- 项目结构：顶层 CMakeLists 通过 `add_subdirectory()` 引入 vendored 第三方子库（如 abseil-cpp、wavpack、aiff 等 git submodule 或内嵌源码）
- Conan 配方 `options` 声明 `shared`，`default_options` 为 `shared=True` 或用户以 `-o shared=True` 构建

## 根因分析

Conan 2.x 的 `CMakeToolchain` 内部 `SharedLibBock` 会在生成 `conan_toolchain.cmake` 时，根据 `self._conanfile.options.shared` 强制写入：

```cmake
set(BUILD_SHARED_LIBS ON CACHE BOOL "Build shared libraries")
```

这是一个 **CACHE 变量**，优先级高于配方 `generate()` 中 `tc.variables["BUILD_SHARED_LIBS"] = "OFF"` 写入的普通变量，因此**配方层面无法覆盖**。其后果：

1. 顶层 CMakeLists 中所有 `add_subdirectory()` 引入的 vendored 子库（未显式指定 STATIC/SHARED 的 `add_library(<name> ...)`）全部按 `BUILD_SHARED_LIBS=ON` 构建为共享库；
2. 上游项目自身的 `install()` 规则通常只安装主库（如 `sfizz_shared`），不安装这些第三方子库；
3. 主库 `libsfizz.so` 的 `DT_NEEDED` 记录了对子库（如 `libwavpack.so`）的依赖，但包内没有该 .so → test_package 运行期 `Error loading shared library`。

本地手动 `cmake -D...` 构建时无此问题（没有 conan toolchain 注入），因此该错误是 **conan 环境特有的行为差异**。

## 解决方案

### 推荐方案（shadow-cache-variable-in-top-cmakelists）

在项目**顶层 CMakeLists.txt** 中，位于 `include(SfizzDeps)`（即任何会触发 `add_subdirectory(vendored_sub_lib)` 的 include）**之前**，添加一条**普通（非 CACHE）变量**：

```cmake
set(BUILD_SHARED_LIBS OFF)
```

原理：CMake 中普通变量优先于同名 CACHE 变量（CACHE 变量被普通变量"遮蔽"），且普通变量会被 `add_subdirectory()` 继承到子目录作用域。这样：
- vendored 子库（wavpack/aiff/abseil 等）全部保持静态构建；
- 主库共享与否由项目自身的选项（如 sfizz 的 `SFIZZ_SHARED`）单独控制，不受影响；
- 主库 `.so` 内部静态包含子库符号，无运行期缺失依赖。

配合 `conanfile.py generate()`：
```python
tc.variables["SFIZZ_SHARED"] = "ON" if self.options.shared else "OFF"
```

### 禁止做法

- ❌ 在 `generate()` 中单独设 `tc.variables["BUILD_SHARED_LIBS"] = "OFF"`：会被 SharedLibBock 的 CACHE 变量覆盖，无效；
- ❌ 把 `set(BUILD_SHARED_LIBS OFF)` 放在 `include(SfizzDeps)` **之后**：此时 `add_subdirectory(st_audiofile)` 已执行，wavpack 已按共享配置，不生效（本次实测踩坑）。

## 验证

```bash
# 1. 配方验证（含 test_package 运行期）
export LD_LIBRARY_PATH=/data/service/hnp/ohos-sdk.org/ohos-sdk_26.0.0.18/ohos/native/llvm/lib/aarch64-linux-ohos:$LD_LIBRARY_PATH
python3 scripts/ohc-run.py conan-verify sfizz 1.2.3
# → G2: PASS（conan create 干净构建 + test_package 消费者测试通过）

# 2. 产物检查：主库无对子库共享库的运行期依赖
llvm-readelf -d p/lib/libsfizz.so | grep NEEDED
# → 仅 libc++_shared.so、libc.so，无 libwavpack.so（子库已静态内联）

# 3. DT_SONAME 存在（配合 E330 的 SONAME 修复）
llvm-readelf -d p/lib/libsfizz.so | grep SONAME
```

## 适用边界

- 适用：CMake 项目在 Conan 配方中以 `shared` 构建、且通过 `add_subdirectory` 引入 vendored 子库的场景；
- 不适用：所有子库均来自 Conan 外部 requires（无 add_subdirectory vendored）的项目；或配方固定 `shared=False` 的项目（SharedLibBock 注入 OFF，无此问题）。
