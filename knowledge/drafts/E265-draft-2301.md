# E265 - Positive Win32 Selection and POSIX Capability Fallback

## Symptom

A cross build for an unknown CMake system compiles `ProcessWin32.c` or
`tif_win32.c` and fails because `windows.h` is unavailable, even though the
target provides the POSIX APIs needed by the corresponding Unix source.

## Root Cause

CMake's `UNIX` variable is a positive platform classification. Its absence
does not establish Windows. Selectors such as `if(NOT UNIX)` therefore
misclassify systems for which CMake has no built-in platform file.

## Recommended Fix

1. Reserve the Windows implementation for the positive `WIN32` predicate.
2. For other systems, compile and link a narrow probe for the exact APIs used
   by the POSIX source.
3. Accept the POSIX implementation when either `UNIX` or the capability probe
   passes.
4. Fail configuration when neither implementation contract is proven.
5. Do not add platform-named source conditionals.

## Validation

ITK 5.4.6 reproduced the pattern independently in bundled KWSys and TIFF.
Directed matrices covered Windows, classified Unix, unknown systems with the
required capability, and unknown systems without it. The final target build
compiled `ProcessUNIX.c` and `tif_unix.c`, completed the consumer test with
RC 0, and released the device cleanly.

## Scope

This pattern applies to mutually exclusive CMake source selectors for process,
file-descriptor, socket, and similar platform API families. The capability
probe must match the selected source; one generic `unistd.h` check is not
evidence for unrelated APIs.
