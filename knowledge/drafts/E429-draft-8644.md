# E429 — 手写 Makefile 硬编码 GNU 工具链名 / `-static`：OHOS 上构建失败且产物非 PIE

> 草稿（draft）· 来源任务：`piler/0-20140707`（PILER 1.0）OHOS aarch64 适配
> 贡献者：ran060619 <ran060619@noreply.gitcode.com> · Agent 8644 · 2026-10-01

## 错误特征

```
$ make -j1
g++ -c -O3 -DNDEBUG=1  annot.cpp -o annot.o
make: g++: No such file or directory
make: *** [Makefile:22: annot.o] Error 127
rc=2
```

以及（改用工具链编译器后仍存在的隐性硬化问题）：

```
$ readelf -hl piler2 | grep -E "Type:|GNU_RELRO"
  Type:                              EXEC (Executable file)      # 非 PIE
  GNU_RELRO      ...                                           # 有 RELRO，但无 BIND_NOW
$ readelf -d piler2
  (无 dynamic section)                                          # -static 全静态
$ readelf -h t_dyn | grep Type                                  # 对照：默认动态链接
  Type:                              DYN (Position-Independent Executable file)
```

`conan-verify` L4（NX/PIE/RELRO 扫描）会给出 `PIE disabled (non-PIE executable)`。

## 触发条件

- 构建系统：上游自带**手写 Makefile**（无 configure / 无 CMake）
- 阶段：`compilation`（编译期即失败）/ `installation`（硬化属性检查期）
- 平台：OHOS aarch64（工具链为 `aarch64-unknown-linux-ohos`，只提供 `clang++`）

## 根因分析

上游 Makefile 把"工具链"当成固定事实而非可注入变量：

```make
CFLAGS  = -O3 -DNDEBUG=1          # 硬赋值：丢弃工具链/conan 传入的 CFLAGS
LDLIBS  = -lm -static             # 硬赋值：丢弃 LDFLAGS，并把 -static 写死
GPP     = g++                     # 硬编码 GNU 编译器名
LD      = $(GPP) $(CFLAGS)
CPP     = $(GPP) -c $(CFLAGS)
```

三层后果：

1. **`make Error 127`（阻断）**：OHOS 工具链没有 `g++`，只有
   `/data/service/hnp/bin/clang++`（target `aarch64-unknown-linux-ohos`）。
2. **工具链标志失效**：`CFLAGS = ` 覆盖式赋值使 conan profile 的
   `-fPIC -O2` 等标志被丢弃（在 `GPP` 修好后才能观察到）。
3. **非 PIE 产物**：`-static` 产出 `ET_EXEC`（`Type: EXEC`），且没有
   `BIND_NOW`；鸿蒙硬化基线要求 PIE + full RELRO + NX。

## 解决方案

### 推荐方案（本项目实测通过）

```make
-CFLAGS = -O3 -DNDEBUG=1
-LDLIBS = -lm -static
+CFLAGS += -O3 -DNDEBUG=1
+LDLIBS = $(LDFLAGS) -lm -static-pie
...
-GPP = g++
+GPP = $(CXX)
```

配合 conanfile.py（满足 R33：禁止裸用 shell 环境变量）：

```python
cxx = self.conf.get("tools.build:compiler_executables", default={},
                    check_type=dict).get("cpp") or "clang++"
self.run(f'make CXX="{cxx}" -j1', cwd=self.source_folder)
```

三种链接方式的实测产物属性（同一源码、同一工具链）：

| 链接方式 | Type | DT_NEEDED | GNU_RELRO | BIND_NOW | NX |
|---|---|---|---|---|---|
| `-static`（上游） | EXEC | 0 | 有 | ✗ | ✓ |
| 默认动态 | DYN | 2（含 `libc++_shared.so`） | 有 | ✗ | ✓ |
| **`-static-pie`（采用）** | **DYN(PIE)** | **0** | **有** | **✓** | **✓** |

选 `-static-pie` 而非"直接删 `-static`"的原因：保留上游"自包含单文件二进制"
语义（OHOS CLI 运行期不保证共享 libc++ 可用），同时满足 PIE/RELRO/NX。

### 回退方案

若目标链接器不支持 `-static-pie`（`unrecognized option`），可只修编译器注入与
`CFLAGS +=` / `LDLIBS = $(LDFLAGS) ...`，保留 `-static`；此时需在 PR 说明里
记录 `conan-verify` L4 的 `PIE disabled` 为已知取舍。

### 禁止做法

- ❌ 安装/挂载一个 `g++` 包装来"绕过" Error 127 —— 掩盖了工具链注入缺失的
  真问题，且 CI clean 环境不可复现。
- ❌ 把 `-D__OHOS__` 之类平台宏塞进补丁来"条件化"这套标志 —— 本问题的修复
  与平台宏无关，纯属工具链注入；补丁平台宏会被 CI PF5/R8 拦截。

## 验证命令

```bash
# 1) 构建（CXX 由 conan conf 注入）
make CXX=/data/service/hnp/bin/clang++ -j1 ; echo rc=$?      # 期望 rc=0
# 2) 硬化属性
readelf -h  ./<bin> | grep Type                             # 期望 DYN
readelf -lW ./<bin> | grep -E 'GNU_RELRO|GNU_STACK'          # RELRO 存在 + STACK RW(NX)
readelf -dW ./<bin> | grep -E 'NEEDED|FLAGS'                 # BIND_NOW；NEEDED 计数符合预期
```
