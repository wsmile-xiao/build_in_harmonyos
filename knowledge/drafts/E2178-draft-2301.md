# E2178: Published Conan versions require a new recipe identity

## Symptom

Platform CI stops at L0 with `version_not_incremented` and reports that the
same package/version is already published with a different recipe, even when
the local recipe builds and the target consumer passes.

## Root cause

The Conan registry identity is package plus version plus recipe revision, but
the OHPCD publication gate does not allow a changed recipe to reuse an already
published package/version. Local caches and local `conan create` results do not
prove that the remote identity is available.

## Fix

1. Freeze the failed PR, its exact HEAD, and the authoritative CI diagnosis.
2. Increment only the adaptation suffix, such as `X.Y.Z` to `X.Y.Z.1`; keep
   the upstream source release URL, source version, and SHA-256 unchanged.
3. Create a new version directory and branch whose names end in the new
   package/version identity, then update `self.version`, `conandata` keys,
   manifests, test metadata, and PR/Issue evidence together.
4. Create a distinct Issue and PR and rerun PRE_CREATE/POST_CREATE contracts
   against the new candidate tree before triggering exact-head CI.

## Verification

Allegro 4.4.3.1 CI build #37181 failed before compilation with
`allegro4.4/4.4.3.1 already published with different recipe` and explicitly
requested `allegro4.4/4.4.3.1.1`. The successor uses the new directory and
branch identity while retaining the official 4.4.3.1 source hash.

## Applicability and safety boundaries

This applies to any changed Conan recipe rejected by the registry's published
version gate. It does not authorize force-pushing or mutating the failed PR,
guessing an unpublished revision, or changing the upstream source version just
to avoid a collision. A successor must carry fresh hashes and fresh CI; old
CI/build/runtime results remain provenance only and cannot be counted as
successor CI evidence.
