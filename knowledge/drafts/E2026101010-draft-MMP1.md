# 原测试的零退出码必须与功能输出及数值 oracle 同时核验

## 触发特征

旧 Fortran 示例、命令行数值程序或脚本的退出码为零，却包含库级错误信息，
没有原功能输出，或保存／恢复并未完成。这样的程序可能在统一清理路径执行
不带错误码的 STOP。不能把命令成功当成功能通过。

## 根因与失败反例

真实 MUMPS r003 的保存／恢复在不可写 `/tmp` 返回 INFOG(1)=-71，
程序随后 STOP，SSH 和进程 RC 却为零。失败输出与原源码证明问题属于目录
及功能结果边界；不能用 RC0、已有一次普通求解成功或新消费者测试掩盖它。
该事务保留为 1 PASS、1 FAIL、9 NOT_RUN，总分母 11。

## 可复用修复步骤

1. 从原 Makefile、README 与 fixture 绑定所有原用例及功能语义，不用静态注册
   或 assertion 数替代执行。保留原算例和清理流程。
2. 仅让持久化目录读取任务私有输入。Fortran 同时检查 LENGTH/STATUS，C 在复制
   前检查目标数组容量。变量缺失保留原默认，截断和其他错误失败闭锁。
3. 每个真实原进程既检查 RC，又检查库级错误、原功能终态与独立数值预期。
   实数、复数和不同精度按原输入单独核验；实例创建不是数值求解，不混计。
4. 保存每个原 stdout/stderr 的 SHA-256、命令 RC、源码 ID、同事务身份和完整
   回执链。原失败与局部成功不可跨 run 拼成全量成功。

## 适用与安全边界

本模式适用于退出码与功能错误脱节的原测试和受限平台持久化路径。
不能用于放宽认证、虚构硬件能力、忽略未知崩溃或修改原数值预期。
上述历史 native 结果不能认证随后修改的候选，也不是提供者发布、FEniCS 完成或平台 CI PASS。

## 增量：功能成功与交付共享库身份须分别验证

绿色流水线和数值求解成功仍可能包含真实 ELF 交付缺陷。build95859 原始日志的
L5 失败来自五个共享库没有 SONAME，不能套用其他任务的“缺 readelf”解释。
修复共享链接时仅识别精确交付 basename，为真实链接补 SONAME；原正确显式值
保持不变，冲突值失败闭锁，编译／预处理及无关目标不注入。九项参数控制只证明
参数边界，必须继续用真实产物的动态节证明所有 SONAME 和非路径 NEEDED。

r576 已证明成品六项 SONAME 正确，但 bare readelf 缺失使原 L5 门禁失败；
该事务仍为失败。全新 r585 冻结私有 argv 透传包装器，调用已验证的 LLVM
检查器且不改变原判定，真实正式 Conan 和完整本地门禁通过：原 11/11、消费者
4/4、鸿蒙 1/1、SONAME 6/6、L5 PASS，零跳过。独立观测 SHA-256：
176099c0bdee2d15361c412c8d78915e4bf2ff2a4866df8e378dfee4e7307380。
完整回执和任务进程清零已核验；不把它当新 HEAD 平台 CI 或已发布依赖。

通用决策顺序是：保留原始失败 → 实际工具及动态节 → 精确共享链接修复 →
参数正负控制 → fresh 目标完整验证。工具缺失不能解释确有问题的 ELF，正确
链接参数也不能替代交付成品检查；不得修改系统工具或手写 CI 成功标记。
