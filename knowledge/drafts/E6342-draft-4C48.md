# E6342 — 将 FUSE 测试拆成 CLI 契约和授权挂载能力

> 状态：draft，仅作为路径 B / B 类知识库扩展候选材料提交评审。

## 错误特征

FUSE 文件系统包经常出现“编译成功，但不能挂载”的情况：

```text
/dev/fuse: Permission denied
fuse_session_mount: Permission denied
mount test skipped
```

另一个容易误判的情况是，通用 L2 smoke 执行 `--version` 或 `--help` 时看到
非零返回码，但包自己的 CLI 合约规定这两个路径返回 `9`。如果不读源码和
test_package，可能把合法行为误判为失败。

还要避免反向少报：上游把测试放在 vendored 目录、没有接入顶层 `make check`
时，不能写成“上游没有测试”。ext2fuse 的
`tests/pjd-fstest-20080412/tests/` 递归盘点得到 12 类、184 个 `.t` 文件；
每个文件都必须进入 discovered/executed/passed/failed/blocked 台账。

## 为什么需要分层

ext2fuse 至少有三层不同的能力：

1. **安装层**：Conan package 中存在可执行的 `bin/ext2fuse`。
2. **CLI 层**：版本、帮助、缺少参数时输出和退出码稳定。
3. **FUSE 运行时层**：打开 `/dev/fuse`、访问内核 FUSE 接口、读取 ext2 块
   设备、挂载目录和处理文件系统请求。

前两层可以在普通消费者测试中确定性验证，第三层受设备节点权限、SELinux/
安全域、挂载点类型、可用块设备和测试镜像影响。把三层压成一个“运行程序”
断言，会导致 CI 要么假绿，要么把外部设备限制错误归因给配方。

## 推荐测试设计

### 无特权 test_package

测试安装后的二进制，不引用源码目录：

```bash
"$BIN_DIR/ext2fuse" --version
# ext2fuse 0.8.1 的上游约定返回 9
"$BIN_DIR/ext2fuse" --help
"$BIN_DIR/ext2fuse"
```

每个路径都应显式记录返回码和关键输出。ext2fuse 的消费者测试验证了：

- `--version` 返回 `9`，输出包含 `ext2fuse version 0.8.1`；
- `--help` 返回 `9`，输出包含 `ext2fuse devicename mountpoint`；
- 无参数时返回非零并输出用法；
- 安装的二进制具有执行权限。

### 条件化 mount test

只有在下面条件都满足时才进入真实挂载：

```bash
test -r /dev/fuse && test -w /dev/fuse
command -v mke2fs
test -d "$MOUNT_POINT" && test -w "$MOUNT_POINT"
```

随后创建一次性 ext2 镜像，在独立目录挂载，检查文件创建、读取、目录枚举
和卸载。测试结束必须清理进程、挂载点和镜像。没有设备授权时，必须输出
`not run: /dev/fuse permission denied` 这类可追溯结论。

### 上游 suite 的完整台账

对于 `prove -r`、递归 shell 测试或外部 runner，不要只保留一个总的
“not run”。建议固定使用以下五个数量：

```text
discovered = 从源码树发现的测试文件数
executed   = 实际启动并得到测试结果的文件数
passed     = 通过文件数
failed     = 真实失败文件数
blocked    = 因 runner、权限、设备或前置条件未能启动的文件数
```

必须满足 `discovered = executed + blocked`，并且
`executed = passed + failed`（若一个文件内部还包含多条 TAP assertion，
另行记录 assertion 数，不能把文件数冒充 assertion 数）。

本次 ext2fuse 的目标设备上游脚本执行记录是：

```text
discovered 184
executed 184
passed 111
failed 73
blocked 0
```

设备端已完成源码解包和数量复盘；上游原始 `make` 已执行但因 Makefile 硬编码
`gcc` 返回 `2`，使用可写 `TMPDIR` 的 OHOS Clang wrapper 编译 `fstest` 成功，
并创建了 32 MiB ext2 镜像。随后 `prove`/`perl` 未安装，`mount` 报
`bad /etc/fstab`，`/dev/fuse` 读写均为 `Permission denied`，所以官方
`prove` + 真实 ext2/FUSE 挂载闭环仍单独记为 blocked，而不是 pass 或被隐藏。

在缺少 `prove`/Perl 时，还可以做一项不等价但有价值的设备端能力验证：将每个
`.t` 文件放到独立的普通 HMDFS 目录，用 `/bin/sh` 直接启动，并单独保存 TAP
文本。本轮新真机 `10.62.178.77:2222` 的 184 个脚本全部启动，shell 返回码
均为 0，TAP 中有 1115 个 `ok` 和 833 个 `not ok` 断言。这个结果揭示了两个
可复用边界：

1. 上游脚本可能把断言状态写进 TAP，但进程本身仍返回 0；不能只看 shell 返回码
   判断测试通过。
2. 普通 HMDFS 目录不具备真实 ext2 挂载和 FUSE 内核语义；即使脚本产生了
   `ok`，也只能作为设备端 shell/syscall 启动证据，不能并入目标文件系统 suite
   的 `passed/failed`。

因此建议同时保留两组统计：目标设备上实际启动的上游脚本
`discovered/executed/passed/failed/blocked`，以及官方 runner/真实挂载能力门禁的
`runner_status/mount_status/fuse_status`。两者不能混算。

## 宿主机补工具后的边界

“设备缺少 `prove`”不应成为停止调查的理由，但补齐宿主机工具后也必须判断
执行环境是否等价。一个可复用的排查顺序是：

1. 尝试安装官方或兼容的 TAP runner；记录安装器、版本和失败码，不因安装
   失败就把测试改成未尝试。
2. 用目标 SDK 交叉编译测试辅助程序，检查 ELF 架构和 sysroot 头文件；
   这可以证明源码和目标编译链可用，但不能证明宿主机能够运行目标 ELF。
3. 用真实 `prove` 对少量代表性 `.t` 文件做实际启动，保留 TAP 断言和首个
   错误；再对完整套件设置限时，避免无限等待掩盖根因。
4. 将宿主机结果单独放入 `local_host_attempts`，不写入 OHOS
   `executed/passed/failed/blocked`，除非运行时具备相同的目标 OS、文件系统、
   用户/组权限、设备节点和挂载能力。

ext2fuse 本轮的本机证据如下：

```text
Git for Windows Perl + Test-Harness 3.52：runner 可加载
OHOS Clang：fstest.c 交叉编译成功，生成 AArch64 ELF
mkdir/00.t：36 assertions，5 passed，31 failed
open/00.t：47 assertions，9 passed，38 failed
prove -r：实际启动 41 个文件后 timeout 124
共同首错：../../fstest: No such file or directory
```

失败不是测试被静默跳过，而是 Windows/Git Bash 没有可执行的 `fstest`，且
OHOS AArch64 ELF 不能直接在 Windows 主机执行。即使部分 shell 断言显示
`ok`，也不能据此宣称 ext2fuse 的 OHOS FUSE 行为通过。宿主机结果必须与随后
真机普通 HMDFS 目录的 `184 discovered / 184 executed / 111 passed / 73 failed /
0 blocked` 分开记录，并在旁边附上官方 `prove` 与真实挂载闭环的恢复条件。

## 本次适配证据

ext2fuse 的 Shadow CI 已完成 OHOS armv8 构建、安装和 test_package，runner
返回码为 `0`，消费者 4/4 断言通过。在新真机上的上游 suite 前置检查显示：
184 个测试文件已盘点，`fstest` fallback 编译、ext2 镜像创建和 184 个脚本逐个
启动均完成；普通 HMDFS 目录直跑的文件级结果为 111 通过、73 失败、0 阻塞。
同时，`prove`/`perl`、ext2 mount 和 `/dev/fuse` 权限均不可用，因此本轮没有把
真实 ext2/FUSE 挂载写成通过。这是一个明确的运行时外部条件边界，而不是编译
配方失败。

## 禁止做法

- ❌ 看到 `--version` 非零就修改上游 CLI 或测试脚本，把合法退出码改成 `0`。
- ❌ 没有 `/dev/fuse` 授权时用 `echo PASS`、mock mount 或空目录替代真实挂载
  证据。
- ❌ 为了让 CI 变绿在配方里删除 FUSE session 初始化。
- ❌ 把“二进制能执行”写成“文件系统功能已验证”。

## 验证

```bash
set +e
"$BIN_DIR/ext2fuse" --version >version.txt 2>&1
version_rc=$?
"$BIN_DIR/ext2fuse" --help >help.txt 2>&1
help_rc=$?
set -e
test "$version_rc" -eq 9
test "$help_rc" -eq 9
grep -q "ext2fuse version 0.8.1" version.txt
grep -q "ext2fuse devicename mountpoint" help.txt
```

设备端无 `prove` 时的补充能力探针可以使用：

```sh
for test_file in $(find tests/pjd-fstest-20080412/tests -type f -name '*.t'); do
    mkdir -p "$probe_root/$(basename "$test_file")"
    cd "$probe_root/$(basename "$test_file")"
    /bin/sh "$test_file" > tap.txt 2>&1
done
```

该探针必须标注为 ordinary-HMDFS shell probe；它可以计入目标设备已实际启动的
上游脚本执行台账，但不替代真实 ext2 mount、`/dev/fuse` 检查和 `prove -r`。

真实 suite 的恢复条件是设备管理员提供可执行的 `prove`/Perl，授予当前测试域
ext2 mount 和 `/dev/fuse` 能力，并保留可丢弃的 ext2 镜像或块设备。条件满足
后，先按上游 README 编译 `fstest`，再进入挂载点执行 `prove -r`，最后把
184 个文件的通过/失败/阻塞数字和 TAP 原始结果回填。
