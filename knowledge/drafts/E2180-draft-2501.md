# E2180 draft: GNU make's HMDFS FIFO warning is not a terminal verdict

GNU make can print `jobserver mkfifo: .../GMfifo...: Operation not permitted` when its `TMPDIR` is on HarmonyOS PC's HMDFS. FIFO creation is denied, but the warning does not by itself identify whether the build and tests ultimately failed. Existing E074 explains why `-j1` is prudent but describes the FIFO denial as a hang or command failure. E292 mentions the warning in a broad test migration. A zlib shadow-CI draft notes one successful build despite it. The increment here is an explicitly paired failure-and-success diagnostic: the same warning occurred in an earlier run that failed for a different C++ error and in a final run that passed, including a nested Conan/CMake consumer despite `-j1` for the upstream build.

In the MAdLib mesh-adaptation run `madlib-w3-20260929T042222Z`, the warning appeared before a separate, fatal C++ error: `_SC_PAGE_SIZE` was undeclared because the source omitted `<unistd.h>`. After that source fix, the final run `madlib-w3-20260929T043214Z` still printed the same FIFO warning during library and consumer builds, but `conan create` returned 0, the static package was created, upstream `make check -j1` completed with zero registered cases, and the installed-package consumer passed 1/1. The final log SHA-256 is `4ca43c65ba0422dbacef04b2f5bc92d864fe7ea0234013ab50efa126a761abe1`; the frozen transaction and postrelease validator passed.

For another GNU make or CMake Unix Makefiles recipe on HMDFS, bind temporary files to the task's own directory and use `-j1` when parallel jobserver behavior is unsafe. Then judge the result by the process exit code, first actual fatal diagnostic, expected package artifacts, upstream test count, and consumer execution. `-j1` does not guarantee the warning disappears: a nested Conan/CMake step may invoke make with a separate `-j` value. Conversely, never ignore a nonzero exit just because the FIFO warning can be harmless. If a policy-approved task-private native filesystem is available, moving `TMPDIR` there is a separate bounded remedy; do not use a shared or foreign task path.
