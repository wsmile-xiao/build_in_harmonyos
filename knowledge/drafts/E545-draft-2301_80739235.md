# E545: Header-only Conan recipes still require target identity and signed consumer evidence

## Problem and trigger

A Conan recipe that packages one public header and declares no dependencies can look complete after a Windows `conan create`. That result does not establish the OpenHarmony target package identity or prove that a consumer can execute under the target loader. The trigger is a header-only package whose host test passes while the target profile, signer, or runtime domain is still unverified.

## Root cause

Header-only layout removes the library link closure, but Conan still computes a target package identity from `os.version`, architecture, compiler, libc++, and C++ standard. A real consumer is an ELF executable and therefore crosses the target loader and code-signing boundary even when the package itself has no `.so` or `.a` output. Treating “no dependencies” as “no target gate” hides both classes of failure.

## Reusable repair

1. Create a task-private Conan home and bind the authoritative OHOS profile, including `os.version=6.0`, `arch=armv8`, clang 15, libc++, and C++17.
2. Run `conan graph info` with `--build=never` and record the full graph, `info_invalid`, and target package identity. Keep graph-only evidence separate from a build result.
3. Compile the smallest real consumer with the target toolchain and bind its exact bytes and SHA-256.
4. Transfer the consumer and the frozen native signer over the authorized USB-HDC transport (SSH only through that HDC forward when the shell domain needs it), independently read back byte count and SHA-256, sign in the target domain, and verify `display-sign`.
5. Launch exactly once, capture the consumer result, verify no leftover process or temporary output, then release and independently verify the task root is absent.

## Evidence and validation

For `fast-cpp-csv-parser/0.0-git20160525-9bf299c-3`, the target graph had one node, zero dependencies, `info_invalid=null`, and target package ID `6b129b068851896169fae42d399fa922d239ce8a`. The signed AArch64 consumer ran once on USB serial `3QC0124C20000792` through the HDC-forwarded endpoint and returned `fast-cpp-csv-parser smoke rows=2` with RC 0. The monitor found no process and no temporary CSV; release and postrelease cleanup both passed.

## Safety boundary

This pattern proves only the target W0 graph and one target consumer run for the frozen candidate. It does not replace upstream tests, platform CI, AI Review, Pre-PR, or submission gates. Once `launch_count=1`, do not relaunch or overwrite the run; any payload, endpoint, boot identity, signer, or test-denominator drift requires a create-new successor.
