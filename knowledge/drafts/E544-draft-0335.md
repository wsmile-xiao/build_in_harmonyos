# E544（草稿）— 设备 grep 遇 NUL 截断，二进制产物内容断言在真机误报失败

**类别**：OHOS / 测试 / toybox / 可移植性
**来源**：lcab 1.0b12，PR !11486，CI #56257

## 错误特征

```text
OK: usage banner reports v1.0b12
FAIL: file name not stored in cabinet
ERROR: lcab/1.0b12 (test package): Error in test() method, line 37
```

编译、`make install` 都通过；同一个 `test_package` 脚本在 x86 开发机（GNU grep / busybox grep）全绿，只在 OHOS 真机 CI 失败。

## 触发条件

- `test_package` 用 shell 脚本对**二进制产物**做内容断言，例如 `grep -q "payload.txt" single.cab`。
- 产物文件头含 NUL 字节，被查找的字符串位于同一“行”中第一个 NUL 之后。
- 在 OHOS 真机 runner 上运行（PATH 中的 grep 为 toybox 实现）。

## 根因分析

toybox grep 逐行读入后以 C 字符串调用正则匹配，一行里第一个 NUL 之后的字节对匹配不可见。cab 头部（`MSCF\0\0\0\0...`）之后直到数据块里的第一个 `\n` 之前都算同一行，文件名和数据全在 NUL 之后，所以永远查不到。GNU grep 与 busybox grep 按字节匹配二进制文件，本地复现不了。

`head -c 4 file | grep -q MSCF` 不受影响（魔数在 NUL 之前），这也是该日志里魔数检查通过、文件名检查失败的原因。

## 推荐方案

对二进制文件改用 bash 内建按 NUL 切段匹配，不依赖设备的外部工具：

```bash
cab_has() {
    local LC_ALL=C chunk
    while IFS= read -r -d '' chunk || [ -n "$chunk" ]; do
        [[ $chunk == *"$2"* ]] && return 0
    done < "$1"
    return 1
}
cab_has single.cab "payload.txt" || fail "file name not stored in cabinet"
```

文本文件（`--help` 输出、日志）照常用 grep。

回退：`tr '\000' '\n' < file > file.txt && grep -qF needle file.txt`（需确认设备 tr 支持八进制转义）。

## 禁止做法

- 只加 `-a` / `--binary-files=text` 就当修复：开发机上 GNU/busybox 本来就通过，无法证明它能绕过设备 grep 的 C 字符串匹配，未经真机实证不可依赖。
- 删断言或 `|| true` 吞返回码：测试退化为空壳（R34/L1e）。

## 验证

```bash
printf 'MSCF\0\0name.txt\0data\n' > t.bin
grep -q name.txt t.bin; echo rc=$?     # 真机 toybox: 1；GNU/busybox: 0
```

lcab 修复后：x86 原生临时构建跑 `test_lcab.sh` 5 场景全过；`cab_has` 查不存在的字符串返回 1（反向用例）。真机效果以 PR !11486 修复后的 CI 为准。

## 查重

`engine` 用该失败日志只命中 E161（stdin 管道权限），不相关；现有 toybox 条目 E182（install）、E254 / E510（patch）、lesspipe 草稿（file --mime）均未覆盖 grep 的 NUL 截断。
