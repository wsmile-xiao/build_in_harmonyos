# E2162 - Prove Conan source-cache semantics before replay

## Symptom

An offline replay copied files from Conan's cache `s` directory and attempted
to reverse the previous patch set. The first reverse patch failed, while files
known to be added by earlier patches were absent.

## Root Cause

The cache `s` directory retained pristine downloaded sources. The recipe had
applied archive patches later in a separate build copy. A successful build log
therefore proved that the build used the patches, but not that `s` held their
postimages.

## Fix

Inspect exact bytes from a known modified file and the presence of a known
patch-added file. When those checks prove the cache is pristine, copy only the
existing target preimages. Require every missing target to be an explicit
`/dev/null` addition in the ordered current patch set, leave it absent, and
apply all patches exactly once in order. Preserve failed roots and create a new
successor for the corrected replay.

## Validation

The corrected `synergy-core/1.20.4` replay copied 33 pristine targets, accepted
15 declared additions, applied 43/43 patches, and produced 48/48 postimages.
The postimage inventory was hashed, and the source/patch conditional-macro scan
reported zero added conditions whose macro name contains `OHOS`.

## Safety Boundaries

- Do not infer pristine or postimage state from a cache directory name.
- Do not reverse patches until exact bytes prove the input is a postimage.
- Do not synthesize missing preimages unless the patch declares an addition.
- Replay success does not replace full build or target execution evidence.
