# E635 — x86_64 runner 无法启动 OHOS aarch64 动态产物：同源 .o 静态重链 + qemu 做功能验证

- 软件实证：multitee 3.0（CLI 工具，test_package 执行包内 bin/multitee）
- 阶段：本地 W3（conan create 的 test 阶段）与适配期功能验证
- 日期：2026-09-23

## 错误特征

```text
aarch64-binfmt-P: Could not open '/lib/ld-musl-aarch64.so.1': No such file or directory
```

这条报错出现在 x86_64 runner 上：直接执行 OHOS 产物，或 test_package 在 `conan create` 的 test
阶段执行包内二进制时都会出现。同一配方在 aarch64 OHOS CI worker 上正常。

## 触发条件

- 宿主：x86_64，binfmt_misc 注册了 `qemu-aarch64`（`cat /proc/sys/fs/binfmt_misc/qemu-aarch64`
  显示 `interpreter /usr/libexec/qemu-binfmt/aarch64-binfmt-P`、`flags: POF`）
- 产物：OHOS clang 默认链接出的 PIE 动态可执行文件，`PT_INTERP=/lib/ld-musl-aarch64.so.1`
- 宿主根文件系统没有 OHOS 的 musl loader

## 根因分析

qemu-user 负责模拟 CPU，但动态可执行文件的第一步是装载 `PT_INTERP` 指定的 loader。
x86_64 宿主上没有 `/lib/ld-musl-aarch64.so.1`，所以镜像在进入 `main` 之前就失败了。
这不是产物的问题：同一个文件拿到 aarch64 OHOS 设备上可以正常运行。

## 解决方案

### 推荐方案：同源 `.o` 静态重链 + qemu 实跑功能用例

`conan create` 的构建目录保留着与交付产物同源的目标文件，用同一把 OHOS clang 重新静态链接一次即可：

```bash
B=$CONAN_HOME/p/b/<pkg-id>/b/src          # multitee: 7 个 .o
/data/service/hnp/bin/clang -static -O3 -o $HOME/tmp/multitee.static \
    $B/multitee.o $B/sigsched.o $B/sigdfl.o $B/ralloc.o $B/getopt.o $B/fmt.o $B/scan.o
file $HOME/tmp/multitee.static   # ELF 64-bit LSB executable, ARM aarch64, statically linked
# 静态 aarch64 镜像由 binfmt/qemu-aarch64 直接执行，把 test_package 的功能用例指向它
```

`-static` 链接的是 NDK sysroot 自带的 `usr/lib/aarch64-linux-ohos/libc.a`，也就是 OHOS 的 musl，
不是通用 musl。multitee 实测结果：交付产物与构建目录产物 sha256 一致；静态副本在 qemu 下跑
11 项功能用例，11/11 通过。其中包括管道 EPIPE/SIGPIPE、select 多路调度、EOF 联动这些依赖 libc 实现的路径。

test_package 侧写法（multitee `test_multitee.py`）：

1. 制品检查在任何宿主都执行：ELF64/EM_AARCH64、PIE、`PT_INTERP`、可执行位。
2. aarch64 宿主（CI worker）上功能用例强制执行，任何失败都报失败。
3. 非 aarch64 宿主上，只有当启动失败带显式标记（`Could not open '/lib/ld-musl`、`Exec format error`
   等）时，才把功能层报为 `[skip] … (SKIPPED)`。镜像一旦启动，结果一律按断言判定。
4. 二进制缺失直接失败，不在 PATH 上回退查找，这样 CI L1e 反向验证依然有效。

### 必须如实声明的边界

- 静态副本验证的是程序逻辑与 OHOS musl libc 的实现，**不等于交付的动态产物已实跑**。
  它不经过动态 loader，重定位也不同（静态产物是非 PIE）。
- qemu-user 把系统调用转发给宿主 Linux 内核，**不覆盖 OHOS 内核差异**（seccomp、HMDFS、只读 /tmp 等）。
- 所以 notes/PR 里要写"本地 qemu 静态副本 N/N，交付产物功能用例由 aarch64 CI 执行"，
  不能写成"已在 OHOS 上实跑通过"。

### 回退方案

无法静态重链时，改走"通用 musl loader + 注入 OHOS fortify 符号"的路径，见
`DRAFT-yosys-0.66-ohos-aarch64-local-run-missing-fd-chk`。典型场景是依赖只有共享库、用了 libc++_shared，或需要 dlopen 插件。

### 禁止做法

- ❌ test_package 捕获启动异常后 `return 0` / `|| true`，既不打标记也不声明 SKIPPED。
  这属于假绿，aarch64 CI 上真实的启动失败也会被同一分支吞掉。
- ❌ 为了让动态产物"跑起来"去拼 `QEMU_LD_PREFIX`、伪造 loader 路径。这是未验证的环境改造，
  结论也无法迁移到 CI。

## 验证

```bash
file <bin> | grep -o 'interpreter [^,]*'           # interpreter /lib/ld-musl-aarch64.so.1
test -e /lib/ld-musl-aarch64.so.1 || echo 'no OHOS loader on host'
file $HOME/tmp/<tool>.static | grep -q 'statically linked' && $HOME/tmp/<tool>.static <args>
```
