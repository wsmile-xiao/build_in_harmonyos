# E7009 — Conan 包名、codeload 固定下载和 Windows buildenv 边界

## 错误特征

适配一个依赖上游 C/C++ 库的简单 Makefile 项目时，按上游库名查询 Conan
制品可能出现 `No package ... found`，但 OHPCD 中实际包已存在；GitHub
codeload 的提交 URL 末段没有文件扩展名时，配方下载还可能无法稳定确定
归档文件名；在 Windows worker 中直接执行 Conan 生成的 POSIX buildenv 脚本
会在编译前报命令或语法不识别。

## 触发条件

- 上游项目名称、API 名称、Conan 制品名和 CMake target 名称不完全相同。
- `conandata.yml` 使用 `https://codeload.github.com/.../tar.gz/<commit>` 这类不可变提交 URL。
- 配方的 `build()` 在 Windows 主机运行，编译器和归档器由 Conan profile/conf
  注入，而不是由固定的系统 PATH 提供。

## 根因分析

1. **包名是制品仓契约。** 本次 `ccurl` 使用 `libcurl` API，但 OHPCD 的精确
   包名是 `curl/8.15.0`，其消费者目标为 `curl::libcurl`。使用 `libcurl/8.15.0`
   查找会产生缺包假象，不能据此导入依赖。
2. **codeload URL 不提供扩展名。** 提交归档 URL 的末段只有 40 位提交号，
   Conan `get()` 应同时接收 `filename` 和 SHA-256，才能把下载、缓存和校验
   绑定到同一文件身份。
3. **Windows 与 POSIX 激活语法不同。** Conan 可能生成 `conanbuildenv-*.sh`，
   但 PowerShell/Windows 原生命令不理解 POSIX 的 `.` 激活命令。把激活字符串
   交给 `shell=True` 也会引入未绑定的环境和路径解析；应读取结构化
   `tools.build:compiler_executables`，再以参数列表调用 `subprocess.run(...,
   check=True)`。

## 解决方案

### 1. 先校准精确包名

```text
conan download curl/8.15.0 -r=ohpcd --only-recipe
conan install --requires=curl/8.15.0 --build=never -r=ohpcd
```

记录实际的 RREV/PREV、目标 profile 和依赖闭包。上游名称或链接名只能作为
候选线索，不能替代制品仓回读。

### 2. 固定提交源码并显式命名

```yaml
sources:
  url: "https://codeload.github.com/gsauthof/ccurl/tar.gz/<40-hex-commit>"
  filename: "ccurl-1.0.0.tar.gz"
  sha256: "<downloaded-bytes-sha256>"
```

`filename` 必须与 `get()` 的下载契约一致，哈希必须来自该提交归档的实际
字节。不要用 `refs/heads/master` 等可变地址作为交付候选。

### 3. 结构化调用 Windows 工具链

```python
executables = self.conf.get("tools.build:compiler_executables", default={}) or {}
cxx = executables.get("cpp", "c++")
subprocess.run([str(cxx), "-std=c++11", "-c", source, "-o", object_file], check=True)
```

这只解决 host-side 配方执行边界；目标 OHOS/arm64 的交叉构建、真机运行和
平台 CI 仍需单独验证。

## 本次验证

`curl/8.15.0`、`openssl/3.5.6.1`、`zlib/1.3.1.1` 在 OHOS/aarch64、
`--build=never` 下解析成功。固定提交 `6f55068a7038c9ec16e6c904ab6f639163f1bb9f`
的归档 SHA-256 为
`dba5f916b08560b671b8caf70ae6b4a8c7ca42e6da913085cf82c0d76ca03723`；配方语法、
本地受限编译、静态归档和消费者源编译通过。Windows MinGW 不能直接链接
OHOS ELF 依赖，这一 host 工具链限制没有被误报为目标平台通过。

## 适用范围与安全边界

该结论适用于 Conan 制品名与上游命名存在偏差、codeload 提交归档无扩展名、
以及 Windows host 执行 custom/Makefile recipe 的场景。它不证明目标机工具链
或真机测试已通过，也不允许把同名但不同版本的包、可变源码地址或本地缓存
当作发布证据。

## 禁止策略

- 不用 `libcurl` 等推测名称替代 OHPCD 的精确 `curl` 包名。
- 不省略 codeload 无扩展名归档的 `filename` 或 SHA-256。
- 不在 Windows 配方里 source POSIX `.sh` 激活脚本，也不以 `shell=True` 拼接
  未绑定命令。
