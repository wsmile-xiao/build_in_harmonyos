# E2158 - Target plain-char signedness can change INT8 API results without changing stored bytes

> Contributor: 2301_80739235 | Status: DRAFT | Created: 2026-08-21

## Why this is a reusable pattern

C does not require plain `char` to be signed. Code can therefore pass on a host
where plain `char` is signed and fail on a target where it is unsigned, even
though both systems store the same 8-bit pattern.

## Symptom

An unchanged upstream target test expects negative INT8 values but receives
their unsigned promotions instead:

```text
expected -120, actual 136
expected -17, actual 239
```

Both differences are exactly 256. The source uses plain `char` variables or
`char *` output parameters for values whose API meaning is signed INT8.

## Root cause

The target compiler treats plain `char` as unsigned. When a stored byte such as
`0x88` or `0xef` is promoted to `int`, it becomes 136 or 239 instead of -120 or
-17. The byte representation is not corrupted; its language-level signedness
is different.

## Recommended solution

1. Confirm the 256-value relationship in the real failure.
2. Audit the upstream variable and API declarations to prove plain `char` is
   carrying signed 8-bit semantics.
3. Add `-fsigned-char` through the package toolchain so all affected C
   translation units use the same mode.
4. Run the complete unchanged upstream suite and package consumer on the real
   target.
5. Review ABI compatibility before replacing public API types with `int8_t` or
   `signed char` in source.

## Forbidden shortcuts

- Do not change upstream test expectations to 136 or 239.
- Do not cast only in tests or consumers.
- Do not add an OHOS conditional source macro for a compiler-mode issue.
- Do not compile only part of the library with a different plain-char mode.

## Verification

The r47 librasterlite2 target run established the failure with the complete 71
test inventory and preserved its immutable result. The r49 successor rebuilt
the same inventory with `-fsigned-char` and improved the result from `47/71` to
`70/71`, repairing 23 signedness-dependent tests. The remaining
`test_map_ascii` failure did not contain the r47 unsigned-promotion symptoms.
R65 restored both audited fixtures and still produced `70/71`, disproving the
fixture diagnosis; r68/r70 then isolated the separate `tmpfile()` EACCES and
`mkstemp()` fallback boundary. The final r196 product closure retained
`-fsigned-char` and passed `71/71` upstream tests plus the consumer's `14/14`
assertions. All consumed runs remain immutable and cannot be replayed or
relabeled.
