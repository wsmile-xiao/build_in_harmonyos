# E6343 — Conan patch_ng 需要针对实际解压源码验证补丁上下文

> 状态：draft，仅作为路径 B / B 类知识库扩展候选材料提交评审。

## 错误特征

补丁在开发者当前源码树中看起来正确，但 Conan 或 Shadow CI 在源码编译前失败：

```text
Hunk FAILED
patch cannot apply
Invalid Context
patch_ng ... context does not match
```

本次 ext2fuse 适配中，前两轮 Shadow CI 都在
`0006-fuse3-session-direntry.patch` 阶段终止，没有进入编译。失败原因不是
OHOS 编译器，而是 hunk 上下文和实际 Conan 解压源码不一致。

## 根因分析

unified diff 的 `@@ -703,7 +703,7 @@` 起始行不是补丁应用的唯一依据。补丁引擎会结合上下文寻找目标位置，
而以下因素都可能改变结果：

- 使用的源码归档不是开发者手上的同一份文件；
- 归档解压时换行或文件根目录不同；
- `conandata.yml` 中前序补丁已经改变了后续 hunk 的上下文；
- 生成文件在 source/build 阶段被重写；
- 本地使用 Git patch，Conan 使用 `patch_ng`，两者对 fuzz、new-file 和边界
  上下文的容忍度不同。

因此“`git apply --check` 通过”只能说明 Git 引擎接受，不能单独证明 Conan
构建会接受。

## 推荐工作流

### 1. 绑定真实源码

使用与 recipe 相同的 URL、SHA256、`strip_root` 和解压方式，创建全新的临时
源码目录。不要在已经失败过的 Conan source tree 上继续刷新补丁。

### 2. 按实际顺序应用

严格按 `conandata.yml` 的顺序应用 `0001`、`0002`、`0003` 等补丁。每一步都
检查退出码和目标文件差异，最后再执行 `git diff --check`。

### 3. 做双引擎验证

至少做两类检查：

```bash
git apply --check patches/*.patch
```

以及用 Conan 实际使用的 `patch_ng` 对同一份干净源码应用。不能把设备上的
toybox `patch --dry-run` 作为唯一证据。

### 4. 优先保留稳定上下文

如果 hunk 只修改一两行，应缩小范围并保留函数声明、相邻语句等稳定锚点。
不要手工把起始行号改到“看起来对齐”就结束；修改后必须从干净源码重新跑
整套补丁序列。

## 禁止做法

- ❌ 在污染过的源码树上继续 `refresh-patch`。
- ❌ 只看 hunk 起始行号，不检查上下文和前序补丁结果。
- ❌ 只使用设备 toybox patch 的 dry-run。
- ❌ 为了绕过失败把补丁应用改成 `|| true`。
- ❌ 把“补丁应用失败”误报为编译器或依赖包缺失。

## 验证证据

ext2fuse 的修复过程形成了可复现的失败到成功链：

1. Shadow CI 第一次运行在 0006 hunk 上下文不匹配处失败。
2. 第二次运行仍因 hunk 起始位置偏移在编译前失败。
3. 使用 Conan 实际 `patch_ng` 对干净源码验证修正版通过。
4. 最终 run 的 `conan create`、`test_package`、补丁洁净检查均通过，runner
   返回码 `0`。

这类链路比单次“补丁已应用”更能说明方法对 Conan/Shadow CI 是可迁移的。

## 验证命令

```bash
git apply --check patches/0001*.patch patches/0002*.patch patches/0003*.patch \
  patches/0004*.patch patches/0005*.patch patches/0006*.patch
python -c "import patch_ng; print('patch_ng available')"
conan create archives/e/ext2fuse/0.8.1 --build=missing
```

如果本机 Conan 不支持 `settings.os=OHOS`，应如实记录本机只能做补丁和配方
静态检查，并把最终交叉验证交给 OHOS Shadow CI。

## 与相似条目的区别

E526 关注 Conan `apply_conandata_patches` 的基本调用和补丁失败；E515 关注
Git 风格补丁的路径层级。本条增加的是“补丁引擎一致性”方法：源码归档、前序
补丁、生成文件和 patch engine 必须绑定到同一份干净快照，并用实际
`patch_ng` 复跑。它特别适用于本地 Git 检查通过、但 Shadow CI 在编译前失败
的场景。
