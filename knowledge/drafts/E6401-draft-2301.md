# E6401 - Conan auxiliary downloads require bounded, hash-verified mirrors

## Symptom

A package's CI wrapper reports that mirror fallback has been enabled, yet
`conan create` fails in `source()` while downloading a test framework from
GitHub. The primary release archive may already have been retrieved through a
mirror, but an auxiliary `source_url` passed directly to
`conan.tools.files.download` still uses the restored official URL. In the
DOSBox Staging build, Buildbot `42652` completed checkout and Conan setup, then
failed before compilation when GoogleTest `v1.14.0` timed out. The archived
response from `gh-proxy.com` was 867,764 bytes and had the declared SHA-256,
which distinguishes a transport failure from a bad source identity.

## Root Cause

The CI mirror transform is deliberately disposable: it rewrites
`conandata.yml`, runs a predownload helper, and restores the official file
before invoking Conan. A recipe-level `download()` call therefore receives a
single URL and cannot see the wrapper's temporary list. A worker that cannot
reach `github.com` fails even when the approved proxy is reachable. Conversely,
accepting any non-empty proxy response is unsafe because HTTP error pages and
truncated archives can look like successful downloads.

## Fix

1. Keep the official URL and expected digest in `conandata.yml` so provenance
   and metadata remain stable.
2. At the recipe boundary that downloads the auxiliary input, derive a fixed
   candidate sequence: the CI-approved GitHub proxy followed by the official
   URL. Do not accept arbitrary environment-provided URLs.
3. Call Conan's normal `download()` for each candidate with the same SHA-256.
   After an exception, delete only the destination when it is a regular file;
   retain the error text and continue to the next candidate.
4. Raise a terminal Conan error when every candidate fails. The caller must
   never receive a partial file or a digest-less success.
5. Validate the exact bytes independently before rerunning CI. For the
   GoogleTest archive, the proxy response was `867764` bytes with SHA-256
   `8ad598c73ad796e0d8280b082cebd82a630d73e73cd3c70057938a6501bba5d7`, equal
   to the frozen official value.

## Validation

The failure was reproduced from the Buildbot `conan-build-test` log (`buildid`
`48590`, log `273025`) with all prior steps at `results=0`. A bounded HTTP
probe downloaded the proxy candidate and verified its exact size, gzip header,
and SHA-256. The repaired production `source()` path is covered by Python
syntax validation and a local candidate-selection test; the official URL is
still present in the recipe metadata. A new Buildbot run is required to prove
the worker can complete Conan source acquisition and all subsequent tests.

## Applicability and Safety Boundary

This pattern applies to Conan recipes whose `source()` or helper methods fetch
auxiliary archives outside the CI wrapper's primary `conandata.yml` transform.
It does not authorize uploading cached archives, committing binary test
artifacts, or replacing an official URL with an unverified mirror. Every
candidate must pass the same byte and SHA-256 contract, and a successful
download only establishes source acquisition; build, upstream tests, target
validation, Review, and CI remain separate gates.
