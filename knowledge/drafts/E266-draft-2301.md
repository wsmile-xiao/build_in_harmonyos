# E266 - Align NEON Call Sites with CMake Implementation Sources

## Symptom

Compilation succeeds until final link, which reports undefined libpng NEON
symbols. Target headers enabled the intrinsic call sites, but CMake omitted
`arm_init.c`, `filter_neon_intrinsics.c`, and
`palette_neon_intrinsics.c`.

## Root Cause

The preprocessor and CMake used different authorities. The target compiler
proved NEON support, while the source list relied only on
`CMAKE_SYSTEM_PROCESSOR` matching an ARM spelling. Unknown cross-system
processor metadata therefore enabled declarations without implementations.

## Recommended Fix

Preserve upstream known-ARM and Apple selectors. For otherwise unknown
processor metadata, compile a real `arm_neon.h` intrinsic with the target
compiler. Append the complete implementation source set only when that probe
passes, and preserve a negative case that appends none.

## Validation

The directed matrix passed known aarch64, Apple, unknown-plus-capability, and
unknown-without-capability cases. The final ITK target linked all four
previously missing libpng NEON symbols and completed the installed-package
consumer with RC 0.

## Forbidden Shortcuts

Do not infer ARM from an unknown processor string, add an OHOS-specific source
guard, or suppress the undefined symbols. All call sites and implementation
objects must follow the same target capability.
