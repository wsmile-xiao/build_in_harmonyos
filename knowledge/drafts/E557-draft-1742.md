# E557 — OHOS 交叉工具链宿主动态库缺失导致 compiler/linker probe 失败的诊断与恢复

## 使用说明

当 OHOS 交叉构建（Conan/CMake/Meson/Autotools 等）在 configure/compiler probe 阶段报
"The C compiler is not able to compile a simple test program"，而日志更深处出现
`Error loading shared library libxml2.so.16`、`Error relocating .../llvm/bin/lld: ...: symbol not found`
一类宿主加载器错误时，适用本条知识。

判别要点：失败的是**宿主工具自身**（clang/lld 等在构建机上运行的 SDK 工具），
而不是目标二进制。SDK 的 lld 是动态链接的宿主 ELF，其 NEEDED 依赖（如 libxml2.so.16）
在当前宿主环境无法解析（例如其 RUNPATH `$ORIGIN/../lib` 未被加载器展开），
导致工具进程在启动/链接步直接死亡；CMake 只把表面症状报为编译器探测失败。

处理入口：不要去改目标包源码，也不要绕过编译器检查；按"通用处理算法"一节，
先做 ambient 真实 probe，再做工具链派生的宿主运行时发现与受限作用域重试，
最终让真实的 CMake/Conan compiler probe 自行通过。

## 适用范围

- OHOS/OpenHarmony 交叉编译（HarmonyOS PC / OpenHarmony L0-L2 / OHOS SDK 工具链）。
- Conan、CMake、Meson、Autotools 等任何调用目标工具链的构建系统，其 compiler/linker probe
  或链接步骤会启动宿主工具 clang/clang++/ld.lld/lld 的场景。
- 每个独立调用 compiler/linker 的 recipe / build context——包括主 recipe、Conan test_package
  这类独立消费者配方、以及任何子构建——都可能**单独**触发本问题（见下一节"独立配方与环境传播"）。
- 宿主工具自身因 NEEDED 动态库（.so）缺失而无法启动：缺 libxml2.so.16 只是实例，
  任何宿主动态库缺失（libz、libcurl、libedit、其他 LLVM 运行库等）均同样适用。
- 工具链路径经符号链接/wrapper 目录间接指向真实 SDK 布局的情形（realpath 解析后才能找到 lib）。

## 不适用范围

- 目标 ELF 自身缺运行时依赖（目标机 musl 加载器报 `needed by ./conftest` 或目标机运行期加载失败）
  —— 目标侧问题，见 E505（OHOS 加载器 LD_LIBRARY_PATH 压过 DT_RPATH 的目标侧语义）等条目。
- Conan registry/network/auth 类失败（下载 403/超时、远端认证）。
- 第三方源码自身的编译错误（语法、API 缺失、检测到目标平台能力差异）。
- 普通的 dependency missing（构建系统明确报缺某个 -l 库或头文件，属依赖声明问题）。

## 输入定义

| 输入 | 来源/含义 |
| --- | --- |
| compiler_executables | Conan conf `tools.build:compiler_executables`（c/cxx 等），OHOS profile 权威配置 |
| PATH | 当前环境 PATH，用于 basename 兜底定位与 bin 目录候选 |
| LD_LIBRARY_PATH | 当前环境已有值（ambient 状态），同时是候选目录来源之一 |
| compiler/linker path | realpath 解析后的 clang 与 ld.lld 真实位置（含 `-print-prog-name=ld.lld` 派生） |
| missing shared library | 从报错提取的缺失 .so 名称（如 libxml2.so.16）；通用化为"缺失宿主动态库" |
| toolchain location | clang/lld realpath、resource-dir、受限向上遍历得到的 SDK 树位置 |

## 输出定义

| 输出 | 含义 |
| --- | --- |
| resolved compiler/linker | 实际生效的 clang 与 ld.lld 真实路径（realpath 后） |
| host runtime candidate dirs | 从工具链派生、且实际包含缺失 .so 的候选目录列表（按优先级） |
| scoped environment | 通过 Conan Environment 局部 prepend 的 LD_LIBRARY_PATH（仅作用于构建，不污染全局） |
| compiler/linker probe result | ambient probe 与 scoped probe 的返回码与完整输出 |
| failure diagnostics | 失败时输出的 compiler/linker、缺失库名、已试候选目录、probe 输出（fail closed） |

## 独立配方与环境传播

Conan 的 test_package（以及任何 `conan create` 之后独立展开的消费者配方）是**独立运行上下文**，
不是主 recipe 的子进程延续。两条关键事实：

1. **主 recipe 的局部 Environment 不会自动传播到 test_package**。主 recipe 在其 `build()` 内用
   `Environment().prepend_path("LD_LIBRARY_PATH", dir)` 修复的是**自己那一次** configure/build 的
   工具链运行时；test_package 随后在自己的 `CMake.configure()` 中重新执行 CMake 编译器检查，
   重新 spawn clang/lld——此时环境回到 ambient，宿主动态库缺失问题会**原样复现**。
2. **每个独立调用 compiler/linker 的 recipe / build context 都必须单独执行**同一套
   发现 → 真实 probe → scoped 作用域序列。同理适用于一个 CI 作业里串联的多个构建
   （主包 → test_package → 下游包），它们不共享局部环境。

由于 Conan 导出 test_package 后无法直接 import 主 recipe 的 Python 代码（除非引入
python_requires 等跨 recipe 基础设施），惯用做法是：test_package 内实现**等价且最小**的
同套逻辑，并与主 recipe **保持行为一致**（候选目录派生顺序、probe 形态、fail-closed 诊断
字段逐项对齐）；两处实现需要同步维护，diff 可直接比对共享方法。

## 通用处理算法

1. **读取权威配置**：优先取 Conan `tools.build:compiler_executables`；路径有效则用实际路径，
   否则 basename + PATH/which 兜底。禁止硬编码个人绝对路径。
2. **解析真实工具位置**：realpath clang；linker 用 `clang -print-prog-name=ld.lld` 派生，
   再以 realpath 解析（覆盖符号链接/wrapper 布局）。
3. **派生宿主运行时候选目录**（按优先级，全部来自工具链自身与环境，非个人路径）：
   1. clang realpath 上两级目录下的 `lib`；
   2. ld.lld realpath 上两级目录下的 `lib`；
   3. `clang -print-resource-dir` 上两级（`<prefix>/lib`）；
   4. PATH 中各 bin 目录；
   5. 现有 LD_LIBRARY_PATH 各目录；
   6. 从工具链 bin 目录向上受限遍历（≤4 层）的 `<node>/lib` 与 `<node>/llvm/lib`。
4. **过滤**：只接受实际包含缺失 .so 文件的目录（例如存在 `libxml2.so.16` 文件的目录）。
5. **ambient probe**：用配置的 compiler/linker 做真实 compile+link probe
   （`int main(void){return 0;}` → 编译并链接出可执行文件）。成功则环境健康，直接进入构建。
6. **scoped retry**：对每个候选目录，prepend 到 LD_LIBRARY_PATH 后重试同一 probe；
   成功的目录即 SDK 宿主运行时。
7. **作用域应用**：通过 Conan `Environment().prepend_path("LD_LIBRARY_PATH", dir)` 仅在
   build 阶段局部生效；configure/build/test 全部在该上下文内运行，不修改全局环境。
8. **fail closed**：所有候选均失败时，抛出带完整诊断的异常（compiler/linker、缺失库、
   候选目录列表、最后一轮 probe 输出），构建终止。禁止静默吞错、禁止跳过检查。

## fail-closed 安全边界

- **禁止跳过编译器检查**：不得使用 `CMAKE_C_COMPILER_WORKS=TRUE`、`CMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY`
  一类绕过（见 E191 的反面教训——绕过探测会把能力误判写进产物）。
- **禁止硬编码个人绝对路径**：任何 `/storage/Users/currentUser/...`、`/data/service/hnp/...`
  一类只在特定 CI worker/个人机器上成立的路径不得写入配方或知识方案。
- **禁止全局污染环境**：不得 `export LD_LIBRARY_PATH=...` 全局导出（子进程继承会抢占其他工具
  的库解析——全局导出压过工具自身 DT_RPATH 的目标侧案例见 E505）；必须用 Conan Environment 局部作用域。
- **禁止 ln -sf 覆盖系统库**：HMDFS 软链接限制与系统稳定（R5 铁律，P016）。
- **禁止静默降级**：找不到宿主运行时必须 fail closed 并输出完整诊断，不得让错误进入后续阶段。
- **真实 probe 优先**：`clang --version` 能跑通不代表链接可用，probe 必须包含链接步
  （lld 正是死在链接步）。

## 实际示例：ls-hpack 2.3.5

- 仓库：`archives/l/ls-hpack/2.3.5/conanfile.py`（HarmonyOS PC Conan/CMake 交叉构建）。
- 症状：CI（PR #7487）上 `conan create` 主库构建成功、上游 CTest 5/5 通过，但随后的
  test_package 在 `CMake.configure()` 再次失败：`The C compiler is not able to compile a
  simple test program`；深处为 `Error loading shared library libxml2.so.16: needed by
  .../ohos/native/llvm/bin/lld` 与 `xmlFreeDoc/xmlReadMemory/xmlDocGetRootElement:
  symbol not found`。主 recipe 已用局部 Environment 修复过同一问题，但该环境不传播到
  test_package（见"独立配方与环境传播"），问题原样复现。
- 根因：OHOS clang 驱动在最终链接步 spawn `lld`；lld 是动态链接宿主 ELF，NEEDED 含
  libxml2.so.16，正常经其 RUNPATH `$ORIGIN/../lib`（SDK llvm/lib）解析，但 CI 宿主
  加载器未展开该 RUNPATH，lld 启动即失败。ls-hpack 源码无错。
- 恢复：主配方实现 `_get_cc` / `_resolve_lld` / `_libxml2_host_libdirs` / `_cc_link_probe` /
  `_linker_runtime_environment`（见 conanfile.py），严格按上述通用算法：conf 优先 →
  realpath → 六类候选派生 → 只认实际含库目录 → ambient probe → scoped retry →
  Conan Environment 局部 prepend → 失败抛 ConanException（含完整诊断）。
  test_package/conanfile.py 实现**同一套等价逻辑**（核心方法与主配方逐字节一致，
  候选派生/probe/fail-closed 诊断同步），在其 `build()` 内 configure 前独立执行
  发现与 probe，并将 scoped Environment 仅应用于 `CMake.configure()`/`CMake.build()`。
  两处均未跳过 CMake 编译器检查、无硬编码路径、无全局环境修改。
- 结果：CMake/Conan 构建成功；上游 CTest 5/5 通过；test_package 亦恢复通过。

## 验证

```bash
# 1. 确认宿主工具缺库（诊断面）
ldd <llvm-bin>/lld 2>&1 | grep "not found"          # 预期: libxml2.so.16 => not found
# 2. 派生 linker 与 resource-dir
<cc> -print-prog-name=ld.lld
<cc> -print-resource-dir
# 3. 真实 compile+link probe（ambient）
echo 'int main(void){return 0;}' > /tmp/p.c && <cc> /tmp/p.c -o /tmp/p; echo rc=$?
# 4. scoped retry（用发现的目录重试）
LD_LIBRARY_PATH=<discovered-lib-dir>:<old> <cc> /tmp/p.c -o /tmp/p; echo rc=$?   # 期望 rc=0
```
