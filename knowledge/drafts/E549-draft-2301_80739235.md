# OHOS HMDFS 上 SQLite autosetup 的手工 amalgamation 路径

## 问题现象

SQLite 的 `configure` 只是 autosetup 的 Tcl 启动器，随后由 `jimsh0` 执行
探测与子命令。OHOS HMDFS worker 即使提供目标 clang 和完整源码，也可能在
这一阶段因子进程执行受限而无法生成 Makefile。SQLite 的系统同名库还会使
共享构建依赖运行时搜索路径，难以证明消费者使用了任务包。

## 根因

该源包把生成器和测试 Tcl 树拆开：`sqlite-autoconf` 提供 amalgamation 与
shell，而完整 Tcl 测试树在 `sqlite-src` 中。生成器失败不是 C 源码不兼容，
而是目标文件系统的 host-process 能力不足。共享同名库则可能把链接解析到
系统库，掩盖任务库是否真正参与构建。

## 修复步骤

1. 固定官方 `sqlite-autoconf-3530400.tar.gz` 的 URL 和 SHA-256，确认其中有
   `sqlite3.c`、`sqlite3.h`、`sqlite3ext.h`、`shell.c` 和 `sqlite3.1`。
2. 不调用 autosetup/configure；从 Conan `tools.build:compiler_executables`
   读取目标 clang，并从同一目录解析 `llvm-ar`。
3. 使用统一特性宏编译 `sqlite3.c` 与 `shell.c`，创建 `libsqlite3.a`，再用
   同一对象链接 CLI。将 `dl` 和 `pthread` 作为 OHOS/Linux 系统库元数据。
4. 只安装头文件、静态库、CLI 和手册，并让 CMakeDeps 消费者通过
   `sqlite3::sqlite3` 链接真实 API。

## 本次验证

本任务官方页面确认 3.53.4 为最新稳定版本，源码包 SHA-256 为
`0e9483900e92cd5de8fd48d16bf9200145a61f7fd5be542a5ac81d8a9516eb9c`；包内
存在上述 amalgamation、shell 和手册文件，未包含独立 `test/` 或 Tcl
`testfixture`。消费者测试通过内存数据库建表、插入、预处理查询、两行结果
断言和 `sqlite3_libversion()` 版本断言，作为 1/1 目标消费者测试。

## 适用范围与安全边界

该模式适用于 OHOS/HMDFS 上生成器无法执行子进程、而源包自带可直接编译
amalgamation 的 C/C++ 配方。它不适用于依赖生成代码或独立上游测试树的项目；
不得用预编译主机二进制替代目标构建，不得复制系统库或跳过源校验、真实目标
验证与存在的上游测试。
