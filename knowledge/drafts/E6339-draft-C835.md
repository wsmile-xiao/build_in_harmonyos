# E6339 — OHOS Fortran 库必须用 flang 当链接驱动，且链接 flag 要齐

## 错误特征

两条互斥的错误面，分处「构建期」与「交付期」：

**构建期（flag 不全时，ld.lld 直接失败）**

```
ld.lld: error: cannot open Scrt1.o: No such file or directory
ld.lld: error: cannot open crti.o: No such file or directory
ld.lld: error: cannot open crtbeginS.o: No such file or directory
ld.lld: error: unable to find library -lm
ld.lld: error: unable to find library -l:libunwind.a
ld.lld: error: cannot open crtn.o: No such file or directory
flang-20: error: linker command failed with exit code 1
```

**交付期（用 clang 顶替 Fortran 链接规则时，构建全绿但消费者加载失败）**

```
Error loading shared library libnetcdff.so.7: (needed by ./test_netcdf_fortran)
Error relocating ./test_netcdf_fortran: _FortranATrim: symbol not found
Error relocating ./test_netcdf_fortran: _FortranAioBeginExternalFormattedOutput: symbol not found
Error relocating ./test_netcdf_fortran: _QMnetcdfPnf90_create: symbol not found
→ rc=127
```

第二种更危险：`conan create` 成功、上游 CTest 51/51 全绿，缺陷只在**安装后的库被真实
消费者加载**时才暴露。

## 触发条件

- 平台：OHOS / 鸿蒙 PC（aarch64）
- 构建系统：CMake（`project(... LANGUAGES C Fortran)`）
- 工具链：`flang-ohos/20.1.0`（精简运行集，无 crt、无 libclang_rt.builtins.a）
- 场景：Fortran 库或混合 C/Fortran 库的 Conan 适配

## 根因分析

flang-ohos 只是 Fortran 前端 + Fortran 运行时静态库，链接所需的一切要由 OHOS SDK 提供，
且分散在三个不同目录：

| 缺什么 | 由哪个参数补 | 缺失症状 |
|---|---|---|
| `Scrt1.o` / `crti.o` / `crtn.o`、`libc`、`libm` | `--sysroot=<sdk>/sysroot` | `cannot open Scrt1.o`、`unable to find library -lm/-lc` |
| `crtbeginS.o` / `crtendS.o`、clang 内建库 | `-resource-dir=<sdk>/llvm/lib/clang/<ver>` | `cannot open crtbeginS.o` |
| **`libunwind.a`** | `-L<sdk>/llvm/lib/aarch64-linux-ohos` | `unable to find library -l:libunwind.a` |

第三项是剪枝实验确认的**唯一承重项**：`-B<sdk>/llvm/bin` 不是必需，但只要缺
`-L<sdk>/llvm/lib/aarch64-linux-ohos` 就必现 `libunwind.a` 报错（该文件只存在于这一个目录）。

反向的根因：**clang 不能顶替 Fortran 的链接规则**。Fortran 的链接规则默认由
`<CMAKE_Fortran_COMPILER>` 驱动，CMake 的 `CMAKE_Fortran_CREATE_SHARED_LIBRARY` /
`CMAKE_Fortran_LINK_EXECUTABLE` 带 `if(NOT ...)` 守卫，因此在 toolchain 里可以覆盖。
但改成 `<CMAKE_C_COMPILER>` 后，链接出的 `libnetcdff.so` 虽然动态符号表里**看得到**
Fortran 运行时符号（`llvm-nm -D --defined-only` 计数与正确产物相同，均 2177 个），
消费者加载时仍解析不到——产物无法把 Fortran 运行时符号正确交付给消费方。

另有一处 CMake 规则陷阱：`<FLAGS>` 变量在 `CMAKE_Fortran_CREATE_SHARED_LIBRARY` 中
不会被展开，会被原样当参数传给编译器：

```
clang-15: error: no such file or directory: 'FLAGS'
```

## 解决方案

### 推荐方案

保持 flang 作为 Fortran 的编译器与链接驱动，不动 CMake 的 Fortran 链接规则，
只在 recipe 的 `generate()` 里把三组参数喂齐：

```python
tc.variables["CMAKE_Fortran_COMPILER"] = "<flang-ohos>/bin/flang"
tc.variables["CMAKE_Fortran_FLAGS"] = (
    "--target=aarch64-unknown-linux-ohos "
    "--sysroot=<sdk>/sysroot "
    "-resource-dir=<resource-dir>"
)
tc.variables["CMAKE_EXE_LINKER_FLAGS"] = "-L<sdk>/llvm/lib/aarch64-linux-ohos"
tc.variables["CMAKE_SHARED_LINKER_FLAGS"] = "-L<sdk>/llvm/lib/aarch64-linux-ohos"
```

- `<resource-dir>` 现场向 `<sdk>/llvm/bin/clang -print-resource-dir` 询问，不写死版本号。
- `-L` 放**链接** flags 而非编译 flags：放编译 flags 会被 flang 每次编译告警
  `argument unused during compilation`（实测 84 行噪音 → 移到链接 flags 后 0 行）。
- 构建期若要运行 Fortran 测试可执行文件，`LD_LIBRARY_PATH` 需补
  `<sdk>/llvm/lib`（给 lld 正确的 libxml2）与 `<flang-ohos>/lib`（给 flang 运行期的
  libLLVM/libMLIR/libclang-cpp），以及各依赖的 libdir。

### 回退方案

上游若硬编码 Fortran 链接器且无法改 CMake 变量，用薄包装脚本让「链接器」仍是 flang
（脚本内补齐上述 flag 后 `exec flang`），**不要**换成 clang。

### 禁止做法

- ❌ 把 `CMAKE_Fortran_CREATE_SHARED_LIBRARY` / `CMAKE_Fortran_LINK_EXECUTABLE` 改成
  `<CMAKE_C_COMPILER>`。构建期可能全绿，但产物无法为消费者的 Fortran 运行时符号提供服务。
- ❌ 在共享库链接规则里使用 `<FLAGS>`（该变量在该规则中不展开）。

## 验证

```bash
# ① 最小探针：flang 直接当链接驱动（编译+链接+真跑）
flang hello.f90 -o hello \
  --target=aarch64-unknown-linux-ohos \
  --sysroot=<sdk>/sysroot \
  -resource-dir=$(<sdk>/llvm/bin/clang -print-resource-dir) \
  -L<sdk>/llvm/lib/aarch64-linux-ohos
./hello            # 必须打印预期结果且 rc=0

# ② 剪枝：去掉 -L 必现 libunwind.a 缺失（证明它是承重参数）
# ③ 交付面：对**安装后**的库跑真实消费者，并核对 Fortran 运行时符号导出
llvm-nm -D --defined-only <pkg>/lib/lib<name>.so* | grep -c 'Fortran'
```

netcdf-fortran 4.6.4 实测：上游 CTest `51/51`（`100% tests passed, 0 tests failed out of 51`），
消费者 `27/27`。
