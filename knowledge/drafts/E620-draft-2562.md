# E620 — musl `<dirent.h>` 不定义 BSD 宏 MAXNAMLEN，老代码报 undeclared identifier

> **Contributor**: 2562 | **Status**: DRAFT | **Updated**: 2026-09-24
> **Severity**: 2 | **Category**: musl / libc / headers / portability / compat

## 触发

- 工具：clang/gcc 编译阶段。
- 源码形态：只包含 `<dirent.h>`（或 `<sys/dir.h>`）就使用 `MAXNAMLEN` 的 C 代码，
  多为 BSD 或 glibc 时代移植过来的老工具。
- 实例：ren 1.0（ibiblio `utils/file/ren-1.0.tar.gz`，1988 年 comp.sources.unix 投稿、
  1997 年 Linux 移植版），`ren.c` 的 `makerep()` 用 `char b[MAXNAMLEN]` 作文件名缓冲区。

## 症状

```
ren.c:309:9: error: use of undeclared identifier 'MAXNAMLEN'
ren.c:316:25: error: use of undeclared identifier 'MAXNAMLEN'
ren.c:329:20: error: use of undeclared identifier 'MAXNAMLEN'
```

改用 `-std=gnu89`、定义 `_GNU_SOURCE`/`_BSD_SOURCE` 都不能消除，因为这不是特性宏问题。

## 根因

`MAXNAMLEN` 最初来自 4.2BSD 的 `<sys/dir.h>`。各 libc 的放置位置不同：

| libc | 定义位置 | 值 |
|---|---|---|
| glibc | `<dirent.h>`，`__USE_MISC` 下（默认开启） | `NAME_MAX` |
| musl（OHOS） | 仅 `<sys/param.h>` | `255` |

ren 的 Linux 移植补丁把 `<sys/dir.h>` 换成了 `<dirent.h>`，在 glibc 上恰好仍能拿到
`MAXNAMLEN`；OHOS sysroot 的 `<dirent.h>`、`<sys/dir.h>` 都没有这个宏。实测 OHOS sysroot
中只有 `sys/param.h:6` 定义 `MAXNAMLEN 255`（`linux/nfs*.h`、`linux/coda.h` 中是带前缀的
`NFS_MAXNAMLEN`、`CODA_MAXNAMLEN`，不相关）。

## 修复

推荐：在使用 `MAXNAMLEN` 的源文件中补一行 `#include <sys/param.h>`。BSD、musl 都在这里定义
该宏，glibc 同样提供这个头文件，所以补丁不需要平台宏，也可以原样回馈上游。按流程修改
`.work` 源码后用 `refresh-patch --auto` 生成补丁：

```diff
 #include <sys/types.h>
+#include <sys/param.h>
 #include <dirent.h>
```

回退：若 `<sys/param.h>` 带来的 `MIN`/`MAX`/`howmany` 等宏与项目标识符冲突，改为包含
`<limits.h>`，并在该文件内加 `#ifndef MAXNAMLEN` / `#define MAXNAMLEN NAME_MAX` / `#endif`，
与 glibc 语义一致。

## 验证

```bash
SYSROOT=<OHOS sysroot>
CC=/data/service/hnp/bin/clang   # OHOS 目标编译器（NDK 的 aarch64-unknown-linux-ohos-clang）
grep -rn MAXNAMLEN "$SYSROOT/usr/include/sys/param.h" "$SYSROOT/usr/include/dirent.h"
printf '#include <dirent.h>\nchar b[MAXNAMLEN];\n' | "$CC" -x c -fsyntax-only -
# error: use of undeclared identifier 'MAXNAMLEN'
printf '#include <sys/param.h>\n#include <dirent.h>\nchar b[MAXNAMLEN];\n' | "$CC" -x c -fsyntax-only -
# rc=0
```

必须用 OHOS 目标编译器验证：glibc 主机上的 clang/gcc 会从 glibc 的 `<dirent.h>` 拿到
`MAXNAMLEN`，复现不出该错误。

ren 1.0 实测：补丁后 `conan create` 通过，test_package 13 个场景（53 条断言）在
qemu-aarch64 上全部通过。

## 禁止做法

1. 在配方 CFLAGS 注入 `-DMAXNAMLEN=255`：只掩盖头文件差异，补丁审查看不到，头文件以后也
   定义该宏时会重定义漂移。
2. 用 `#ifdef __OHOS__` 包裹定义：这是 libc 头文件布局差异，可移植写法即可覆盖；补丁中加
   平台宏违反 R8，会被 PF5 拦截。

## 关联

- 相似：E032（musl 下 dirent API 要用 `_GNU_SOURCE` 而不是 `_BSD_SOURCE` 才完整暴露，同属
  musl 的 dirent 头文件差异）、E420（老 C 代码必须包含声明 API 的那个头文件）、E500（musl 没有
  `MAX_INPUT`）。
- 与 E500 的区别：E500 的宏在 musl 中完全不存在，只能兜底定义；本条的宏在 musl 中存在，
  只是放在 `<sys/param.h>`，补 include 即可，不需要自定义取值。
- 查重：`engine` 对该报错误命中 E493（`program_invocation_name`）；`knowledge/` 全库检索
  `MAXNAMLEN` 为 0 条；`draft-review` 最相似为 E500（0.42，review-similar），属新增知识。
