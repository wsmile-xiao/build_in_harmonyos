# 文本解析器必须区分原始字节、Unicode 标量和显式字符串长度

## 可复用触发场景

纯 C 解析器声称支持 Unicode，但官方语料中 escaped-NUL 字符串被
截断、NUL 键与空键混淆、非法 5/6 字节 UTF-8 被接受，或修复解码后
编码器仍输出不同值。不能仅凭普通 ASCII 消费者成功判断协议完整。

## 精确根因

输入字节合法性、反斜杠转义后的 Unicode 标量及解码后字符串长度是
三个不同层次。源文件中的原始 NUL 可以非法，而合法转义得到的
U+0000 必须按显式长度存储。把 strlen/strcmp 当作协议字符串长度
或身份比较，会把零字节后的内容丢失，甚至使不同键发生语义碰撞。
放宽 UTF-8 又会接受超长编码、代理区或超出 Unicode 范围的标量。

## 修复决策步骤

1. 根据当前规范分别列出原始字节和转义标量允许域；先拒绝原始非法
   字节，再解码合法转义，不能用删除控制字符的方式“清洗”输入。
2. UTF-8 解码/编码使用 RFC3629 的 1–4 字节与标量范围，检查长度
   和 continuation 字节之后再访问；拒绝 overlong、surrogate、越界。
3. 内部节点同时保存 bytes+length；身份比较先比长度再 memcmp。
   提供兼容的带长度访问器，原 C 字符串 API 只作为受限包装，不破坏
   不透明结构 ABI，也不把合法 NUL 键与空键混为一个键。
4. 输出编码器使用相同长度域，明确转义控制字符；对多个独立键、
   embedded-NUL 值和空值做全结构 roundtrip，不只查退出码或对象数。
5. 旧 golden 若记录旧 bug，先以官方规范和原输入证明矛盾；保留其
   SHA/ID、公开精确规范修正，验证完整新输出，不删用例或缩小分母。

## 适用和不适用边界

适用于允许转义 Unicode/零标量的 C 文本协议解析器及其编码器。
禁止零标量的其他协议必须按自身规范拒绝，不机械增加 NUL 支持。
不能把高字节都删掉、放宽所有控制字符、仅修打印端或关闭测试；
显式长度不替代原始输入验证、内存生命周期与边界检查。
本草稿是独立的新机制，不重复申报滚动版本/SONAME，也不把当前
原生测试冒充平台 CI、AI Review、正式 Conan 或已提审。
