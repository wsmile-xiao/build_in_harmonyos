# E6346: HMDFS Release handoff across owner boundaries

## Problem symptom

The HarmonyOS PC target run completed its native tests and wrote
`result.status=PASS`, but the frozen Release phase failed with RC 93. The
remote log reported `Permission denied` for every member copied into
`evidence/output.pending`. The output tree was visible to read-only status and
the target processes were already gone.

## Root cause

HMDFS mapped the task tree to the `file_manager` service owner. Files produced
under the run output had a restrictive owner/mode such as `0640`; the task
shell could still read selected files with `cat`, and `chmod`/`umask` did not
change the cross-owner copy behavior. `cp -R` failed at the destination member
creation boundary, so treating a PASS result as releasable would have hidden a
real evidence gap.

## Reusable repair

1. Freeze the failed run and never replay its Release or Launch phases.
2. Create a new run with a unique remote root and bind the full candidate,
   endpoint, boot ID, controller, validator, and receipt identities.
3. In the successor Release helper, create the pending evidence directory
   explicitly and copy content through a `tar` stream. The stream avoids
   `cp -R` mode/owner preservation and keeps the operation inside the task
   root.
4. Verify the copied output manifest before atomically moving the pending tree
   to final evidence, then collect, validate, and retire the task root.

## Verification and evidence

For `ogmtools/1.5.1`, r011-r014 each reached target PASS but failed Release
with RC 93. r014 showed the same boundary even after `umask 022` and a
post-run `chmod`. r016 and r017 used the tar-stream helper; r017 is the
current candidate binding (`HEAD=d3e11a0c5dd67030f718e6e73af72b77984cc90d`,
`TREE=3dd0613a4154874d7b869e8f3eaf4fc6951de45f`). It completed 12/12
receipt phases, 8/8 Harmony programs, 11/11 state items, 6/6 version
assertions, consumer 2/2 programs and assertions, data paths 2/2, Release,
PostRelease, validator PASS, and `retired=true`. The final receipt SHA-256
was `9640ecd2c73ae09a8fb526ae0be3b692f354dd55d36b5c93bf53d7a23c80ed13`.

## Applicability and safety boundary

Use this pattern for task-private OHOS/HMDFS evidence handoff when service
ownership and restrictive modes make recursive copy fail. It does not apply to
ordinary Linux directories without the owner mapping. It cannot authorize
second launches, repair of an in-flight run, cross-run evidence splicing,
forceful cleanup, or skipping exact-byte transfer, signatures, receipt-chain
validation, or current-HEAD CI gates.
