# E703 — Windows-hosted OHOS Meson 的生成模块与传递链接闭包

## 问题现象

在 Windows 主机交叉构建 OHOS 的 Meson/Conan 配方中，配置阶段可能找不到 `pkg-config` 或归档工具；即使 `.pc` 文件已经生成，真实 consumer 仍可能只收到裸 `-lintl`，最终在链接阶段丢失 provider 路径或 GLib/intl 符号。Conan 还可能只为 OHOS host profile 生成 POSIX `.sh` 环境脚本，Windows `cmd.exe` 执行默认 `self.run()` 包装时会先报 `. is not recognized`，命令甚至没有启动。GLib generator 条目也可能是无扩展 Python 脚本，Windows Meson 不能直接执行。另一种独立失败是 consumer 已经链接成功，但 `test_package` 运行时通过 `env="conanrun"` 找不到被测包的共享库 SONAME，返回 127；即使日志打印了内联 `LD_LIBRARY_PATH`，目标 shell 仍可能未将其导出给加载器。

## 根因

主机工具边界和目标库闭包是两套独立契约。Meson 的 native/cross machine files 需要宿主侧 `pkg-config/pkgconf`、`llvm-ar` 和 `llvm-ranlib`；而 Conan 的 `package_info()` 必须把目标侧公共依赖和实际 intl provider 作为传递 headers/libs 导出。把 Conan provider 投影成系统库名会丢掉 provider 的任务路径和静态编译宏，生成的 `.pc` 也无法为下游恢复完整闭包。Windows/OHOS 还要处理环境脚本格式和宿主脚本可执行性：只要默认 `self.run()` 选择了 `.sh`，或 `.pc` 直接指向无扩展脚本，主机构建就会在 Meson/生成步骤前失败。运行时还需要单独生成 `VirtualRunEnv`；仅调用 `self.run(..., env="conanrun")` 不会凭空创建被测包及传递依赖的 `LD_LIBRARY_PATH`。即使直接包有 `runenv_info`，共享库闭包仍应从测试包的依赖 `libdirs` 重新解析并绑定。部分目标 shell 对带参数展开的内联赋值不会按预期导出 loader 环境，因此必须显式 `export LD_LIBRARY_PATH=... && executable`。

Conan worker 还可能在 `build()` 与 `test()` 之间重建测试构建目录。只在构建阶段复制 runtime 闭包会留下一个已通过构建期检查、执行时却消失的目录。因此 runtime staging 是执行边界契约：必须在 `test()` 中按同一输入闭包幂等重建，并在闭包为空时 fail closed。

原生 OHOS worker 还存在文件身份边界：Meson 安装生成的 SONAME 符号链可能指向 loader 已认可的原始 ELF，而把同一字节复制成新的普通 alias 或 staging 文件后，即使文件非空可读、`DT_RPATH` 与显式 `LD_LIBRARY_PATH` 都正确，loader 仍可能把新目录项视为不可装载。CI #60550 同时记录了完整 staging 清单、正确 RPATH 和 `libjson-glib-1.0.so.0` 加载失败，证明“字节存在”不能替代“loader 可接受的文件身份”。

## 修复步骤

1. 在 `PkgConfigDeps` 生成后验证宿主存在 `pkg-config` 或 `pkgconf`，并把 `pkg-config`、`ar`、`ranlib` 写入 native/cross machine files。
2. OHOS Windows 主机构建使用目标前缀 `/`，避免把 Windows 路径当成目标安装前缀。
3. 用真实 Conan 依赖声明 GLib 和 intl provider，启用 `transitive_headers=True` 与 `transitive_libs=True`；不要使用 `system_libs=["intl"]` 替代 provider。
4. 让生成的 pkg-config 模块带有 provider 的 `-L`、`-l` 和必要的静态编译宏，并在 `test_package` 中查询模块后编译一个真正调用库 API 的 consumer。

5. 在 Windows/OHOS 主机构建中，只为无扩展的宿主 Python 生成器创建任务私有 `.cmd` wrapper，并用 `env=None` 执行 configure/build/test/install，避免将 POSIX `.sh` 环境脚本交给 `cmd.exe`；POSIX worker 继续使用 Conan 环境文件。

6. 在 `test_package` 中用 `cross_building(self)` 区分原生 OHOS worker 与 Windows→OHOS 交叉 profile。仅在交叉构建且没有 `tools.build:sysroot` 时 fail closed；原生 worker 缺少该 conf 时使用目标编译器默认 sysroot；有显式值时才追加 `--sysroot`。
7. 对可运行的共享库 consumer 生成 `VirtualRunEnv`，以被测包 `lib` 目录优先，再按 Conan 依赖顺序解析绝对 `libdirs`；跳过 `build/test` trait、过滤不存在目录并去重。原生 POSIX OHOS worker 在安装阶段保留 Meson 生成的版本化 ELF，不再强制 build/package hardlink，随后只接受经过 `samefile()`、字节和 mode 校验的 SONAME alias 符号链接；消费者旁的任务私有 `runtime` 目录使用经过字节/mode 校验的副本，避免复制能力差异阻塞 loader 闭包。Windows-hosted 交叉构建继续把 alias 物化为字节与 mode 一致的普通文件。链接时写入同时含 `$ORIGIN/runtime` 和绝对包路径的 `DT_RPATH`，用 `llvm-readelf -d` 确认无 `DT_RUNPATH` 且 `DT_NEEDED` 包含被测 SONAME，随后显式导出 `runtime` 优先的 `LD_LIBRARY_PATH` 执行 consumer。

8. 不把 `build()` 阶段的 staging 目录存在性当作 `test()` 的前置事实；在执行 consumer 前，用相同的已过滤 runtime paths 再次调用幂等 staging，要求返回目录非空，再把该目录置于 `LD_LIBRARY_PATH` 首位。这样目录被 worker 重建时会恢复闭包，而复制或解析失败会在执行前明确终止。

## 平台失败边界

平台 CI #48962 的源码编译、安装和 17/17 上游测试均通过，失败只发生在消费者 `build()` 的无条件 `tools.build:sysroot` 校验。该错误不是库源码或依赖闭包失败，而是把 Windows 交叉构建的输入误套到了原生 OHOS worker。随后 CI #49061 已通过源码构建、安装、17/17 上游测试及 consumer 链接，但运行阶段报 `Error loading shared library libjson-glib-1.0.so.0` 和 RC 127，证明缺少 `VirtualRunEnv`/运行时路径是另一条独立边界。CI #49167 已生成完整路径但仍失败，进一步表明目标 shell 需要显式 export。CI #50036（构建 57257）再次在 `test_package` 运行阶段以缺失 `libjson-glib-1.0.so.0` 返回 RC 127，确认链接成功和 loader 搜索路径是两条独立契约。current-head CI #50093（Buildbot 57314）已回读出正确的单一 `DT_RPATH` 和 `DT_NEEDED`，但 worker 仍无法从 Conan 缓存路径装载 SONAME，说明平台运行隔离还要求把闭包复制到消费者旁的任务私有目录。随后 CI #50100（Buildbot 57321）在原生 OHOS worker 的 consumer link 阶段暴露了另一条环境边界：`lld` 自身缺少 SDK 侧 `libxml2.so.16`，导致 clang 无法启动链接器；这不属于目标库运行时闭包。修复必须把编译器旁的 SDK `lib`/`lib64` 目录只注入 clang/readelf 子进程的 host `LD_LIBRARY_PATH`，不能把它们混入目标 consumer 的 RPATH；同时保留交叉 profile 的显式 sysroot 门禁，不能简单删除所有校验。

## 适用范围与安全边界

适用于同时支持原生 OHOS worker 与 Windows-hosted、MesonToolchain、PkgConfigDeps 的 OHOS Conan 库，尤其是有生成式宿主工具和公共传递库的配方。不适用于把真正系统 ABI 依赖错误地包装成 Conan provider 的项目；系统库仍须由目标平台提供并经过独立 ABI 验证。`.cmd` wrapper 只能指向已验证的任务自有宿主脚本，不能把目标 ELF 当作 Windows host tool，也不能把任意路径加入 PATH。原生 profile 不提供显式 sysroot 只说明编译器有默认闭包，不等价于 Windows 交叉构建可省略 sysroot；主机工具补齐只解除配置前置条件，不等价于目标编译、真机验证、平台 CI 或提审通过。

执行边界 restaging 必须只使用已解析、已过滤的依赖 `libdirs`，不能扫描系统目录或把 host SDK 库混入目标 runtime；幂等重建也不能覆盖消费者目录之外的路径。POSIX 符号链接只能由已验证依赖目录内的精确条目创建，并必须用 `samefile()` 回读目标身份；不得接受悬空链接、路径漂移或任意外部目标。

## 新增验证：原生 worker 的跨文件系统硬链接边界

CI #61434 在当前候选 HEAD `525711869e65612133a6f6fc4ea4b86a2aad04b0` 上已经完成源码编译、安装和上游 17/17 测试，但在 `package()` 将版本化 ELF 与 build 产物做硬链接时失败；日志对应的根因是两个路径的 `st_dev` 不同，而不是库字节或 SONAME alias 缺失。将不同文件系统直接当作 loader 身份失败会把 worker 能力差异误报成代码错误。

配方现在不再在 native `package()` 阶段重绑定 build/package ELF；版本化 ELF 由 Meson 安装副本直接保留，alias 仍只接受安装器生成且 `samefile()` 校验过的符号链。`test_package` runtime staging 固定使用经字节/mode 校验的副本，避免跨文件系统或 `os.link` 能力把可运行闭包误判为失败。这样不删除可用的 package ELF，也不把 alias hardlink 能力误当作目标运行时契约。合并后的 Windows-hosted OHOS `local-win-r045-no-native-hardlink` 返回 RC 0，recipe RREV `b2ccb948a96ca4edd87b5837b28b3522`、PREV `a90dee4bf4f018466b9a28b5932d32f2`；当前候选仍需新的 USB HDC W3、平台 CI 和 AI Review 证明该处理在目标 worker 上可接受。
