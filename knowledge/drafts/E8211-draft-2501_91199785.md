# libtoolize 的失效 `GREP` 默认值会悄悄放错 `ltmain.sh`

## 现象与根因

在只含 `configure.ac`/`Makefile.am` 的 Autotools 源码上运行 `autoreconf`，Libtool 输出了 `/data/service/hnp/bin/grep: inaccessible or not found`，接着仍报 `putting auxiliary files in '.'`、复制 `./ltmain.sh`，最后 Automake 才因缺少 `config/ltmain.sh` 失败。`configure.ac` 已明确写 `AC_CONFIG_AUX_DIR(config)`，因此不能把失败归咎于上游没声明辅助目录。

原因是此 OHOS Libtool 制品中的 `GREP`、`EGREP`、`FGREP` 默认值指向当前目标机不存在的旧 HNP 路径。Libtoolize 使用 grep 追踪 `configure.ac`，该命令失败后仍继续，误将辅助目录判为源码根目录；后续 Automake 按声明寻找 `config/ltmain.sh` 时才报错。两个错误相隔多行，且第一处没有令 libtoolize 退出，是诊断重点。

## 修复与复验

在配方调用 `autoreconf` 时明确传入当前构建环境可用的三个命令：

```sh
GREP=grep EGREP='grep -E' FGREP='grep -F' autoreconf --force --install -I config -I m4
```

先确认目标环境的 grep 实现支持 `-E`、`-F`；随后要求日志显示 `putting auxiliary files in AC_CONFIG_AUX_DIR, 'config'`，且生成 `config/ltmain.sh`，再进入 `configure`。本适配在失败批次 `w3-libgenome-20260926T134000Z` 复现“放在 `.` / 缺 config/ltmain.sh”，在后续冻结批次 `w3-libgenome-20260926T142000Z` 使用环境覆盖完成 `conan create`、上游测试 1/1 和安装包消费者测试。任务私有日志 SHA-256 为 `e10870443e63f73c923eb5f3e78933b1704b4290e63f34169b2c58974cf7ca17`。

## 适用范围和安全边界

适用于 `AC_CONFIG_AUX_DIR` 已声明、但构建主机上的 libtoolize 内置 grep 路径失效的项目。先核对 Libtool 输出及实际 `ltmain.sh` 位置；若源码未声明辅助目录、或是 `SED` 失效、父目录 stray `install.sh`，不能套用本结论。不要直接在共享 Conan 工具包里改脚本，也不要只把 `ltmain.sh` 手动搬进 `config` 后宣称修复：那会遮蔽同一误判对其他生成文件的影响。

知识增量：E521 已覆盖失效 `SED` 路径，E514 覆盖父目录的 `install.sh` 污染，E729 覆盖 Automake/Perl 解释器混用。本条补充的是 **Libtoolize 的 grep 家族变量失效仍返回继续、导致明确的 `AC_CONFIG_AUX_DIR` 被忽略** 的独立诊断与最小环境修复。
