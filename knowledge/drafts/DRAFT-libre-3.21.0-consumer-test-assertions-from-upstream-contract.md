# DRAFT：消费者测试断言必须源自**上游契约**，不得臆测 API 语义

> Contributor: CIW | Status: Draft | Updated: 2026-09-21
> Source: libre 3.21.0 适配（PR #11645，test_package 22 程序 / 245 断言）
> 同 stem 知识文件：`DRAFT-libre-3.21.0-consumer-test-assertions-from-upstream-contract.kv`

## 错误特征

`test_package` 里的消费者测试**成批失败**，而库本身编译、运行、API 调用都正常。
典型比例：libre 22 个消费者程序**首跑 11 个失败**（近半），失败点分散在多个模块。

危险之处在于它**看起来像适配缺陷**：很容易反手去改库、加补丁、或把断言放宽到"返回非空即可"——
那等于把测试写成迁就实现，验证价值归零。

## 根因分析

断言是**按作者对 API 的想当然理解**写的，而不是照上游契约（头文件签名/注释/文档/实测）：
- 传了**未初始化**的 `struct re`；
- 断言 `sa_in` 的字节序/字段序（`sockaddr_in` 的字节序约定本就不直观）；
- 把 `mem_deref()` 的返回值当布尔用（实际语义可能返回 `NULL`）；
- 假设 `pl_dup()` 是浅拷贝/深拷贝而未核对。

## 推荐方案

**方法**: derive-assertions-from-upstream-contract-then-fix-one-by-one

1. **先证明"库是对的"**：用能单独跑通的 API 调用（或直接跑打包产物）确认库行为 ⇒ 把失败归因到**断言**而非库；
2. **逐项对照上游契约**修正断言：读头文件签名与注释、必要时写 10–30 行**探针**打印真实语义
   （字节序/返回值/refcount），以探针输出为准；
3. **不得**为通过率删断言、放宽断言或改库迁就；
4. 在 test_package 注释/report 里写明**每条断言的依据**（头文件行、文档或探针输出），便于复核。

```bash
# 找"猜测型"断言的味道：未初始化结构、硬编码字节序、把 deref 当布尔、假设拷贝语义
grep -nE 'memcmp|== *0x|strcmp|sa_in|refcount|pl_dup|deref' test_package/*.c | head -40
```

## 适用范围与反例

- **适用**：任何为第三方库写 `test_package` 的任务；尤其 API 语义不直观者（引用计数、内存所有权、
  字节序、深/浅拷贝、错误码约定）。
- **判据**：库的独立调用通过 + 消费者测试**成批**失败 + 失败点集中在**语义型断言**。
- **反例/边界**：
  - 若失败源于平台限制（如 HMDFS/权限），那是另一类问题（引相应条目），别误归到断言；
  - 与 **E310**（CLI 版本测试不得臆测**品牌前缀**）同族但不同：E310 是单点品牌字符串，本条是**接口语义层**成批失败；
  - 消费者测试通过 ≠ 上游测试通过（§10.1 两者分开计）。

## 验证证据（libre 3.21.0 / PR #11645）

- `test_package` 共 **22 个消费者程序 / 245 条断言**（此前从未真正运行）；
- 首次全部实跑：**11 个程序失败** → 逐条对照上游语义修正断言 → **22/22 通过**；
- `notes.md` 记录原文：`# 6 | 22 个消费者程序 11 个失败 | 断言按臆测 API 语义书写 | 逐个修正断言口径`。

## 与既有条目的差异（查重结论）

- KB 中"臆测"仅命中 **E310**（CLI 版本测试不得臆测品牌前缀）——**单点品牌字符串** vs 本条**接口语义层成批失败**，
  症状与适用范围不同 ⇒ 按 **create** 申报（`similar_to: E310` 作家族关联）。
- 未发现其他条目覆盖"消费者测试断言须源自上游契约"这一方法论。
