# 导出头文件不应依赖未发布的依赖私有头

## 现象与根因

一个库在源码树或开发机上可以编译，但它安装给下游的公共头又包含了依赖包未公开的子头。下游只通过包管理器获取依赖时，编译会报该子头不存在；把私有头复制进包会掩盖 ABI 风险。诊断时应区分“库自身构建通过”和“安装包消费者能包含公共头”。

## 可复用修复与验证

将导出头中的私有路径替换为依赖官方提供的公共 umbrella header，在配方中显式声明依赖，并让消费者只包含被测包的导出头、链接并调用实际 API。验证必须在安装包视角进行；单独给编译器加源码树 include 路径不能证明修复。

dssi 1.1.1 的 `dssi/dssi.h` 原来包含 `alsa/seq_event.h`，本轮改为 `alsa/asoundlib.h`，同时声明 ALSA 与 LADSPA 依赖。鸿蒙 PC 真机事务 `dssi-w3-20261004T043844Z` 中，上游 Automake controller 测试 1/1 和已安装 DSSI 编码宏消费者 1/1 均通过；原始日志 SHA-256 为 `8403f4e9ba990c4259527505da01bf70d7cf6c78bebdae0d830ebcfa1a99d9082`。

适用于公共头确实使用依赖类型、且依赖提供兼容公共 umbrella header 的库；不能机械替换任意私有头，需核对符号和版本。与已有“消费者缺传递 include 路径”知识不同，本条根因是导出头选择了依赖不公开的文件，单纯扩大 include 目录不能解决。

## 2026-10-10 增量：release 辅助数据的闭包及三段 tuple 边界

PR #14655 的完整 HEAD `c680d47e79d14dd23e69558a6fe3a305b6880d88` 在 CI #80114 失败于 `automake executable missing`。它已经采用含 configure/Makefile.in 的完整 release，Automake 的用途却只是定位开发机安装的两份 config helper；这引入了不必要的环境工具和单目录/固定版本假设，使此前公共头与上游测试闭环无法在 worker 进入执行。

本次以官方 release SHA-256 `f2c82b073a947c8255284249097667f9b14e660bf86186f3fcd3b3b3e087814e` 的 bundled helper 为输入，先核验哈希并保留任务内备份，再仅在 OHOS 对旧 config.sub 的两个 machine 分支和两个 OS 分支作有唯一锚点的扩展。编译器来自 Conan `tools.build:compiler_executables`，`-dumpmachine` 必须实际返回 OHOS aarch64 元组；由 config.sub 规范化后生成任务内 config.guess，并执行它回读确认。

定向实测暴露了一个容易漏掉的边界：`aarch64-linux-ohos` 在旧 config.sub 去掉 kernel/OS 后，basic_machine 是没有 vendor 的 `aarch64`，仅增加 `aarch64-*` 仍报 `machine aarch64 not recognized`。因此必须同时覆盖 bare CPU 和 CPU-vendor 分支；扩展后，三段和四段元组都得到 `aarch64-unknown-linux-ohos`。helper 哈希漂移、非 OHOS 编译器输出必须拒绝，不能靠硬编码 `--build/--host` 掩盖检测失效。

实际 recipe helper 的正向、错误 tuple、helper 哈希漂移三项本地检查全部符合预期，另外直接执行四段元组亦通过。当前修复候选真机事务 `dssi-repair-w3-20261010T101340Z` 的上游 controller 1/1、已安装消费者 1/1 全通过，Conan RC0，12 阶段及 release/postrelease 完成。独立回读完整日志 SHA-256：`892a57d171d130d075480f74be33b713142c6566462f429591c793d5707cf3d6`。该证据不等于比赛 worker 新 CI 已通过。

跨库决策边界：首先确认 release 已有生成文件，区分“辅助分类数据”与“构建生成工具”；只有实际需要 regenerate 时才引入 Autoconf/Automake 工具依赖。对旧 canonicalizer 的精确适配应覆盖其解析后的变量形态，不只测试表面输入字符串。不能移植到缺 configure 的快照，不改变非 OHOS 行为，也不能借该修复删除或跳过原上游测试。

### 2026-10-12 新反例：公共头和平台 tuple 的闭包不包含临时生成文件的可写性

上述 header/helper 修复不能证明 config.status 可以写文件。官方 release 仍有 mktemp-d 的0700创建模式及 fallback umask077；其失败属于文件生成契约，不应扩大 include 路径、替换 ALSA 或伪造 tuple 来修。复用 E114/E129，仅对 OHOS 的三处唯一发布锚点作替换，在新建的私有 TMPDIR 内以 umask007+mkdir 创建两条分支，保留 cleanup。

Conan Environment.apply 只覆盖这次构建的 TMPDIR；原 controller/plugin 使用的已发布依赖 LD_LIBRARY_PATH 继续由原构建逻辑设置。不能用全局环境替换破坏公共依赖的运行闭包，也不能把旧 worker 的 fork 资源耗尽改写为这个潜在兼容性缺口。

新事务 `dssi-w3-20261012-hmdfs-tmp-substep-r2` 使用官方 W3 子步骤，上游1/1、安装消费者1/1、完整12回执和释放全部通过，日志 SHA256 `217916e1725afb6847438ea5b7b0d0e92ee4dab5d78865e6128e7133984d85c7`。这扩展了原条目的验收边界，不宣称发明现有 HMDFS 修复。此前完整 finish 的归档缺失失败保留，不冒称整体 finish 或比赛 CI 通过。


## 2026-10-13 CI 反例与修复增量

Autoconf can select the mksh print builtin while detecting the configure interpreter, then execute config.status under Bash where print does not exist. That breaks generated Libtool contents even though configure returns success. Use a declared Bash tool consistently for configure and generated-helper execution.

The earlier native tuple/header closure does not prove generator interpreter consistency. Diagnose print failures before the later Libtool syntax error; do not rewrite generated Libtool, insert fake print commands, or add -fcommon/compiler relaxations.
