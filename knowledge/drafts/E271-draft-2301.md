# E271 - Link-Aware Optional pthread Cancellation Capability

## Symptom

A project configures with POSIX threads and later fails while compiling bundled
Boost sleep code because `pthread_setcancelstate` is undeclared. The same code
still needs the ordinary POSIX `nanosleep` path.

## Root Cause

`BOOST_HAS_PTHREADS` proves basic pthread support, not the optional thread
cancellation-state API. Platform-name exceptions such as Android do not cover
other POSIX-capable targets whose pthread implementation omits cancellation.

## Recommended Fix

Use CMake `CheckCXXSymbolExists` with `Threads::Threads` in
`CMAKE_REQUIRED_LIBRARIES` to test the real compile-and-link capability. Restore
the probe state afterward. If the symbol is absent, add
`BOOST_SP_THREAD_SLEEP_NO_PTHREAD_SETCANCELSTATE` only to the target that
contains the bundled Boost code, and guard only the two cancellation-state
calls. Keep `nanosleep` and the rest of the POSIX implementation unchanged.

## Validation

The ITK/KWStyle directed matrix passed 5/5 cases: strict patch application,
symbol-absent full KWStyle build, symbol-present no-guard behavior, both call
guards, and zero platform-name conditional macros. The symbol-absent build
completed without a pthread stub.

## Deduplication

Existing `E127` identifies missing pthread cancellation APIs but recommends a
platform-name macro for a libomp-specific switch. It does not provide the
link-aware CMake probe or the narrow bundled-Boost target definition described
here, so no equivalent reusable solution was found.

## Safety Boundary

Do not define `__OHOS__`/`HarmonyOS` branches, provide no-op pthread symbols,
or disable all POSIX sleep support. The adaptation must follow the observed
symbol capability and preserve normal `nanosleep` behavior.
