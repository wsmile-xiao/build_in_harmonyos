# E568 — 手写 Makefile 的工具链注入陷阱：命令行变量覆盖语义（复合定义 `CC` vs `+=`）

> 状态：草稿（路径 B）。合并/提升由知识库维护流程分配正式编号并生成 `doc/`。
> 来源：`crashmail/1.7`（CrashMail II）HarmonyOS PC 适配，设备实测 2026-09-10。

## 错误特征

用 Conan 配方给**手写递归 Makefile** 项目注入 OHOS 工具链时，第一错不在工具链本身，
而在注入方式。两种典型形态（同一 GNU make 语义，两种表象）：

**形态 A — 复合定义被整体替换（本品实测）**

上游 `src/Makefile.linux`：

```make
CC = gcc $(CPPFLAGS) $(CFLAGS) $(DEFS) $(LDFLAGS) -I $(INCDIR) -Wall
```

配方写 `make CC=clang`（或 `make CC="$CC"`）后编译：

```text
clang -c cmnllib.c -o cmnllib.o
cmnllib.c:5:10: fatal error: 'oslib/os.h' file not found
```

注意命令行回显里 **`-DPLATFORM_LINUX -I ../ -Wall` 全部消失**——不是头文件真的缺失，
是 `$(DEFS)` 与 `-I $(INCDIR)` 随整条定义一起被丢掉了。

**形态 B — `+=` 被静默抑制（另有先例：libcyaml）**

上游 `CPPFLAGS += $(VERSION_FLAGS)`，配方命令行传 `CPPFLAGS='-I<dep>/include'`：

```text
src/util.c:50:6: error: use of undeclared identifier 'VERSION_MAJOR'
```

## 触发条件

- 构建系统：手写 / 递归 GNU Makefile（无 `configure`、无 cmake/meson）。
- 阶段：compilation（形态 A 表现为找不到头文件，形态 B 表现为找不到宏）。
- 用 Conan 配方（或任何 CI 脚本）在 `make` **命令行**上传编译器或 flags。

## 根因分析

GNU make 的变量优先级：**命令行赋值 > makefile 内赋值 > 环境变量**（除非用
`override` 或 `make -e`）。由此派生出两个不同后果：

1. **形态 A**：`CC` 在 makefile 里是**复合值**（编译器 + 全部 flags 拼在一起）。
   命令行 `CC=clang` 不是"替换编译器"，而是**整条定义被替换**，于是该 makefile
   自己拥有的 `$(DEFS)`、`-I`、`-Wall` 一并丢失。命令行赋值还会**抑制** makefile
   内对该变量的所有赋值（含 `+=`），所以"在 makefile 里补救"不会生效。
2. **形态 B**：makefile 用 `+=` 累积 flags。命令行赋值会**抑制 `+=`**，累积内容
   全部消失。

共同点：**命令行的 `VAR=value` 不是"追加"，是"接管"**。所以"给 make 传参注入
工具链"这一常见做法，在手写 Makefile 上按定义形态不同会以两种完全不同的错误
表象失败，且两种表象都不指向 make 的变量优先级。

## 诊断：先判形态，再选修法

**第一步：看清 `CC`/`CFLAGS` 在 makefile 里是"复合值"还是"累积值"。**

```sh
grep -nE '^\s*(CC|CXX|CFLAGS|CPPFLAGS|LDFLAGS)\s*[:+?]?=' src/Makefile*
```

**第二步：看命令行回显里 flags 是否消失**——这是形态 A 的判据，比错误文本可靠：

```sh
make CC=clang V=1 2>&1 | grep -m1 '^clang\|^gcc'
# 形态 A 特征：-D... / -I... / -Wall 全都不在回显行里
```

**第三步（形态 A 专用）：确认真实缺失的是宏/头路径而不是头文件本体。**
`grep -rn 'oslib/os.h' src/` 能找到文件，就说明是 `-I` 丢了，不是平台缺文件。

## 推荐方案

### 形态 A（复合定义）：在 makefile 里新增一个**只承载编译器本体**的旋钮

对每个含复合 `CC` 的 makefile（含递归子目录）追加一行，并把 `CC` 改为引用它：

```diff
-CC = gcc $(CPPFLAGS) $(CFLAGS) $(DEFS) $(LDFLAGS) -I $(INCDIR) -Wall
+CC_BIN ?= gcc
+CC = $(CC_BIN) $(CPPFLAGS) $(CFLAGS) $(DEFS) $(LDFLAGS) -I $(INCDIR) -Wall
```

配方侧传 `CC_BIN="$CC"`（编译器来自 Conan 图，R33）：

```python
self.run('make -j1 linux CC_BIN="$CC" STRIP=:', env="conanbuild", cwd=self.source_folder)
```

`?=` 保证不传时仍是上游默认的 `gcc`（平台中立，不引入 OHOS 专属条件编译）。
注意**递归构建要逐个 makefile 改**：crashmail 1.7 的 `make linux` 会先进入
`src/cmnllib`、`src/jamlib`、`src/oslib_linux` 三个子目录，四处 `CC` 都要改；
只改顶层会在第一个子目录就失败。

### 形态 B（`+=` 累积）：用**环境变量**传，不要用命令行参数

```python
self.run(f"CPPFLAGS='-I{inc}' LDFLAGS='-L{libd} -l{lib}' "
         f"make -C {self.source_folder} VARIANT=release CC=clang")
```

环境变量在 makefile 内赋值之后仍是 `+=` 的累积基底，因此不会被抑制。
（先例：`DRAFT-libcyaml-1.4.2-makefile-conan-env-cppflags`。）

### 决策表

| makefile 形态 | 可否用命令行 `VAR=` 注入 | 修法 |
| --- | --- | --- |
| `CC = gcc <flags...>`（复合） | ❌ 会丢 flags | 加 `CC_BIN ?=` 旋钮 + 传 `CC_BIN=` |
| `CFLAGS += <flags>`（累积） | ❌ 抑制 `+=` | 改用**环境变量**传 |
| `CC ?= gcc`（弱默认） | ✅ | 命令行直接 `CC=clang` |
| `override CC = ...` | ❌ 命令行也被压过 | 只能改 makefile 源码 |

## 验证

```sh
# 1) 形态判定
grep -nE '^\s*CC\s*[:+?]?=' src/Makefile*

# 2) 全部子目录都要覆盖（漏一个就在该子目录失败）
grep -rn '^\s*CC\s*=' src/ --include='Makefile*'

# 3) 命令行回显应同时含编译器与 flags
make -j1 linux CC_BIN="$CC" 2>&1 | grep -m1 '^clang'   # 期望: clang ... -DPLATFORM_LINUX ... -I

# 4) 产物真的跑起来（手写 makefile 常带 strip，见"关联条目"）
./bin/<tool> --help; echo rc=$?
```

## 禁止做法

- ❌ **把形态 A 的失败归因成"平台缺头文件"** 去改源码或加 `-I` 补丁：真实原因是
  配方丢掉了上游自己的 `-I $(INCDIR)`；加 `-I` 补丁会掩盖问题并污染上游源码。
- ❌ **用环境变量 `CC=clang make` 绕过复合定义**：makefile 里的普通 `CC =` 赋值
  会压过环境变量（无 `-e`），等于什么都没做，或只在部分子目录偶然生效。
- ❌ **用 `make -e`**：会让**所有**环境变量压过 makefile，破坏 `$(DEFS)` 之外的
  上游默认值，故障面从"少一个 flag"扩大到"整份 makefile 默认值失效"。
- ❌ **只修顶层 makefile**：递归构建会在第一个子目录失败，误判为"补丁没生效"。
