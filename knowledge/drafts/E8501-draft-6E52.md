# E8501 草稿：DMS RLE 长计数字节顺序导致 `Extract failed`

## 错误特征

生成的 DMS 轨通过外层数据与头部 CRC 校验，`undms` 仍输出 `Extract failed`、退出码 1，不能得到期望的 8192 字节 RLE 轨。

## 根因

上游 `undms.c:198-206` 在见到 DLE `0x90` 与 count=`0xff` 后先读取 **被重复的值**，再读两个大端计数字节。`[0x90,0xff,0x20,0,0x5a]` 错把长度放在值之前。属于消费者样本生成错误，和 `.Z` 源码解压的 E6417 不同；后者已覆盖，本草稿不重复提交其解法。

## 修复与执行证据

样本改为 `[0x90,0xff,0x5a,0x20,0x00]`，把解包输出作为编译期头文件输入，交叉编译并运行消费者检查存储轨与 RLE 轨的每个字节。

```bash
conan create archives/u/undms/1.3 \
  -pr:h=ci/conan/profiles/ohos-aarch64 -pr:b=ci/conan/profiles/ohos-aarch64 --build=missing
# test_package 阶段：包内 bin/undms 解出 16384 字节（exit 0），消费者经 qemu-aarch64 执行输出：
# OHOS consumer: stored and RLE tracks decoded; 16384 bytes verified
```

禁止仅检查 CRC 或文件存在性：CRC 可以匹配错误编码的 RLE 数据，不能代替完整消费者执行。

## 知识查重

`engine 'init-build ... .Z not a gzip file'` 初次未命中；随后仓库草稿检索确认 E6417 已详细覆盖 LZW 解码，于是配方复用其纯 Python LZW 解法。本草稿只记录**此前未覆盖的 DMS 载荷字节顺序**，由主编审查后决定是否 promote。
