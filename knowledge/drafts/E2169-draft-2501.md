# E2169 draft: A present Automake script can fail with ENOENT because its interpreter is missing

Status: draft. Contributor: `2501_91199785`. Source: `libpsortb/1.0`, task #8343, HarmonyOS PC arm64, 2026-09-25.

## Failure, diagnosis, and deduplication

`libpsortb` needs `autoreconf -fi` because its Debian DFSG repack leaves an Autotools source tree. Three consecutive target-device failures exposed separate layers of the published Automake tool package:

1. Its `aclocal` wrapper attempted to run `.aclocal-real` through an interpreter path unavailable on this HarmonyOS PC. The target log reported `.aclocal-real: No such file or directory` and `autoreconf` exited 126 (run `libpsortb-w3-20260925T052000Z`, log SHA-256 `d154a64f0c1569b40c8f750d870ffec627ede5f5442bcd464a7428291dccda75`). Independent target readback confirmed that `.aclocal-real` **exists** (SHA-256 `ea86be4a56a996c6bc0ab2fc39e59d170faa682a2cd9dd47cca2ec0ed06d8a8e`), its first line is `#!/data/service/hnp/bin/perl`, that interpreter does **not** exist, and the native Perl is `/storage/Users/currentUser/usr/local/bin/perl`. Invoking the real script through the native interpreter bypassed the unusable shebang.
2. Merely using `perl` still inherited a Perl library search path containing an ABI-incompatible binary `Cwd` module: `Cwd.c: loadable library and perl binaries are mismatched` (run `...T053320Z`, log SHA-256 `1f9bf1819f385b52ca163d71f7d977fedb1a8d6adf136ada49f82ebc4bcc54af`). Limiting `PERL5LIB` to Automake's pure-Perl module directory removed that incompatible module path.
3. Passing `share/automake-1.18` as `--automake-acdir` caused `internal/ac-config-macro-dirs.m4: no such file or directory` (run `...T054000Z`, log SHA-256 `c972506eda0ffeee249e7bec62a40527db22653a0f071d3e7047d9fbe5060bde`). That option needs `share/aclocal-1.18`; `share/automake-1.18` belongs to `--libdir` and `PERL5LIB`.

Existing E037 and E049 identify broken or hard-coded shebangs. E116 identifies Automake Perl module lookup failure but recommends rebuilding Automake or avoiding regeneration. Existing `DRAFT-6051-libnxml-0.18.5-remote-automake-pkg-missing-dotfiles` addresses a **different** cause of the same ENOENT symptom: the real dotfile is absent. Its proposed `conan remove` + rebuild would not diagnose this run, because the dotfile is present and the named interpreter is absent. `DRAFT-6049-libnxml-0.18.5-autotools-perl-dual-arch` already covers the Cwd ABI mismatch. This draft's increment is an evidence-based two-probe decision (`real script present?` / `shebang interpreter present?`) followed by a tested recipe-local execution method for the present-script branch, including the correct Automake macro directory. It does not claim the Cwd mismatch itself as new knowledge.

## Reusable method and boundary

First distinguish missing payload from missing interpreter: verify the real script with `test -f`, read its shebang, then check that exact interpreter with `test -e`. If the real script is absent, investigate the package itself (the DRAFT-6051 branch); the following method applies only when the real script is present but its interpreter is absent. Also inspect that the tool package contains `.automake-real`, `share/automake-<version>`, `share/aclocal-<version>`, and `share/aclocal`. Resolve a native `perl` from the build PATH, then set the four command-environment values for the `autoreconf` invocation:

```sh
PERL=<native-perl> \
PERL5LIB=<automake-share>/automake-<version> \
ACLOCAL='<native-perl> <automake-bin>/.aclocal-real --automake-acdir=<automake-share>/aclocal-<version> --system-acdir=<automake-share>/aclocal' \
AUTOMAKE='<native-perl> <automake-bin>/.automake-real --libdir=<automake-share>/automake-<version>' \
autoreconf -fi
```

Do not copy a binary Perl module path from a different interpreter into `PERL5LIB`, and do not point `--automake-acdir` at `share/automake-*`. The method assumes the published Automake package has this particular split layout; other packages require their own path inspection. Fixing tool invocation does not by itself prove the consuming library builds or functions.

## Verified outcome

The final `libpsortb` recipe uses this exact method in `_automake_commands()` and ran on the same HarmonyOS PC. `autoreconf` completed, the two retained shared libraries built and installed, and the independent Conan `test_package` compiled, linked, and ran (`LIBPSORTB_CONSUMER_PASS`). Final `conan create` returned 0; the frozen log SHA-256 is `fdc056d434ad713a559966a104278528cfc7b33e19e3ca51108441f09bd04dbe`; the W3 receipt-chain validator passed. `make check -j1` returned 0 with **no upstream test cases** (0/0); consumer coverage is 1/1 executable with six checks.
