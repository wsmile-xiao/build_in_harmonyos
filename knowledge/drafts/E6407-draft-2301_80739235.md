# E6407 - Strict patch-ng context bytes must match the pristine source

## Symptom

An OHOS Conan build can pass a local `git apply` replay while `conan create`
fails in `source()` with `hunk no.1 doesn't match`, `source file is different`,
or `Failed to apply patch`. The two tools may print apparently identical
context lines even though the indentation bytes differ.

## Root cause

Conan 2.x applies `conandata.yml` patches through `patch_ng` with strict
context matching (`strip=0`, `fuzz=False`). `git apply` can accept a hunk whose
context has a whitespace difference, while `patch_ng` compares the exact
preimage bytes. A missing indentation byte in a context record therefore
passes the permissive check but fails the production source phase.

## Fix

1. Reproduce the ordered patch list on a fresh pristine source archive using
   the same `patch_ng` API and options used by Conan.
2. Compare every context record byte-for-byte with the source line at the
   declared hunk offset, including leading indentation and explicit blank-line
   markers.
3. Correct only the context bytes or regenerate the hunk from the exact
   cumulative preimage; do not relax fuzzing or alter the source archive.
4. Replay the complete ordered set again and retain the failed and corrected
   trees as separate evidence.

## Validation

For dosbox-staging 0.82.2-r1, `0002-meson.build.patch` initially differed by
one leading space in three context records. The corrected patch passed
`patch_ng 1.19.1` with `strip=0,fuzz=False` for `0001` through `0021` in order,
with all 9 entries returning `True`; no source or patch semantics changed.

## Applicability and safety boundary

This applies to Conan recipes whose production `source()` path uses
`apply_conandata_patches`. A successful GNU patch or `git apply` dry-run is only
an early diagnostic. Do not copy a postimage into the recipe cache, loosen
patch matching, mutate an immutable failed tree, or claim CI success without a
fresh `conan create` result bound to the current commit.
