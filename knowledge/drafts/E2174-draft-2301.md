# E2174: A passing check target can still omit the packaged library

## Symptom

A hand-written Makefile test suite runs successfully, but the Conan consumer
fails while CMakeDeps is generating the imported target:
`Library 'jbig' not found in package`. The recipe declares the library in
`cpp_info.libs`, yet the package `lib` directory contains no matching archive.

## Root cause

Build systems often keep validation targets separate from distributable
artifacts. In JBIG-KIT, `check` depends on `tstcodec` and `tstcodec85`; those
programs compile their own objects and do not depend on `libjbig.a`. Running
`check` therefore proves test behavior but does not build the archive selected
by `package()`. Conan can finish package creation without warning when `copy()`
matches no library, and the missing artifact is only exposed by the generated
consumer target.

## Fix

1. Inspect the upstream target graph and identify the exact artifact target
   named by `cpp_info.libs`.
2. Invoke that target explicitly before the upstream validation target, for
   example `make ... all check` or `make ... libjbig.a check`.
3. Keep the normal upstream tests enabled; do not replace them with an
   artifact existence check.
4. After `package()`, verify that every declared library exists under the
   package `lib` root, then compile an independent `test_package` through
   CMakeDeps and the generated imported target.
5. Bind the result to a fresh target run when the earlier candidate already
   consumed a device launch; do not edit or reinterpret the failed evidence.

## Validation

For jbjg 2.1, r3 ran the T.82/T.85 checks but produced no `libjbig.a`, and the
consumer stopped at CMakeDeps with the missing-library diagnostic. A create-new
r4 changed only the Make invocation to `all check`. The target then built the
archive, completed both upstream suites, compiled the consumer, and ran the
real `jbg_dec_init/free` API test with `conan_create_rc=0`. The r4 payload was
`445373` bytes with SHA-256
`4d76d8540f3177967dd00d5bf21ab801d3792493baddeffc116a99545d0c209d`.

## Reusable decision rule

Whenever a recipe maps a hand-written build to Conan artifacts, treat
validation targets and package targets as separate contracts. First prove the
artifact target is in the invocation, then prove the package file exists, and
only then use the generated consumer as the final link/runtime check. A green
upstream test target alone is insufficient.

## Safety boundary

This rule applies to build systems whose test targets do not transitively
depend on the distributable library. It does not authorize skipping upstream
tests, copying a locally built artifact into a package by hand, treating
`--build=missing` as release availability, or reusing a consumed W3 run.
