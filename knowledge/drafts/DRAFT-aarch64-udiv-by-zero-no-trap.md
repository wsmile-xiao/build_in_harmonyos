# draft-aarch64-udiv-by-zero-no-trap

## 症状

同一份含无保护整数除法的 C 源码：

- 在 x86_64 上构建/复审 → `Floating point exception (core dumped)`，gdb 回溯落在
  `(a * 1000) / b`；
- 在 OHOS aarch64 上构建并运行 → 完全不崩，`rc=0`，产物照常写出，只是字段值不对。

于是复审/审计方容易得出「这个测试用例根本不可能通过 → 声明的结果是伪造的」，
或者反过来把 aarch64 的「没崩」当成「数据是对的」。

## 根因

三层语义叠加：

1. **架构差异**：AArch64 架构规定 `UDIV`/`SDIV` 在除数为 0 时结果为 0，**不触发任何异常**；
   x86_64 的 `IDIV` 除零触发 #DE → SIGFPE。
2. **C 标准**：除数为 0 是 UB，编译器可任选结果。`clang -O3` 对**编译期常量** 0 直接折叠，
   实测同一段代码在 x86 上得到 `quotient=1`（既不是 0 也不是崩溃）。
3. **上游代码未防御**：本例 `src/mctools.c:651`
   `(mc_parms->v_width * 1000) / mc_parms->v_height` 中 `v_height` 是 `uint32_t`，
   来源是外部录像流的头部字段，上游没有任何零值检查。

## 解决方案

1. **构造测试数据时保证除数合法**（本例 DHAV 扩展头必须给出非 0 的 height）。
2. **断言落在产物字段上，而不是「rc=0 / 文件非空」**：反查产物 MKV 头固定偏移
   `0x170`/`0x174` 的大端宽高是否等于预期值，非法数据立刻暴露。
3. **跨架构结论不互相迁移**：
   - x86 上 SIGFPE ≠ aarch64 会崩；
   - aarch64 通过 ≠ x86 通过（也不代表数据合法）。
4. 确实要覆盖这条边界行为时，单独写成**负向用例**（显式断言 SIGFPE，或断言产出 0 宽高），
   与成功路径分开，避免「靠崩溃证明正确」。

## 验证

tanidvr/1.4.1 实测链条：

| 场景 | x86_64 原生 | OHOS aarch64 |
|---|---|---|
| 错位扩展头（height=0） | SIGFPE（gdb → mctools.c:651） | rc=0，PixelWidth=480 / PixelHeight=0，输出 1009 字节 |
| 修正扩展头（height=480） | 正常 | 正常，PixelWidth=640 / PixelHeight=480 |

修正后测试新增两条宽高断言长期防回归；审计二轮复核也据此推翻了第一轮「伪造通过」的判断，
但同时采纳了其中「数据构造有问题」的实质结论。
