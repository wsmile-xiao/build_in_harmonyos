# E2183: Validate no-arch build-system packages through their installed consumer interface

## Symptom

A build-system-only archive can complete its upstream make test target while a
downstream consumer cannot find Makefile.tools, resolves the wrong NSBUILD
directory, or fails to produce its output archive. The upstream target is
intentionally empty, so a successful package build alone does not exercise the
installed interface.

## Root cause

The release contains makefile fragments and helper scripts rather than compiled
objects. Flattening those files into the package root or omitting Conan
environment metadata breaks the documented share/netsurf-buildsystem and
NSSHARED contract. A no-op upstream test therefore provides no evidence for the
consumer path.

## Fix

1. Preserve the upstream share/netsurf-buildsystem/{makefiles,testtools,citools}
   layout in the package.
2. Export the absolute shared root as NSSHARED through Conan build and run
   environments while keeping the package ID architecture-independent.
3. Run the official upstream test target during build() and record its terminal
   result.
4. Add a consumer fixture that checks installed fragments and helper modes,
   includes Makefile.tools and Makefile.top, and compiles/archives a small
   source file with the packaged rules.

## Validation

For any no-arch package made only of build metadata, the minimal complete check
is the upstream test entry plus a real consumer compile using the installed
package path. A dry-run parser check is only a fallback when the target
compiler is unavailable and must not be reported as native consumer success.

## Applicability and safety boundaries

This pattern applies to makefile, CMake module, pkg-config metadata, and similar
build-support packages with no compiled output. It does not replace upstream
tests for packages that do compile code, and it does not permit flattening or
relabeling the installed layout to make a smoke check pass.
