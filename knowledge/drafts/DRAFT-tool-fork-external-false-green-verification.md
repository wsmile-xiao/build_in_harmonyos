# 会 fork 外部程序的 CLI 包：真假绿的判据是「产物真实生成 + 真实运行」，因果链要靠三列差分钉死

配套机制稿：`DRAFT-ldpl-5.1.0-runtime-bare-cxx-and-baked-libdir`（讲为什么坏；本条讲怎么在提交前抓出来）。
实例：`ldpl/5.1.0`，HarmonyOS PC 真机，2026-10-03。

## 1. 为什么这条包的绿是不可信的

`conan create` 的日志门禁看得见的东西：编译痕迹（L1b）、上游套件痕迹（L1c）、
测试不是 echo 假跑（L1d）、产物目录非空（L5）。它们共同的特点是先验假设
「失败会留在这条包的 stdout 里」。

会 fork 外部程序的包不是这样：**失败发生在子进程**，父进程照常打印自己的横幅再
`exit(1)`。于是出现最坏的组合——create 退出码 0、消费者断言全过、包完全不可用。

```
$ ldpl -v                    # 一切正常
 This is LDPL version 5.1.0 'Groovy Gualicho'.
$ ldpl hello.ldpl            # 核心能力
* Building hello-bin
sh: c++: inaccessible or not found
LDPL Error: compilation failed.          # ← 如果 test_package 没跑这一步，就没人知道
```

## 2. 消费者套件的三类必备证据（缺一即空壳）

`archives/l/ldpl/5.1.0/test_package/test_ldpl.sh` 共 26 项断言，按三类组织：

| 类 | 断言 | 抓什么 |
|---|---|---|
| (a) 真在做事 | [22][23] 语法错误样本必须非 0 退出并报 `LDPL Error`；[6] 未知选项必须被报告 | 证明工具没有「什么都返回 0」 |
| (b) 产物落地 | [9]–[21] 每个 `.ldpl` 样例：编译 rc=0 → **可执行文件确实存在** → **运行它** → 比对 stdout（[10] 精确逐字节、[12][14] 数值、[16][17] 子流程、[19] `accept` 读 stdin）；[26] 校验产物 ELF magic `177 E L F` | 证明 fork 出去的外部程序真的产出物并可用 |
| (c) 可重定位 | [7] 运行期变量由包注入；[8] 生成的 C++ 里 `#include` 用的是**注入路径**而非烧死路径；[24][25] 把随包资源复制到他处、改指变量后仍能构建并得到同一程序 | 证明不依赖构建机路径 |

要点：**不要只断言工具的退出码**。父进程 rc=0 只说明它把子进程叫起来了，
子进程成功与否要去看产物和它的输出。

## 3. 三列差分：把因果链钉死的方法

单点成功不能证明「修的是哪一个缺陷」。本次用三列，在同一台真机、同一份
上游语料上跑：

- A 列：打补丁，随包资源走**编译期烧死路径**（= 正常安装形态）
- B 列：打补丁，烧死路径故意指向空目录，资源走 `LDPL_LIB_LOCATION`（= 重定位形态）
- C 列：**未打补丁**（上游常量写死，任何 env 都惰性）

| 差分 | 样本量 | 结果 | 说明什么 |
|---|---|---|---|
| A vs B（代码生成，`ldpl -r` 输出 md5） | 50 个上游文档示例中 39 个可转译 | **39/39 相同，差异 0 行** | 补丁不改变生成的 C++，只改变资源来源 → 无行为回归 |
| A vs B（真编译 + 真运行，`-O0`，输出截 4 KB） | 6 个样例 | 6 对 md5 **全部相同**（3 个非空 / 1 个触到截断上限也相同 / 2 个空输出） | 端到端行为一致 |
| A vs C | 同 6 个样例 | C 侧 **6/6 build=1**，签名一律 `inaccessible or not found` | 修复是「能不能用」的开关，不是装饰 |
| 机制矩阵（hello 单样本） | 9 组 | 见机制稿 §3 | 两层缺陷各自都是必要条件 |

护栏是必须的：上游文档示例里有无限打印的样例，本次第一次运行一个样例就写出
**616 MB** stdout（当场杀掉并清理）。语料差分一律 `timeout 10` + `head -c 4096`，
比对前 4 KB —— 相等性结论不受影响，设备磁盘不受威胁。

## 4. 上游用例数为 0 时，证据从哪里来（R51 三步法的落地）

清点（`LDPL-5.1.0` 官方归档，逐字节核对）：

```
tar tzf ldpl-5.1.0.tar.gz | wc -l                        # 84
tar tzf ldpl-5.1.0.tar.gz | grep -cE '/(tests?|test)/'   # 0
makefile 目标：all man clean install uninstall           # 没有 check/test
src/CMakeLists.txt：只有 add_executable(ldpl ldpl.cpp)
```

→ 该版本坐标内**确实没有**测试套件，上游用例数如实写 `0/0`，走「上游无测试 ⇒
必须新增鸿蒙特有用例（≥1）」这条路径。

反面对照（同时说明为什么不能借 master 的 `tests/` 凑数）：上游 master 有
`tests/{expressions,features,structures}` 共 21 个 `.ldpl` + 3 个 `run.sh`，
把它们喂给 5.1.0 的转译器 → **0/21 可转译**（`IMPORT`/module/structure 等语法
当时还不存在）。所以既不能拿它们当 5.1.0 的用例数，也不能拿它们当有效性证据；
本次只把它们作为「A/B 差分同样逐点相等」的骨架证据，并如实标注 0 个可转译。

## 5. 禁止做法

1. 只测 `-v/-h`（见 §1，这是这条包类的典型空壳测试）。
2. 拿后续版本的 `tests/` 数量当本版本声明数（版本坐标被顶替，实测还 0 个能跑）。
3. 语料差分不加 timeout/输出上限（实测写出 616 MB）。
4. 用 `PATH` 上的 `c++` 软链「满足」上游要求来替代补丁 —— 见机制稿 §4 的遮蔽后果，
   以及 R33 对编译器来源的规定。
