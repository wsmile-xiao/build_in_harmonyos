# draft-hamlib-4.7.1-refresh-patch-drops-non-regenerable-configure

## 症状

`ohc-run.py finish <pkg> <ver>` 的 Step1 会执行 `refresh-patch --auto`。
若配方含一个**不可再生**的补丁——最典型的是改写 `configure`/`Makefile.in` 这类
「生成物」的补丁——它会被静默清掉，而 `conandata.yml` 仍然引用它：

```
patches/0006-configure-umask.patch   <-- 被移除（_is_likely_generated: configure
                                         头部含 "Generated by GNU Autoconf 2.71"）
conandata.yml                        <-- 仍然有 patch_file: patches/0006-...
```

后果：下一次 `conan create` / conan-verify 的 G2 直接失败
（`apply_conandata_patches` 找不到文件），而 `finish` 本身不报错。

## 根因

`refresh_patch._is_likely_generated()` 依据文件头注释把 `configure` 判定为
生成物并从再生集合里排除；而 `refresh --auto` 的语义是「以 .orig/.work 重新
生成补丁集」，未在再生集合里的补丁文件会被当作陈旧产物删除，没有与
`conandata.yml` 的引用做一致性校验。

## 规避

1. 备份：`archives/<l>/<pkg>/<ver>/patches/.patch-backup-<ts>/`（refresh-patch
   自己会留备份，但 finish 之后要立即核对 `patches/` 与 `conandata.yml` 一致）。
2. 在 `finish` 之前把补丁目录整体复制到 `$HOME/tmp`，出问题后拷回并确认
   `conandata.yml` 的条目顺序与文件名一致。
3. 已有先例：`aaphoto 0.45`（`patches/0003-configure.patch`）、
   `activity-log 0.9.7`（`patches/0003-configure-umask.patch`）同样把手写的
   configure 补丁入库——说明这是被接受的实践，需要的是工具链别删它。

## 建议修复

- `refresh-patch --auto` 只删除「本次再生集合内、且内容确实过期」的补丁；
  对不在再生集合内的补丁文件给出 `[warn] 保留不可再生补丁 0006-configure-umask.patch`。
- 增加一致性校验：`conandata.yml` 引用的每个 `patch_file` 必须存在，否则
  `finish` 直接失败（fail fast），而不是留到 G2 才炸。
- 可选：`refresh-patch --include <path>` 允许显式把生成物纳入再生集合。

## 验证

hamlib 4.7.1：手工从 `.patch-backup-20260928193713/` 恢复
`0006-configure-umask.patch` 并登记回 `conandata.yml` 后，clean-verify
（补丁应用 + configure + make + install）与 conan-verify G0–G4 全绿；
此后**不再执行 finish**（避免补丁再次被清）。最终补丁集为 0001–0005。
