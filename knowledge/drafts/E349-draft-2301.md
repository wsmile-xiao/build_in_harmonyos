# E349 — X11 扩展库头文件来源归属：按头文件决定依赖与是否 vendoring

## 错误特征

X11 扩展客户端库的头文件来源分散在多个包：**协议头/常量来自 xorgproto，Xext 内部
工具头来自 libxext，扩展自身公有头来自本库**。不核对来源就容易多依赖（把 xorgproto
提供的头当作需额外 vendoring）或少依赖（漏掉实际产生 NEEDED 的库）。libXv 1.0.13
的 `Xv.h`/`XShm.h` 来自 xorgproto/2025.1，`extutil.h` 来自 libxext/6.4.0，三者同轨
可用时**无需任何 vendoring**。

## 触发条件

- X11 扩展客户端库（Xv/XShm/Xrandr/Xcursor 等），头文件 `#include
  X11/extensions/*.h`、`X11/extensions/extutil.h` 等。
- 依赖的 xorgproto/libxext 已在同轨 cmd-pkgs 发布（libx11/6.4.0、libxext/6.4.0、
  xorgproto/2025.1）。

## 根因分析

- **xorgproto** 聚合 X11 协议头与常量（`Xv.h`/`XShm.h`/XInput 协议头等）；
  **libxext** 提供 Xext 内部工具头（`extutil.h`）与部分扩展实现；各扩展库自身只发布
  其公有扩展头（如 libXv 除 Xv.h 外的扩展实现）。
- 头文件级依赖只影响编译（`-I`），链接级依赖才产生 NEEDED。把每个被 include 的头
  映射到来源包，就能精确列出 `requirements`（含 transitive_headers 与否）与
  `package_info.requires`。
- 错误地 vendor 已在同轨发布的头 → 维护负担 + 符号分叉（同 E340）。

## 解决方案

1. 列出本库所有 `#include` 的 X11 头，逐一归属：协议头/常量→xorgproto；Xext 内部
   工具头→libxext；其他扩展库公有头→对应库。
2. `requirements`: 头文件级依赖用 `transitive_headers=True`（同轨可用时，见 E340），
   链接级依赖用普通 requires。
3. `package_info.requires` 只列实际产生 NEEDED 的链接依赖（`readelf -d <lib>.so |
   grep NEEDED` 校验）。
4. 同轨全部可用 → 不写桩 .pc、不 vendor 头、不打 patch（libXv 即此情形：依赖
   libx11 + libxext + xorgproto，无 vendoring）。

验证：`readelf -d libXv.so.1 | grep NEEDED` 仅 libX11.so.6/libXext.so.6；configure
日志各依赖模块 found；无 vendored 头。

## 禁止策略

- 不把 xorgproto/libxext 提供的头当作需 vendoring 的缺失依赖。
- 不把头文件级依赖写进 `package_info.requires`（会让消费者链接到错误的库）。
- 不在同轨可用时写桩 .pc（过度工程，见 E340）。
