# E342 — X11 库头文件自包含陷阱：consumer 测试的 include 顺序与宏/函数区分

## 错误特征

部分 X11 库的公开头文件（如 libxkbfile 的 `XKBfile.h`）**不包含任何
`#include`**，却大量使用 `FILE *`、`XkbDescPtr`、`Bool`、`KeySym`、`Atom`、
`Display *` 等来自 stdio.h / Xlib.h / XKBstr.h 的类型。直接 `#include
<X11/extensions/XKBfile.h>` 会因 `FILE`、`XkbDescPtr` 未定义而编译失败。
同一头文件里还混着 `#define` 宏（`XkbMapDefined`、`XkbKSIsLower` 等）与真正的
导出函数——写符号强制测试时若按"名字像函数"一刀切提取，会把宏也当成可链接
符号，导致链接期 `undefined reference`。

## 触发条件

- 目标库: X11 家族库，公开头文件不自包含（不引依赖头）。
- test_package: 用 `DECLARE_SYMBOL`/强类型重定位逐符号校验导出面。
- 消费者: 需手动按序补齐 stdio.h → Xlib.h → 协议头 → 库头。

## 根因分析

- 上游头文件假设使用者已有 `-I` 里可见的 Xlib/协议头，且历史上总在引用前
  先 include。头文件自包含只是近年 best practice，X11 老库普遍不遵守。
- 宏与函数在头文件里无法用"名字以 Xkb 前缀开头 + 后跟左括号"区分：
  `XkbKSIsLower(k)` 是宏，`XkbKeysymText(...)` 是函数。正则提取必须
  排除宏表，否则 api_surface.c 里 `DECLARE_SYMBOL(XkbKSIsLower)` 报
  `undefined reference to 'XkbKSIsLower'`。
- 协议类型（`XkbDescPtr`）来自 **xorgproto** 的 `XKBstr.h`，而非库本身——
  库头文件不传递依赖，消费者必须显式 include 并确保 xorgproto 头在
  include 路径里（依赖上设 `transitive_headers=True` 即可）。

## 解决方案

### 1) include 顺序显式化

```c
#include <stdio.h>                      /* FILE *  */
#include <X11/Xlib.h>                   /* Display, Atom, KeySym, Bool */
#include <X11/extensions/XKBstr.h>      /* XkbDescPtr（来自 xorgproto） */
#include <X11/extensions/XKBfile.h>     /* 库头最后，类型已就绪 */
```

### 2) 区分宏与函数再生成符号面

从头文件提取导出面时，先手工核对宏表并排除：

```python
exclude = {'XkbMapDefined','XkbStateDefined',      # #define 常量
           'XkbKSIsLower','XkbKSIsUpper',          # #define 宏
           'XkbKSIsDeadKey','XkbKSIsKeypad', ...}
funcs = sorted(set(funcs) - exclude)
```

再以 `src/*.c` 里是否真的有定义做二次确认（`re.search(r'\b'+name+r'\s*\(')`），
两头夹击后剩下的才是可链接符号。

### 3) 签名契约用函数指针类型断言

```c
CHECK(sizeof(&XkbKeyNameText) == sizeof(char * (*)(char *, unsigned)),
      "XkbKeyNameText signature (char *, unsigned) -> char *");
```

无需调用即校验签名（无 X server 也能跑）。

## 禁止策略

- 不依赖库头文件自带 include（X11 老库不自包含）。
- 不把 `#define` 宏当导出符号写进 api_surface.c。
- 不改库头文件来"修复"自包含问题——消费者按序 include 即可。
