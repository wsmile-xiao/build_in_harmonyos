# E321 — compat/export_sources 目录残留 libtool 构建产物导致 conan create 链接失败

> **严重度**: 🔴 blocking | **分类**: conan | autotools | libtool | export-sources | compat-shim
> **触发工具**: conan | libtool | make | autotools | **阶段**: packaging | linking
> **错误签名**: `not a valid libtool object` | `Copied .*\.lo file`

## 问题现象

依赖 compat shim + `export_sources()` 发布的 autotools 插件（abiword 系 clarisworks/paint 等）：
explore 阶段直接在源码树内执行 `make` 后，`compat/`（或 `tests/`）目录会残留 libtool
构建产物（`.lo` / `.o` / `.dirstamp` / `.Plo` / `.Po` / `.la` / `.lai`）。归档时若
conanfile.py 的 `export_sources()` 用 `copy(self, "*", ...)` 全量复制该目录，脏 `.lo`
会被当作源码发布进 recipe，`conan create` 干净重建时链接报：

```
libtool:   error: 'compat/libabiword_plugin_paint_la-abiword_shim.lo' is not a valid libtool object
make: *** [Makefile:754: libabiword-plugin-paint.la] Error 1
```

且日志中会出现 `Copied 1 '.lo' file: ...` / `Copied 2 '.o' files: ...` 字样（recipe
导出阶段把构建产物也复制进 cache）。

## 根因分析

1. explore 阶段（Step 2 AI 手动编译）直接在源码工作树内运行 `make`，libtool 在
   每个包含源文件的子目录（含 `compat/`、`tests/`）生成 `.libs/`、`.deps/`、`.lo`、
   `.o`、`.dirstamp` 等中间产物。
2. 归档时 `export_sources()` 全量复制 `compat/`、`tests/`，把构建产物一并带进 recipe。
3. `conan create` 从干净的 export sources 重建时，Makefile 引用的 `.lo` 是上一轮
   构建留下的旧对象（路径/时间戳与当前源码不匹配），libtool 判定其非法。

## 解决方案

**推荐（自动）**：归档前清理 `compat/`、`tests/` 下全部构建产物：

```bash
find compat tests -type d \( -name .deps -o -name .libs \) -exec rm -rf {} + 2>/dev/null
find compat tests -type f \( -name '*.lo' -o -name '*.o' -o -name '*.Plo' -o \
  -name '*.Po' -o -name '*.dirstamp' -o -name '*.la' -o -name '*.lai' \) -delete
```

**回退**：`export_sources()` 改为白名单 glob（只复制 `*.h` / `*.cpp` / `*.m4` 等纯源码
扩展名），从源头杜绝构建产物混入。

## 禁止策略

- `forbid`: 不清理直接归档 → G2 门禁误判（复用脏缓存）或链接失败，发布后运行时行为不可预期。

```bash

conan create archives/a/abiword-plugin-paint/3.0.8 \
```
