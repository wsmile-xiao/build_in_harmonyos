# Qt 制品可用，不代表原生配置和公开头文件传递正确

## 现象与根因

预编译 Qt SDK 的头文件、`libQt5OpenGL.so`、`moc` 和 `uic` 可以真实存在，但原生 Qt CMake 配置仍引用构建机路径，而且 Conan 导出的组件不一定包含 Qt5OpenGL。消费者通过 `find_package` 生成的生产者目标链接成功后，仍可能先后在公开头文件的 `QMap`、`GL/glu.h` 处编译失败：Qt、GLU 和 Mesa 的包含目录在 Conan 依赖图中被当成非传递头文件剪掉。生产者自身使用绝对包路径编译通过，不能证明下游可消费。

## 修复与验证

先核对依赖包内真正存在的头文件、共享库与代码生成器。仅在任务配方的构建描述中绑定该包本地的 `moc`/`uic`/include/lib，避免改写共享 Qt 包。公开头文件暴露 Qt/GLU 类型时，对相应依赖声明 `transitive_headers=True` 与 `transitive_libs=True`；若还公开引用 Mesa GL 头，显式声明它并加入 `cpp_info.requires`。最后让安装包消费者只通过 `libqglviewer::libqglviewer` 目标编译、链接、运行。真机 run `libqglviewer-w3-20261003T195815Z` 完成库构建、打包和无界面消费者 1/1，日志 SHA-256 为 `fef8264d126e1a9f2faec289e991dba9971f585ea7a0b5ea23be19ca4b43a7a8`。

## 范围和边界

本次消费者构造 `QApplication`/`QGLViewer`，调用 camera 和 Vec 数学接口；没有建立受检的图形上下文、绘制帧或验证真实 GPU/窗口系统。因此只能称 Qt5 core 库及此消费者边界通过，不能宣称交互式 OpenGL 渲染已适配。既有 E581 讨论 Qt6 Meson 经 pkg-config 找到陈旧工具路径；本条补充 Qt5 原生配置损坏与 Conan `CMakeDeps` 公开头文件传递这两个不同层次，尤其要求用安装包下游编译暴露问题。
