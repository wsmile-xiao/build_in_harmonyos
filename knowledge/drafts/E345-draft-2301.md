# E345 — Cross-built Conan provider metadata must be relocated by suffix and slash style

## 错误特征

目标机已收到依赖包，但 qmake/CMake/pkg-config 在消费阶段报告模块或文件不存在，或日志仍出现主机的 Conan build/package 根路径。只修复 `.pri` 或只匹配 POSIX 路径时，另一个生成文件可能继续泄漏旧路径。

## 触发条件

- 依赖由交叉编译 Conan 配方生成，并把构建根写入 `.pri`、`.prl`、`.la`、`.pc` 或 `.cmake`。
- Windows 主机生成的元数据使用反斜杠，目标侧工具使用正斜杠。
- 目标验证只做了配置或编译，没有运行真实的已安装包消费者。

## 根因分析

传输字节完整并不意味着元数据中的路径身份正确。生成文件把临时 Conan build/package 根当成永久前缀，消费者会沿着主机路径查找模块、库或依赖。元数据后缀由不同工具分别消费，路径分隔符又随主机构建环境变化，因此单一正则或单一文件类型会留下未修复的泄漏。

## 解决方案

1. 从 Conan 依赖对象取得当前 `package_folder`，不要硬编码缓存目录。
2. 对 provider 包内所有相关 `.pri`、`.prl`、`.la`、`.pc`、`.cmake` 文件执行有界扫描，同时识别 POSIX 和 Windows 两类旧根。
3. 仅将精确的旧 provider build/package 根替换为当前 `package_folder`，保留非 provider 路径；回扫确认旧根为零。
4. 运行真实 target consumer，调用被测 API，并验证目标 ELF 架构和进程退出状态。仅 qmake configure 或静态文本扫描不能替代该验证。

5. 在 Conan recipe 叠加工具链运行库时，对 `LD_LIBRARY_PATH` 使用 `Environment.append_path`（保留已有占位路径）；不要用不带占位符的 `Environment.append` 覆盖 worker SDK 路径。否则 `clang` 调用的 `lld` 可能无法加载 SDK 自带的 `libxml2.so.*`，在链接阶段以 signal 失败，即使源码和目标依赖均正确。

6. CMakeDeps 生成器会在日志中给出可用的包级 `find_package` 名称和目标；测试配方应以该输出为准（本例为 `qt5-qtsvgv` 与聚合 `Qt5`），不要仅凭组件的 `cmake_file_name` 猜测独立配置文件一定可被 `CMAKE_PREFIX_PATH` 找到。

7. `test()` 调用的可执行文件必须与 `CMakeLists.txt` 的 `add_executable` 名称逐字一致，并使用 `self.cpp.build.bindir` 派生路径。目标机上“已构建”而入口名漂移会在执行阶段直接返回 RC 127，不能算消费者通过。

## 本次证据

qt5-qtsvgv 5.15.2.2 的 r9 首次暴露 `include/QtSvg` 缺失，r10 暴露 qtbase `.prl/.la` 泄漏旧 Conan 根，修复后 r13 在 `10.62.195.15:8022` 唯一 launch 完成五组上游测试与 `QSvgRenderer` 消费者 smoke；消费者为 AArch64 ELF，结果哈希绑定在任务证据 `w3-r13-launch-receipt.json`。
随后平台 Buildbot #37226 在 Conan qmake 链接阶段报告 `lld` 缺少 `libxml2.so.16`；将 `Environment.append("LD_LIBRARY_PATH", ...)` 改为 `append_path` 后，必须以新 HEAD 重新执行平台 CI，不能把旧 W3 或本机构建结果拼接为通过。

## 适用范围与安全边界

该模式适用于交叉编译依赖的生成元数据重定位，不适用于任意文本全局替换或未知 schema 的猜测修复。旧 W3 run 的 launch/receipt 不得重放；输入、provider 身份、目标架构或消费者清单漂移时必须建立新的冻结验证。平台 CI 仍需在 PR 创建后以当前 HEAD 的 Buildbot 结果确认，不能用本机 Windows Conan 失败或历史 CI 代替。
