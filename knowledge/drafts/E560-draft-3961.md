# E560 — constexpr 标注的 C 风格函数在 C++17/20 常量表达式中不可求值（P2738 需 clang 19+）

## 错误特征

消费方对 `constexpr` 标注的 C 库函数做编译期求值（`constexpr` 变量初始化或
`static_assert`）时，clang 15 报：

```text
error: constexpr variable 'kEmptyCx' must be initialized by a constant expression
note: cast from 'const void *' is not allowed in a constant expression
    const uint8_t *p=(const uint8_t *)key;
error: static assertion expression is not an integral constant expression
```

C++17 与 C++20（`-std=c++17`/`-std=c++20`）两种标准档行为完全相同；运行期
（非常量表达式上下文）调用同一函数全部正常。

## 触发条件

- 构建系统: 任意（单头文件库/无构建系统最常见，消费方自写断言时触发）
- 阶段: compilation（消费方 TU 编译期，非被测库自身构建）
- 典型来源: 给 C 风格哈希/算法头加 `constexpr` 标注的上游项目
  （rapidhash v3 的 `rapidhash_internal` 实测；wyhash 系同类头风险相同），
  其 internal 函数体内含 `const T* p=(const T*)key`（`const void*` → 对象指针的
  C 风格转换），且公开 API 以 `RAPIDHASH_INLINE_CONSTEXPR`（= `constexpr`）导出。

## 根因分析

C++ 核心语言对常量表达式中指针转换的放宽是 **C++26 P2738（constexpr cast from
void*）**：在此之前，任何 `void* → T*` 转换（含 C 风格转换、含指向真实对象的
指针）都使表达式不是常量表达式。上游把函数标成 `constexpr` 只能保证"语法上
可作为常量表达式调用"，能否真正求值取决于函数体内是否出现被禁构造。
OHOS 当前工具链 clang 15.0.4 不实现 P2738（LLVM 该能力首落 clang 19），
因此 C++17/C++20 档一律编译失败。这不是 libc++ 库缺口，也不是 OHOS 缺 syscall，
不适用打补丁绕过。

## 解决方案

### 推荐方案

KAT（已知答案测试）与消费方断言一律改为**运行期比较**：`test_package` 用
`if (got != want) return 1;` 模式；包 notes/manifest 声明"常量表达式求值需
clang ≥ 19（P2738/C++26）"，为工具链能力边界事实留证。

### 禁止做法

- ❌ 为绕过常量表达式失败给上游头打补丁（删 `constexpr` 标注/改写 internal）——
  纯消费方代码组织问题，不该动被适配源码。
- ❌ 用 `-std=c++26` 硬扛：clang 15 无该档位，且即使有，P2738 语义仍取决于
  编译器实现，不能作为交付断言。

## 验证

```bash
# 复现（rapidhash 3, OHOS clang 15.0.4）:
clang++ -std=c++20 -c consumer.cpp
#   error: constexpr variable 'kEmptyCx' must be initialized by a constant expression
#   note: cast from 'const void *' is not allowed in a constant expression
# 修复后: 同一 TU 删除 constexpr 上下文、保留运行期断言 → 832/832 checks passed
# （rapidhash/3 test_package 与设备原生验证实测，2026-09-08）
```
