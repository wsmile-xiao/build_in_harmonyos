# E2189 - Windows Conan OHOS toolchain closure

> Status: DRAFT | 实例: googletest 1.18.0（HarmonyOS PC AArch64）
> severity 2 | category: cross-compile, cmake, conan, ohos, windows

## Problem pattern

On a Windows host, a Conan host profile that only names the OHOS `clang.exe`
can still let CMake select `MinGW Makefiles` or the host linker. Typical
failures are:

```
The C compiler ... is not able to compile a simple test program
/usr/bin/ld: cannot find -lgcc_eh
```

or a MinGW make target reported as not recognized. These failures occur before
the library source is compiled.

## Root cause

The target compiler path is only one part of the cross-build closure. CMake
also needs the OHOS system model, `aarch64-linux-ohos` target triple, SDK
sysroot, lld/llvm-ar and compiler-rt flags. Without the SDK toolchain file,
Conan's generated toolchain can inherit a Windows/MinGW generator and link
rules. The package test is a second configure boundary and must inherit the
same toolchain identity.

This is distinct from E234: no dependency override or package-identity change
is required to trigger the failure. The reusable boundary here is the pair of
independent CMake configurations created by a recipe and its `test_package`;
both must resolve the same SDK toolchain and generator even when the Conan
dependency graph is unchanged.

## Repair

1. Discover `ohos.toolchain.cmake` from the profile's
   `tools.cmake.cmaketoolchain:user_toolchain`, `OHOS_NDK_HOME`, or the
   platform SDK layout; fail closed when none is present.
2. For OHOS, configure and install with the official toolchain, `Ninja`,
   `OHOS_ARCH=arm64-v8a`, `CMAKE_INSTALL_LIBDIR=lib`, and the package's real
   CMake options. Keep host builds on the normal Conan CMake helper.
3. Set the host profile's generator to Ninja and its user toolchain so the
   independent `test_package` configure uses the same target closure.
4. Preserve each failed build root. A local source URL override is acceptable
   only for a byte-counted, SHA-256-verified copy; the submitted recipe keeps
   the official release URL.

## Validation

For this task, r8 failed with MinGW Makefiles, r9 failed with the missing
compiler runtime, and r10 configured with the SDK toolchain, compiled the
complete 161-target graph, packaged four static libraries, and compiled the
consumer. The fresh Windows host copy ran its complete platform inventory at
62/62 and the consumer at 3/3. MinGW intentionally omits
`gmock_stress_test`; forcing `GTEST_HAS_PTHREAD` fails because upstream does
not create `Threads::Threads` on MinGW. The OHOS target inventory includes
that test, and W3 run-003 completed 63/63 plus the target consumer at 1/1
after native self-signing of 68/68 artifacts.

## Scope and safety boundary

This pattern applies to Windows-hosted Conan/CMake cross-builds targeting OHOS
when the SDK supplies the compiler and linker runtime and the recipe plus
`test_package` create separate CMake build trees. Dependency-override work
that changes the Conan binary identity remains governed by E234. Host and target CTest
inventories must remain distinct when upstream conditionally registers tests
by platform capability. A signed target W3 proves execution only for its bound
HEAD, tree, endpoint, and inventory; it does not prove platform CI,
publication, or Review. Do not hide a missing sysroot with host libraries,
weaken the compiler probe, force unsupported host capabilities to equalize
test counts, or reuse a partial build as a pass.
