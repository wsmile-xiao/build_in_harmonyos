# E2155 - Clear Conan's Default Include Directory for Headerless Libraries

## Symptom

A Conan package contains its linkable library and completes packaging, but a
real CMakeDeps consumer fails during configure because the imported target
references a package `include/` directory that does not exist.

## Root Cause

Conan's default `cpp_info.includedirs` value is `include`. It is a metadata
claim rather than a check of installed files. A library that intentionally has
no public headers exports an invalid usage requirement unless the recipe
overrides that default.

## Resolution

For a genuinely headerless public library contract, set:

```python
self.cpp_info.includedirs = []
```

Keep `cpp_info.libs`, target names, transitive `requires`, and system libraries
based on the actual link interface. Validate through a consumer that only calls
`find_package()` and links the generated imported target.

If public headers should exist, this rule does not apply. Install the missing
headers and retain the corresponding include directory.

## Validation

ScaLAPACK 2.2.3 r8 completed 100/100 upstream tests and packaging but failed at
the CMakeDeps consumer because its package contained no `include/`. The exact
r10 input added `self.cpp_info.includedirs = []`. The
`scalapack::scalapack` consumer then configured, compiled, linked, was signed,
and ran under packaged `mpiexec -n 2`; both ranks reported `failures=0`.

## Negative Checks

- The consumer must not add the package include or library path manually.
- A recipe with installed public headers must not clear `includedirs`.
- A configure-only check is insufficient when target runtime is available;
  compile, link, and execute the consumer.
- Package file existence alone does not prove generated target correctness.

## Related Knowledge

E221 covers the wider contract for packages that expose both a CLI and a public
library. This entry isolates the headerless-library default that also affects
library-only packages such as ScaLAPACK.
