# rule1「PR 模板格式」：复选框必须紧跟其 `###` 问题标题（模板行位），互斥「是/否」只勾事实成立的一侧

**条目**: `DRAFT-worklog-2.1-rule1-template-checkbox-order`
**来源**: worklog 2.1 · PR #14141 rule1 判定两次反复（初判 FAIL → 误判 PASS → 定位到真缺口）
**状态**: DRAFT

## 现象

同一份 PR 描述，rule1 判定在两轮之间来回翻转：

- 第 1 轮：按「复选框必须位于 `##` 节直属行、不能落到 `###` 小节内」判 **FAIL**，
  据此把 4 行 `- [x]/- [ ]` 从 `###` 之后**上移**到所属 `##` 直属行。
- 第 2 轮：抽样已合并 MR 推翻该口径，改判 **PASS**——但描述仍停在「上移到 `##` 直属行」的形态。
- 第 3 轮（本文）：把 8 个已合并 MR 的骨架逐一 dump 后发现，真正与模板不一致的是
  **顺序**：`###` 问题标题必须在其复选框**之前**，而当时描述里复选框被放到了标题**之上**。

⇒ 两次判定都不对，根因是**只抽样了「行位归属」这一个维度，没比对「模板行位顺序」**。

## 口径（取证结论）

`templates/积分赛事PR模板.md` 第 27–50 行定义的两个说明节，行位是**强制的**：

```
## 上游测试用例修改说明
                              ← 空行
### 是否存在对上游测试用例的修改？   ← 问题标题
                              ← 空行
- [x] **否**，未修改上游任何测试用例  ← 复选框块，紧随标题
- [ ] **是**，存在对上游测试用例的修改（请在下方逐条说明）
                              ← 空行
> 若选择「是」，须逐条列出： …      ← 解释性引用块
```

已合并 MR 抽样（查询 12 个 MR，其中 8 个 `state=merged` 且 body 可读，下表为这 8 个；
全部经 `GET /pulls/<n>` 实测 body，非推测）：

| MR | state | 该节有无 `###` 问题标题 | 复选框位置 | 复选框行数 | 勾选情况 |
|---|---|---|---|---|---|
| 13764 | merged | 有 | **紧随标题之后** | 1（只写命中的那侧） | 仅「否」 |
| 13905 | merged | 无 | 直属 `##` | 1 | 仅「否」/「是」 |
| 14050 | merged | 有 | **紧随标题之后** | 2 | 「否」+「是」同勾 |
| 14106 | merged | 无 | 直属 `##` | 2 | 仅「是」 |
| 14107 | merged | 有 | **紧随标题之后** | 2 | 「否」+「是」同勾 |
| 14156 | merged | 有 | **紧随标题之后** | 2 | 「否」+「是」同勾 |
| 14157 | merged | 有 | **紧随标题之后** | 2 | 仅「是」 |
| 14175 | merged | 有 | **紧随标题之后** | 2 | 「否」+「是」同勾 |

结论：

1. **8/8 已合并 MR 里，没有一个把复选框放在 `###` 问题标题之上。**
   6 个写了 `###` 标题的，**6/6 都是「标题 → 复选框」**；另 2 个（#13905、#14106）
   干脆不写 `###` 标题、复选框直属 `##`——两种形态各自内部都是自洽的。
   ⇒ 唯一与全部先例都不同的形态，正是「有 `###` 标题、复选框却跑到标题之上」，
   本 PR 修复前的描述就是这个形态。
   一旦解析器按「找到 `###` 问题标题，再读其后若干行找 `- [x]`」来找勾选，
   复选框位于标题之上就会**读不到勾选** ⇒ 判不出选择 ⇒ rule1 FAIL。这是可解释的失败机制。
2. **互斥的「是/否」允许只勾一侧**；两侧同勾在平台上被接受过（4/8 已合并 MR），
   **不是**阻塞项。但当上游确实 0 用例时，勾「否，上游已有测试用例覆盖」是**事实错误**
   （描述失真），应只勾「是」——这一条与平台是否容忍无关，属于自检义务。
3. **首行必须是「否」、次行「是」**（与模板 31–32 行、8/8 已合并 MR 一致）。

## 落地做法

1. 首节加 `## 三方库信息`（或工具骨架的 `## PR 信息`）标题，把 5 个抬头字段收进该节。
   已合并 MR 里 3/8 有标题、5/8 没有，两种都过；但 rule1 的判定口径把
   **「三方库信息」列为必备分节**，加标题是零成本的严格化。
2. 两个说明节一律按模板顺序写：`##` → `###` 问题标题 → 空行 → 2 行复选框 → 空行 → `>` 解释块。
3. 只勾事实成立的一侧；上游 0 用例 ⇒ 「补全测试用例说明」只勾「是」，
   「上游测试用例修改说明」只勾「否」（无可修改对象）。
4. 自检脚本按模板逐项断言，最后打印 `RULE1_FAILS=0`：抬头 5 字段、6 节顺序、
   两表类目与合计自洽、每节复选框行位与勾选数、验证结果 3 字段、零占位符残留。

## 禁止做法

- ❌ 用**单个**已合并 MR 的形态推导平台规则（本次就是被 #14106「该节无 `###`、复选框直属 `##`」
  这一例带偏的）。口径必须 **n ≥ 5 且覆盖全部已合并 MR 的骨架 dump** 才可采信。
- ❌ 判定翻转时只改「结论」不同步改「描述」——第二轮改判 PASS 后描述仍是非模板行位，
  等于把误判固化。
- ❌ 为迁就未经取证的行位口径重排描述。行位类判定要么按模板、要么按多数先例，
  不接受「让宽松/严格两种口径都过」的重排——重排本身会让描述偏离模板。
- ❌ 把「平台曾经接受过」当成「可以不改」。事实错误的勾选要改，平台容忍不等于描述正确。

## 验证

```bash
# rule1 逐项自检（模板 5 抬头 + 6 节顺序 + 两表合计 + 复选框行位/勾选数 + 占位符）
python3 rule1_check.py            # 期望末行 RULE1_FAILS=0
# 取证：dump 已合并 MR 的标题+复选框骨架，逐个核对行位
for n in <已合并 MR 列表>; do curl -s "$API/pulls/$n" | python3 -c 'import json,sys; …'; done
```

> 判据要写成「若该节有 `###` 问题标题，则复选框行号必须 > 标题行号且二者同节」，
> 而不是「复选框是 `##` 直属」或「复选框必须在 `###` 内」这类单侧断言——
> 后两者都会在真实先例上误判（`##` 直属是 2/8 的合法形态，见上表 #13905、#14106）。
