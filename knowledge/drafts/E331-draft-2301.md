# E331 - Make Case-Only Archive Renames Three-Way Replayable

> Contributor: 2301_80739235 | Status: DRAFT | Created: 2026-08-19

## Symptom

An OpenHarmony PC repair PR lowercases an existing archive directory. The
repository and local staged tree look correct, but Buildbot stops in
`checkout-pr` before recipe validation or compilation:

```text
error: archives/a/appconfig/1.71/conanfile.py: already exists in working directory
```

Retrying the same revision produces no new technical information because the
failure is deterministic for that patch and filesystem behavior.

Even after three-way checkout succeeds, CI can still fail later when its
changed-package selector receives both the deleted uppercase path and the new
lowercase path:

```text
CI_PACKAGES received: archives/a/AppConfig/1.71 archives/a/appconfig/1.71
[fail] L0m: ... package directory 'AppConfig' is not a Conan slug
```

## Root Cause

Git tracks path bytes, but a case-insensitive checkout maps `AppConfig` and
`appconfig` to the same physical directory. A direct patch application sees
the lowercase destination as already present. Pure case-only renames also
carry little or no changed blob context, so a patch consumer may be unable to
associate the old and new paths through its three-way fallback.

This differs from a dirty-worker failure: cleaning the worktree does not make
two case variants become distinct filesystem entries.

A second failure mode appears when any tracked file is left as a deletion-only
entry under the old spelling. A changed-path collector can derive the old
package directory from that deletion. On a case-insensitive worker, testing
`archives/a/AppConfig/1.71/conanfile.py` still succeeds because it aliases the
new lowercase file, so the obsolete package token reaches L0m instead of being
discarded as missing.

## Recommended Solution

1. When a merged-but-unpublished recipe legitimately requires a numeric repair
   version, change both the package-directory case and the version segment
   (for example, `AppConfig/1.71` to `appconfig/1.71.1`). The two physical
   paths no longer alias on a case-insensitive checkout.
2. Move every tracked file under the package, including empty sentinels, to the
   lowercase repair-version destination. Require the final tree and changed
   package projection to contain no old-case package path.
3. If the exact version must remain, keep a real, truthful content change in
   each case-only rename so Git has usable preimage and postimage blobs for a
   three-way merge.
4. Handle unchanged empty files through an unambiguous temporary path/two-step
   rename, or fix the CI package selector in a separate infrastructure change:
   derive packages only from added/modified files and rename destinations,
   then require an existing canonical lowercase `conanfile.py` path. A software
   PR must not mix that infrastructure change into its archive repair.
5. Export the exact candidate diff from current main to the staged candidate
   tree with binary data enabled.
6. In a clean case-insensitive worktree at that exact main revision, record
   that direct apply fails and leaves zero partial changes.
7. Reset only that owned validation worktree, run `git apply --3way --index`,
   and require return code zero.
8. Require the resulting index tree to equal the candidate tree. Also compare
   the candidate and replay path sets and per-file identities, and require no
   uppercase recipe or package-input path in the final tree.
9. Independently inspect the provider-facing changed path list. It must contain
   no old-case package path, and package-directory projection must yield only
   the canonical lowercase package/version.

If the real CI patch consumer has no three-way fallback, use a two-commit
rename through an unambiguous temporary path and verify the hosting provider's
actual generated PR diff. Do not assume that a local `git mv` proves CI
applicability.

## Validation

For AppConfig 1.71, the technical case-fix candidate before this knowledge
draft was added was based on
`5116ab2fa920e2224098e41804c00feb82c241ca` and had staged tree
`41109e61263aeabd90f970a36f44548b0dcf85f1`.

- Direct apply returned 1 with 11 `already exists in working directory`
  diagnostics and zero post-failure changes.
- `git apply --3way --index` returned 0.
- The replay index tree exactly equaled the candidate tree.
- Candidate and replay each contained 16 current files, with zero path-list
  differences, zero hash mismatches, and zero uppercase paths in the final
  candidate.

The immutable reproduction result for that technical candidate is
`E:\HarmonyPC\validation\appconfig-1.71\ci-casefix-r2-41109e61-20260818T222042Z\CASEFIX-RESULT.json`
with SHA-256
`67f669d04584ebd68666672642f0f564b1aa3f89b556e94c8dd91cb75663913b`.

Buildbot #27565 (global build 30716) later proved the changed-package boundary:
checkout-pr passed, but two deletion-only files caused both case variants to
enter `CI_PACKAGES`; the uppercase alias then failed L0m. The content-bearing
historical report still cannot be a pure unchanged rename on the
case-insensitive worker; its migrated copy therefore adds truthful relocation
metadata while preserving the original audit conclusion. The empty `.gitkeep`
cannot carry equivalent metadata. The final AppConfig repair therefore uses
the new numeric version `1.71.1`, moves that empty file with every other
tracked package file, and leaves no `archives/a/AppConfig/` path in the final
tree. Changing both case and version avoids the physical-path alias instead of
relying on an old-case sentinel exception. This is distinct from the same
build's lowercase-package registry probe failure, where the Worker Python
lacked SSL support.

The first current-main replay after the package-selection repair confirmed this
boundary: all content-bearing renames applied through three-way merge except
the unchanged historical W4 JSON. The attempt returned RC 1 atomically with a
clean base tree, so the successor adds only the relocation metadata described
above and reruns the full replay.

## Safety Boundary

This replay proves only that the identified technical candidate can be
reconstructed on a case-insensitive checkout. A final pre-push replay must bind
the later candidate that includes this draft. Neither result replaces W3,
independent W4, Buildbot
success on the pushed revision, Review closure, submission, merge, `/release`,
or a fresh artifact-registry readback.
