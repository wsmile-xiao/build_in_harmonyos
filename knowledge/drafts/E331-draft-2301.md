# E331 - Separate XSync subtraction results from the overflow flag

> Contributor: 2301_80739235 | Status: DRAFT | Created: 2026-08-20

## Symptom

An installed-package consumer calls `XSyncValueSubtract` with the public values
`1` and `2`. The result equals `-1`, but the historical implementation sets the
overflow output and the consumer exits with RC 8 because it requires that flag
to be zero.

## Root cause

The returned `XSyncValue` and the auxiliary overflow output are separate API
observations. In libXext 1.3.7, the historical subtraction implementation can
set the flag on this sign transition even though `-1` is representable and is
returned exactly. Treating the flag as the only validity signal turns an
implementation compatibility detail into a false package failure.

## Recommended solution

Keep the public call and verify that `1 - 2` equals the exact public `-1`
value. Do not require a particular overflow bit for that historical case.
Continue checking the overflow contract independently with a true boundary
operation such as maximum plus one, including the expected wrapped result.

This keeps the consumer substantive: it still exercises the installed header,
links the packaged library, calls the arithmetic API and checks both ordinary
and boundary behavior.

## Forbidden shortcuts

- Do not remove `XSyncValueSubtract` from the consumer.
- Do not skip the consumer on OpenHarmony.
- Do not accept any subtraction result merely because the overflow flag is set.
- Do not weaken the separate maximum-plus-one boundary assertion.

## Verification

In the libxext 1.3.7 r27 target run, the corrected consumer printed exactly one
`LIBXEXT_TEST sync_value_contract PASS` marker in the normal recipe build and
again in the forced-static replay. The registry consumer also passed in both
variants. The r27 aggregate wrapper remained FAIL because the repository-wide
`finish` command returned RC 1 in later knowledge/readiness stages; that does
not alter this consumer-level result and is tracked separately.
