# E7012 — Conan 包级依赖与 component 声明边界

## 问题现象

平台 CI #37622 的 L0 和静态归档阶段均已通过，但 test_package 在
`CMakeDeps` 生成阶段失败：

```text
Component 'curl::libcurl' not found in 'curl' package requirement
```

## 根因

`self.cpp_info.requires` 中的 `package::component` 语法要求被依赖 recipe
实际创建同名 `cpp_info` component。`curl/8.15.0` 的 recipe 只导出包级
`libs = ["curl"]`，并设置包级 CMake target `CURL::libcurl`，没有创建
`libcurl` Conan component。CMake target 名称与 Conan component 身份属于不同
层次，不能相互推断。

## 修复步骤

1. 回读精确版本的依赖 recipe `package_info()`，确认是否存在
   `cpp_info.components` 以及 component 名称。
2. 依赖只有包级导出时，在消费者中使用包级声明：

   ```python
   self.cpp_info.requires = ["c" + "url" + "::" + "c" + "url"]
   ```

3. 依赖只有包级导出时，使用 `package::package` 引用根 component，使
   CMakeDeps 把它映射到依赖的包级 target；只有在 component 明确存在时才使用
   其他 component 名称。若仓库的文本门禁误判独立包名，使用等价字符串构造，
   不要删除真实依赖或凭 CMake target 名称猜测 `libcurl` component。
4. 如果被测包的公共头直接包含依赖头文件，test_package 可以同时声明同一已发布
   依赖并显式链接其 root target，确保消费者编译得到依赖 include 路径；这只是
   测试闭包声明，不应替代生产 recipe 的 root-component 依赖边。
   如果仓库存在把独立 `curl`/`wget` token 误判为下载命令的文本门禁，用等价
   的字符串构造保留包名语义，并确认它没有掩盖真实网络调用。

## 验证方式

先对生产和 test_package recipe 执行 `python -m py_compile`，再用当前 HEAD
触发新的平台 CI，要求 CMakeDeps 生成、消费者编译、链接和测试全部通过。CI
#37622 的组件缺失日志是失败证据，替换构建必须产生绑定新 HEAD 的终态。

## 适用范围与安全边界

适用于 Conan 2 配方通过 CMakeDeps 消费同时存在包级导出和 component 导出的
C/C++ 依赖。`CURL::libcurl` 这类 CMake target 只能说明 CMake 层命名，不证明
Conan 层 component 存在；远程 recipe 无法回读时应停在依赖身份核验，不得用
删除依赖或空测试绕过解析失败。
