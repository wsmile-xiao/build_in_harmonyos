# MinGW DLL 导出闭包与 Windows test_package shell 边界

## 现象

在 MinGW 的 shared 构建中，基础 DLL 可以完成编译，但依赖它的线程/插件 DLL 在链接阶段找不到内部符号。即使把库打包成功，Conan Windows `test_package` 还可能在运行探针时出现 `syntax error: unterminated quoted string`；这不是被测库 ABI 的失败，而是 `cmd.exe` 对 POSIX `bash -c '...'` 引号和 Windows 反斜杠路径的解释不同。

## 根因

GNU ld 在 DLL 含有显式 `dllexport` 时不会继续对所有非静态符号执行隐式 export-all，导致子 DLL 所需的基础库符号不在 import library 中。运行测试时，Conan 的 Windows 执行器经由 `cmd.exe` 传递命令，POSIX 单引号不会像 Unix shell 那样剥离；把带反斜杠的包路径拼入 `bash -c` 会使 shell 看到错误的转义和引号边界。

## 修复步骤

1. 只在 `settings.os == "Windows"` 的 CMake toolchain 中启用 `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS` 和 `-Wl,--export-all-symbols`，再检查基础 DLL/import library 的符号闭包，确认线程或插件目标的每个必需符号均可解析。
2. test_package 仍以真实 API 编译链接。Windows 分支直接运行 `test_probe.exe`，依赖 `VirtualRunEnv` 注入的 PATH；POSIX 分支才使用 bash 导出 `LD_LIBRARY_PATH`。
3. 目标平台独立回读产物架构、SONAME、NEEDED 和签名，并完成上游测试与消费者测试；不要以禁用链接错误、全局权限或静态扫描替代运行验证。

## 适用范围与安全边界

适用于 MinGW shared DLL 存在显式导出且子模块通过 import library 链接，以及 Conan Windows test_package 需要运行本地探针的库。若上游明确要求受限导出，应逐项证明 ABI 后再添加导出；若 VirtualRunEnv 未提供可验证的 DLL 搜索路径，必须 fail closed。此结论不授权修改系统 PATH、关闭链接错误、复用其他 run 的测试结果或跨 endpoint 拼接 W3 证据。
