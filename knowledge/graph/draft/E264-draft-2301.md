# E264 - Metadata-Derived Signed ELF Adapter for Legacy `*-config` Probes

## Symptom

A dependency resolves successfully in Conan and exposes valid include,
library, link, and version metadata, but the consumer's `configure` script
still insists on executing a legacy helper such as `geos-config`.

The build then fails before compilation because the packaged dependency does
not ship that legacy program, or because a shell helper in the package cache
cannot be executed reliably from HMDFS. Supplying a machine-specific helper
path can appear to work locally while failing in a fresh Conan home.

## Scope

Use this pattern when all of the following are true:

- the upstream configure contract requires an executable `*-config` helper;
- the exact Conan dependency already exposes equivalent structured metadata;
- changing upstream discovery to a different system would be broader than
  preserving its existing query contract; and
- the build executor can compile and, when required, sign a small target ELF.

This is not a general replacement for CMake or pkg-config. Prefer the
upstream-supported structured discovery path when one exists and is complete.

## Root Cause

Legacy configure logic treats `*-config` as an executable protocol. Modern
packages increasingly export CMake targets or pkg-config data instead, so a
Conan package can be semantically complete while lacking the executable that
the older consumer expects.

Two tempting substitutes are not portable:

1. A shell shim retains the direct-script-execution failure on HMDFS.
2. Hard-coded cache paths are detached from the dependency revision selected
   by the current Conan graph.

The adapter must therefore be derived from the resolved dependency object and
must itself satisfy the target executor's binary policy.

## Solution

In the consumer recipe:

1. Read the required values from `self.dependencies["<name>"].cpp_info`.
2. Fail immediately if required include or library directories are absent.
3. Escape those values as C string literals and generate a minimal C program
   in the recipe build folder.
4. Implement only the query switches used by the upstream configure script,
   returning nonzero for a wrong argument count or an unknown switch.
5. Compile with the active C compiler from
   `tools.build:compiler_executables`, rather than a hard-coded toolchain.
6. Sign the resulting ELF after its final byte-changing operation when the
   target execution policy requires a signature.
7. Pass the helper's absolute path through the upstream
   `--with-<name>config=<path>` option.

A `geos-config` adapter, for example, can answer `--cflags`, `--clibs`,
`--ldflags`, `--includes`, and `--version` from the exact GEOS node selected
by Conan. It should not pretend to implement unrelated switches.

## Forbidden Shortcuts

- Do not hard-code a Conan cache directory, device home, include directory, or
  library directory.
- Do not copy a helper from another recipe revision without proving that its
  output matches the current dependency node.
- Do not generate another shell script when direct script execution is the
  failing capability.
- Do not return success for unknown switches or missing metadata.
- Do not sign before compilation or before any later ELF modification.

## Verification

Use positive and negative checks bound to one exact Conan graph:

| Check | Expected result |
|------|-----------------|
| Each supported query | Output equals the resolved dependency metadata |
| Unknown query | Nonzero exit status and no misleading flags |
| Missing required metadata | Recipe raises an invalid-configuration error |
| File identity | Target ELF for the active architecture |
| Signature gate | Final ELF has a valid executable signature when required |
| Configure | Consumes the absolute adapter path successfully |
| Consumer | Compiles, links, and executes against the same dependency graph |

The pattern was first implemented for `librttopo/1.1.0.1` and then reused by
`libspatialite/5.1.0.1`, both against the exact `geos/3.13.1` Conan metadata.
The second use demonstrates that the method is a reusable dependency-discovery
contract rather than a one-library patch.
