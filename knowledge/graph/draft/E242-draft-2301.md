# E242 - Compiler-Specific Fortran Module ABI in Conan Packages

## Symptom

A Conan package can install a Fortran archive and its generated `.mod` files,
and CMake can successfully create an imported target for that component. The
consumer may still fail during compilation with diagnostics such as:

```text
Cannot open module file
module file was created by a different version of the compiler
Unexpected EOF in module file
```

The failure can be delayed until the first source imports the module because
ordinary library metadata describes headers and link archives, not the binary
format of a compiler-generated Fortran module.

## Scope

Use this pattern for Conan packages that distribute precompiled Fortran module
files. It is especially useful for mixed C and Fortran libraries where:

- C-only consumers should not need a Fortran compiler.
- Fortran consumers need an exact compiler family and version.
- The compiler is supplied as a Conan build tool rather than by the base image.
- A package revision must change identity when the compiler tool package changes.

## Root Cause

Fortran standardizes source semantics, but it does not standardize the binary
format or cross-version compatibility of `.mod` files. Compiler family and
version are therefore part of the packaged module ABI.

Two independent metadata gaps must be closed:

1. A normal Conan library package ID does not automatically include the exact
   build-tool package that generated the modules.
2. A generated CMake imported target does not automatically verify the active
   Fortran compiler before a consumer links the component.

## Fix

### Producer package identity

Declare the exact compiler tool package with full package-ID propagation:

```python
def build_requirements(self):
    self.tool_requires(
        "flang-ohos/20.1.0",
        package_id_mode="full_mode",
    )
```

Package the Fortran archive and `.mod` files as a separate component. Keep the
C component separate so C-only consumers do not inherit the Fortran contract.

### Consumer contract

Require Fortran consumers to declare the same exact tool package. Export a
CMake build module through `cmake_build_modules` and make it fail closed unless:

1. the consumer explicitly requests a `Fortran` component;
2. the Fortran language is enabled before `find_package()`;
3. `CMAKE_Fortran_COMPILER_ID` matches the producer compiler; and
4. `CMAKE_Fortran_COMPILER_VERSION` exactly matches the producer version.

When the component is not explicitly requested, keep a deliberately unresolved
guard dependency on the imported Fortran target. Remove that guard only after
all compiler checks pass. This prevents accidental direct use while leaving
the C target available.

## Verification

The validation matrix must include distinct positive and negative consumers:

| Case | Expected result |
|------|-----------------|
| C-only consumer, no Fortran tool | Configure/build succeeds |
| Matching compiler and explicit Fortran component | Configure/build succeeds |
| Fortran target without explicit component | Configure or generate fails |
| Explicit component before enabling Fortran | Configure fails |
| Wrong compiler ID | Configure fails |
| Wrong compiler version | Configure fails |
| Compiler tool package revision changes under `full_mode` | Package identity changes |

For an OHOS package, also run the real target `conan create` and the substantive
Fortran consumer. Host-only CMake logic tests do not replace that target gate.

## Forbidden Shortcuts

- Do not treat `.mod` files as portable headers.
- Do not rely only on the Fortran archive SONAME or library version.
- Do not make every C consumer install the Fortran compiler.
- Do not accept a broad compiler major range unless compatibility is proven for
  the exact module format in use.
- Do not mark the package validated from static metadata or host-only checks
  when the target Fortran consumer has not run.

## Source Evidence

The libxc 7.1.2 OpenHarmony PC candidate packages `xc_f03_lib_m.mod` and
`xc_f03_funcs_m.mod` generated by `flang-ohos/20.1.0`. Its Conan graph binds
the tool requirement with `package_id_mode="full_mode"`, and its exported CMake
module gates `Libxc::xcf03` on an explicit Fortran component plus exact
`LLVMFlang 20.1.0` checks. A host CMake logic matrix accepted the C-only and
exact-compiler cases, and rejected missing-component, disabled-language,
wrong-compiler-ID, and wrong-compiler-version cases. A fresh HarmonyOS PC
aarch64 Conan run then compiled, linked, and executed both the C and LLVMFlang
Fortran KXC consumers. All 328 inspected objects from `libxc.a` and the single
Fortran object from `libxcf03.a` were confirmed as ELF64 AArch64. The two
consumer flows passed 2/2 with every unexpected terminal class at zero, and the
independently downloaded evidence bundle passed all 39 hash checks.
