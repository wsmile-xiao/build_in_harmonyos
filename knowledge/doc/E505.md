# E505: OHOS loader: LD_LIBRARY_PATH overrides DT_RPATH and symlinked soname aliases cannot resolve

## 基本信息
- **严重度**: 1
- **类别**: autotools, configure, dynamic-loading
- **作者**: Awstme <awstme@qq.com>
- **来源 PR**: !7080

## 错误特征
```
Error loading shared library [^:]+: \(needed by\)|cannot run C compiled programs|configure: error: cannot run C compiled programs|Error loading shared library .*: Permission denied
```

## 根因分析
OHOS 上 musl 加载器认 LD_LIBRARY_PATH，并且一旦该变量被设置，其查找会压过二进制内嵌的 DT_RPATH。依赖包安装的版本化别名（libfoo.so.1 -> libfoo.so.1.2.3）在 HMDFS 上无法由加载器经别名名解析，因此把 LD_LIBRARY_PATH 指向依赖包 lib 目录会让查找失败，即使 DT_RPATH 指向的实体化目录是可加载的。表现是 configure 报 cannot run C compiled programs（rc=77）或运行期 Error loading shared library X (needed by Y)，而 ls/lld 层面文件都存在。

## 推荐方案
**方法**: materialised-signed-runtime-view

**说明**: 在任务私有构建目录里为依赖共享库闭包建立实体化视图：按依赖 cpp_info.libdirs 遍历，resolve 符号链接后以真实文件名复制为普通文件（保留 owner 可执行位），然后只把该视图嵌入所构建二进制的 DT_RPATH（-Wl,--disable-new-dtags,-rpath,<view>）。不要为此导出全局 LD_LIBRARY_PATH：无论指向包目录还是视图目录都有害（包目录因符号链接别名解析失败，视图目录会毒化被继承的工具链子进程，见 forbid_2）。

**验证/命令**:
```
mkdir -p $BUILD/runtime-libs && for e in $(ls $DEP/lib | grep -E '\.so(\.[0-9]+)*'); do cp -p $DEP/lib/$(readlink -f $DEP/lib/$e 2>/dev/null || echo $DEP/lib/$e) $BUILD/runtime-libs/$e; done; export LDFLAGS="$LDFLAGS -L$BUILD/runtime-libs -Wl,--disable-new-dtags -Wl,-rpath,$BUILD/runtime-libs"; unset LD_LIBRARY_PATH
```
