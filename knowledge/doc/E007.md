# E007: config.guess 无法识别 HarmonyOS 系统

> **结构化数据**: [graph/E007.kv](../graph/E007.kv) | **原则**: [P-AUTOTOOLS-001](../graph/principles.kv), [P-AUTOTOOLS-002](../graph/principles.kv)
> **严重度**: 🟡 medium | **分类**: autotools-config | **自动修复**: ✅ run-patch-script

---

## 错误特征

```
configure: error: cannot guess build type
If you meant to cross compile, use '--host'.
checking build system type... Invalid configuration
config.guess: unable to guess system type
```

## 根因

GNU `config.guess` 脚本不包含 HarmonyOS / `__OHOS__` 检测分支。当 `uname -s` 返回 `HarmonyOS` 时，脚本无法匹配任何已知系统模式。

**问题链**：
```
./configure → 调用 config.guess → uname → UNAME_SYSTEM=HarmonyOS → 无匹配
    → configure: error: cannot guess build type → 编译流程中断
```

## 影响范围

**所有 autotools 项目**。这是鸿蒙编译的**第一道门槛**，在 configure 阶段就阻塞后续所有步骤。

---

## ⚠️ 铁律：禁止 --build/--host 绕过

> 此规则于 2026-04-09 由 xz 5.6.2 编译事件确立（F069）。

| 做法 | 结果 |
|------|------|
| ❌ `--build=aarch64-unknown-linux-gnu` | 掩盖问题，`cross_compiling=yes`，AC_RUN_IFELSE 全跳过，config.h 错误 |
| ✅ 打补丁 config.guess + config.sub | 正确识别为 `aarch64-unknown-linux-ohos`，所有检测在正确三元组下执行 |

### 级联后果链

```
--host= 绕过 → cross_compiling=yes
    → AC_RUN_IFELSE 跳过 → conftest 不执行 (E064)
        → gnulib 模块选错 (E061)
        → 符号未声明 (E062)
        → -Werror 级联失败 (E063)
        → 链接错误 (E005)
        → 运行时崩溃 (E019/E040)
```

## 解决方案

### 唯一正确做法：打补丁修改 config.guess + config.sub

使用内置脚本一键完成：

```bash
perl ${SKILL_ROOT}/scripts/patch-autotools-ohos.pl build-aux/config.guess build-aux/config.sub
# 输出: ✅ Patching successful. (Score: 5/5)
```

该脚本已处理 `linux-uclibc*` / `linux-uclibc*-` 等变体，并包含 grep 验证。

### 手动补丁详情

#### config.guess — 两处修改

**位置 1（§2.1）：LIBC 检测**

```diff
 #if defined(__ANDROID__)
 LIBC=android
+#elif defined(__OHOS__)
+LIBC=ohos
 #else
 #include <features.h>
```

**位置 2（§2.2）：系统识别 case 分支**

在主 `case $UNAME_MACHINE:$UNAME_SYSTEM:$UNAME_RELEASE:$UNAME_VERSION in` 开头添加：

```diff
     *:HarmonyOS:*:*)
+       case "$UNAME_MACHINE" in
+           aarch64|arm64) MACHINE=aarch64 ;;
+           armv7*|armv8*) MACHINE=arm ;;
+           x86_64|amd64)  MACHINE=x86_64 ;;
+           i?86)         MACHINE=i686 ;;
+           *)            MACHINE="$UNAME_MACHINE" ;;
+       esac
+       GUESS=${MACHINE}-unknown-linux-ohos
+       ;;
     *:NetBSD:*:*)
```

#### config.sub — 三处修改

**位置 1（§3.1）：ohos-linux 三元组**

```diff
 android-linux)
     basic_machine=$field1-unknown
     basic_os=linux-android
     ;;
+ohos-linux)
+    basic_machine=$field1-unknown
+    basic_os=linux-ohos
+    ;;
```

**位置 2（§3.2）：操作系统列表**

```diff
 case $os in
-    gnu* | android* | bsd* | ...
+    gnu* | android* | ohos* | bsd* | ...
```

**位置 3（§3.3）：内核支持列表**

```diff
 case $kernel-$os in
     linux-gnu* | linux-dietlibc* | linux-android* | linux-musl*
-    | linux-uclibc*- )
+    | linux-uclibc*- | linux-ohos* )
```

> ⚠️ 不同版本的 config.sub 中 `linux-uclibc` 可能为 `linux-uclibc*` 或 `linux-uclibc*-`。修改前先 `grep -n 'linux-uclibc' config.sub` 确认实际文本。

---

## 三元组格式

### 标准格式

```
<架构>-<厂商>-<操作系统>
```

### HarmonyOS 标准三元组

| 架构 | 三元组 |
|------|--------|
| ARM64 | `aarch64-unknown-linux-ohos` |
| ARM32 | `arm-unknown-linux-ohos` |
| x86_64 | `x86_64-unknown-linux-ohos` |

### 为什么是 `linux-ohos`

- `linux`：兼容 Linux ABI，复用 Linux 代码路径
- `ohos`：OpenHarmony 系统变体标识

## 验证命令

```bash
# 1. 验证 config.guess
./build-aux/config.guess
# 应输出: aarch64-unknown-linux-ohos

grep -n "__OHOS__"   build-aux/config.guess  # 应 >= 1
grep -n "HarmonyOS"  build-aux/config.guess  # 应 >= 1

# 2. 验证 config.sub
./config.sub aarch64-linux-ohos
# 应输出: aarch64-unknown-linux-ohos

grep -n "ohos-linux" build-aux/config.sub    # 应 >= 1

# 3. 完整测试
./configure --prefix=$HOME/usr/local
# 应看到: checking build system type... aarch64-unknown-linux-ohos
grep "build-aarch64-unknown-linux-ohos" config.log
```

## 常见问题

### Q: 旧版 config.guess 打补丁后不输出三元组？

**症状**：`build-aux/config.guess` 已包含 HarmonyOS 检测分支，但运行后仍报 "unable to guess system type"，没有任何输出。

**根因**：2018 年以前的 config.guess 使用 `echo ... exit` 语法输出结果。而较新版本（2018+）引入了 `GUESS=` 变量赋值机制，在脚本末尾统一 `echo $GUESS`。如果将新版补丁（用 `GUESS=`）打到旧版脚本上，`GUESS` 变量虽被赋值但不会被输出和 exit，脚本直接 fall through 到底部的 "unable to guess" 错误。

**判断方法**：检查 config.guess 结尾是否有 `echo $GUESS`：
```bash
tail -20 config.guess | grep "echo.*GUESS"
# 无输出 = 旧版，必须用 echo+exit
```

**修复**：将 `GUESS=` 赋值改为 `echo ... exit`：
```diff
-    GUESS=${MACHINE}-unknown-linux-ohos
+    aarch64|arm64) echo aarch64-unknown-linux-ohos; exit ;;
+    armv7*|armv8*) echo arm-unknown-linux-ohos; exit ;;
+    x86_64|amd64)  echo x86_64-unknown-linux-ohos; exit ;;
+    i?86)          echo i686-unknown-linux-ohos; exit ;;
+    *)             echo ${UNAME_MACHINE}-unknown-linux-ohos; exit ;;
```

> 注意：`patch-autotools-ohos.pl` 脚本会自动检测版本并选择正确的语法。

### Q: config.guess/config.sub 不在项目根目录？

部分软件（如 wget）将这些文件放在 `build-aux/` 子目录而非根目录。打补丁前必须先确认实际位置：
```bash
find . -name config.guess -o -name config.sub
# wget: ./build-aux/config.guess, ./build-aux/config.sub
```

如果补丁路径错误，patch 不会生效但也不报错（因为 orig 文件不存在），导致 configure 仍然失败。

### Q: 补丁后仍报 "invalid triplet"？

检查 config.sub 是否包含全部三处修改（尤其是 §3.3 内核列表）：

```bash
grep -n "ohos" config.sub  # 应匹配 3 处以上
```

### Q: 与非 autotools 项目的关系？

autotools 项目用 **libffi 模式**（改 config.guess/sub）。自定义构建系统（如 OpenSSL）参考 **OpenSSL 模式**（新建配置文件）。详见本文档 §8（OpenSSL vs libffi 对比）。

### Q: 为什么不用下载最新 GNU config.guess？

GNU 上游未必已合并 HarmonyOS 支持。"碰运气"的下载方案不可靠。打补丁精确可控。
