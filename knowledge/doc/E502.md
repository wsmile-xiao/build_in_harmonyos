# E502: OHOS CI workers refuse dlopen and LD_PRELOAD of every user-directory shared object regardless of ELF signature while exec-time NEEDED loading still works

## 基本信息
- **严重度**: 3
- **类别**: platform, limitation, ohos, musl, security
- **作者**: Awstme <awstme@qq.com>
- **来源 PR**: !6848

## 错误特征
```
Error loading shared library /[^:]+: Permission denied|\(needed by |do_dlsym failed: Symbol not found.*so=/data/service/hnp
```

## 根因分析
The worker loader policy applies to any shared object mapped after process start (dlopen, LD_PRELOAD) for files under user storage directories and rejects it with Permission denied whether the ELF carries a fresh build-time self-signature or the release signature downloaded from the artifact registry. The same freshly self-signed libraries load fine as DT_NEEDED of a process at exec time (verified: the isl C tests passed against the build-time-signed libgmp.so.10 copy resolved from LD_LIBRARY_PATH in build #33895). The interactive device environment is more permissive, so a local dlopen success does not transfer to workers and signature work alone cannot unblock the worker dlopen path.

## 推荐方案
**方法**: probe-then-route-to-exec-time

**说明**: Echo one structured short line per load attempt (never head-slice a multi-line traceback buffer) to localize which file and reason the loader reported, then route the required library into the process through the accepted exec-time path; for python ctypes tests use the embedded launcher pattern of E2167.

**验证/命令**:
```
keep per-file probes line-structured and short (status, errno, last chars of the OSError message, one line per attempt); reference implementation _OHOS_DLOPEN_PROBE_SRC in archives/b/barvinok/0.41.9/conanfile.py
```
