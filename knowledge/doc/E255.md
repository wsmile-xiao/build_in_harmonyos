## 根因分析
OHOS Conan 流水线主要为编译型 C/C++ 库设计，其 L0/L1/L2/L4/L5
                        质量门禁（commands.json, test_sources by find, self.run() 检查等）
                        对纯资源型数据包不适用。资源型数据包的特殊性：
                        1. 无编译步骤：build() 应直接 pass，没有 make/cc 调用
                        2. 源码包可能包含大量符号链接（包括上游符号链接循环），
                           tarfile 默认提取会因 OSError [Errno 40] 失败
                        3. 验证焦点是资源内容的正确性（文件存在性、格式合法性、
                           目录结构完整性），而非编译/链接/运行测试
                        4. 安装通过 cp -R 复制目录树到 share/ 下，不生成 bin/lib/include/
                        5. 部分平台 FS（如 HMDFS）上 find 命令使用绝对路径时不枚举目录内容，
                           导致 CI 脚本的 L0c 检测永远找不到测试源文件
                        6. 无 ELF 产物，L4 安全扫描、L2 --version/--help 测试均不适用

## 推荐方案
**方法**: resource-data-package-conan-recipe

**说明**: |
    纯资源/数据型 Conan 配方应遵循以下通用模式：
    1. package_type = "unknown" — 标记非库/非应用，避免触发 commands.json 门禁
    2. no_copy_source = True — 源码和包目录分离
    3. settings = "os", "arch" — 仅需要 os/arch，不需要 compiler/build_type
    4. build() — 直接 pass（无编译步骤）
    5. package() — 用 copy() 将资源目录树复制到 share/ 对应子目录
    6. package_info() — cpp_info 的 bindirs/libdirs/includedirs/libs 全部置空
    7. export_sources() + apply_conandata_patches() — 仍需声明以通过 G1 检查

    source() 处理符号链接循环：使用 tarfile 手动提取 filter="data"。
    test_package 验证焦点：资源描述文件存在性、格式合法性、断链检测。

**验证/命令**:
```
|
    # 创建/验证
    conan create . -tf test_package
```
