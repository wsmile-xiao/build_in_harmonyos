# E492: Materialize Meson shared-library aliases when OHOS does not expose SONAME names

## 基本信息
- **严重度**: 2
- **类别**: meson, linking, packaging, runtime, testing
- **作者**: wxjshr <wxjshr@noreply.gitcode.com>
- **来源 PR**: !6611

## 错误特征
```
Error loading shared library lib[^ ]+\\.so\\.0|NEEDED.*lib[^ ]+\\.so\\.0|lib[^ ]+\\.so\\.0.*symbol not found|meson test.*exit status 127
```

## 根因分析
Meson built the real versioned library, but the OHOS build/install tree did not expose the SONAME and developer-name aliases that the runtime loader and consumers search for. Adding only LD_LIBRARY_PATH is insufficient when the exact NEEDED filename is absent.

## 推荐方案
**方法**: build-and-package-soname-alias-materialization

**说明**: After meson build and after meson install, ensure the real versioned shared library has the SONAME alias and developer alias in the relevant build or package lib directory. Prefer relative symlinks on capable filesystems and fall back to copying the real ELF when symlinks are denied.

**验证/命令**:
```
ensure libfoo.so.X and libfoo.so exist next to libfoo.so.X.Y.Z before meson test and after install
```
