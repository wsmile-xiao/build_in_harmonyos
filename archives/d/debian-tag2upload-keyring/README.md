# debian-tag2upload-keyring

https://salsa.debian.org/dgit-team/debian-tag2upload-keyring

This package provides the OpenPGP public signing key for the Debian
tag2upload service. The tag2upload service signs Debian source packages and
git tags with this key; the keyring lets APT/consumers authenticate those
signatures.

## OHOS Adaptation

- Pure data package: the binary keyring is installed under
  `share/keyrings/debian-tag2upload.pgp`; nothing to compile.
- The consumer-side test (`test_package/test_verify.py`) locates the artifact
  through the package's published runenv contract (`OPENPGP_KEYRING_DIR`), then
  parses the OpenPGP old-format packet stream and checks key identity:
  a v4 RSA-4096 public key whose fingerprint and long key id are re-derived
  with the RFC 4880 §12.2 rule (SHA-1 over `0x99`, the two-octet body length
  and the whole public-key body) —
  `374D8CE4DB96E9CBD4C0972A606D084E4683C079` / `606D084E4683C079`, cross-checked
  against `gpg --check-sigs` — plus the tag2upload user ID and creation time.
- It also asserts the certification structure: 2 self-certifications
  (sigtype 0x13, whose issuer fingerprint equals the key's own) and generic
  certifications (sigtype 0x10) from 3 distinct third-party certifier keys.
- 46 assertions, backed by 9 negative controls that must all fail — so a
  passing run cannot be vacuous. All 9 are automated inside `test_verify.py`
  and run on every `conan create`: truncation, header corruption, length
  inflation, RSA modulus substitution, algorithm swap, bit-count swap,
  creation-time change, runenv contract break, and missing keyring.
- The end-to-end consumer case (`test_package/test_consumer_e2e.py`) answers the
  question a verifier actually asks — *may I trust the tag2upload signing key
  given this keyring?* — by running one pipeline over the real artifact
  (open → select key → re-derive identity → classify certifications → three
  policy gates → deterministic report) and emitting a verdict. The report is
  compared byte for byte against a reference transcribed from GnuPG 2.4.5's
  `gpg --with-colons --check-sigs` (an independent OpenPGP implementation), not
  against a golden regenerated by this program. 24 assertions, plus an OHOS
  delivery-surface precheck and 5 mutation controls that the same pipeline must
  refuse.
- Every check the three programs make is counted at run time and printed, so
  the totals quoted here and in `1.2/manifest.yaml` are measured rather than
  hand-derived. The measured total is 85 assertions.
- The upstream autopkgtest `debian/tests/verify-one` **is** executed, unmodified,
  by `test_package/run_upstream_tests.py`. The script is a byte-identical copy of
  the upstream file (sha256 pinned in `test_package/upstream-test.sha256`,
  derived from the tarball locked in `conandata.yml`) and is run against the
  *packaged* keyring: the upstream script resolves the keyring as
  `$PWD/debian-tag2upload.pgp`, so the package's own
  `share/keyrings/debian-tag2upload.pgp` is staged under that name. Its
  `perl` split and its final `rsop verify` both run for real.
- The one substitution is the `rsop` binary, which is absent from the OHOS
  toolchain and artifact repository — `archives/d/debsig-verify/0.34` documents
  the same gap when its `atlocal.in` probes `sqop/rsop/gosop/pgpainless-cli/sq/gpg`
  and finds none of them. `test_package/rsop.py` implements the same
  `rsop verify` contract in pure Python (`rsop verify <sig> <keyring>`, signed
  data on stdin): RFC 4880 packet parsing, the RFC 4880 §5.2.4 v4 signed-data
  construction, and RSA EMSA-PKCS1-v1_5 with full padding validation.
- That substitution is cross-checked, not assumed. On the upstream fixture
  GnuPG 2.4.5 reports a good signature, and running the *same* unmodified
  upstream script against pristine and mutated inputs yields identical verdicts
  under GnuPG and under `rsop.py`:

  | input | GnuPG-backed `rsop` | `rsop.py` |
  |---|---|---|
  | pristine fixture | accept | accept |
  | tag object plaintext altered | reject | reject |
  | signature MPI altered | reject | reject |
  | keyring RSA modulus replaced | reject | reject |
  | empty keyring | reject | reject |

  The same four mutations are asserted on every test run, so a pass cannot come
  from a verifier that accepts everything.
- GnuPG is deliberately not invoked at test time: `gpg`/`gpgv` are absent from
  the OHOS toolchain and artifact repository
  (`archives/l/librnp/0.18.1/conanfile.py`: "cli_tests need GnuPG gpg/gpgconf
  (not available on OHOS workers)"), so all three programs stay pure Python and
  run the same code on the worker as on a developer machine. `gpg` is used only
  as an offline cross-check to calibrate the pinned constants and to validate the
  `rsop.py` substitution.

## Usage

Point your verification tooling at the keyring path:

```
share/keyrings/debian-tag2upload.pgp
```

The Conan package exports `OPENPGP_KEYRING_DIR` (via runenv) so consumers can
locate the keyring directory without hard-coding paths.

- `share/keyrings/debian-tag2upload.pgp` — OpenPGP signing keyring
