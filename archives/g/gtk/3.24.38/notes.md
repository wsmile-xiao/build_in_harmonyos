## Build strategy

GTK 3.24.38 normally enables platform and desktop integrations that are not
available in the target package graph. The recipe enables Broadway as the
only GDK backend and disables X11, Wayland, Win32, Quartz, introspection,
documentation, demos, examples, cloud providers, Tracker, and colord.

The recipe uses the published GNOME dependency packages and generates
pkg-config forwarding metadata for names that GTK probes directly, including
`gio-unix-2.0` and `pangocairo`. It also aligns the cairo-gobject and
fontconfig variants required by the selected Pango dependency graph.

The graph force-pins the direct dependency `harfbuzz/14.2.0`, overriding
Pango's exact `14.2.0.1` requirement. Its published OHOS/shared binary is
usable with the shared GLib package required by Pango. The newer recipe
coordinate `14.2.0.1` has one binary whose metadata points to a removed static
GLib package ID; Conan therefore attempted a source build and hit the known
HMDFS Python-script execution restriction. Selecting the available compatible
upstream 14.2.0 binary avoids modifying or rebuilding the dependency in this PR.

Temporary files are kept under the Conan build folder. Build tools such as
`xmllint`, `llvm-ar`, `llvm-ranlib`, and the HarmonyOS signing tools are found
from the active environment; no username or SDK-version path is embedded in
the recipe.

Meson records configure-time absolute paths for GLib tools. All GLib generators
are resolved from the pinned Conan GLib package, including the compiled
`glib-compile-resources`, `glib-compile-schemas`, and `gio-querymodules` tools.
The build environment supplies library directories from the same dependency
graph, preventing a device-global executable from loading an incompatible or
missing `libffi.so.8`. Because HMDFS cannot spawn the Python scripts directly,
the Ninja `COMMAND =` entries for `glib-mkenums`, `glib-genmarshal`, and
`gdbus-codegen` are prefixed with Python 3.

GTK's generated resource manifest normally marks theme PNGs with the optional
`to-pixdata` preprocessor and UI XML with the optional `xml-stripblanks`
preprocessor. Those transformations spawn the device-global
`gdk-pixbuf-pixdata` and `xmllint` host tools, whose unsigned copies and ABI
chains are not portable to an isolated HMDFS build. The second source patch
embeds the original PNG/XML resources without these optional transformations;
runtime resource paths and contents remain available without a host-tool ABI
dependency.

GTK helper executables are not part of this library-only Conan package. The
recipe removes the installed `bin/` directory and does not export a runtime
PATH, so task 3718 does not require a software-level `commands.json`.

## Patch

`0001-run-broadway-gen-c-array-with-python.patch` invokes the Broadway
`gen-c-array.py` generated-header helper through Meson's discovered Python 3
interpreter. It applies cleanly to the verified upstream archive.

`0002-embed-resources-without-external-preprocessors.patch` removes only the
optional resource preprocessor attributes from GTK's generated resource list.
It leaves resource paths, compression flags, and source assets unchanged.

## Tests

The contest review enumerates 453 source-level test cases in the upstream GTK+
3.24.38 tag. Upstream conditionally includes `tests/` and `testsuite/` when
`tests=true`; the 1,524 files below those roots also include fixtures,
reference images, UI data, and loop inputs. After the HarmonyOS Broadway-only
configuration, Meson introspection reports 237 concrete registrations. The
remaining 216 source-level cases belong to disabled platform backends or
optional features and are not generated by this package configuration.

The recipe now enables upstream tests, asserts the exact 237 registration
count, and checks that the seven required HarmonyOS-safe tests are still
present. The upstream default setup selects 192 tests; 45 tests tagged
`gtk+:flaky` are excluded by that setup.

All 237 registrations were scheduled on the HarmonyOS aarch64 device after
incrementally signing 219 Meson project/test ELF files and creating build-tree
shared-library aliases. The default set produced `7 OK / 185 TIMEOUT / 0 FAIL`;
the separate flaky set produced `0 OK / 45 TIMEOUT / 0 FAIL`. The 230 display
tests start without loader errors but wait in display/rendering initialization
because Broadway has no connected browser output client on the device. The
full commands, suite counts, pass list, run path, and logs are recorded in
`reports/upstream-test-inventory.md`.

Every OHOS package build requires the seven display-independent upstream tests
to pass under an isolated Broadway server: bitmask, rbtree, typename, C++
keywords, RGBA, gtk-builder-tool simplify, and settings. This adds an upstream
regression gate without claiming the environment-limited 230 cases passed.

The explicit Conan `test_package` links the exported `gtk3::gtk3` target,
checks the runtime version, validates `gtk_check_version()`, resolves the
`GtkWindow` GType without opening a display, prints a deterministic PASS line,
and signs and verifies its consumer ELF on HarmonyOS. CI's R34 destructive
negative test must additionally prove that it depends on package artifacts.

  rebuilt `gtk/gtkresources.h` and `gtk/gtkresources.c` successfully, and

- Official CI #28058 exposed worker-specific leakage to
  `/data/service/hnp/bin/glib-compile-resources`, whose `libffi.so.8` was absent.
  `PkgConfigDeps` had already emitted the GLib tool variables, so an append-only
  correction left those device-global paths unchanged. The recipe now replaces

  GLib tools from the pinned package and its matching dependency library paths.
- Official CI #28187 confirmed the `.pc` replacement works, then rejected the
  unsigned compiled tools with `Operation not permitted` from the Conan cache.
  The recipe now copies the four compiled GLib tools into a GTK-private build
  directory and self-signs each ELF before Meson configure; GLib's Python tools

- Official CI #32509 resolved every declared Conan dependency and installed the
  complete dependency graph, then failed before Meson configure because the SDK
  `lld` process could not load its matching `libxml2.so.16`. The recipe now
  prepends the dynamically discovered SDK `ohos/native/llvm/lib` directory to
  the build-only `LD_LIBRARY_PATH`. This supplies the linker's own runtime
  library without adding libxml2 to GTK's public package dependency graph or
  embedding a worker-specific SDK version.
- Official CI #32853 then built, installed, signed, and packaged GTK successfully,
  but its separate `test_package` process did not inherit the main recipe's
  temporary linker runtime environment. Its CMake compiler probe therefore hit
  the same `lld`/`libxml2.so.16` loader error. The test recipe now applies the
  dynamically discovered SDK `llvm/lib` path around CMake configure and build as
  well; the path remains build-only and does not change GTK's consumer graph.
