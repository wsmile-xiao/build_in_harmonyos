# wily 0.13.42

## Software

wily is an Acme-like X11/Xt text editor and window manager.  It is an old
Autoconf 2.4, X11, Xt, and C project.  The release archive does not contain an
automated test suite.

- Debian source: `https://deb.debian.org/debian/pool/main/w/wily/wily_0.13.42.orig.tar.gz`
- SHA256: `5f5498b11c28c8d1fde7750f133a4ab2faca4b23f2ca0a563103ea34e667c4cb`
- Source audit: no `TESTS` or `check` target is generated by the top-level or
  subdirectory Makefiles.  `libXg/test.c` is an interactive graphics demo and
  `tools/python/testwily.py` is an old Python integration demo; neither is a
  reproducible automated suite.

## Dependency Strategy

The source directly uses Xlib and Xt only.  The recipe therefore declares:

- `libxt/1.3.1`
- `libx11/1.8.13` (explicitly pinned so the graph uses one compatible X11 ABI)

`libXmu` and `libXi` are available in the archive but are not included because
nothing in this source tree includes or calls either library.  The transitive
`libSM`, `libICE`, `xorgproto`, `libxcb`, `libxau`, `xtrans`, and `xcb-proto`
packages are resolved through `libxt` and `libx11`.

Because the 1990s configure script expects headers and libraries in one X11
prefix, `generate()` creates `build/x11stage`.  It copies all dependency header
trees into `x11stage/include` and materializes the shared/static libraries in
`x11stage/lib`, resolving symlinks to real files.  `--x-includes`,
`--x-libraries`, `X_CFLAGS`, and `X_LIBS` all point at that private stage.

## Build Strategy

- OHOS clang through the Conan 2 Autotools toolchain.
- GNU triplet is supplied explicitly for OHOS because this
  `config.guess`/configure generation predates HarmonyOS.
- `-std=gnu89 -fcommon` is used for the pre-C99 source and its tentative global
  definitions.
- The Autoconf 2.4 configure predates the later `getcwd` and `umask 077`
  probes handled in newer X.Org recipes.  Build still runs from a private
  staging directory with `PWD` set for HMDFS safety; the configure patcher
  is intentionally idempotent for those newer probe forms.
- No `make check` is called because upstream has no check target.  The manifest
  records zero upstream tests.
- Autoconf 2.4 ignores `DESTDIR` and writes `/bin/wily`, which is read-only
  on the device.  The recipe therefore copies the successfully built binary
  directly into the Conan package's `bin/` directory.
- On OHOS, `bin/wily` is signed with `binary-sign-tool` and executable mode is
  restored with best-effort `chmod`.

## Consumer Validation

wily calls `xtbinit()` before parsing its own `getopt` arguments.  There is no
version/help path that exits before Xt initialization.  A GUI smoke test is
not attempted, and a plain `wily --help` would only test X connection failure.

`test_package/test_wily.sh` performs the strongest non-GUI startup/load check
that is actually meaningful for this program:

1. Require the packaged `bin/wily` to exist and be executable.
2. Execute it as a child process with `DISPLAY=:65535`, a deliberately absent
   display, and a temporary `HOME`.
3. Require a nonzero exit and an Xt/Xlib diagnostic containing
   `Can't open display` or `unable to open display`.

This proves that the dynamic loader resolved the executable and its Conan X11
shared libraries, control reached `main()` and Xt startup, and the expected X
connection path was exercised.  It does not prove window creation, rendering,
fonts, clipboard behavior, editing, or any other GUI workflow because no X
server is available.  Those paths remain unverified by this recipe.

OpenDesk job `20260927-044619-dc4b6d-batch6-wily-ci4` ran the complete
`conan create` pipeline on OHOS arm64.  The job built and signed the package,
then executed all three consumer assertions successfully (`3/3`).

## Limitations and Risks

- The build and consumer checks were executed on OHOS arm64 through OpenDesk.
- The runtime check intentionally expects an X connection failure; it is not a
  GUI functional test.
- The staged library list follows package graph resolution.  If a future
  `libxt` graph removes a shared-library linker name from an installed
  package, the recipe will fail with an explicit missing-library diagnostic.
- Upstream has no automated tests, so regression coverage is limited to the
  consumer startup/load assertions above.
