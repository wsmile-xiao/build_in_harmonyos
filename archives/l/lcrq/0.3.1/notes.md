## 编译步骤

```bash
source .build-context-lcrq-0.3.1
cd $BUILD_SRC_DIR
# R3 探索阶段：先按 E007 修补 config.guess/config.sub（后续由 refresh-patch 固化为补丁）
perl $SKILL_ROOT/scripts/patch-autotools-ohos.pl config.guess config.sub
# 补充：config.sub kernel-os 校验表需加 linux-ohos*（见问题 #2）
PATH="/system/bin:$PATH" CC=clang ./configure --prefix=$DEFAULT_PREFIX   # exit 0
PATH="/system/bin:$PATH" make -j4                                        # exit 0
PATH="/system/bin:$PATH" make install DESTDIR=$TEST_PREFIX               # exit 0
PATH="/system/bin:$PATH" LD_LIBRARY_PATH=$BUILD_SRC_DIR/src make test    # exit 0
```

注：PATH 前置 /system/bin 是因为会话 PATH 首位是 WorkBuddy electron shim 的 rm
（缺 /bin/bash 解释器），configure 内部调用 rm 会报 "bad interpreter"。

## 对话记录

### 对话 #1 [2026-09-19]

- 问题: `init-build lcrq 0.3.1` 复制源码失败（copytree EPERM→ENOENT）
- 操作: 定位到上游 tarball 中 `test/all/*.test` 全是悬空符号链接（指向构建期才生成的 `../00NN-00MM.test`）；改用 Python tarfile 手动解压生成 `.work`（保留符号链接），再复用该目录重跑 init-build
- 结果: 源码树就绪，符号链接形态与上游一致

### 对话 #2 [2026-09-19]

- 问题: `config.guess` 报 "unable to guess system type"；打完 E007 补丁后 `config.sub` 仍报 "Kernel 'linux' not known to work with OS 'ohos'"
- 操作: 运行 `patch-autotools-ohos.pl config.guess config.sub`，并在 `config.sub` 的 kernel-os 校验表补 `linux-ohos*`
- 结果: 平台识别为 `aarch64-unknown-linux-ohos`，configure 通过

### 对话 #3 [2026-09-19]

- 问题: 会话 PATH 首位是 electron shim 的 rm（缺 /bin/bash 解释器），configure 内部调用 rm 报 bad interpreter
- 操作: 构建/安装/测试命令统一前置 `PATH="/system/bin:$PATH"`
- 结果: configure / make / make install / make test 全部 exit 0

### 对话 #4 [2026-09-19]

- 问题: 远程 CI 出现 `configure: fork: Out of memory` → `configure: error: cannot find sources (src/) in  or ..`
- 操作: 判定为 worker 内存压力下 configure 早期 fork 失败、srcdir 自动探测算空；本包为 in-source 构建，在 `generate()` 显式传 `--srcdir=.`
- 结果: 绕开依赖 fork 的 srcdir 探测，该报错消除

### 对话 #5 [2026-09-19]

- 问题: 远程 CI 运行 #51743 报 `./config.status` 第 603 行 `subs1.awk: Permission denied` → `could not setup config files machinery`
- 操作: 比对知识条目 E129 / E114（错误特征逐字命中）；按仓库 572 个 conanfile.py 的既有惯例（如 4ti2 1.6.10）在 `build()` 内联把 `umask 077` 换成 `umask 022`
- 结果: 修复生效，conan-verify G0–G4 + L2/L4/L5 全 PASS
- 更正: 初版填的理由「`configure` 含 `Generated by GNU` 会被 refresh-patch 过滤，故只能内联」**不准确**——仓库内 990 个 configure 类补丁证明先 `track-edit add` 即可正常产出。真实机制是 `refresh_patch.auto_mode()` 双路径（有追踪器→绕过生成文件过滤；无追踪器→被 `_is_likely_generated()` 静默丢弃）

### 对话 #6 [2026-09-19]

- 问题: 需确认修复真正进入被执行的构建树，且未造成上游测试回归
- 操作: 检查 conan 缓存内被执行的 `configure`（5824/5829 行）与其生成的 `config.status`（574/579 行）均为 `umask 022`；在该构建树上重跑 `make test`
- 结果: 19 run / 18 OK / 1 SKIP / 0 FAIL，TEST_EXIT=0，与修复前完全一致

## 遇到的问题与解决方案

| # | 问题 | 根因 | 解决方案 |
|---|------|------|----------|
| 1 | init-build 复制源码失败（copytree EPERM→ENOENT） | 上游 tarball 中 test/all/*.test 全部是悬空符号链接（指向构建期才生成的 ../00NN-00MM.test）；copytree 默认解引用，HMDFS 拒绝硬链接，copy2 跟随断链失败 | 脚本只读不改：手动用 Python tarfile 解压生成 .work（保留符号链接），重跑 init-build 复用 |
| 2 | config.guess 报 "unable to guess system type"（E007） | config.guess 2022-05-25 版无 HarmonyOS 分支 | patch-autotools-ohos.pl 一键补丁（知识库 E007 rec） |
| 3 | config.sub 报 "Kernel 'linux' not known to work with OS 'ohos'"（E007 变体） | E007 补丁脚本只改了 OS 列表与 ohos-linux 别名，未加 kernel-os 兼容表的 linux-ohos* 组合 | 手工在 config.sub 校验表 `linux-gnu* \| ... \| linux-uclibc* )` 分支追加 `\| linux-ohos*`，已并入 0002 补丁 |
| 4 | configure 报 rm "bad interpreter: /bin/bash" | 会话 PATH 首位 electron shim 的 rm 损坏 | 调用时 PATH="/system/bin:$PATH" |
| 5 | **CI：`config.status` 报错 `could not setup config files machinery`**（首个错误 `./config.status` 第 603 行：`./confXXXXXX/subs1.awk: Permission denied`） | **E129/E114**：`configure` 内嵌的 config.status 用 `umask 077 && mktemp -d "./confXXXXXX"` 建临时目录；HMDFS 对新目录强制 setgid，`umask 077` 得到 `drwx--S---`（组无搜索位），该目录在 CI worker 的 HMDFS 挂载上不可写 → 写 `subs1.awk` 报 Permission denied。**本机无法复现**（本机挂载可写，实测 `drwx--S---` 属主可写），故按知识条目 + 仓库先例确定性修复 | `configure` 内两处 `umask 077` → `umask 022`（E129 rec；仓库 494 处同写法先例，如 a52dec `0002-configure-umask-022.patch`）。因 `configure` 是 tarball 内**生成文件**（含 `Generated by GNU` 标记），refresh-patch 会将其过滤，故该修复**在 build() 内联**完成（同 4ti2 1.6.10 配方思路） |
| 6 | CI 出现过 `configure: fork: Out of memory` → `configure: error: cannot find sources (src/) in  or ..` | CI worker 内存压力导致 configure 早期 `fork` 失败（同一日志里 CI 自身的 knowledge_check.sh/junk_check.sh 也在报 `xargs`/`tr`/`cut`/`grep: Out of memory`），srcdir 自动探测（需 fork `expr`/`sed`）算空 → 报错 | 本包为 in-source 构建，srcdir 恒为 `.`，故显式传 `--srcdir=.`，跳过该 fork 依赖的探测（仓库 25 处先例，如 fontutils 0.7）。环境类抖动本身无法消除，需重试 |

### 配方内联修改（不走 patches/ 管线，原因见问题 #5）

| 位置 | 内容 | 知识条目 |
|------|------|----------|
| `build()` → `_fix_hmdfs_tmpdir_umask()` | OHOS 分支下将 `configure` 内 `umask 077` → `umask 022`（共 2 处：mktemp 分支 + mkdir 回退分支）；未命中时告警 | E129 / E114 |
