- Issue: pending assignment. No libgav1 issue reference was found in the workspace or adaptation notes.
- Branch: `feat/libgav1-0.20.0`.
- Build system: CMake. The production library has no external runtime or build dependencies.
- W0: passed. The only external component in the upstream test suite is GoogleTest; the recipe disables upstream tests and examples, so it is not a package dependency.
- Source: upstream publishes no byte-stable archive (Gitiles `.tar.gz` output is not reproducible) and `chromium.googlesource.com` is unreachable from the build network, so an official Git checkout cannot produce this package in CI. The recipe downloads Debian's libgav1 0.20.0 orig tarball, whose SHA-256 `953f98a5147f556f358ef986601fda7804cfaaa634302aa9b842fea889aa7e6c` is published in the PGP-signed `libgav1_0.20.0-2.dsc`, with `mirrors.tuna.tsinghua.edu.cn` and `mirrors.aliyun.com` as sha256-verified fallbacks. Upstream tag `v0.20.0` and commit `c05bf9be660cf170d7c26bd06bb42b3322180e58` stay recorded in `conandata.yml` as provenance: the Debian tree is byte-identical to that revision (387 files, 0 differences). Evidence and reproduction steps: `reports/source-verification.md`.
- Why the source changed: PR CI runs #50298, #52414, #53532 and #59757 all failed inside `source()` with `Failed to connect to chromium.googlesource.com port 443`; a direct probe from the build network times out on that host while the Debian mirrors answer HTTP 200. Upstream offers no pinnable archive, so `sha256: null` could not be resolved while keeping the official Git host as the fetched source.
- Build configuration: `LIBGAV1_THREADPOOL_USE_STD_MUTEX=1` keeps Abseil out of the production dependency graph when tests and examples are disabled. libgav1 0.20.0 validates this CMake cache value as an integer (`0` or `1`), so a Conan boolean (`ON`) is rejected.
- Local validation: `conan source` downloads the pinned archive and verifies its `sha256`; the mirror fallback and the integrity guard were exercised locally too (a deliberately wrong `sha256` makes the recipe refuse every source instead of silently accepting it). A Windows `conan create` is not a reference validation path for this package — the OHOS device and the PR CI are.
- HarmonyOS validation: passed on aarch64 OHOS 6.0 with Clang 15.0.4. The isolated single-package runner completed `conan create`, built and ran `test_package`, and reported `L0=pass`, `L1=pass`, `L2=skip` (no `bin/` for this static library), `L4=pass`, and `L5=pass`. The R34 negative test also confirmed that the consumer test genuinely needs the package headers and library.
- HarmonyOS re-validation after the source switch: run `currentUser-0.20.0-libgav1-0.20.0-097f5d5f38-conan-20260926-181022-54835` on the same device fetched the Debian archive (`Sources correctly downloaded from https://deb.debian.org/debian/pool/main/libg/libgav1/libgav1_0.20.0.orig.tar.xz`), built `lib/libgav1.a` and the 7 `include/gav1/` headers, compiled and ran `test_package`, and reported the same `L0/L1/L4/L5=pass`, `L2=skip`, R34 pass, exit-code `0`. The runner had no `curl` for the CI subprocess, so its pre-download pre-cache step was unavailable — i.e. the run exercised exactly the path the PR CI worker uses: conan downloads directly from the reachable mirror and verifies `sha256` itself.
- HarmonyOS CMake processor / NEON: on OHOS, CMake resolved `CMAKE_SYSTEM_PROCESSOR` to the literal string `unknown`, so upstream's `cmake/libgav1_cpu_detection.cmake` — which enables NEON only when the value matches `^arm|^aarch64` — turned the whole ARM DSP path off (`LIBGAV1_ENABLE_NEON=0`) and also skipped the `tests/libgav1_tests.cmake` target `common_neon_test`. `generate()` now fills the Conan toolchain's `generic_system` block for OHOS (`cmake_system_name=OHOS`, `cmake_system_processor=aarch64`, guarded by `settings.os == "OHOS"`), the same workaround `libmatio`/`libaec`/`libnghttp2` use in this repository. Device evidence after the fix: `CMakeSystem.cmake` reports `CMAKE_SYSTEM_PROCESSOR "aarch64"`, `LIBGAV1_ENABLE_NEON=1` in `flags.make`, 25 NEON object files compiled (previously 0).
- Upstream tests: passed on the same OHOS device. `ctest -N` registers **58** upstream tests and all 58 passed (`58/58`, `100.00%`, `0` failed, `0` skipped; 43.11 seconds), including `common_neon_test` (test #4) which the pre-fix configuration could not register. `tests/libgav1_tests.cmake` declares 59 targets, one of which (`common_dsp_test`) is x86-only, so 58 is the full aarch64 inventory. The test tree is a checkout of the pinned upstream commit `c05bf9be…`; it used upstream-pinned GoogleTest `release-1.12.1` and Abseil `20220623.0`; `LIBGAV1_ENABLE_EXAMPLES=ON` is required for three upstream tests that consume file reader/writer object targets, and `TMPDIR` must be writable because the device mounts `/tmp` read-only. No upstream source or test assertion was modified. See `reports/upstream-tests.md`.
- Consumer test: initializes `libgav1::Decoder`, proving the public C++ header, static link, and basic decoder API are usable.
- Review follow-up: the installed v0.20.0 public header declares `StatusCode Init(const DecoderSettings* settings)`; the original `decoder.Init(&settings)` is the correct call. A review suggestion to pass a reference was checked against the true-device header and rejected because it produces a compile error.
