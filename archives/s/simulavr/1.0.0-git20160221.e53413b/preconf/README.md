# preconf/ — pre-generated autotools files for simulavr 1.0.0-git20160221.e53413b

The pristine orig source tree ships only the autotools *inputs*
(`configure.ac`, `Makefile.am`, `m4/*.m4`) and **no** generated build system:
there is no `configure`, `aclocal.m4`, `config.guess`, `config.sub`,
`ltmain.sh`, `install-sh`, `missing`, `depcomp`, `ar-lib`, `compile`,
`src/config.h.in` or any `Makefile.in`. Upstream expects the developer to run
`./bootstrap` (aclocal + autoheader + libtoolize + automake + autoconf).

This directory carries the output of exactly that bootstrap step so the Conan
recipe does not have to run the autotools toolchain on the build host.

## Provenance / how these files were produced

Generated by running `autoreconf -fi` on the *unmodified* upstream tree inside
a clean Debian container:

```
docker run --rm -v <src>:/work debian:stable bash -c \
  'apt-get install -y autoconf automake libtool && cd /work && autoreconf -fi'
# autoconf 2.72, automake 1.17, libtool 2.5.4
```

The 47 generated files (relative to the source root) are copied here verbatim.
`doc/texinfo.tex` (an updated copy of an upstream file) and the transient
`autom4te.cache/` directory are intentionally not included.

## Why this is needed on HarmonyOS PC

The `ohos-aarch64` shadow-CI job runs as `构建用户`, whose writable paths
all live on HMDFS. On this device `autoreconf` cannot run there:

- the only `autoconf`/`autoreconf`/`m4`/`perl` are in `/data/service/hnp/bin`
  (executable, 755) but the device profile does not add that directory to PATH;
- `automake`/`aclocal`/`libtoolize` are **absent from the device entirely**
  (`/data/service/hnp` ships only `autoconf.org`, `m4.org`, `perl.org`), and
  the copies in `~/usr/local/bin` and in the Conan cache are mode 750 owned by
  another uid, so they cannot be executed;
- HMDFS is mounted `nosuid` with a MAC policy that denies direct `execve` of
  the job user's own files, so a self-built `automake` cannot be executed either.

This is the same wall the `libhugetlbfs/2.24` shadow run hit
(`aclocal: Permission denied` → `autoreconf: error: aclocal failed`).
Pre-generating the build system avoids needing the autotools toolchain at all.

## Local modifications carried in this preconf

1. `libsim` is built as an automake **convenience library** instead of an
   installed libtool library: `lib_LTLIBRARIES` is emptied, `noinst_LTLIBRARIES = libsim.la`,
   `libsim_la_LDFLAGS = $(am__append_4)` (the upstream `-shared -avoid-version
   -rpath $(libdir)` is dropped), and `simulavr_LDADD = libsim.la …`.

   Why: the AVR device models self-register at static-init time via the
   `AVR_REGISTER` macro (one registrar object per device `.cpp`), and `main`
   never references them. A normal archive link therefore drops every
   registrar and `simulavr -d atmega128` fails with "Invalid device
   specification". Upstream never hits this because it ships `libsim` as a
   *shared* library (all objects live in the `.so`). Wrapping the libtool
   archive in `-Wl,--whole-archive` does **not** work here: libtool reorders
   the flags around the `.la` input. A convenience library is the automake
   idiom for "link all these objects into the program", and libtool always
   includes 100% of a convenience library's objects, so the registrars are
   guaranteed to be present. libsim is compiled non-PIC (fine for a static
   link into the executable).

   Consequence: the package ships only the CLI (`bin/simulavr`); `libsim.a`
   is not installed, and the recipe's `package_type` is `application`.

2. `src/Makefile.in`'s `AM_CXXFLAGS = -Ielfio … -Icmd -Iui -Ihwtimer` is made
   `$(srcdir)`-relative (`-I$(srcdir)/elfio …`), because Conan always builds
   out-of-tree and the relative `-I` otherwise points at the build directory.

3. The top-level `Makefile.in` rule `check-versions.out` runs
   `$(SHELL) ./check-versions.sh` instead of `./check-versions.sh`, because
   HMDFS denies `execve` of the generated script (see below).

4. `configure`'s two `umask 077` occurrences become `umask 027` (below).

`config.guess` / `config.sub` additionally carry the standard HarmonyOS
detection (`__OHOS__` / `HarmonyOS` / `*-linux-ohos`) so configure identifies
the platform without needing an explicit triplet.

## Detail: `umask 077` → `umask 027`

`configure` creates its config.status scratch directory with
`(umask 077 && mktemp -d "./confXXXXXX")`.  On HMDFS the resulting directory
comes out as `drwx--S---` (setgid but **no group write**), and config.status
then cannot write `subs1.awk` into it:

```
./config.status[1200]: can't create ./confCEDglK/subs1.awk: Permission denied
config.status: error: could not setup config files machinery
```

Measured on this device for the four candidate umasks (same directory type):

| umask | resulting dir mode | write into it |
|---|---|---|
| 077 | `drwx--S---` | **fail** |
| 027 | `drwxr-s---` | ok |
| 022 | `drwxr-s--x` | ok |
| 000 | `drwxrws--x` | ok |

The two `umask 077` occurrences are therefore changed to `umask 027` (the same
change the working `duff/0.5.2` recipe makes).  Because this block is the
template from which `config.status` is emitted, the fix reaches config.status
as well.

## Detail: run `check-versions.sh` through `$(SHELL)`

The top-level `Makefile.in` has

```
check-versions.out: check-versions.sh
	./check-versions.sh > check-versions.out
```

and `all-local: check-versions.out`, so every `make` tries to execute
`./check-versions.sh`.  That script is generated at configure time and, like
every other job-user file on HMDFS, cannot be `exec`'d directly:

```
/system/bin/sh: ./check-versions.sh: Permission denied
make[1]: *** [Makefile:965: check-versions.out] Error 126
```

The recipe line is changed to `$(SHELL) ./check-versions.sh` (Configure
substitutes `SHELL` with the shell it was invoked through, i.e.
`/system/bin/sh`), which reads the script instead of exec'ing it.  This is a
plain text edit to a committed generated file, consistent with the technique
the `duff/0.5.2` recipe reaches for.
