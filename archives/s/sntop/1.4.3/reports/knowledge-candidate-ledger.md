## 一、候选 1：M12 —— 自研 configure 只认命令行 `var=value`、忽略环境变量

**预匹配来源**：SCT 入表备注 `B配送=M12`；池件
`经验文档/B草稿库/DRAFT-PKG-VER-custom-configure-only-cli-args-no-env.{kv,md}`。

### 1.1 适用面前置条件（读 configure 头部）

草稿 `.kv:30` 给的判据原文：
"autoconf 产物含 `# Generated by GNU Autoconf`，手写产物没有，且内部用
`case "$optarg" in CXX=*) …` 这类分支自己解析参数"。

sntop 的 `configure` 第 1-6 行实拍：

```
#! /bin/sh

# Guess values for system-dependent variables and create Makefiles.
# Generated automatically using autoconf version 2.13
# Copyright (C) 1992, 93, 94, 95, 96 Free Software Foundation, Inc.
```

⇒ **是 autoconf 生成物**（2.13），不是手写自解析脚本。
`--prefix` 等选项由 autoconf 的 `for ac_option … case` 标准块处理，
不存在 `case "$optarg" in CXX=*)` 形态的自解析。

### 1.2 草稿自写的"不适用"边界

`.kv:27-28`：
"**不适用**于 autoconf 生成的 configure：那类脚本按标准读取同名环境变量"。

### 1.3 两臂 A/B 探针（一手，鸿蒙 B 机）

| 臂 | 命令 | 结果 |
|---|---|---|
| **环境变量臂** | `env CC=<abs clang> CFLAGS=-DM12_ENV_MARKER ./configure --prefix=…` | `rc=0`；生成的 `Makefile` 第 38 行 `CC = /data/service/hnp/bin/clang`（**被采纳**）；`config.status` 内出现替换规则 `s%@CFLAGS@%-DM12_ENV_MARKER%g`；`config.log` 内标记命中 9 次 |
| **命令行臂** | `./configure --prefix=… CC=<abs clang> CFLAGS=-DM12_CMD_MARKER` | `rc=1`；**没有产出 Makefile**；报错原文见 1.4 |

> 载体口径：上表环境变量臂那三条"缺一不算证到"的生效读数，实测载体是设备侧一次性
> 取证目录 `~/tmp/uc2/z45-sntop/probe/arm-env/`（`Makefile:38` =
> `CC = /data/service/hnp/bin/clang`、`config.status:38` =
> `s%@CFLAGS@%-DM12_ENV_MARKER%g`、`config.log` 标记 `grep -c` = **9**；
> `p1.sh:36-39` 把这三条单独打到控制台）。该目录是**未随 PR 提交的中间产物**；
> 仓内跟踪件 `reports/p1-arm-env.log` 只含该臂 configure 的标准输出（`p1.sh:34`
> 重定向而来），不含这三条读数，也不含 `echo $?` 的退出码行。


### 1.4 命令行臂报错原文（`reports/p1-arm-cmdline.log`）

```
configure: warning: CC=/data/service/hnp/bin/clang: invalid host type
configure: warning: CFLAGS=-DM12_CMD_MARKER: invalid host type
configure: error: can only configure for one host and one target at a time
```

### 1.5 结论

M12 的症状是"**环境变量被忽略、命令行 `var=value` 被采纳**"；
sntop 实测**恰好相反**：环境变量臂生效、命令行臂 error 退出。
叠加 1.1 的头部判据与 1.2 的自述边界 ⇒ **M12 在本包不成立，不取用**。
若强行套配即草稿 `.kv:8` 警告的"空走"。

**复现判定：NO（明确否证）。**

## 二、候选 2：M15 —— hishell 吞掉 SIGALRM（池内 `sigalrm` 面）

**预匹配来源**：SCT 信号 `机制命中 sigalrm:sntop.spec`；池件
`经验文档/B草稿库/DRAFT-PKG-VER-hishell-swallows-sigalrm.{kv,md}`。

### 2.1 适用面（草稿 `.kv:26-29`）

"任何以'子 shell 被 SIGALRM 杀死'为计时语义的上游软件 —— …
`alarm()`/`setitimer(ITIMER_REAL)` + exec 后代进程走 `/bin/sh` 的包 …"

### 2.2 本包实测（三面同查）

1. **源码面**：`grep -niE "SIGALRM|alarm\(|setitimer|ualarm" sntop.c sntop.h` →
   实跑 **4 处命中**（本轮在 `~/tmp/builds/sntop-1.4.3.orig` 原样复跑，命中的正是
   下面列的那四行：`sntop.c:222`、`sntop.c:230`、`sntop.c:405`、`sntop.h:56`）。
   **这 4 处全部是 sntop 自己的功能名 `exec_alarm()`**（模式里的 `alarm\(` 作为子串
   把它带了出来）——那是"主机掉线时 `fork + execve(用户脚本)`"的回调，与计时信号无关。
   同口径补跑两条限定式：`grep -nE "SIGALRM|setitimer|ualarm"` → **0 命中**；
   把 `alarm(` 限定成"前面不是标识符字符"的独立调用面
   （`grep -nE "(^|[^_[:alnum:]])alarm\("`）→ **0 命中**。
   ⇒ 本行上一版写作"零命中"是**表述失真**（把"没有 `alarm(2)` 调用面"写成了
   "这条 grep 零命中"），现按实测命中数改述，四条命中列表原样保留。
   **本节结论不变，但它不靠这条 grep 的空结果支撑**，靠的是第 3 点二进制符号面
   （`llvm-nm -u` 的未定义符号只有 `clock_gettime` / `ctime` / `select` / `time`，
   没有 `alarm` / `ualarm` / `setitimer`）与第 2 点计时机制面（`select(2)` + `timeval`）。
2. **计时机制面**：轮询节奏由 `select(2)` + `timeval` 实现，不是 alarm 计时：
   `sntop.c:250` 注释 "we use select() to sleep for REFRESH seconds or until a
   key is pressed"、`:253 timeout.tv_sec = refresh;`、`:255 if (select(1,
   &readfds, NULL, NULL, &timeout) > 0)`。守护分支才用 `sleep(refresh)`。
3. **二进制符号面**：`llvm-nm -u <产物>` 的信号/计时相关未定义符号只有
   `clock_gettime` / `ctime` / `select` / `time`，**没有 `alarm`、`ualarm`、
   `setitimer`**。
4. **prescan 命中来源核对**：`sigalrm:sntop.spec` 这条命中的实际文本是
   `sntop.spec:25` 的 `%description` 散文
   "…execution of external file on alarm (configurable for either host DOWN
   or any change in host status)…" —— 描述的是 2.2 第 1 点那个用户脚本回调。
   ⇒ **该 prescan 命中是关键词假阳性**（散文里的 "alarm" ≠ `alarm(2)`）。

### 2.3 结论

本包不存在任何"子 shell 被 SIGALRM 杀死"的计时语义，也没有 `alarm()` 调用面
可被 hishell 吞。**M15 在本包不成立，不取用。**

**复现判定：NO（明确否证）。**

## 四、本包**新撞上**的两条机制（是否升 create 交主理，本棒不自取知识位）

### M-A：autoconf 2.13 世代的 configure 拒绝命令行 `VAR=value`

- 一手签名：见 1.4 三行原文（`rc=1`，无 Makefile 产出）。
- 对配方的实际后果：本仓同族先例 `archives/a/alpine/2.26/conanfile.py` 的
  惯用写法是往 `tc.configure_args` 里塞 `"LDFLAGS=…"`/`"LIBS=-ldl"`。
  **该写法照搬到 2.13 世代的 configure 上必红**，必须改走环境变量。
  本棒按 1.3 的探针结论采用环境变量通道（`generate()` 里 `Environment().define`）。
- 最接近的既有表述（**都只是附带告诫，没有签名、没有解法，不构成 hit 的"解法已被覆盖"**）：
  - `knowledge/drafts/libgetline-1.0-ohos-autotools-configure-args.kv:35`
    与同名 `.md:46`："不要把 `CPPFLAGS=…` 放进 configure_args
    （VAR=value 形式**可能被工具链吞掉**）" —— 措辞是"可能被吞掉"，
    与"被判成 host 三元组并 error 退出"不是同一定性；
  - `knowledge/drafts/cvsgraph-1.7.0-autotools-no-canonical-host.kv:49`：
    "cadaver 的 VAR=value 路线**只适用 2.6x+ 生成物**" —— 已触到版本号边界，
    但没给错误签名、没给适用判据、也没给替代写法。
- 若升 create 的建议标题机制句：
  "autoconf 2.13 生成的 configure 把命令行 `VAR=value` 判为 host 三元组
  （`invalid host type` → `can only configure for one host and one target at a time`
  并 error 退出），故 ≥2.5x 上通行的 configure_args 传参写法必须改走环境变量。"

### M-B：上游 `Makefile.in` 不引用 `@CFLAGS@`/`@LDFLAGS@` ⇒ configure 探到的旗标进不了编译

- 一手签名：`sntop.c:38:10: fatal error: 'ncurses.h' file not found`（尽管
  `CPPFLAGS=-I<inc>` 已被 configure 读到并写进 `config.status` 的替换表）。
- 解法（本包采用，零补丁）：借上游编译规则里**已存在**的 `-I$(INCLUDE)` 钩子，
  用 `make INCLUDE=<dep>/include` 注入头路径；`-L` 随 `LIBS` 进**存在**的
  `@LIBS@` 占位符。
- 与既有知识的关系：这一步**依赖**于
  `knowledge/drafts/E568-draft-5818.md:55`（同名 `.kv:20-21`）记的
  GNU make 变量优先级 "命令行的 `VAR=value` 不是追加，是接管"。
  那条讲的是"接管会**丢**上游 flags"的**风险面**，本包用的是同一定律的
  **正面用法**（只接管 `INCLUDE = .` 这个单值变量，不动 CFLAGS，因此不丢上游旗标）。
  ⇒ 按 hit 四条件第 2 条（"症状相同但你用的是既有条目没写的另一条解法 ⇒ 不算 hit，
  按 create 报"），M-B 与 E568 是**同一定律的两个方向**，
  既可判"新增价值升 create"，也可判"E568 已覆盖根因、本包只是应用"。**这一格由主理定。**
- 依赖库侧事实与同族差异见 notes.md"方案取舍"节：alpine 用补丁改探测库名，
  sntop 因 `HAVE_LIBNCURSES` 不被源码读取而**不需要**该补丁。
