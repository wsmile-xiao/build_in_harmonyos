# HarmonyOS OHAudio device test

`ohos_device_test.cpp` runs the 27 upstream behavior items on the physical device and two HarmonyOS-specific checks. It exercises the C and C++ API-name functions, enumerates real input/output routes and capabilities, plays a temporary synthetic raw PCM fixture, runs sawtooth output, records microphone callback progress, and covers duplex start/stop/restart, callback stop/abort, repeated reopen, and repeated instance creation. Each upstream item reports its own `U01`–`U27` result; the inventory counts those behaviors rather than executable targets.

Microphone capture is requested at runtime. The test only aggregates callback/frame counts and sample magnitude in memory; it never retains captured samples or writes microphone audio to disk. U17 uses a generated output-only PCM fixture in the app's cache directory and removes it after playback.

H01 creates an OHAudio renderer directly, waits up to four seconds for at least ten write callbacks, and measures callback count, bytes, and nonzero generated 440 Hz PCM. A failure reports the OHAudio result from each setup/start/stop/release stage. H02 opens the packaged RtAudio `OHOS_OHAUDIO` backend and measures live renderer callback count, delivered frames, and nonzero output magnitude. These device checks exercise real HarmonyOS APIs and callbacks rather than assertion-only behavior.

HarmonyOS chooses the actual OHAudio callback quantum when the renderer is created. The backend therefore queries `OH_AudioRenderer_GetFrameSizeInCallback` (and the capturer equivalent), updates RtAudio's returned `bufferFrames`, and sizes its buffers from that value. On the connected device, the request was 480 frames and OHAudio selected 960 frames; the test observed 104 RtAudio callbacks, 99,840 frames, and nonzero output samples. This exercises runtime OHAudio behavior and is not a compile-only or assertion-only check.

The test runs inside the small Stage-model HAP under `ohos_device_app/`. This device denies direct execution of transferred ELF binaries, so the Conan OHOS test installs, launches, reads the uniquely identified per-item `hilog` results from, and then uninstalls this temporary HAP. The app invokes the suite through a NAPI module linked against the Conan package. The runner requires all 29 result markers and rejects older HAPs that report only an output pass.

The HAP project targets HarmonyOS SDK `26.0.0` and must be signed with a DevEco debug certificate and debug profile registered for the connected device. Either set `user.rtaudio:harmonyos_signed_hap` in the local Conan profile to a signed HAP built from the prepared app project, or set `user.rtaudio:harmonyos_signing_config` to a JSON file containing one DevEco `signingConfigs` entry (or an `app.signingConfigs` array from a DevEco `build-profile.json5`) and `user.rtaudio:harmonyos_sdk` to the installed HarmonyOS SDK root so Conan can build it. Relative paths for `certpath`, `profile`, and `storeFile` resolve from that file's directory. A signing config contains credentials; keep it local and do not commit or share its contents, private keys, or passwords. The current local command-line Hvigor build reports SDK error `00303312`; the prepared DevEco project can be built and signed in the IDE.

Conan's OHOS test profile must provide `user.rtaudio:hdc_serial`, `user.rtaudio:hdc_executable`, `user.rtaudio:hvigor_js`, `user.rtaudio:node_executable`, and `user.rtaudio:ohos_base_sdk`. The HAP test host is built against the installed OpenHarmony base SDK because the local DevEco installation has no HarmonyOS-specific SDK components. HDC installs, starts, observes, and removes the temporary app; SSH is not used for package installation or app launch.

CI workers without any `user.rtaudio` device, SDK, or signing settings log an explicit skip for HAP runtime execution after the Conan consumer target has compiled and linked. A partially configured profile remains an error. The CI skip is not a device-test pass; the full HAP suite must be run with the local profile and a connected physical device.
