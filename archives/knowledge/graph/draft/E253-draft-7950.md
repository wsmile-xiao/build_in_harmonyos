# E253 - Isolate Non-Relocatable Libtool Dependency Metadata

## Usage

Use this pattern when an Autotools project links a Conan dependency through
Libtool and either reports that a dependency `.la` file was moved or produces
a static archive that contains another complete `.a` file as a member.

## Scope

This applies when all of the following are true:

- A Conan dependency provides a static archive and a sibling `.la` file.
- The `.la` metadata contains an install-time `libdir` or `dependency_libs`
  value that is invalid after package relocation.
- The consumer project builds a Libtool static library before linking its CLI
  or package consumer.

It is not a replacement for normal shared-library SONAME and runtime-loader
validation.

## Symptom

The first failure occurs even though the static archive exists:

```text
libtool: warning: library '.../libpcre2-8.la' was moved
libtool: error: '//lib/libpcre2-8.la' is not a valid libtool archive
```

Replacing `-L... -lpcre2-8` with an absolute archive path can move the failure
to the final executable link:

```text
archive member 'libsqlite3.a' is neither ET_REL nor LLVM bitcode
undefined symbol: sqlite3_open
```

## Root Cause

Libtool treats visible `.la` files as authoritative metadata. Conan relocation
does not rewrite arbitrary paths stored inside those files, so a stale
`libdir='//lib'` or `dependency_libs` value redirects Libtool away from the
valid sibling archive.

An absolute `.a` value also changes Libtool semantics. When it is consumed by
`LIBADD` while another static Libtool library is constructed, `llvm-ar` can
store the complete dependency archive as one member. That member is not an ELF
relocatable object, and the dependency is no longer represented as a normal
link input for the final executable.

## Fix

1. Leave the dependency package cache unchanged.
2. Create a build-private directory that contains no `.la` files.
3. Copy only the required static dependency archives into that directory.
4. Pass the private directory through the upstream dependency-scoped variables
   such as `PCRE2_LIBS` and `SQLITE3_LIBS` using `-L<dir> -lname`.
5. Keep include flags in the matching scoped `*_CFLAGS` variables.
6. Remove generated `.la` metadata from the final package unless it is an
   intentional public artifact.

For a `PKG_CHECK_MODULES` dependency, predefining the matching scoped variables
keeps feature detection inside the declared Conan graph without exposing the
dependency package's stale Libtool metadata.

## Forbidden Approaches

- Do not delete or rewrite `.la` files inside a shared Conan package cache.
- Do not pass an absolute dependency `.a` through `LIBADD` without auditing the
  produced target archive.
- Do not move all flags into global `LIBS`; retain feature-specific variables
  so optional dependency detection remains deterministic.
- Do not infer success from configure or library creation alone.

## Verification

1. Start with a new Conan home and a clean build folder.
2. Confirm configure detects the intended dependency and feature macro.
3. Require all enabled upstream tests to pass on the HarmonyOS PC target.
4. Build, link, and run a real installed-package consumer on the target.
5. Run `llvm-ar t` on the target archive and require object members rather than
   nested PCRE2, SQLite, or other dependency archives.
6. Require the final package to contain zero unintended `.la` files.
7. Inspect the packaged CLI and library for build-cache path leakage.

## Validated Example

Link Grammar 5.13.0 was built on HarmonyOS PC with `pcre2/10.45` and
`sqlite3/3.49.1`. A clean target-native Conan run passed all four enabled
upstream tests, an API consumer, `link-parser --version`, and a real CLI
sentence parse. `liblink-grammar.a` contained 66 object members, no nested
PCRE2 or SQLite archives, and the 546-file package contained no `.la` metadata.
