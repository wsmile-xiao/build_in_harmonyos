# ntbtls 0.3.2 HarmonyOS 适配记录

## 构建信息

- 上游源码：`https://gnupg.org/ftp/gcrypt/ntbtls/ntbtls-0.3.2.tar.bz2`（sha256 `bdfcb99024acec9c6c4b998ad63bb3921df4cfee4a772ad6c0ca324dbbf2b07c`，
  与 Homebrew `ntbtls` formula 的 checksum 逐字一致，双源核对通过）
- 构建系统：Autotools（发布 tarball 自带 `configure`，不重新 autoreconf）
- Conan 依赖：`libgpg-error/1.55`、`libgcrypt/1.12.2`、`libksba/1.6.7.1`、`zlib/1.3.2`
- 目标平台：HarmonyOS PC arm64（`--build=aarch64-unknown-linux-gnu` / `--host=aarch64-unknown-linux-ohos`）
- 当前状态：built（本地 Conan 验证通过，尚未由 CI 发布）

## 平台适配

1. **config.sub 增加 HarmonyOS 三元组识别**（`patches/0002`，必需）：`--host=aarch64-unknown-linux-ohos` 由
   config.sub 规范化，未打补丁时报 ``Invalid configuration `aarch64-unknown-linux-ohos': OS `ohos' not recognized``。
2. **config.guess 增加 HarmonyOS 识别**（`patches/0001`）：本配方显式传 `--build` 因而跳过 config.guess
   （设备 HMDFS 上 config.guess 的 mktemp 探针会 Permission denied），补丁为可移植性补齐，与同族
   `libksba/1.6.7` 保持一致。
3. **依赖定位全部走 Conan 包内路径**：`generate()` 生成 `config-overrides/`，把三个 GnuPG 依赖的
   `*-config` 换成本配方生成的等价脚本（`GPG_ERROR_CONFIG`/`LIBGCRYPT_CONFIG`/`KSBA_CONFIG` 进程级注入），
   并置 `ac_cv_path_GPGRT_CONFIG=no` 把 m4 宏彻底挡在 `gpgrt-config` 之外；头文件/库路径另由
   `AutotoolsDeps` 注入。**未向共享 `/usr/local` 注入任何内容**。
4. **依赖 libtool 归档（.la）修复**：把 `libgpg-error.la`、`libksba.la` 的 `libdir`/`dependency_libs`
   重写为 Conan 包内真实路径，并以 `-L<config-overrides>/lib` 前置，使 libtool 优先命中修复版。
5. **构建期临时目录**放在 Conan `build_folder`（HMDFS 写读延迟 / 权限限制），并把 `configure` 内
   `umask 077` 改为 `umask 022`。
6. 产物只装出 `lib/libntbtls.so*`、`include/ntbtls.h`、`lib/pkgconfig/ntbtls.pc`、`share/aclocal/ntbtls.m4`
   与 `bin/ntbtls-config`（上游 autotools `bin_SCRIPTS`，仅元数据脚本）；上游 `ntbtls-cli` 是
   `noinst_PROGRAMS`，不安装，非命令行工具发布物，因此不需要 `commands.json`。

## 踩坑与解法（可复用结论）

### 1. zlib 是"标称可选、实际硬依赖"

- 位置：`configure.ac:479-497`（`AC_ARG_WITH(zlib)` 在 `use_zip=yes` 分支内 + `AC_CHECK_HEADER(zlib.h)`），
  但 `src/context.h:24` **无任何守卫**地 `#include <zlib.h>`，且 `src/context.h:188-189` 直接内嵌
  `z_stream ctx_deflate/ctx_inflate`；`src/protocol.c:1336` 还比较 `Z_OK`。
- 结论：必须提供 zlib 头文件，`zlib` 是真实依赖（本次 `self.requires("zlib/1.3.2")`）。
  同类手法：`ncview-udunits` 教训——上游"可选依赖"必须读源码验证。

### 2. libgpg-error 1.55 的 `gpgrt-config` 在 Conan 布局下会自我递归（构建挂死）

- 位置：`m4/ksba.m4:49` / `m4/libgcrypt.m4:45`（`KSBA_CONFIG="$GPGRT_CONFIG ksba"`）、
  `m4/gpg-error.m4:128`（`GPGRT_CONFIG="$GPGRT_CONFIG --libdir=$gpgrt_libdir"`）。
- 现象：`configure` 在 `checking KSBA API version... okay` 之后不再前进；`ps` 显示
  `sh gpgrt-config --libdir=<libgpg-error>/lib ksba --libs` 反复以父→子同命令形式再入，约每分钟一层，
  40 分钟未终止（首次 `conan create` 挂死）。
- 根因：`gpgrt-config` 拿到 `--libdir` 后，若该目录下没有被查询的 `.pc`（`ksba.pc` 在 libksba 包里，
  不在 libgpg-error 的 `lib/pkgconfig` 下），它不是报错而是**再执行一次自己**；`gpg-error.pc` 恰好就在
  该 libdir 下，所以 libgpg-error 自身不触发，只有 libgcrypt/libksba 触发。
- 解法：配方自行生成三个依赖的 `*-config` 等价脚本（只 `echo` 固定值，无文件系统探测），并用
  `ac_cv_path_GPGRT_CONFIG=no` 让 m4 不把 `gpgrt-config` 当 `*-config`。
- 附带事实：libgpg-error 1.55 已**不再安装 `gpg-error-config`**（包内 `bin/` 只有 `gpg-error` 与
  `gpgrt-config`），所以 `--with-libgpg-error-prefix` 会指向不存在的脚本，不可用。

### 3. 已发布 GnuPG 系 conan 包的 `*-config` 与 `.la` 都烘焙了 `prefix=/`

- 现象 A（warning，非致命）：`config.guess`/`*-config` 报
  `checking for gpgrt-config... /.../bin/gpgrt-config` 后 `-I//include`、`-L//lib`（`libgcrypt-config --cflags`
  实测输出 `-I//include`）。`-I` 由 `AutotoolsDeps` 兜住，`-L//lib` 本身无害。
- 现象 B（致命）：链接 `libntbtls.la` 时
  ```
  sed: //lib/libgpg-error.la: No such file or directory
  libtool: link: `//lib/libgpg-error.la' is not a valid libtool archive
  make[2]: *** [Makefile:550: libntbtls.la] Error 1
  ```
  根因：`libksba.la` 的 `dependency_libs` 里写死了 `-L//lib //lib/libgpg-error.la`
  （包内 `lib/libksba.la`，`libdir='//lib'`），libtool 顺着它去找不存在的归档。
  单靠补 `-L` 顺序无法绕过——**必须**用修复版 `.la`（把 `libdir`/`dependency_libs` 改成 Conan 包内真实路径）
  并前置该目录。
- 现象 C（隐蔽）：修好 `.la` 内容后仍报
  ```
  libtool: link: `<build>/config-overrides/lib/libksba.la' is not a valid libtool archive
  ```
  libtool 的 `func_lalib_unsafe_p` 只认**前 4 行里出现 `# Generated by ... $PACKAGE`（此处 PACKAGE=libtool）**
  的文件；自造 `.la` 若把说明注释写在前面就会被判非法。⇒ 重写 `.la` 时必须保留
  `# Generated by libtool (GNU libtool) <ver>` 这一行且位于前 4 行内。
- 上游同样做法的先例：高分案例 `MR5079-gpgme`（写入修复版 `libgpg-error.la`/`libassuan.la` + 自造
  `libassuan-config` + 前置 `-L`），知识条目 `E012`（.la 硬编码路径）已覆盖同类问题。

### 4. `can_run()` 在本机恒为 False，测试会被静默跳过

- 现象：`ntbtls/0.3.2 (test package): WARN: Cross build: consumer execution skipped`，
  `conan create` 仍 rc=0 —— 测试"通过"但根本没跑。
- 根因：本机 Conan 全局配置 `~/.conan2/global.conf` 写死 `tools.build.cross_building:can_run=False`，
  于是 `can_run()` 恒 False（而 `cross_building()` 实际为 False，build/host profile 完全相同）。
- 解法：test_package **不要用 `can_run()` 门控执行**（本仓同族 `libksba/1.6.7` 即无条件 `self.run`）。
  去掉门控后本机实测真实执行：`ntbtls consumer test: 11/11 checks passed`。
- 教训：`conan create` 返回 0 不等于测试跑过——必须读日志确认 `Running test()` 后确有 `RUN: ./<binary>`
  与用例输出。

### 5. 上游 0.3.2 没有测试套件

- `find . -name "*test*"` 无结果：tarball 无 `tests/` 目录，`src/Makefile.am`/`configure.ac` 无
  `TESTS`/`check_PROGRAMS` 目标（只有 `RUN_TESTS` 宏用于 `ntbtls-cli` 的构建条件）。
- 唯一"测试性"产物是 `src/ntbtls-cli.c`：手工网络客户端（需真实 TLS 对端），且是 `noinst_PROGRAMS`，
  不安装、CI 无法无头运行。故上游用例数为 **0**，未做任何"削弱上游测试"的动作。

## 已知限制

- 交叉编译产物为 OHOS aarch64 ELF，只能在 OpenHarmony / HarmonyOS PC 环境运行。
- 上游只实现 TLS 客户端（`src/protocol.c:3568-3571`，服务端分支为 `GPG_ERR_NOT_IMPLEMENTED`），
  且 TLS 压缩相关调用在上游被注释（压缩路径恒返回 `GPG_ERR_COMPR_FAILED`）——这是上游状态，不是适配缺陷。
- 上游 `ntbtls-cli`（`noinst_PROGRAMS`）未安装，本包不提供可执行命令行工具；
  `bin/ntbtls-config` 仅是 autotools 生成的元数据脚本（由于 Conan 用 `--prefix=/` 打包，其 `prefix`
  输出为 `/`，与同族 `libgcrypt`/`libksba` 包一致；Conan 消费者应使用 `cpp_info`/`pkg-config`）。
- 依赖包自身 `.la`/`.pc` 仍带 `prefix=/`，本配方在构建期以 `config-overrides/` 隔离修正，未改动依赖包内容。
