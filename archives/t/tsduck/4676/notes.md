## 3. 零依赖构建（nodep 标志集，无 requirements）

- 上游 `make nodep` 官方支持的零外部依赖形态，本配方将其 14 个标志逐字用于每次构建，另加 `NOGITHUB=1`（发行打包惯例：关闭运行时 GitHub 版本检查/下载）：
  `NODEKTEC NODTAPI NOHIDES NOVATEK NOCURL NOPCSC NOOPENSSL NOZLIB NOSRT NORIST NOJAVA NOPYTHON NOEDITLINE NOHWACCEL NOGITHUB`
- 效果：跳过 DTAPI/VATek 的联网下载（沙箱无网也可构建）、跳过 curl/openssl/zlib/editline/pcsc/srt/rist 的系统探测与链接（`NOZLIB` 时改用内嵌 Small Deflate；部分插件如 aes/descrambler、工具如 tsdektec/tshides/tsvatek/tssmartcard 自动剔除，约 37 工具 / 85 插件）。
- 因此 `requirements()` 为空，R36 依赖发布检查天然通过（无依赖可查）。
- `LLVM=1` 故意不传：`make-config.sh` 遇到它会无条件覆盖 `CXX=clang++`；改为显式传 `CXX=<conan compiler_executables:cpp>`，版本探针（`$CXX --version` 含 clang）会自动选中 LLVM 警告集。

## 4. OHOS 适配点（零源码补丁，全部在命令行/环境解决）

1. `SHELL=<bash>`（R5）：`Makefile.inc` 硬编码 `SHELL=/usr/bin/env bash`；OHOS 无 `/bin/sh` 且 `/usr/bin/env` 无保证，make 命令行变量覆盖 makefile 赋值。bash 来源为条件式：`build_requirements()` 先在本机探测可用 ambient bash（`CONFIG_SHELL` / `HMBS_BASH` / `SHELL` 首词元 → `/data/service/hnp/bin/bash` → `/bin/bash` → `/usr/bin/bash` → `which bash`，逐个过 `$BASH_VERSION` 身份 + 主版本 ≥4 检查），命中则跳过 `tool_requires("bash/5.3")`，未命中才拉起 hermetic bash（in-repo 静态版，只需 POSIX sh 即可构建自身）。原因见 §8 round6：provisioning bash/5.3 会跑该配方的 `get()` 系 `source()`，其 fork 的真机 harmonybrew `tar` 无执行权限，整轮 `create` 在本配方运行前即死；本配方自己的 `source()` 早已纯 Python 化（round1 修复），复发的同指纹只能来自依赖 provisioning，必须换策略。
2. `CXX/CC` 取自 Conan `tools.build:compiler_executables`（R33），绝不裸用 `${CC}`；`AutotoolsToolchain` 的 `CPPFLAGS/CFLAGS/CXXFLAGS/LDFLAGS` 经 `CPPFLAGS_EXTRA/CXXFLAGS_EXTRA/LDFLAGS_EXTRA` 转发（上游按设计忽略裸 CFLAGS）。其中 `CXXFLAGS_EXTRA` 内容先经 `_cap_extra_flags` 清洗：conan `-O1+/-O2+/-Ofast` 一律压到 `-O0`（last -O wins，EXTRA 在编译行最后，未过滤会把全树静默推高），一切 `-g*` 调试令牌替换为 `-g0`（调试信息使头文件大户 TU 的 clang 峰值内存近乎翻倍，而 Release 产物本就不带调试信息）；`CXXFLAGS_OPTIMIZE` 与 `CXXFLAGS_FULLSPEED` 均显式钉为 `-O0 -fno-strict-aliasing`（后者不可少：`src/libtsduck/Makefile` 给 `tsDVBCSA2.o` 的 target-specific `CXXFLAGS_OPTIMIZE = $(CXXFLAGS_FULLSPEED)` 优先级高于命令行，不钉则该文件静默留在 `-O3 -funroll-loops`）；conan `-std=...` 令牌一律丢弃（profile 钉 `cppstd=17`，上游要求 `-std=c++20` 且 `CXXFLAGS_STANDARD` 同样在 EXTRA 之前，透传会静默降级语言标准）。`-O0` 即上游 `DEBUG=1` 实测包络（构建同一棵树，仅优化力度/CPU 时间变化）；`CXXFLAGS_SECURITY` 由上游默认 `-fstack-protector-all` 降为 `-fstack-protector`（round13：round9 曾用 `-strong`；kill 点漂移到百行小 TU 证明是外部 killer，逐 TU codegen 节省仍有意义，basic 仍保护含字符数组等脆弱函数）；`DONT_BUILD_DEPS=1`（round13，`Makefile.inc` 明文支持：干净一次性构建跳过整个 `[DEP]` 预处理 pass，约 750 次 clang `-MM` 头文件闭包解析，显式先决条件不受影响）；`_cap_extra_flags` 另丢弃 LTO 系令牌（上游默认无 LTO，防 `libtsduck.so` 千目标链接期内存尖峰，不存在时为 no-op）。警告集与静态 blob 布局不动。
3. 预置 `SUDO=true`：使 `make-config.sh` 短路 `$(id -u)` 探针（OHOS 未必有 `id`，空展开会导致条件表达式语法错误）；不执行任何 install 目标，该值无实际作用。
4. 预置 `PYTHON`（`HMBS_PYTHON3` / `python3`）：构建脚本（`make-config.sh`、`build-tables-model.py`、`build-tsduck-header.py` 等）需要 Python3。
5. 不用 `make install`（E108anknowledge/doc/E108：HarmonyOS 无 GNU `install`）：`package()` 按 §2 布局手工复制；工具用“`ts` 开头且无点号”规则从 `BINDIR` 顶层挑选（插件/数据文件均含点号，`utest*` 以 `ut` 开头，天然排除）。
6. 复刻 `install-devel`：把 `TS_NO_OPENSSL/GITHUB/DTAPI/HIDES/VATEK/EDITLINE/CURL/ZLIB/SDEFL?/SRT/RIST`（实际追加见 `PRECONFIG_DEFINES`，与本次 nodep 标志一一对应）追加进已安装的 `include/tscore/tsPreConfiguration.h`，保证消费者编译特性与构建一致。
7. `BINDIR` 固定为 `<build>/tsduck-bin` 绝对路径（上游默认名嵌入主机名/架构，不可复现）；`-j1`（R9；`MAKEFLAGS_SMP` 在 makefile 层无消费点，并行只受 make `-j` 控制）。
8. `validate()` 限定 `os in ("Linux","OHOS")`（R32）；`package_type` 缺省（library，如 tesseract：既出库又出工具）+ `bindirs=["bin"]`，软件级 `commands.json`（`type=tool`）满足 R38/PF8。

## 5. 上游测试审计（TSUnit，全部在真机实跑）

- 位置：`src/utest/`；runner（`utest.cpp` + `tsunit.cpp/h` 自研框架）+ 87 个 `utest*.cpp` 测试类文件。
- 静态清点：`TSUNIT_DECLARE_TEST(...)` 宏共 747 个；其中 `utestDirectShow.cpp` 全文件在 `#if defined(TS_WINDOWS)` 内，Linux/OHOS 缺席 1 个 -> **可运行 746 个**（`upstream_test_total: 746`，`upstream_test_count_method: auto`，单一可解析框架）。
- 计数单源（配方与 MANIFEST 口径一致）：
  - discovered：`utest -l` 输出，每测试一行 `    Suite::test`（正则是 `^\s+\S+::\S+\s*$`）。
  - passed/failed：成功汇总行 `OK (N tests, M assertions)`（`with weak failures` 修饰仍计 passed）；失败汇总行 `*** FAILURES (F tests FAILED, P passed, A assertions FAILED, B passed`。
  - 恒等式：`executed=passed+failed`，`skipped=discovered-executed`（正常为 0；为负则配方直接报错、绝不凑数）。
- 运行方式：`TSPLUGINS_PATH=<bindir> LD_LIBRARY_PATH=<bindir> ./utest`（复刻 `src/utest/Makefile` 的 `test-shared` 环境）；另跑 `utest_static`（静态库版本，不含插件测试）仅记日志，不计入标记（同一套测试代码的严格子集）。
- `test-suite`（`tsduck-test` 独立仓库，TypeScript 集成测试，需 `../tsduck-test` 检出 + DVB 硬件/网络 fixture）不在本源码包内，上游 `make test-suite` 无仓库时仅打印 `No test repository`；本源码树内可完整执行的即 utest 全集，不存在“跳过整个上游套件”。
- 上游证据持久化：`build()` 写 `hmbs_upstream.json`，`package()` 存入 `res/`，`test_package` 在每轮（含缓存命中轮）重发 `HMBS_UPSTREAM_TEST_RESULT`。

## 7. 真机风险清单（preflight 若红，按此顺序排查）

1. `make-config.sh` 系统探针（`which`/`hostname`/`nproc` 缺失）——已预置 `PYTHON/SUDO`，`which` 缺失则全变量探空，需按日志加预置。
2. OHOS clang `--version` 若不含 `clang` 字样，警告集回退为裸 `-Werror`，仍可构建；若 `-Weverything -Werror` 遇新警告，需加 `CXXFLAGS_NO_WARNINGS`（等真机日志定点加，不预判）。
3. `utestTuner`（需 DVB 硬件）、`utestForkPipe`（需 fork）、网络类用例在 OHOS 的行为——实测后记 gaps（`ohos_feature`/`test_failure`），缺依赖则补齐重测，不记豁免。
4. 构建体量（libtscore+libtsduck 约 1500+ 文件，`-j1`）：若超默认 3600s 配额，需另起框架 PR 在 `ci/config/build_timeouts.txt` 加 `tsduck/4676` 条目（W2 原子性：不混入本配方 PR）。
5. `LD_LIBRARY_PATH` 在 OHOS 加载器是否生效：若 `utest` 起不来，改用 rpath 方案（上游 `LDFLAGS_LINKER` 在 `LINUX=1` 时已 baked `$ORIGIN`，`uname -s` 若报 Linux 则自带）。
6. `utest -l` 实测行数若与 746 有差（平台条件编译），以实测为准同步 `MANIFEST.yml`/`manifest.yaml`/PR 草稿（zurl #49 教训：计数三处必须一致）。
