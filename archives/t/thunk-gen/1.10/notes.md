### 对话 #4 [2026-10-08]

- 问题: 首次 `conan create` 成功编译，但新增的 OHOS 消费者测试 4 个模式全部 `checks=1 passed=0 failed=1`，`asms.filtered` 为 0 字节
- 操作: 逐层定位——用真实输入（`0\tvoid ASMCFUNC _dos_open(...)`）在 toybox-first 与 GNU-first 两种 PATH 下系统性枚举 `parse_decls.sh` 的 7 个模式并对比
- 结果: 根因是 `gen_asms_tmp()`（模式 2）用 GNU grep 的 BRE 扩展 `grep 'ASMFUNC\|ASMPASCAL'`，而 conan buildenv 的 PATH 把 `/system/bin`（toybox grep）排在 `/data/service/hnp/bin`（GNU grep 3.12）之前，toybox 把 `\|` 当字面量 → 零输出且退出 1。新增补丁 0002 改为 `grep -E 'ASMFUNC|ASMPASCAL'`

### 对话 #5 [2026-10-08]

- 问题: 同期发现 `gen_plt_asmp()`（模式 5）的 `sed -E 's/([0-9]+).+ ([^ \(]+) *\(.+/ASMPSYM(\3, \1)/'` 引用了不存在的第 3 个捕获组
- 操作: 在 toybox sed 与 GNU sed 3.12 下分别实测同一输入
- 结果: 两者**都**报 `sed: no s//\3/` 并退出 1（早先"只有 toybox 有问题"的判断被推翻）。新增补丁 0001 改为第 2 个捕获组 `\2`。两补丁按序应用于全新官方 tarball：dry-run exit 0、apply exit 0、与应用目标 `.work` 逐字节 `cmp` 一致

### 对话 #6 [2026-10-08]

- 问题: 第二轮 `conan create` 中构建与消费者测试全绿（65/65），但 `test_package` 有 2 项断言失败：`m4 形态 THUNK(0, 0, 1, _P)`
- 操作: 检查 `test.sh` 的 `check_has` 实现——它走裸 `grep`（BRE）；在 BRE 中 `\(` 是**分组**而非字面括号，故模式 `^THUNK\(0, 0, 1, _P\)$` 实际等价于 `THUNK0, 0, 1, _P$`，与真实输出不匹配
- 结果: 属测试断言写法错误而非产品缺陷；改为 `'^THUNK(0, 0, 1, _P)$'` 并在源码中加注说明。`conan test` 复验 `TEST_EXIT=0`

## G0（clean_verify）结果说明 —— 必读

`finish` Step3 的 G0 输出为 `⚠️ G0: configure 失败 (exit 1) — 预期行为`。这里**留痕说明真实根因**，避免"预期行为"标签掩盖事实：

- **真实根因**：`scripts/ohc/clean_verify.py` 硬编码 autotools 三步（`:69 ./configure` → `:191 make` → `:218 make install`），其 `add_argument` 只有 `software`/`version`/`--project-dir`，**不接受构建系统参数**。本工程是纯 Meson/Ninja 工程，根目录 `configure` 只是 `meson setup` 的 bash 包装，故裸环境下 `meson: command not found` → exit 1。
- **为何不能"修好"**：即便把 `meson` 放进 PATH 让 `./configure` 成功，Step4/Step5 仍会执行 `make` / `make install`，而 meson 产出的是 ninja 构建文件、不含 Makefile → 结构上必然失败。**除非改框架，否则本包 G0 不可能通过。**
- **为何归入"预期行为"**：`clean_verify.py:164-177` 以"配方是否含 `replace_in_file`"来识别"只在 `package()` 阶段施加的运行时修复"，并据此把 G0 失败归入预期（G0 不执行 `package()`，拿不到该修复）。本包**确实**存在这类真实修复——meson 把 `prefix=/` 烘进随包 `.pc`，必须在 `package()` 里改写为 `${pcfiledir}/../..` 才能重定位——因此改用 Conan 官方 `replace_in_file` 实现它（同时 `strict=True` 保证改不动时直接报错，而不是静默把 `prefix=/` 留给消费者）。这是**真实命中**，不是为凑绿而伪造的标记。
- **等价的真实洁净构建证据**：G2 `conan create`（`Building from source` → 5 个 meson 步骤 → `Package '6b129b06…' created`）与 W3 本地 CI 模拟（通过）。

| 7 | meson 的 project() 阶段找不到归档器 | CI worker 的 PATH 不含 `llvm-ar`/`llvm-ranlib` | 从 profile 的 `tools.build:compiler_executables` 推导同目录工具写入 `tc.binaries`（c-list/3.1.0 同款先例） |

## 注意事项

- **测试入口的诚实申报**：上游 1.10 确实没有自动化测试套件。本包 `build()`
  里跑的 65 个断言来自**本适配新增**的 OHOS 消费者测试，`test_package`
  里的 49 个断言是消费者视角复跑；两者都不得被当作"上游测试统计"。
- **`parse_decls.sh` 的调用约定是 `<模式> <文件>` 两参数**，模式 1..7；漏传
  模式会让 `case` 落空、静默输出空内容并返回 0（易被误判为"上游缺陷"）。
- **`thunk_gen` 的 CLI 是 `[-d] [-p <ptr_size>] [-a <align>] <thunk_type>`**，
  其中 `-p` / `-a` **必填**（未设时报 `Set alignment and ptr size` 并退出 1），
  `thunk_type` 是**位置参数**（不是 `-t`）。下游通过 `TFLAGS` 传 `-a 4 -p 4`。
- **模式 5（`plt_asmp.h`）与模式 2（`thunk_p.h`）是本适配的两个补丁覆盖点**，
  回归时优先复跑这两个模式的产物。
- 终端工具按 R26 以 `-Ddefault_library=static` 构建；`thunk_gen` 本身仍是
  动态链接 musl 的可执行文件（OHOS 常态），包内不落任何 `.so`。
